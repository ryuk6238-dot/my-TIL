# Spring Data JPA 도입하기 — Q&A

### Q1. SQL과 테이블의 관계

> **Q.** SQL 이라는게 테이블 말하는거지?
>
> 아니다. SQL은 테이블 자체가 아니라 **테이블(관계형 데이터베이스)에 접근하기 위한 언어**다.
>
> - **테이블**은 실제 데이터가 행(row)과 열(column) 구조로 저장되는 대상. 정리 노트의 `tbl_menu`, `categories` 같은 것이 테이블이다.
> - **SQL**은 그 테이블에 대해 조회(SELECT), 삽입(INSERT), 수정(UPDATE), 삭제(DELETE) 같은 작업을 수행하기 위한 질의 언어(Query Language)다.
>
> 정리 노트의 "SQL 중심 기술"이라는 표현은 "테이블 자체"가 아니라, 개발자가 SQL 문장을 직접 작성해서 DB에 접근하는 방식(MyBatis, Spring JDBC 등)을 뜻한다. 반대로 JPA/Spring Data JPA는 SQL을 직접 쓰지 않고 엔티티 객체(자바 클래스)를 통해 테이블에 접근하며, SQL은 JPA가 내부적으로 자동 생성해준다.

> **Q.** 반대로 JPA/Spring Data JPA는 SQL을 직접 쓰지 않고 엔티티 객체(자바 클래스)를 통해 테이블에 접근하며, SQL은 JPA가 내부적으로 자동 생성해준다. 이게 noSQL 인가?
>
> 아니다. JPA/Spring Data JPA는 여전히 **관계형 데이터베이스(RDBMS)와 SQL**을 사용한다 — 그 SQL을 개발자가 직접 타이핑하지 않고 JPA가 대신 생성해줄 뿐이다.
>
> - **NoSQL**은 애초에 테이블·행·열 구조 자체를 쓰지 않는 별도의 데이터베이스 종류다(MongoDB의 document, Redis의 key-value, Cassandra의 wide-column 등). SQL 언어 자체가 필요 없는 구조다.
> - **JPA**는 "SQL을 안 쓴다"가 아니라 "SQL을 직접 작성하지 않아도 된다"는 것이다. 내부적으로는 여전히 PostgreSQL, MySQL 같은 RDBMS에 접속해서 진짜 SQL(`SELECT`, `INSERT` 등)을 실행하며, 그 SQL 문자열을 개발자 대신 JPA/Hibernate가 엔티티 정보를 보고 자동으로 만들어낸다.
>
> 즉 SQL을 누가 작성하느냐(개발자 vs JPA)의 차이일 뿐, 둘 다 관계형 DB + SQL 세계 안에 있다. NoSQL은 그 세계 바깥의 완전히 다른 데이터베이스 패러다임이다.

### Q2. Entity 클래스 기반 작성과 패러다임 불일치의 관계

> **Q.** "패러다임 불일치: 객체지향과 관계형 DB는 데이터를 표현하는 방식이 근본적으로 다르다. 객체의 상속 구조, 참조, 컬렉션 필드는 테이블로 그대로 표현되지 않아 매핑 문제가 발생한다." — 이 경우에는 내 기억에 entity 클래스를 기반으로 작성했던거 같은데
>
> 맞다. `Entity 설계 기초` 실습(Category.java)이나 `Spring Data JPA 시작하기` 실습(Menu.java)에서 실제로 **Entity 클래스를 먼저 작성 → `ddl-auto: create` 설정으로 JPA가 테이블 DDL을 자동 생성**하는 순서로 진행했다.
>
> - `@Entity`, `@Table(name = "categories")`, `@Id`, `@GeneratedValue`, `@Column(nullable = false, length = 30)` 같은 어노테이션으로 자바 클래스를 작성하면, 앱 실행 시 Hibernate가 그 정보를 읽어 `CREATE TABLE categories (...)` DDL을 자동 생성한다.
> - 이는 **객체 우선(code-first)** 방식이다. 반대로 테이블을 먼저 설계하고 Entity를 거기에 맞춰 작성하는 **테이블 우선(schema-first)** 방식도 있는데, 실무에서는 `ddl-auto: validate`/`none`을 쓰면서 스키마는 Flyway/Liquibase 같은 도구로 관리하고 Entity를 그 스키마에 맞춰 작성하는 경우가 더 흔하다.
>
> 패러다임 불일치와 모순되지 않는다. 패러다임 불일치는 "객체와 테이블의 구조가 원래 다르다"는 것이고, `@Entity`/`@Table`/`@Column`/`@OneToMany` 같은 JPA 어노테이션들이 바로 그 간극을 메우는 역할을 한다. Entity 클래스를 기반으로 작성했다는 것은, 그 어노테이션들이 "이 객체를 이런 테이블 구조로 번역해달라"고 JPA에게 지시하는 것이고, 실제 변환(매핑) 작업 자체가 패러다임 불일치를 해소하는 과정이다.

### Q3. ORM 등장 배경과 패러다임 불일치의 인과관계

> **Q.** "ORM은 이 불일치를 해소하기 위해 객체 ↔ 테이블 매핑을 자동 처리하는 기술. 생산성·가독성이 향상되지만, 내부 동작을 모르면 성능 저하나 예기치 못한 쿼리가 발생할 수 있다." 이거 좀 의문인게, 위에서 패러다임 불일치라는 문제가 생겨서 orm이라는 기술이 도입돼서 매핑을 도와주는건가?
>
> 맞다. 정확히 그 인과관계다.
>
> - 객체지향과 관계형 DB는 애초에 데이터를 표현하는 방식이 다르다(패러다임 불일치) → 개발자가 SQL을 직접 짜서 이 간극을 수작업으로 메워야 했다(SQL 중심 기술, JDBC/MyBatis) → 이 수작업이 반복적이고 번거로우니, 그 매핑 작업 자체를 자동화하는 기술로 ORM이 등장했다.
> - 정리 노트에도 "ORM(Object-Relational Mapping)은 객체와 테이블 사이의 매핑을 자동으로 처리하는 기술로, 위 문제(패러다임 불일치)를 해결하기 위해 등장했다"고 명시돼 있다.
> - 같은 흐름에서 JPA는 자바 진영에서 이 ORM 기능을 "표준화"한 명세이고, Hibernate는 그 명세를 실제로 구현한 라이브러리다. 즉 `패러다임 불일치(문제) → ORM(해결 기술의 개념) → JPA(자바 표준 명세) → Hibernate(구현체)` 순서로 이어지는 계보로 이해하면 된다.

> **Q.** 그럼 지금 학습 흐름대로면 기존에 SQL 중심 기술로는 spring의 객체 지향 방식과 DB의 데이터 매핑 문제가 생겼고 이를 해결하기 위한 ORM이 등장했다 로 이해하면 되나?
>
> 거의 맞지만 한 가지만 짚어야 한다 — "Spring의 객체지향 방식"이 아니라 "Java(객체지향 언어) 자체의 특성"이다. Spring은 프레임워크일 뿐이고, 패러다임 불일치는 Spring을 쓰든 안 쓰든 자바(또는 다른 OOP 언어)로 개발하면서 관계형 DB를 쓸 때 항상 존재하는 근본적인 문제다.
>
> 정리하면: **기존에 SQL 중심 기술(JDBC, MyBatis)로는 자바(객체지향)의 표현 방식과 관계형 DB(테이블 중심)의 표현 방식이 근본적으로 달라(패러다임 불일치) 매핑 문제가 있었고, 이를 자동으로 해결하기 위해 ORM이라는 기술이 등장했다.**
>
> - 패러다임 불일치는 "언어 vs DB" 차원의 문제(Java ↔ RDBMS)다.
> - Spring/Spring Data JPA는 그 위에서 "이 매핑 작업(ORM)을 자바 생태계에서 얼마나 편하게 쓸 수 있게 해주느냐"를 다루는 계층이다 — 문제의 원인이 아니라 해결책을 편리하게 제공하는 쪽이다.

> **Q.** "JPA(Java Persistence API)는 자바 진영의 ORM 표준 명세(인터페이스 규약)일 뿐이고" — 이게 무슨 말이지? 1) jpa가 ORM이라는거야? 2) JPA가 ORM의 역할을 한다는거야? 3) JPA가 ORM과 같은 역할을 한다는거야?
>
> 셋 다 애매하게 맞을 수 있어 헷갈리지만, 정확히는 ①도 ②도 아니고 ③에 가장 가까우면서도 조금 더 정밀하게 표현해야 한다. **JPA는 "ORM이 어떤 모습이어야 하는지"를 정의한 명세(규약)일 뿐, JPA 자체가 실제로 매핑 작업을 수행하지는 않는다.**
>
> - ① "JPA가 ORM이다" (X) — JPA는 ORM 자체(실제로 동작하는 기술/도구)가 아니다. 동작하는 실체가 없다.
> - ② "JPA가 ORM의 역할을 한다" (X, 미묘하게 틀림) — "역할을 한다"는 실제로 뭔가를 수행한다는 뜻인데, JPA 자체는 아무 동작도 하지 않는다. 실제 역할(매핑, SQL 생성)은 Hibernate 같은 구현체가 수행한다.
> - ③ "JPA가 ORM과 같은 역할을 한다" — 이것도 정확하진 않고, 더 정확히는 "JPA는 ORM이라는 개념/역할을 자바에서 수행하려면 어떤 인터페이스(`EntityManager`)와 어노테이션(`@Entity`, `@Id` 등)을 갖춰야 하는지 정해놓은 표준 문서"다.
>
> 비유: Java의 `List` 인터페이스가 "리스트가 뭘 할 수 있어야 하는지(add, get, remove...)"만 정의하고, 실제 동작은 `ArrayList`나 `LinkedList` 같은 구현체가 하는 것과 같다. `List` = JPA(규약만 정의), `ArrayList` = Hibernate(실제 구현체, 진짜 동작 수행). 정리 노트에도 "JPA는 하나의 인터페이스 규약이고, 이를 구현한 프레임워크(Hibernate, EclipseLink, DataNucleus 등)를 통해 실제 동작이 수행된다"고 되어 있다.

> **Q.** 이거만 재정리하면 그러니까 JPA가 ORM이 어떤 형태인지 정해주는 명세서 역할을 한다?
>
> 맞다. 정확한 이해다.
>
> - JPA = "ORM은 이런 인터페이스(`EntityManager`)와 이런 어노테이션(`@Entity`, `@Id`, `@Column`...)을 가져야 한다"고 정해놓은 명세서(규약)
> - Hibernate = 그 명세서대로 실제로 코드를 짜서 동작하게 만든 구현체
>
> 명세서 자체는 종이 위의 규칙일 뿐 아무것도 실행하지 않고, 그 규칙을 따라 실제로 SQL을 만들고 실행하는 건 Hibernate다.

> **Q.** "JPA는 자바 진영의 ORM 표준 명세(인터페이스 규약)일 뿐이고, 실제 동작은 구현체(대표적으로 Hibernate)가 담당한다." 이걸 다시 정리해보면 JPA는 ORM이 어떤 형태인지 정하는 명세서이고 하이버네이트는 JPA가 정해둔 명세서를 실제로 동작시키는 구현체다 맞아?
>
> 맞다. 그 정리 그대로다.
>
> - JPA = 명세서(규약) — 예: `EntityManager`, `@Entity` 같은 "이런 게 있어야 한다"는 규칙만 정의
> - Hibernate = 구현체 — 그 규칙을 실제 코드로 구현해서 SQL 생성, 영속성 컨텍스트 관리 같은 진짜 동작을 수행
>
> 이 관계는 "표준(JPA)과 그 표준을 따르는 제품(Hibernate)"의 관계와 같다. Hibernate 외에도 EclipseLink, DataNucleus 같은 다른 구현체도 있는데, 어떤 구현체를 쓰든 JPA라는 같은 명세를 따르기 때문에 코드(어노테이션, API 사용법)는 거의 동일하게 유지된다 — 이것이 JPA가 표준 명세로 존재하는 이유(벤더 독립성)이기도 하다.

> **Q.** 그럼 의문인게 hibernate가 없으면 jpa가 작동 안하는거야?
>
> 맞다. JPA만 있고 구현체가 없으면 아무것도 동작하지 않는다.
>
> - JPA는 인터페이스와 어노테이션 규약만 정의해놓은 API 모음(`jakarta.persistence` 패키지)일 뿐이라 그 자체로는 실행 가능한 코드가 없다. `EntityManager.persist()`를 호출해도 그 메서드의 실제 로직(SQL 생성, DB 연결, 트랜잭션 처리 등)은 JPA 안에 들어있지 않다.
> - 그래서 반드시 JPA 구현체(JPA Provider)가 클래스패스에 있어야 실제로 동작한다. Hibernate가 가장 널리 쓰이지만 EclipseLink나 OpenJPA 같은 다른 구현체로 대체해도 된다 — 핵심은 "Hibernate가 필수"가 아니라 "JPA 구현체 중 하나는 반드시 있어야 한다"는 것이다.
> - Spring Boot에서 `spring-boot-starter-data-jpa`를 추가하면 별다른 설정 없이 Hibernate가 기본 구현체로 자동 포함되기 때문에, 평소에는 "구현체를 별도로 골라야 한다"는 걸 의식하지 못할 뿐이다.
>
> 비유: `List item = new ArrayList<>();`에서 `ArrayList` 없이 `List` 인터페이스만으로는 객체를 만들 수 없는 것과 같은 원리다.

> **Q.** 음 그러니까 개념적으로 JPA 가 결국 API니까 그 호출?을 받아서 동작시킬 구현체가 필요한데 그게 hibernate 다 맞아?
>
> 맞다. 정확한 이해다.
>
> - JPA = API(호출 인터페이스) — "이런 메서드를 이런 이름으로 호출할 수 있다"는 규약만 존재(`EntityManager.persist(entity)`, `@Entity` 등)
> - 그 호출을 실제로 받아서 처리(동작)시키는 게 구현체 — 대표적으로 Hibernate
>
> API는 "무엇을 할 수 있는지(what)"만 정의하고, 구현체가 "어떻게 실제로 할지(how)"를 채워 넣는 구조다. 개발자는 JPA의 API(어노테이션, `EntityManager` 메서드)만 알고 코드를 짜면 되고, 그 뒤에서 실제로 SQL을 만들고 DB에 쏘는 건 Hibernate가 알아서 처리한다.

> **Q.** 아까 ORM은 JPA가 형태를 규정한다고 이해했는데 그럼 ORM은 무조건 JPA 하위에 존재하는거야? 다시 정리하면 JPA만의 기술/개념인거야? 아니면 좀 더 광범위하게 사용되는건데 JPA로 형태를 잡을 수 있다는거야?
>
> 반대다. JPA가 ORM의 하위 개념이 아니라, ORM이 훨씬 더 넓은 범위의 일반 개념이고 JPA는 그 ORM 개념을 자바 진영에서 표준화한 것이다.
>
> - ORM은 언어에 종속되지 않는 일반적인 기술/패턴이다. 자바뿐 아니라 Python(Django ORM, SQLAlchemy), Ruby(ActiveRecord), .NET(Entity Framework), JavaScript(TypeORM, Sequelize), PHP(Doctrine) 등 각 언어마다 JPA와 무관한 독자적인 ORM 도구가 있다.
> - JPA는 그 넓은 ORM 개념 중 "자바에서는 이런 인터페이스 형태로 ORM을 제공하자"고 정한 자바 전용 표준일 뿐이다.
> - 역사적으로도 순서가 증명된다: Hibernate는 2001년에 이미 독자적인 ORM 프레임워크로 등장했고, JPA는 그보다 나중인 2006년에 Hibernate 같은 기존 ORM들의 경험을 바탕으로 자바 표준으로 만들어졌다. 즉 ORM(Hibernate)이 먼저 있었고 JPA가 나중에 그걸 표준화한 것이지, JPA가 먼저 있고 ORM이 그 밑에 생긴 게 아니다.
>
> 정리: "ORM은 JPA로 형태를 잡을 수 있다"가 맞는 방향이다. ORM(광범위한 개념) ⊃ JPA(그중 자바 표준으로 형태를 규정한 하나의 사례).

> **Q.** 그럼 다시 정리해보면 ORM을 JAVA에서 사용하기 위해 JPA로 ORM의 형태를 규정해서 hebernate로 구현할 수 있도록 했다 가 맞겠네?
>
> 맞다. 정확한 최종 정리다 — "ORM을 Java에서 사용하기 위해 JPA로 ORM의 형태를 규정하고, Hibernate로 그걸 구현할 수 있도록 했다."
>
> 이 문장이 지금까지 나온 개념(패러다임 불일치 → ORM 등장 → JPA 표준화 → Hibernate 구현)을 정확히 압축한 결론이다.
>
> (역사적 순서만 참고로 덧붙이면) 실제로는 Hibernate가 2001년에 먼저 독자적인 ORM으로 나왔고, JPA가 2006년에 그걸 포함한 기존 ORM들의 설계를 참고해서 자바 표준 형태로 규정한 것이라, 시간 순서상으로는 "Hibernate 먼저 → JPA가 형태를 나중에 규정 → Hibernate가 그 규정에 맞춰 표준 구현체로 재정비"에 가깝다. 다만 지금 이해해야 할 개념적 구조(무엇이 무엇을 규정하고 구현하는가)로는 이 정리가 맞다.

### Q4. 영속성 컨텍스트 개념 — 생성 시점, Key-Value 관리, Thread-Safe, Request Scope

> **Q.** "영속성 컨텍스트(Persistence Context): 엔티티를 영구 저장하는 환경으로, 엔티티 매니저(EntityManager) 생성 시 함께 만들어지며 Key-Value로 엔티티를 관리한다. 엔티티 매니저는 Thread-Safe하지 않아 Web에서는 보통 Request Scope와 일치시킨다." 이게 개념적으로 헷갈리는데, 영속성 컨텍스트라는게 유저가 의도적으로 삭제하지 않으면 영구적으로 저장한다는거잖아? 1) 엔티티 매니저를 언제 어떻게 생성을 한다는거야? 플러그인과야? 아니면 패키지 구조적인거야? 2) 만들어 질때 키와 값으로 관리를 한다고했는데 그러면 엔티티매니저를 만들때 키 값을 설정해줘야한다는건가? 3) thread-safe가 뭐야 4) web에서 보통 request나 scope를 일으킨다는데 scope은 뭐야? 그리고 영속성 컨텍스트가 결국 엔티티라고 난 이해했는데 아무런 요청도 호출도 없는게 갑자기 왜 웹에서 호출을 받아?
>
> 핵심 오해부터 정정한다 — "영속성 컨텍스트 = 영구 저장(DB에 계속 남음)"이 아니다. "영속(persistent)"은 "DB에 영원히 저장됨"이 아니라 "지금 이 컨텍스트가 그 엔티티를 계속 추적/관리하고 있는 상태"라는 뜻이다. 영속성 컨텍스트 자체는 메모리 상의 임시 저장소이고, `EntityManager`가 종료되면 (커밋해서 DB에 반영되지 않았다면) 그 안의 내용은 다 사라진다. 진짜 영구 저장은 DB가 하고, 영속성 컨텍스트는 그 전 단계의 "작업 중인 메모리 공간(1차 캐시)"이다.
>
> **1) 엔티티 매니저는 언제 어떻게 생성되나** — 플러그인이나 패키지 구조 얘기가 아니라 객체 생성 시점의 문제다. 앱이 시작될 때 Spring이 `EntityManagerFactory`(무거운 객체, 앱 전체에 1개)를 먼저 만든다. 실제 요청 처리 중(`@Transactional` 메서드 시작 시점)에 그 공장에서 가벼운 `EntityManager` 인스턴스를 하나씩 자동으로 찍어내 스레드에 묶어준다. 개발자가 직접 생성 코드를 쓰지 않아도 Spring이 자동으로 처리한다.
>
> **2) Key-Value 관리가 직접 키를 설정해야 한다는 뜻인가** — 아니다, 자동이다. key는 그 엔티티의 `@Id` 필드 값이다. `entityManager.find(Menu.class, 1L)`처럼 조회하면 JPA가 내부적으로 `key=1L, value=menu객체` 형태로 1차 캐시(Map)에 자동 저장한다. 개발자는 `@Id`를 어떤 필드에 붙였는지만 정하면 되고 따로 키를 설정하는 코드는 없다.
>
> **3) Thread-Safe가 뭐야** — 여러 스레드가 동시에 같은 객체를 건드려도 데이터가 꼬이지 않고 안전하게 동작하는 성질. `EntityManager`는 내부에 "지금 관리 중인 엔티티 목록(1차 캐시)"이라는 상태를 갖고 있어서, 만약 사용자 A와 B의 요청이 같은 `EntityManager` 인스턴스를 동시에 쓴다면 두 요청의 데이터가 같은 내부 Map에서 뒤섞여 서로를 오염시킬 수 있다. 그래서 `EntityManager`는 "혼자만 써야 안전한" 객체다.
>
> **4) Scope란? 그리고 왜 "웹에서 호출을 받는다"는 표현이 이상한가** — 먼저 오해 정정: 영속성 컨텍스트가 스스로 뭔가를 "호출받는" 능동적인 존재가 아니다. `EntityManager` 안에 딸린 수동적인 저장 공간일 뿐이고, 그 `EntityManager`의 생명주기(생성~소멸 시점)가 "웹 요청 하나의 생명주기"와 맞춰져 있다는 뜻이다.
>
> - Scope = "이 객체 인스턴스가 얼마나 오래, 어떤 범위 동안 유효하냐"는 개념. 예: Singleton scope(앱 전체에서 인스턴스 1개, `EntityManagerFactory`가 이런 성격), Request scope(HTTP 요청 하나가 들어올 때마다 새 인스턴스를 만들고 응답 나가면 버림).
> - "Web에서는 Request Scope와 일치시킨다"의 의미: 클라이언트가 요청을 보내면 Controller → Service → Repository로 흘러가는 그 한 번의 요청-응답 사이클 동안만 새 `EntityManager`(와 그 안의 영속성 컨텍스트)를 만들어 쓰고, 응답을 돌려준 뒤 닫는다. 다음 요청이 오면 완전히 새로운 `EntityManager`를 또 만든다.
> - 이렇게 하는 이유가 바로 3번의 Thread-Safe 문제 때문이다. 요청마다 별도의 `EntityManager`를 쓰면 동시에 여러 사용자가 요청을 보내도 서로의 데이터가 섞이지 않는다.
>
> 정리: 영속성 컨텍스트는 "영구 저장소"가 아니라 "한 트랜잭션/요청 동안만 살아있는 임시 작업 공간"이고, 그 생명주기를 웹 요청 하나의 생명주기와 맞춰서(Request Scope) 매 요청마다 새로 만들고 버리는 것이다.

> **Q.** 그러니까 천천히 정리해보면 일단 영속성 컨텍스트는 엔티티를 영구적으로 저장하는게 아니야 생성된 엔티티에 대한 지속적인 관찰 상태를 말하는거고 키,값은 spring에서 자동으로 설정한다. 엔티티 매니저는 thread-safe하지 않아서 동시에 같은 객체를 건들면 데이터가 꼬이므로 엔티티 매니저 혼자 사용해야한다 까지 맞아?
>
> 거의 다 맞고, 한 군데만 정정한다.
>
> 1. "영속성 컨텍스트는 엔티티를 영구적으로 저장하는게 아니다" — 맞다.
> 2. "생성된 엔티티에 대한 지속적인 관찰 상태를 말하는거고" — 정확하다. "관찰(추적)하고 관리하는 상태"라는 표현이 맞다(변경 감지, 동일성 보장이 다 이 "관찰" 덕분에 가능).
> 3. "키,값은 spring에서 자동으로 설정한다" — 살짝 정정 필요. 이건 Spring이 아니라 JPA(정확히는 구현체인 Hibernate)가 하는 일이다. Spring의 역할은 `EntityManager`를 언제 만들고 언제 닫을지(생명주기, Request Scope 관리)이고, JPA/Hibernate의 역할은 그 `EntityManager` 내부에서 `@Id` 값을 key로 삼아 1차 캐시(Map)에 엔티티를 저장하는 실제 동작이다. 즉 "Request Scope로 EntityManager를 관리해주는 건 Spring", "그 안에서 Key-Value로 엔티티를 캐싱하는 건 JPA/Hibernate"로 역할이 나뉜다.
> 4. "엔티티 매니저는 thread-safe하지 않아서 동시에 같은 객체를 건들면 데이터가 꼬이므로 엔티티 매니저 혼자 사용해야한다" — 맞다.
>
> 최종 정리: 영속성 컨텍스트는 영구 저장소가 아니라 생성된 엔티티에 대한 지속적인 추적/관찰 상태이며, 그 안의 Key-Value 캐싱은 JPA/Hibernate가 자동으로 처리한다(Spring은 EntityManager의 생명주기·스코프만 관리). 엔티티 매니저는 Thread-Safe하지 않아서 동시에 같은 인스턴스를 여러 스레드가 건드리면 데이터가 꼬이므로, 요청마다 하나씩 독립적으로 사용해야 한다.

> **Q.** "엔티티 매니저는 Thread-Safe하지 않아 Web에서는 보통 Request Scope와 일치시킨다." 이 부분 thread-safe 하지 않다까지는 이해했는데 그 다음이 이해가 안돼 무슨말이야
>
> 인과관계를 구체적 시나리오로 풀면 이렇다: "Thread-Safe 하지 않다" → "여러 스레드가 하나의 EntityManager를 같이 쓰면 위험하다" → "그러니까 스레드(=웹 요청)마다 EntityManager를 따로따로 만들어서 쓰자" → 이 "따로따로 만든다"가 바로 Request Scope다.
>
> **Request Scope로 안 만들면(나쁜 예)**: `EntityManager`를 앱 전체에서 딱 1개(싱글턴)로 만들어 모든 요청이 공유한다고 하자. 웹 서버는 동시에 여러 요청을 처리하려고 요청마다 별도 스레드를 배정한다(사용자 A=스레드1, 사용자 B=스레드2, 동시 실행). 두 스레드가 같은 EntityManager 인스턴스를 동시에 건드리면, 스레드1의 1차 캐시에 스레드2가 조회한 엔티티가 섞이거나, 스레드1이 커밋 안 한 변경사항을 스레드2가 실수로 함께 flush 해버릴 수 있다. 결과적으로 "A가 조회했는데 B의 DB 변경이 섞여 나온다" 같은 데이터 오염이나 예외가 발생한다.
>
> **Request Scope로 만들면(실제 방식)**: 요청이 들어올 때마다(스레드가 새로 배정될 때마다) 그 요청 전용의 새 EntityManager를 하나 만든다. 스레드1과 스레드2는 각자 자기만의 EntityManager를 가지므로 서로 마주칠 일이 없다. 요청 처리가 끝나 응답을 보내면 그 EntityManager는 버려진다(닫힌다). 다음 요청이 오면 또 새로 만든다.
>
> 즉 "Request Scope와 일치시킨다"는 "EntityManager를 공유하지 않기 위해 요청 하나당 정확히 하나씩 만들고 그 요청이 끝나면 버린다"는 뜻이다. Thread-Safe 하지 않은 문제를 "공유를 아예 안 시켜버림으로써" 회피하는 전략이며, Spring이 `@Transactional`을 통해 이 과정을 자동으로 처리해준다.

> **Q.** 아 그러니까 thread-safe 하지 않으니까 데이터가 꼬일 위험이 있어서 Scope request 형태으로 맞춰서 한번에 하나의 엔티티 매니저만 만들어 위험을 방지한다 맞아?
>
> 거의 맞지만 "한 번에 하나의 엔티티 매니저만 만들어"라는 표현은 오해될 수 있어 정정한다. 핵심은 "전체에서 하나만"이 아니라 "요청마다 각자 하나씩, 서로 공유는 안 한다"는 것이다.
>
> - 동시에 여러 요청이 들어오면 그 순간에도 EntityManager는 여러 개가 동시에 존재한다(요청 A용 1개, 요청 B용 1개, 요청 C용 1개... 동시 요청 수만큼).
> - 다만 각 EntityManager는 딱 그 요청 하나만 전담하고 절대 다른 요청과 공유되지 않는다.
>
> 정확한 정리: Thread-Safe 하지 않아서 데이터가 꼬일 위험이 있기 때문에, 요청(스레드)마다 EntityManager를 하나씩 독립적으로 만들어(Request Scope) 서로 공유되지 않게 함으로써 위험을 방지한다. "한 번에 하나만"이 아니라 "요청 하나당 하나씩, 절대 공유 안 함"이 정확한 뉘앙스이며, 나머지 논리 흐름(Thread-Safe 문제 → 공유하면 위험 → Request Scope로 격리)은 정확하다.

> **Q.** "엔티티 생명주기: 비영속(new) → 영속(managed) → 준영속(detached)/삭제(removed), 준영속 → 병합(merge)으로 다시 영속화 가능. 1차 캐시: @Id를 key로 하는 영속성 컨텍스트 내부 캐시... 쓰기 지연(Write-Behind): INSERT/UPDATE/DELETE SQL을 즉시 보내지 않고... 변경 감지(Dirty Checking): 영속 상태 엔티티는 최초 스냅샷과 현재 상태를 flush 시점에 비교해..." 이거 다 영속성 컨텍스트의 특징인거야?
>
> 맞다. 넷 다 영속성 컨텍스트를 이해하는 핵심 요소들이지만, 구분을 좀 더 정확히 하면 다음과 같다.
>
> - 엄밀히 "영속성 컨텍스트의 기능/메커니즘"인 것(3개): 1차 캐시(영속성 컨텍스트가 내부에 갖고 있는 Map 구조 자체 → 컨텍스트의 구성 요소), 쓰기 지연(SQL을 모아뒀다가 한꺼번에 보내는 내부 동작 방식 → 컨텍스트가 하는 일), 변경 감지(스냅샷과 현재 상태를 비교해 자동으로 UPDATE를 만드는 내부 동작 → 컨텍스트가 하는 일).
> - 성격이 조금 다른 것(1개): 엔티티 생명주기(비영속/영속/준영속/삭제/병합)는 영속성 컨텍스트가 "하는 일"이라기보다, 어떤 엔티티가 지금 이 영속성 컨텍스트에 의해 관리되고 있는지 아닌지를 구분하는 상태 분류다. "영속(managed)" 상태라는 것 자체가 "이 엔티티가 지금 영속성 컨텍스트 안에 들어와서 1차 캐시·변경 감지·쓰기 지연의 적용을 받고 있다"는 뜻이라, 나머지 세 개념이 작동하기 위한 전제 조건(이 엔티티가 영속 상태인가?)을 정의하는 것에 가깝다.
>
> 정리: 1차 캐시·쓰기 지연·변경 감지는 영속성 컨텍스트의 "기능"이고, 엔티티 생명주기는 그 기능들이 "언제 적용되는지"를 결정하는 엔티티의 "상태"다. 넷 다 서로 뗄 수 없이 연결되어 있어 "영속성 컨텍스트의 특징"으로 함께 이해해도 실질적으로 문제없다.

> **Q.** 그럼 의문인게 바로 위에서는 jpa, ORM 그리고 hibernate 설명했잖아? 이건 결국 db관리랑 그걸 구현하는 구현부의 조합인데 왜 바로 영속성 컨텍스트가 나오지?
>
> 갑자기 튀어나온 게 아니라, 사실 "JPA/Hibernate가 정확히 어떻게(How) 일을 하는지"를 설명하는 부분이 바로 영속성 컨텍스트다. 지금까지의 흐름은 이렇게 이어진다.
>
> 1. 문제: 패러다임 불일치(객체 vs 테이블)
> 2. 해결 기술 개념: ORM
> 3. 자바의 ORM 표준: JPA(명세, "이런 인터페이스를 써야 한다"는 규약 — 그중 하나가 `EntityManager`)
> 4. 그 명세의 실제 구현체: Hibernate
>
> 여기까지는 "누가(Who) 무엇을(What) 하는가" — 개념·역할·계보에 대한 설명이었다. 이제 노트는 "그래서 실제로 어떻게(How) 동작하는가?"로 넘어가고, 그 답이 영속성 컨텍스트다.
>
> Hibernate가 SQL을 자동 생성해주는 일을 어떻게 해내는지 뜯어보면 그 중심에 영속성 컨텍스트라는 내부 저장 공간이 있다. JPA가 규정한 `EntityManager` 인터페이스를 Hibernate가 실제로 구현하는데, 그 `EntityManager`가 내부적으로 관리하는 것이 바로 영속성 컨텍스트다. 구조: `JPA(EntityManager라는 인터페이스를 규정) → Hibernate(EntityManager를 실제로 구현) → 그 EntityManager 내부의 "영속성 컨텍스트"라는 작업 공간에서 1차 캐시·쓰기 지연·변경 감지 메커니즘으로 실제 SQL 자동 생성이 이루어짐`.
>
> 정리: 영속성 컨텍스트는 JPA/ORM/Hibernate와 다른 주제가 아니라 "Hibernate가 ORM을 실제로 어떻게 수행하는지"에 대한 내부 동작 원리다. 앞부분(JPA/ORM/Hibernate)이 "정의와 역할" 설명이었다면, 뒷부분(영속성 컨텍스트)은 "그 역할을 실제로 수행하는 메커니즘" 설명이라 자연스러운 다음 단계다.

> **Q.** 그러니까 JPA로 ORM을 규칙에 맞게 만들고 호출을 받고 hibernate가 수행하는데에 내부적으로 ORm을 수행하는 방식이 영속성 컨텍스트다 맞아? hibernate 내부적으로 엔티티 매니저를 만들어서 수행한다?
>
> 둘 다 맞다.
>
> 1. "JPA로 ORM을 규칙에 맞게 만들고 호출을 받고 hibernate가 수행하는데, 그 내부적으로 ORM을 수행하는 방식이 영속성 컨텍스트다" — 맞다. JPA가 규칙(인터페이스)을 정하고, 개발자는 그 규칙대로 호출하고(`entityManager.persist()` 등), 실제로 그 호출을 받아 처리하는 Hibernate가 내부적으로 영속성 컨텍스트라는 메커니즘을 통해 ORM 작업(매핑·SQL 생성·캐싱)을 수행한다.
> 2. "hibernate 내부적으로 엔티티 매니저를 만들어서 수행한다?" — 맞다. `EntityManager`는 JPA가 정의한 인터페이스이고, Hibernate는 그 인터페이스의 실제 구현 클래스(Hibernate 용어로는 `Session`)를 제공한다. JPA는 인터페이스만 정의(틀만 제공)하고, Hibernate는 그 인터페이스를 구현한 실제 객체를 만들어내며(Spring이 요청하면 Hibernate가 진짜 인스턴스를 생성), 그 인스턴스(EntityManager) 안에 영속성 컨텍스트가 함께 생성되어 1차 캐시·쓰기 지연·변경 감지가 그 안에서 이루어진다.
>
> 정리: JPA(규칙) → Hibernate가 그 규칙에 맞는 EntityManager를 실제로 생성 → 그 EntityManager가 내부에 영속성 컨텍스트를 두고 ORM 작업을 실질적으로 수행하는 구조다.

### Q5. Spring Data JPA의 계층 순서와 주요 기능

> **Q.** [Spring Data JPA 시작하기 섹션] 그러니까 spring data jpa는 흐름적으로는 jpa -> hibernate -> spring data jpa 흐름으로 동작하고 실제로 설정할 때는 의존성 하나로 일괄 구성이 가능하고 주요기능으로는 기본적인 CRUD 자동 생성, 커스텀 쿼리, 페이징 정렬 등이 있다 맞아?
>
> 전체적으로 맞지만 "흐름"이라는 표현에서 한 가지 뉘앙스를 정확히 짚어야 한다.
>
> **"JPA → Hibernate → Spring Data JPA" 순서**는 계층 구조(역할 정의)로서는 맞다. 정리 노트의 표에도 정확히 이 순서로 나와 있다.
>
> | 구분 | 역할 | 예시 |
> | --- | --- | --- |
> | JPA | 표준 명세 | `@Entity`, `EntityManager.persist()` |
> | Hibernate | JPA의 구현체 | 내부에서 SQL 실행 처리 |
> | Spring Data JPA | JPA를 추상화하여 자동화 | `MyRepository extends JpaRepository` |
>
> 다만 "흐름(동작 순서)"이라는 표현으로 오해하면 안 되는 부분이 있다 — 실제로 코드가 호출될 때(런타임)는 반대 방향으로 흐른다:
>
> ```
> 개발자가 Repository 메서드 호출
>   → Spring Data JPA (프록시가 요청을 가로챔)
>     → JPA API (EntityManager 메서드를 내부적으로 호출)
>       → Hibernate (실제로 SQL 만들어서 DB 실행)
> ```
>
> 즉 "누가 누구 위에 얹혀 있는가"의 계층 순서는 JPA(맨 아래, 표준) → Hibernate(그 위, 구현) → Spring Data JPA(맨 위, 추상화)가 맞지만, 실제 호출은 위(Spring Data JPA)에서 아래(Hibernate)로 내려간다.
>
> 나머지도 다 맞다: 의존성 하나(`spring-boot-starter-data-jpa`)로 Spring Data JPA + Hibernate + JPA가 자동 설정되고, 주요 기능은 CRUD 자동 구현·메서드 이름 기반 쿼리·`@Query`/QueryDSL/Native Query를 통한 커스텀 쿼리·`Pageable`/`Sort` 기반 페이징·정렬이 맞다(추가로 Spring 트랜잭션·예외 변환과의 통합도 있지만 핵심은 다 짚었다).

### Q6. 프록시와 프록시 객체란

> **Q.** 프록시는 정확히 뭐고 프록시 객체는 뭔데
>
> 정리 노트에 "프록시"가 두 군데(Repository 자동 구현, 지연 로딩)에서 나오는데, 일반적인 개념부터 잡고 그 두 가지에 각각 적용한다.
>
> **프록시(Proxy)란**: "진짜 객체 대신 앞에 서서 요청을 받아주는 대리인 객체"다. 프록시는 진짜 객체와 똑같은 모양(같은 인터페이스/타입)을 하고 있어서, 사용하는 쪽은 이게 진짜인지 대리인인지 신경 쓰지 않고 똑같이 사용할 수 있다. 내부적으로는 요청을 그냥 진짜 객체에게 그대로 전달하거나(위임, delegation), 전달하기 전/후에 추가 작업을 끼워 넣는다(로깅, 권한 체크, 지연 로딩, 트랜잭션 처리 등).
>
> 비유: 연예인(진짜 객체) 대신 스케줄을 관리하는 매니저(프록시). 팬(사용하는 쪽)은 매니저에게 연락하지만 실제 공연은 연예인이 한다. 매니저는 필요할 때만 연예인을 실제로 움직이게 하고, 그 사이에 일정 조율 같은 부가 작업도 처리한다.
>
> **프록시 객체**는 이 대리인 역할을 하는 실제 인스턴스를 말한다. 런타임에 자동으로 생성되며, 보통 직접 `new`로 만들지 않는다.
>
> **정리 노트에 나온 두 가지 프록시**
>
> 1) **Repository 프록시**(`Spring Data JPA 시작하기` 섹션): `public interface MenuRepository extends JpaRepository<Menu, Long> {}`처럼 인터페이스만 작성하면, Spring Boot 실행 시 Spring Data JPA가 이 인터페이스를 보고 런타임에 진짜 구현 클래스(프록시 객체)를 자동으로 만들어 빈으로 등록한다. 이 프록시는 내부적으로 `SimpleJpaRepository`를 상속받아 실제 CRUD 로직을 수행하며, 개발자는 그 프록시 객체를 인터페이스 타입으로 주입받아 쓴다.
> 2) **지연 로딩 프록시**(`JPA 활용 시 주의 사항` 섹션): `@ManyToOne(fetch = FetchType.LAZY) private Category category;`처럼 지연 로딩 설정 시, 처음 `Menu`를 조회하면 `category` 필드에는 진짜 `Category` 객체가 아니라 프록시 객체가 들어간다. 겉보기엔 `Category`처럼 생겼지만 속은 비어있고, `menu.getCategory().getName()`처럼 실제로 이 프록시를 건드리는 순간 영속성 컨텍스트에 초기화를 요청해 DB 조회를 트리거한 뒤, 그 뒤로는 진짜 `Category` 객체에게 요청을 위임한다. 이게 지연 로딩이 실제로 구현되는 방식이다.
>
> 공통점: 두 경우 모두 직접 만들지 않은 대리인 객체가 실제 동작을 대신 처리해주고, 그 과정에서 자동화(Repository 구현 자동화 / DB 접근 지연)를 실현한다는 점에서 같은 원리다.

> **Q.** 그럼 프록시는 객체와 객체 사이를 나누는 완충제 같은거네?
>
> "사이에 낀다"는 부분은 맞지만 "완충제"라는 표현은 뉘앙스가 다르다.
>
> - 완충제의 이미지: 두 물체가 직접 부딪히지 않게 충격을 흡수함(수동적, 보호 목적)
> - 프록시의 실제 역할: 요청을 가로채서 능동적으로 판단·처리함(이 요청을 그냥 넘길지, 추가 작업을 할지, 아직 처리하지 말고 미룰지 등을 결정)
>
> 더 정확한 비유는 "완충제"보다 "중개인/대리인/문지기(gatekeeper)"에 가깝다.
>
> - Repository 프록시: `findAll()` 호출을 가로채서 "아 이건 내가 대신 SQL 만들어서 처리해줄게"라고 능동적으로 일을 대신 해줌
> - 지연 로딩 프록시: `category.getName()` 호출을 가로채서 "잠깐, 아직 실제 데이터가 없네? 지금 DB에서 가져와야겠다"라고 판단해서 필요한 시점에 개입
>
> 즉 "사이에 낀 존재"라는 직관은 정확하지만, 그 역할은 "충격을 완화시켜주는 수동적 존재"가 아니라 "중간에서 요청을 통제하고 대신 처리해주는 능동적 대리인"이라는 점이 핵심 차이다.

> **Q.** 객체와 객체 사이의 중개인으로 인지하면 될까?
>
> 맞다. "객체와 객체 사이의 중개인"으로 인지하면 정확하다.
>
> - 호출하는 쪽(클라이언트)과 실제 일을 하는 진짜 객체(Real Subject) 사이에서
> - 프록시가 중개인으로 끼어들어 요청을 가로채 판단하고
> - 필요하면 진짜 객체를 대신 움직이거나, 대신 처리하거나, 처리 시점을 조절한다
>
> 이렇게 이해하면 Repository 프록시(Spring Data JPA가 개발자 대신 CRUD 구현을 중개)와 지연 로딩 프록시(실제 DB 조회 시점을 중개)를 모두 같은 원리로 설명할 수 있다.

> **Q.** 그럼 살짝 복습으로 전에 배운 DTO랑 비슷한 역할 아닌가? DTO는 내부 로직와 외부 데이터 사이에 껴서 내부 로직을 외부로 부터 보호하는거잖아
>
> 비슷해 보이지만 작동 방식이 근본적으로 다르다. "무언가 사이에 껴서 보호한다"는 큰 그림은 비슷하지만 "어떻게" 보호하는지가 다르다.
>
> 공통점(표면적 유사성): 둘 다 "진짜/내부 것"과 "바깥/외부 것" 사이에 끼어서 경계 역할을 한다. Proxy는 클라이언트 ↔ 진짜 객체 사이, DTO는 외부(API 응답/요청) ↔ 내부(Entity/도메인 로직) 사이.
>
> 결정적 차이(가로채서 판단하는가 vs 그냥 모양만 다른 데이터인가):
>
> | | Proxy | DTO |
> | --- | --- | --- |
> | 정체 | 진짜 객체와 같은 타입을 흉내 낸 대리인 | 진짜 객체와 완전히 다른, 더 단순한 데이터 클래스 |
> | 동작 방식 | 메서드 호출을 가로채서(intercept) 판단·위임·지연 | 그냥 필드만 있는 정적인 데이터 덩어리(능동적 판단 없음) |
> | 예시 | `category.getName()` 호출 시 "지금 DB 조회해야겠다" 판단 | `new MenuResponse(menu.getId(), menu.getName(), ...)`처럼 미리 값을 복사해서 새 객체를 만듦 |
> | 목적 | 호출 시점/방식을 통제(지연 로딩, 자동 구현) | 노출할 데이터의 모양(shape)을 통제(Entity 구조 숨기기, 무한루프 방지) |
>
> Proxy는 "행동(behavior)"을 대신 처리한다 — 요청이 오면 그 순간 판단해서 움직인다. DTO는 "데이터(data)"의 모양만 다르게 포장한다 — Entity의 연관관계, 지연 로딩 필드, 내부 구조를 그대로 노출하면 무한루프나 `LazyInitializationException`이 터지니까 필요한 값만 뽑아서 새로운 단순한 객체로 옮겨 담는 것뿐이고, 호출을 가로채거나 지연시키는 능동적 동작은 없다.
>
> 한 줄 정리: DTO가 "내부 로직을 보호한다"는 표현은 정확하지만, 그 보호 방식은 프록시처럼 "요청을 가로채서 통제"하는 게 아니라 "애초에 내부 구조를 노출하지 않고 별도의 단순한 사본을 만들어 건네주는 것"이다. GoF 디자인 패턴으로 분류하면 Proxy는 호출을 가로채는 구조적 패턴, DTO는 단순 데이터 전달 객체(패턴이라기보다 관례)로 성격이 다르다.

### Q7. SQL과 PostgreSQL의 관계

> **Q.** [정리 노트의 "PostgreSQL에서는 일반적으로..." 문장 관련] SQL이 db에서 사용하는 언어니까 postgreSQL은 SQL의 종류지?
>
> 아니다, 관계가 반대다. PostgreSQL은 SQL의 "종류"가 아니라, SQL이라는 언어를 사용하는 여러 RDBMS(관계형 데이터베이스 관리 시스템) 제품 중 하나다.
>
> - SQL: 관계형 데이터베이스를 다루기 위한 언어(표준) 그 자체. 특정 회사나 제품이 아니라 국제 표준(ANSI/ISO SQL)이다.
> - PostgreSQL, MySQL, Oracle, SQL Server, SQLite, MariaDB 등: 그 SQL 언어를 이해하고 실행해주는 각각의 소프트웨어 제품(DBMS)이다.
>
> 비유: SQL은 "영어"라는 언어이고, PostgreSQL·MySQL·Oracle은 각자 조금씩 다른 억양/사투리로 그 영어를 구사하는 "화자들"이다. 기본 문법(SELECT, INSERT, WHERE...)은 다 공유하지만 제품마다 세부 문법이나 고유 함수가 조금씩 다르다.
>
> 정리 노트에도 이미 힌트가 있었다 — `application.yaml`의 `dialect: org.hibernate.dialect.PostgreSQLDialect` 부분. 여기서 "dialect(방언)"이라는 단어 자체가 "SQL이라는 하나의 언어에 여러 제품별 사투리가 있다"는 것을 보여준다. PostgreSQL이 "SQL의 한 종류"라면 dialect라는 개념 자체가 말이 안 되고, "SQL이라는 큰 언어 안에서 PostgreSQL이 자기만의 사투리(dialect)를 쓴다"고 봐야 정확하다(`GenerationType.IDENTITY` 전략이 PostgreSQL 10+ 에서 쓰이는 것도 이런 제품별 차이의 예시).

### Q8. Java-SQL 타입 매핑에서 dialect의 역할

> **Q.** "방언(dialect)에 따라 실제 SQL 타입은 달라질 수 있다." 이렇게 나와있는데 어떤 SQL 타입이든 JAVA로 바꿔준다는거지?
>
> 방향이 살짝 반대로 이해됐다. "어떤 SQL 타입이든 Java로 바꿔준다"가 아니라, "같은 Java 타입이라도 어떤 DB(dialect)를 쓰느냐에 따라 실제 생성되는 SQL 타입이 달라질 수 있다"는 뜻이다.
>
> 방향은 Java → SQL이다. 정리 노트의 표를 보면 `LocalDateTime`(Java 타입, 고정) → `timestamp`(PostgreSQL에서 생성되는 SQL 타입). "방언에 따라 달라진다"는 건 이 Java → SQL 변환의 "목적지(결과물)"가 DB 제품마다 다르다는 뜻이다. 같은 `LocalDateTime` 필드라도 PostgreSQL이면 `timestamp`로, 다른 DBMS면 이름이나 세부 정의가 다른 타입으로 생성될 수 있다. 즉 출발점(Java 타입)은 고정인데 도착점(실제 SQL 타입 이름)이 방언마다 달라진다.
>
> 정확한 그림: `Java 타입(String, LocalDateTime, int...) → (JPA가 변환, 이때 "어떤 dialect를 쓰느냐"가 변환 규칙을 결정) → DB 제품별 실제 SQL 타입(PostgreSQL의 varchar/timestamp, 다른 DB의 다른 표현...)`.
>
> 참고로 이건 테이블을 생성할 때(DDL)의 방향(Java → SQL)이고, 반대로 데이터를 조회할 때는 SQL 결과(SQL 타입) → Java 객체로 다시 변환되는 과정도 있는데, 이때도 마찬가지로 dialect가 "이 DB의 이 타입을 Java의 어떤 타입으로 읽어들일지"를 결정한다. 두 방향 모두 dialect가 "번역 규칙"을 제공하는 것이지, "SQL 타입을 무조건 Java로 바꿔준다"는 단방향 얘기가 아니다.

> **Q.** 그럼 타입 매핑은 어떻게 결정되는거지? 내가 MySQL을 쓸지 PostgreSQL을 쓸지 어떻게 알아? 의존성에서 나뉘나?
>
> 세 가지 설정이 함께 작동해서 결정된다. 의존성이 관련은 있지만 그게 전부는 아니다.
>
> 1) 의존성(Dependency) — "어떤 DB에 연결할 수 있는 능력"을 결정. `runtimeOnly 'org.postgresql:postgresql'`(PostgreSQL용 JDBC 드라이버) 또는 `runtimeOnly 'com.mysql:mysql-connector-j'`(MySQL용). 이 드라이버가 없으면 애초에 그 DB에 연결 자체가 불가능하다.
>
> 2) `application.yaml`의 접속 정보 — "실제로 어떤 DB에 연결할지" 결정. `spring.datasource.url`(예: `jdbc:postgresql://localhost:5432/menudb`)과 `driver-class-name`(예: `org.postgresql.Driver`)이 "지금 이 순간 실제로 접속할 DB가 PostgreSQL이다"라고 명시한다.
>
> 3) `hibernate.dialect` — "그 DB에 맞는 SQL 문법을 어떻게 생성할지" 결정. `spring.jpa.properties.hibernate.dialect: org.hibernate.dialect.PostgreSQLDialect`가 Q8의 "타입 매핑 규칙"을 결정하는 부분이다. 최신 Hibernate(6.x, Spring Boot 3.x 이상)는 접속된 JDBC 커넥션 정보를 보고 dialect를 자동 감지할 수 있어 이 설정을 생략해도 동작하는 경우가 많지만, 명시적으로 지정해두는 게 안전하고 관례적이다.
>
> 정리: "의존성에서 나뉘나?"는 부분적으로 맞다 — 의존성(드라이버)이 "연결 가능한 DB 종류"를 정하고, `url`/`driver-class-name`이 "실제로 연결할 DB"를 정하고, `dialect`가 "그 DB에 맞는 SQL 타입/문법 변환 규칙"을 정한다. 이 세 가지가 함께 맞아떨어져야 PostgreSQL이든 MySQL이든 제대로 동작한다.

### Q9. "Entity 연관관계 매핑" 섹션이 다루는 대상

> **Q.** [Entity 연관관계 매핑 섹션] 이거 자체가 기본적으로 엔티티랑 테이블의 매핑을 말하는거지?
>
> 살짝 정정이 필요하다. "Entity ↔ 테이블"의 매핑(1개 클래스 ↔ 1개 테이블)은 이미 앞 섹션(`Entity 설계 기초`)에서 다룬 내용이고, "Entity 연관관계 매핑"은 그것과는 다른, 한 단계 더 나아간 개념이다.
>
> | | Entity 설계 기초 | Entity 연관관계 매핑 |
> | --- | --- | --- |
> | 다루는 대상 | 엔티티 1개 ↔ 테이블 1개 | 엔티티와 엔티티 사이의 관계(= 테이블과 테이블 사이의 외래키 관계) |
> | 핵심 어노테이션 | `@Entity`, `@Table`, `@Id`, `@Column` | `@ManyToOne`, `@OneToMany`, `@JoinColumn`, `mappedBy` |
> | 예시 | `Menu` 클래스 → `menus` 테이블(각 필드 → 각 컬럼) | `Menu`가 `Category`를 참조 → `menus.category_id`라는 외래키(FK)로 연결 |
>
> - Entity 설계 기초: "`Menu`라는 자바 클래스 하나를 `menus`라는 테이블 하나에 어떻게 매핑할까?"(필드 하나하나를 컬럼에 매핑)
> - Entity 연관관계 매핑: "`Menu`와 `Category`처럼 서로 다른 엔티티(=테이블) 두 개가 서로를 참조할 때, 그 관계를 자바 필드(`private Category category;`)로 어떻게 표현하고 그게 DB의 외래키로 어떻게 연결되는가?"
>
> 즉 "연관관계 매핑"은 "엔티티 하나를 테이블 하나로 바꾸는 것"이 아니라, "엔티티들 사이의 관계(참조)를 테이블들 사이의 관계(외래키)로 어떻게 표현하는가"를 다루는 것이다. `Menu.category` 필드에 `@ManyToOne @JoinColumn(name = "category_id")`를 붙이는 예시가 이를 보여준다 — 자바 객체의 "참조(reference)"가 DB의 "외래키(FK)"로 번역되는 과정이다.

> **Q.** 기본 개념부터 차근차근해야할거 같은데, 일단 내가 지금 이해한건 엔티티 연관관계 매핑 이라는게 엔티티랑 엔티티 사이의 매핑을 다루는거고 이게 다중성을 띌 수 있다? 그리고 엔티티를 참조할때는 외래키가 필요하다는거만 이해했어
>
> 세 가지 모두 맞다. 이어서 나머지 핵심 개념(방향성, 연관관계의 주인)을 순서대로 붙인다.
>
> **개념 ① 다중성 구체화**: "다중성을 띈다"는 관계를 맺는 두 엔티티가 각각 몇 개씩 연결되는지를 말하며 4가지뿐이다.
>
> | 관계 | 뜻 | 예시 |
> | --- | --- | --- |
> | 1:1 | 서로 딱 하나씩 | 주문 1개 ↔ 결제 1건 |
> | 1:N | 하나가 여러 개를 가짐 | 카테고리 1개 ↔ 메뉴 여러 개 |
> | N:1 | 여러 개가 하나를 가리킴 | 메뉴 여러 개 ↔ 카테고리 1개 |
> | N:M | 서로 여러 개씩 | 메뉴 N개 ↔ 알레르기정보 N개 |
>
> 카테고리-메뉴 예시에서 "카테고리 입장에서는 1:N", "메뉴 입장에서는 N:1"인데, 이는 같은 관계를 어느 쪽에서 바라보느냐의 차이일 뿐 결국 하나의 관계다.
>
> **개념 ② 외래키를 자바 코드로 표현**: `@ManyToOne @JoinColumn(name = "category_id") private Category category;`처럼 Menu 쪽에 필드를 선언하면 "menus 테이블에 category_id라는 외래키 컬럼을 만들어라"는 뜻이 된다. 즉 DB의 외래키 = 자바 클래스의 참조 필드(`private Category category`)로 표현된다.
>
> **개념 ③(새로 추가) 방향성(단방향 vs 양방향)**: Menu가 Category를 필드로 갖고 있으면 `Menu → Category` 방향으로만 참조 가능하다(단방향). 반대로 Category에서도 `@OneToMany(mappedBy = "category") private List<Menu> menus;`를 추가하면 양쪽이 서로 참조하는 양방향이 된다. 양쪽 다 필드를 가지면, DB의 외래키 컬럼(category_id)을 실제로 어느 쪽 코드가 책임지고 관리하는지(연관관계의 주인)를 정해야 하는 다음 문제로 자연스럽게 이어진다.

> **Q.** 일단 외래키 개념부터. 내가 이해하기론 a가 b를 참조할려면 a가 b의 외래키를 컬럼으로 만들어야된다는거지?
>
> 핵심은 맞지만 표현을 정확히 다듬어야 한다. 정확한 표현: "A가 B를 참조하려면, A의 테이블에 B의 기본키(PK)를 가리키는 외래키 컬럼을 만들어야 한다."
>
> "B의 외래키"라는 표현이 헷갈릴 수 있다 — 외래키 컬럼은 B가 아니라 A의 테이블에 생긴다. 다만 그 컬럼 안에 들어가는 값은 B의 기본키(PK) 값이다.
>
> 구체적 예시: `@ManyToOne @JoinColumn(name = "category_id") private Category category;`에서 Menu(A)가 Category(B)를 참조할 때, 외래키 컬럼(`category_id`)이 생기는 곳은 `menus` 테이블(A, 참조하는 쪽에 생김)이고, 그 컬럼에 저장되는 값은 `categories` 테이블(B, 참조당하는 쪽)의 `id` 값이다. `categories` 테이블(B)에는 외래키 컬럼이 생기지 않는다.
>
> 정리: "A가 B를 참조" = A 테이블에 "B를 가리키는" 외래키 컬럼을 만들고, 그 컬럼 값으로 B의 PK를 저장하는 것. "B의 외래키를 만든다"보다는 "A에, B를 향한 외래키를 만든다"가 더 정확한 표현이다.

> **Q.** 양방향 관계에서는 A B가 서로의 외래키를 칼럼으로 추가한건가?
>
> 아니다. 양방향이어도 실제 DB에 외래키 컬럼이 생기는 건 한쪽뿐이다. 이게 바로 "연관관계의 주인" 개념이다.
>
> 예시: `@ManyToOne @JoinColumn(name = "category_id") private Category category;`(Menu 쪽, 외래키 컬럼을 실제로 만드는 "주인")과 `@OneToMany(mappedBy = "category") private List<Menu> menus;`(Category 쪽, 조회 편의용, 실제 컬럼은 안 만듦). 결과적으로 `menus` 테이블에는 `category_id` 컬럼이 생기지만, `categories` 테이블에는 메뉴 관련 컬럼이 전혀 생기지 않는다.
>
> Category의 `List<Menu> menus`는 DB에 저장되는 실제 데이터가 아니라 JPA가 자바 객체 레벨에서만 만들어주는 가상의 편의 기능이다. `category.getMenus()`를 호출하면 JPA가 내부적으로 `SELECT * FROM menus WHERE category_id = ?` 쿼리를 대신 날려서 결과를 `List<Menu>`로 채워주는 것뿐이고, `categories` 테이블 자체에는 그 정보를 저장할 컬럼이 없다.
>
> 정리: 연관관계의 주인(`@JoinColumn`을 가진 쪽, 여기선 Menu)은 실제 외래키 컬럼을 만들고 관리하는 쪽이고, 주인이 아닌 쪽(`mappedBy`를 가진 쪽, 여기선 Category)은 컬럼은 안 만들고 반대 방향 조회만 가능하게 해주는 쪽이다. "A와 B가 서로의 외래키를 컬럼으로 추가한다"가 아니라 "둘 중 하나만 진짜 외래키 컬럼을 갖고, 나머지 하나는 그 컬럼을 거꾸로 조회하는 기능만 가진다"가 정확하다.

> **Q.** "@ManyToOne: 가장 흔한 관계(N:1)" 그럼 이 경우에는 a가 b c의 외래키를 가지고 있는경우?
>
> N:1이 뜻하는 바를 살짝 다르게 이해했다. "A가 B와 C의 외래키를 둘 다 가지고 있는 경우"는 N:1 관계 하나가 아니라, 완전히 독립된 N:1 관계가 두 개 있는 것이다.
>
> N:1에서 N과 1이 가리키는 건 "엔티티 종류 개수"가 아니라 "행(row)의 개수"다. `@ManyToOne @JoinColumn(name = "category_id") private Category category;`에서 N(여러 개)은 "Menu라는 같은 종류의 엔티티가 여러 행(row) 있다"는 뜻이고, 1(하나)은 "그 여러 Menu 행들이 결국 Category라는 같은 엔티티의 한 행을 가리킨다"는 뜻이다(`Menu(id=1,category_id=1)`, `Menu(id=2,category_id=1)`, `Menu(id=3,category_id=1)` 전부 `Category(id=1)` 하나를 가리키는 구조). 즉 N:1은 "한 엔티티의 여러 행이 다른 한 엔티티의 한 행을 참조"하는 것이지, "한 엔티티가 서로 다른 두 종류의 엔티티(B, C)를 참조"하는 게 아니다.
>
> 만약 A가 진짜로 B와 C 둘 다 참조하고 싶다면, 그건 가능하지만 N:1 관계 하나가 아니라 N:1 관계 두 개가 된다. 예: `Order`가 `Customer`와 `ShippingAddress`를 둘 다 참조하면, `@ManyToOne @JoinColumn(name="customer_id") private Customer customer;`(Order→Customer 방향의 N:1 관계 1)와 `@ManyToOne @JoinColumn(name="shipping_address_id") private ShippingAddress address;`(Order→ShippingAddress 방향의 N:1 관계 2)로, `orders` 테이블에 외래키 컬럼이 두 개(`customer_id`, `shipping_address_id`) 생기지만 이는 서로 독립적인 두 개의 N:1 관계다. 각각의 `@ManyToOne`은 항상 "하나의 대상 엔티티"만 가리킨다.

> **Q.** 그러니까 N이 말하는게 엔티티 내부적으로 가지고 있는 행의 수 라는거지? 그러면 a(행 3개)가 b(행1개)의 외래키를 가지고 있으면 이건 N:1이라는거지?
>
> 중요한 오해가 있다. N:1은 "지금 이 순간 테이블에 실제로 몇 개 행이 들어있나"를 세는 게 아니다. "여러 개의 A 행이 같은 B 행 하나를 가리키는 것이 구조적으로 허용되는가"를 말하는 것 — 데이터의 스냅샷(현재 몇 개 들어있는지)이 아니라 관계의 설계 규칙(구조)이다.
>
> `Category` 테이블에 지금 딱 1개의 행만 있어도, 그건 우연히 지금 데이터가 1개인 것뿐이지 관계의 종류를 결정하는 게 아니다. 내일 카테고리를 5개 더 추가해도 관계의 종류(N:1)는 그대로다. N:1을 결정하는 건 "여러 개의 Menu가 같은 Category 하나를 공유하는 게 구조적으로 허용되는가"다.
>
> 진짜 기준은 외래키 컬럼에 UNIQUE 제약이 있는가 없는가다.
>
> - N:1 예(`menus.category_id`에 UNIQUE 제약 없음): 여러 메뉴가 같은 `category_id` 값을 가질 수 있음(허용됨). `(1,'김치찌개',1)`, `(2,'된장찌개',1)`처럼 category_id=1이 중복돼도 괜찮다.
> - 반대로 1:1 예(예: `payments.order_id`에 UNIQUE 제약 있음): 같은 `order_id`를 두 개의 payment 행이 가질 수 없다(구조적으로 막혀있음).
>
> 두 예시 모두 "A쪽 행이 3개, B쪽 행이 1개"인 경우가 우연히 생길 수 있지만, N:1인지 1:1인지는 행 개수가 아니라 "중복이 허용되는가(UNIQUE 제약의 유무)"로 결정된다.
>
> 정정된 정의: N:1은 "A의 외래키 컬럼에 같은 B 값이 여러 번 나올 수 있도록(중복 허용) 설계되어 있어서, 여러 A 행이 같은 B 행 하나를 공유할 수 있는 구조"를 말한다. 지금 실제로 몇 개의 행이 들어있는지는 무관하다.

> **Q.** menu 엔티티가 있어 category 엔티티의 외래키를 가지고 있어. 그럼 menu가 category를 참조할 수 있잖아? 이상태에서 category에 있는 id를 중복으로 사용하게 N:1이라는거라고?
>
> 맞다. "Category의 id를 여러 Menu 행이 중복으로(=재사용해서) 참조할 수 있는 상태"가 바로 N:1이다.
>
> 예: `Category(id=1, name='찌개류')` 하나에 대해 `Menu(id=1, category_id=1)`, `Menu(id=2, category_id=1)`, `Menu(id=3, category_id=1)`처럼 `category_id=1`이라는 값이 여러 Menu 행에서 반복(중복) 사용된다. 이게 가능한 이유는 `menus.category_id` 컬럼에 UNIQUE 제약이 없기 때문이다(DB가 "이 값 또 써도 돼"라고 허락). 그래서 "여러(N) 개의 Menu가 하나(1)의 Category를 공유(중복 참조)할 수 있다" → N:1.
>
> 대조로 `menus.category_id`에 UNIQUE 제약을 걸면, category_id=1을 이미 Menu(id=1)이 썼으면 Menu(id=2)는 절대 그 값을 또 쓸 수 없게 되어 "하나의 Category당 딱 하나의 Menu만 연결 가능"해지고, 이건 N:1이 아니라 1:1이 된다.
>
> 결론: "외래키 값(Category의 id)을 여러 참조하는 쪽(Menu) 행이 중복해서 쓸 수 있게 허용된 상태"가 N:1이라는 이해가 정확하다.

> **Q.** 위 예시에서 unique 제약설정해서 1:1까지 이해했어. 그러면 N:M은 어떻게 생기는거지? 서로를 참조하는건 오류잖아? 그러면 추측건데 A에 있는 n개의 카테고리에 b의 id를 m개 참조하는거야?
>
> "서로 참조가 문제"라는 직관은 맞는 방향이다. 외래키 컬럼 하나는 딱 하나의 값만 저장할 수 있는데, N:M은 "A 하나가 여러 B를 가질 수 있고, B 하나도 여러 A에 속할 수 있는" 관계다. Menu에 allergy_id 컬럼을 하나 추가하면 그 메뉴는 알레르기 정보 하나밖에 못 가지고(컬럼 하나=값 하나), Allergy에 menu_id를 추가해도 반대로 같은 문제가 생긴다. 그래서 N:M은 A나 B 어느 쪽에도 직접 외래키를 추가하는 방식으로는 표현이 안 된다. ("A n개가 B의 id를 m개 참조"처럼 한 컬럼에 여러 id를 몰아넣는 방식은 DB에서 불가능하다.)
>
> 실제 해법은 A와 B 사이에 제3의 **중간 테이블(Join Table)**을 만들고, 그 테이블이 A와 B를 각각 N:1로 참조하게 만드는 것이다.
>
> 예: `Menu`, `menu_allergy`(중간 테이블: menu_id, allergy_id), `Allergy`. `menu_allergy`의 한 행 = "이 메뉴에 이 알레르기 정보가 있다"는 하나의 조합. `menu_id=1`(김치찌개)이 여러 행(`menu_id=1,allergy_id=1`과 `menu_id=1,allergy_id=2`)에 걸쳐 중복 등장하면 김치찌개가 여러 알레르기를 가질 수 있고(N:1: 중간테이블→Menu), `allergy_id=1`(갑각류)도 여러 행에 걸쳐 중복 등장하면 갑각류가 여러 메뉴에 속할 수 있다(N:1: 중간테이블→Allergy).
>
> 즉 N:M은 "N:1 관계 두 개를 중간 테이블로 이어붙인 것"이다. 중간 테이블 자체는 A와도 N:1, B와도 N:1 관계를 맺고 있고, 그 두 개가 합쳐져서 결과적으로 "A와 B가 N:M"처럼 보이는 것이다. 정리 노트에서 `@ManyToMany`를 실무에서 잘 안 쓰고, 이 중간 테이블을 아예 엔티티(`OrderCoffee` 같은)로 직접 만들어서 N:1 + 1:N으로 푸는 방식을 권장한다고 한 것이 바로 이 원리다.

> **Q.** (글로 보니까 하나도 이해가 안 된다는 반응에 이어) 학생-수업 예시로 다시 설명. 그러니까 다시 정리를 하면 엔티티가 기본적으로 하나의 값만 가지니까 한 값에 2개를 쓸려면 추가적인 엔티티를 만들어서 각 엔티티에 어떤 값을 넣을지 정하는 엔티티를 추가해서 한 값이 각각 1개의 값을 가진 결과를 2개 만들어낸다고?
>
> 맞다. 정리한 논리 그대로다.
>
> 1. 한 컬럼(값)은 딱 하나의 값만 담을 수 있다(컬럼 하나 = 값 하나 원칙)
> 2. "철수 → [수학, 영어]"처럼 하나가 여러 값을 가지려는 상황이 생긴다
> 3. 이걸 해결하려고 중간에 새로운 표(엔티티)를 하나 추가한다
> 4. 그 표는 "철수-수학", "철수-영어"처럼 한 줄에 딱 한 쌍(조합)만 적어서, 여러 줄로 나눠 표현한다
>
> 즉 "하나의 칸에 여러 값을 억지로 넣는 것"을 "한 줄에 값 하나씩만 있는 여러 줄"로 쪼개서 풀어낸 것이다.
>
> | 학생 | 수업 |
> | --- | --- |
> | 철수 | 수학 |
> | 철수 | 영어 |
> | 영희 | 수학 |
>
> "철수가 2과목 듣는다"는 하나의 사실이 위 표에서는 "철수"가 등장하는 줄이 2개로 표현된다. 한 줄 안에서는 항상 "학생 1명 + 수업 1개"라는 1:1 짝만 있고, 그 짝을 여러 줄 반복해서 "여러 개를 가진다"는 걸 흉내 내는 것이다.
>
> 이 "중간 표"가 바로 앞서 말한 "중간 테이블(Join Table)/중간 엔티티"다. 이 표는 학생 쪽으로도, 수업 쪽으로도 각각 N:1 관계를 맺고 있고, 그 둘이 합쳐진 결과가 N:M이라고 부르는 것이다.

> **Q.** 지금 지키려고하는 대전제가 컬럼 하나에 값을 하나 넣는다 잖아. 지금 말하는 방식으로 해결할려면 그러니까 "철수-수학", "철수-영어"처럼 한 줄에 딱 한 쌍 — 이러면 각각 동일한 성질인건데 어떻게 컬럼 하나 값 하나로 나뉠 수 있어?
>
> "철수-수학"이라고 붙여 쓴 표현이 오해를 만들었다. 그건 "한 칸에 두 값을 합친 것"이 아니라 "한 줄에 서로 다른 두 개의 칸(컬럼)이 나란히 있는 것"이다.
>
> 중간 표의 진짜 구조(컬럼을 명확히 분리):
>
> | 학생컬럼 | 수업컬럼 |
> | --- | --- |
> | 철수 | 수학 |
> | 철수 | 영어 |
> | 영희 | 수학 |
>
> "학생컬럼"이라는 칸 하나에는 값 하나만 들어간다(예: "철수") — 컬럼 하나=값 하나 원칙 지켜짐. "수업컬럼"이라는 칸 하나에도 값 하나만 들어간다(예: "수학") — 이것도 지켜짐. 이 둘은 서로 다른 칸(컬럼)이고, "철수-수학"은 편하게 줄여 쓴 표현일 뿐 실제로는 "학생컬럼=철수"라는 값 하나 + "수업컬럼=수학"이라는 값 하나가 같은 줄(행)에 나란히 놓여있는 것이다.
>
> 쌍(pair)을 만드는 건 "같은 줄(행)에 있다"는 사실 자체다. 값을 합치는 게 아니라 같은 행에 나란히 앉혀놓는 것만으로 "이 학생 + 이 수업이 연결됐다"는 뜻이 된다. 이건 이미 배운 것과 똑같다 — `menus` 테이블의 `menu_name` 컬럼(값 하나) + `category_id` 컬럼(값 하나)이 같은 행에 있어서 "김치찌개는 category_id 1번이다"라는 관계가 성립하는 것과 동일한 원리다. 중간 테이블도 그냥 "학생 참조용 컬럼" 하나, "수업 참조용 컬럼" 하나, 두 개의 평범한(각각 값 하나짜리) 컬럼이 한 테이블에 같이 있는 것뿐이며, 새로운 규칙이 아니라 "컬럼=값 하나" 원칙을 두 번 나란히 적용한 것이다.

> **Q.** 아 그건가? 학생이랑 수업만 있으면 무조건 한 학생 이름에는 수업 하나만 들어가니까 학생 이름 칼럼에 수업 이름 칼럼 이렇게 설정해서 매핑한다는거지?
>
> 정확히 맞다. "학생 하나에는 수업 하나만 들어갈 수 있다"는 제약(컬럼=값 하나 원칙)은 그대로 유지하면서, 그 제약을 지키는 새로운 표(중간 테이블)를 하나 더 만들어서 거기에 "학생 컬럼"과 "수업 컬럼"을 나란히 둬서 매핑한다.
>
> 정리: 1) 학생 테이블만 있으면 "학생 하나 = 수업 하나"만 가능(컬럼 하나=값 하나라서). 2) "학생 하나 = 수업 여러 개"를 표현하고 싶다. 3) 새 테이블(중간 테이블)을 만들어 "학생 컬럼(값 하나)" + "수업 컬럼(값 하나)"을 나란히 두고, 4) 같은 학생이 여러 줄(행)에 걸쳐 반복 등장하게 해서 "이 학생은 이 수업도, 저 수업도 듣는다"를 표현한다.
>
> 이게 정리 노트의 `menu_allergy` 중간 테이블과 완전히 같은 구조다: `menu_id` 컬럼(메뉴 하나를 가리키는 값 하나), `allergy_id` 컬럼(알레르기 하나를 가리키는 값 하나). `menu_id=1`(김치찌개)이 두 줄에 걸쳐 등장하면 김치찌개는 알레르기 정보를 2개 가진다는 뜻이 된다. N:M 개념이 정리됐고, 학생-수업 예시의 원리가 그대로 Menu-Allergy, Order-Coffee(심화 실습의 `OrderCoffee` 중간 엔티티)에도 적용된다.

> **Q.** 그러니까 n:m 좀 다시 정리해보면 2개의 엔티티로는 1:n이 한계여서 추가로 엔티티를 만들어서 1:n을 이중으로 만들어 하나의 값이 결론적으로 2개의 값을 가지도록 한다?
>
> 방향은 맞지만 마지막 표현("하나의 값이 결론적으로 2개의 값을 가지도록 한다")만 정정이 필요하다.
>
> - "2개의 엔티티로는 1:N이 한계" — 맞다. 외래키 컬럼 하나는 값 하나만 담을 수 있어서, 두 엔티티만으로는 한쪽이 다른 쪽을 N:1(또는 반대로 1:N)로만 참조할 수 있다.
> - "추가 엔티티를 만들어 1:N을 이중으로 만든다" — 맞다. 중간 엔티티를 하나 만들면 그 중간 엔티티가 원래 엔티티 A와 N:1, 원래 엔티티 B와도 N:1을 각각 맺는다. A 입장에서 보면 "중간 엔티티가 나를 여러 번 참조할 수 있다(1:N)", B 입장에서도 마찬가지(1:N)라서, 결과적으로 1:N이 두 개 겹친 구조가 된다.
> - "하나의 값이 결론적으로 2개의 값을 가지도록 한다" — 이 부분이 정확하지 않다. 값 하나가 실제로 2개의 값으로 변하는 게 아니다. 컬럼 하나=값 하나 원칙은 끝까지 깨지지 않는다. 대신 같은 값(예: 학생 "철수")이 중간 테이블에서 여러 행(row)에 걸쳐 중복 등장하는 것으로 다중성을 표현한다. "철수, 수학" 행과 "철수, 영어" 행이 각각 따로 존재하는 것이지, "철수"라는 하나의 값 안에 [수학, 영어] 두 값이 들어가는 게 아니다.
>
> 정리: N:M = (중간 엔티티↔A의 N:1) + (중간 엔티티↔B의 N:1)이고, "하나가 여러 개를 가진 것처럼 보이는" 효과는 값 자체가 여러 개를 담아서가 아니라 행(row)이 여러 개로 늘어나서 나오는 것이다.

> **Q.** 일단 그럼 n:m 구조일 때는 중간 관리하는 엔티티에 @JoinColum 인거네?
>
> 맞다. 정확히는 중간 엔티티 안에 있는 각각의 `@ManyToOne` 필드에 `@JoinColumn`을 붙인다.
>
> - 중간 엔티티(예: `MenuAllergy`)는 `Menu`를 향한 `@ManyToOne` 필드 하나, `Allergy`를 향한 `@ManyToOne` 필드 하나, 이렇게 두 개를 가진다.
> - 각 필드에 `@JoinColumn(name = "menu_id")`, `@JoinColumn(name = "allergy_id")`처럼 붙여서, 중간 테이블에 생길 외래키 컬럼 이름을 각각 지정한다.
> - 즉 "N:1 관계 하나당 `@JoinColumn` 하나씩", 총 2개가 붙는 구조다 — 앞서 배운 Menu→Category의 단일 N:1 관계에 쓰던 `@JoinColumn`을 그대로 두 번 적용하는 것뿐이다.
>
> 참고로 헷갈릴 수 있는 비슷한 이름의 어노테이션이 하나 있다: `@JoinTable`은 `@ManyToMany`를 직접 쓸 때(중간 엔티티 없이 JPA가 중간 테이블을 내부적으로 숨겨서 관리하는 방식)에 쓰는 것이고, 지금처럼 중간 엔티티를 직접 만드는 방식에서는 쓰지 않는다. 중간 엔티티 방식에서는 오직 `@JoinColumn`만 두 번 쓰면 된다.

> **Q.** 이게 개념적으로는 이해가 되는게 설명하라니까 못하겠어
>
> 이해는 됐는데 설명이 안 나오는 건 흔한 현상이다 — 읽고 "맞다/이해했다"고 느끼는 건 재인(recognition)이고, 아무것도 없는 상태에서 순서대로 말로 뽑아내는 건 인출(recall)이라 완전히 다른 능력이다. 이해했다고 착각하게 만드는 게 재인의 함정이다.
>
> 연습용으로 아래 4단계 뼈대를 쥐고, 각 단계를 본인 말로 채워서 설명해보는 방법을 제안했다.
>
> 1. 전제: 컬럼(외래키) 하나는 값을 몇 개까지 담을 수 있는가?
> 2. 문제: N:M은 무엇을 원하는 관계인가? 왜 컬럼 하나로는 안 되는가?
> 3. 해결: 그래서 무엇을 추가로 만드는가? 그 안에 뭐가 들어가는가?
> 4. 결과: 그 해결책이 왜 "N:M처럼 보이는 효과"를 만들어내는가?

> **Q.** (사용자가 4단계로 직접 설명 시도) "1. 컬럼은 하나에는 하나의 값만 담을 수 있어서 2. N:M 관계에서 원하는 하나의 컬럼에 2개 이상을 값을 담을 수 없다 3. 그래서 a,b와 각각 1:n 관계인 엔티티 하나를 추가해서 중개한다 4. 이러면 c에서 a와 1:n 관계, c에서 b와 1:n 관계 이므로 c 입장에서 a의 컬럼에 b의 값을 n개 추가가 가능하다 맞아?"
>
> 1~3은 맞고, 4에서 두 가지가 어긋났다.
>
> - 1: 컬럼 하나=값 하나. 맞다.
> - 2: N:M을 컬럼 하나로는 표현 못 한다. 맞다.
> - 3: A, B와 각각 관계를 맺는 중개 엔티티(C)를 추가한다. 맞다.
>
> **4의 어긋난 점 ①(방향 반전)**: "c에서 a와 1:n"이 아니라 반대다 — C 입장에서 A를 보면 N:1이다(C 행 여러 개가 A 행 하나를 가리킴). "1:N"은 A 입장에서 C를 볼 때 쓰는 표현이다(A 하나가 C 여러 개에 의해 참조됨). 지금처럼 "C에서 A와 1:N"이라고 쓰면 "C 하나가 A 여러 개를 가리킨다"는 뜻이 되어 실제 구조와 반대가 된다.
>
> **4의 어긋난 점 ②(컬럼에 값 여러 개 담긴다는 오해로 회귀)**: "a의 컬럼에 b의 값을 n개 추가가 가능하다"는 이전에 이미 정정했던 오해로 되돌아간 것이다. 컬럼 하나에 값이 여러 개 들어가는 게 아니다.
>
> - C의 각 행(row)은 정확히 하나의 A값 + 정확히 하나의 B값만 가진다(컬럼=값 하나, 안 깨짐).
> - 다만 같은 A값을 가진 C행이 여러 개 존재할 수 있고, 그 각 행마다 B값이 다르다 → "A 하나가 여러 B와 연결된 것처럼" 보인다.
> - B 쪽도 마찬가지로 같은 B값을 가진 C행이 여러 개 있어서 "B 하나가 여러 A와 연결된 것처럼" 보인다.
> - 즉 다중성은 컬럼 안에 값을 여러 개 몰아넣어서가 아니라 행이 여러 개로 늘어나서 만들어진다.
>
> 정정된 4번: "C의 한 행은 A 하나·B 하나만 가리키지만(C→A는 N:1, C→B도 N:1), 같은 A를 가리키는 C행이 여러 개, 같은 B를 가리키는 C행도 여러 개 존재할 수 있어서, 결과적으로 A와 B가 서로 여러 개씩 연결된 것처럼(N:M) 보인다."

### Q10. JPQL이란 무엇인가

> **Q.** JPQL 이게 뭐야? JPA 에서 사용하는 SQL 같은건가?
>
> "JPA에서 쓰는 SQL 같은 것"이라는 감은 맞는 방향이지만, 정확히는 SQL이 아니라 SQL과 문법이 비슷하게 생긴, 테이블/컬럼이 아니라 엔티티/필드를 대상으로 쓰는 별도의 쿼리 언어다.
>
> - SQL은 `SELECT * FROM menus WHERE category_id = 1`처럼 테이블 이름과 컬럼 이름을 대상으로 쓴다.
> - JPQL은 `SELECT m FROM Menu m WHERE m.category.id = 1`처럼 엔티티 클래스 이름과 필드 이름을 대상으로 쓴다. `menus` 테이블이 아니라 `Menu` 자바 클래스를 쓰고, `category_id` 컬럼이 아니라 `category` 필드(참조)를 쓴다.
> - JPQL은 특정 DB 제품에 종속되지 않는다는 점도 SQL과 다르다. 개발자가 JPQL을 작성하면 Hibernate가 그걸 현재 설정된 dialect(PostgreSQL, MySQL 등)에 맞는 진짜 SQL로 번역해서 실행한다 — "Java 타입 → dialect → 실제 SQL 타입" 변환과 같은 구조가 여기서도 적용된다.
> - 이미 배운 것 중 JPQL을 쓰고 있는 부분들: 메서드 이름 기반 쿼리 메서드(`findByCategoryName` 등)가 내부적으로 JPQL을 자동 생성하고, `@Query`로 직접 JPQL을 작성하기도 하며, N+1 문제 해결책인 `JOIN FETCH`도 JPQL 문법이다.
>
> 정리: JPQL = "테이블이 아니라 엔티티를 대상으로 쓰는, SQL과 비슷하게 생긴 JPA 전용 쿼리 언어"이고, 최종적으로는 Hibernate가 이를 진짜 SQL로 변환해서 DB에 날린다.

> **Q.** 엥 그러면 왜 JPQL을 쓰는거야? 결국엔 SQL로 변환시킬거면 처음부터 SQL로 쓰면 되는거 아니야?
>
> 당연한 의문이다. 이유는 크게 4가지다.
>
> - **DB 이식성**: JPQL은 엔티티/필드 기준이라 DB 종류와 무관하게 동일한 코드로 남는다. 같은 JPQL을 PostgreSQL에서 MySQL로 바꿔도 JPQL 코드는 그대로고, dialect만 바뀌면 Hibernate가 알아서 그 DB에 맞는 SQL로 번역한다. 반대로 SQL을 직접 쓰면 DB를 바꿀 때 SQL 문법(함수, 페이징 방식 등)을 다시 손봐야 할 수 있다.
> - **엔티티 기준이라 리팩터링에 안전**: JPQL은 `Menu`, `m.category.name`처럼 자바 클래스/필드 이름을 쓴다. 필드명을 바꾸면 그 필드를 참조하는 JPQL도 (Criteria/QueryDSL 같은 타입 기반 도구를 쓰면) 컴파일 시점에 걸리거나 IDE가 추적해준다. Native SQL의 컬럼명은 그냥 문자열이라 오타나 스키마 변경을 컴파일러가 못 잡아준다.
> - **객체 그래프 탐색이 쉬움**: `m.category.name`처럼 연관관계를 점(`.`)으로 따라가며 조건을 걸 수 있어서, 개발자가 직접 `JOIN ... ON ...`을 안 써도 JPA가 매핑 정보를 보고 필요한 JOIN을 알아서 만들어준다.
> - **영속성 컨텍스트와 통합됨**: JPQL로 조회한 결과는 그냥 데이터가 아니라 영속 상태의 엔티티로 반환되어, 1차 캐시·변경 감지(Dirty Checking) 같은 기능이 그대로 적용된다. Native SQL로 직접 조회하면 이 통합이 끊기거나 별도 설정이 필요하다.
>
> 한 줄로 묶으면: JPQL을 쓰는 이유도 맨 처음 배운 "패러다임 불일치 해소"와 같은 맥락이다 — 개발자는 계속 객체(엔티티) 레벨에서만 사고하고, 테이블/SQL 레벨로의 번역은 Hibernate에게 맡기는 것이 일관된 설계다. SQL을 직접 쓰면 그 순간 다시 테이블 레벨로 내려가야 해서, JPA가 지금까지 지켜온 추상화가 깨진다.

> **Q.** 음 그러니까 내 의문은 그거지, 이전에 배운 ORM이 SQL을 DB에 매핑 시켜준다고 배웠는데 왜 또 JPQL로 사용하는거야
>
> 두 가지를 구분해야 한다.
>
> **표현 정정**: "ORM이 SQL을 DB에 매핑시켜준다"가 아니라, ORM은 객체(엔티티)를 테이블에 매핑시켜주는 것이고, 그 매핑을 실제로 실행하기 위한 수단으로 SQL을 자동 생성하는 것이다. SQL은 매핑의 대상이 아니라 매핑을 실행하는 결과물(수단)이다.
>
> **핵심 의문(이미 자동으로 SQL을 만들어주는데 왜 또 JPQL을 쓰나)**: ORM의 자동 SQL 생성이 커버하는 범위와 실제로 필요한 쿼리의 범위가 다르기 때문이다.
>
> - ORM/JPA가 자동으로 SQL을 만들어주는 부분은 `@Entity`/`@Column`/`@JoinColumn` 같은 매핑 정보만으로 추론 가능한 구조적/기본적인 것들이다: `save()`(INSERT/UPDATE), `findById()`(단순 PK 조회), `delete()` 같은 기본 CRUD, 그리고 `findByCategoryName`처럼 메서드 이름만으로 유추 가능한 단순 조건 조회까지는 JPA가 알아서 SQL(정확히는 JPQL → SQL)을 만들어준다.
> - 하지만 "가격이 10000원 이상이고 카테고리 이름이 '한식'이면서 이름순 정렬" 같은 임의의 복잡한 조건은 엔티티 매핑 정보만 봐서는 JPA가 절대 스스로 추론할 수 없다. 매핑 어노테이션은 "이 클래스가 이 테이블에 대응한다"는 구조만 알려줄 뿐, "지금 어떤 조건으로 뭘 보여주고 싶은지"라는 업무 로직/의도는 알려주지 않기 때문이다.
> - 그래서 그 의도를 개발자가 직접 명시해야 하는데, 이때 테이블/컬럼 레벨(SQL)로 내려가지 않고 엔티티/필드 레벨을 유지한 채로 그 의도를 표현하게 해주는 것이 JPQL이다.
>
> 정리: ORM의 자동화는 "구조적 매핑 + 아주 단순한 조회"까지만 커버하고, 그 이상의 복잡한 쿼리는 결국 사람이 조건을 명시해야 한다. JPQL은 그 명시 작업을 SQL(테이블 레벨)이 아니라 엔티티(객체 레벨)에서 하게 해줘서, ORM이 지켜온 "객체 중심 사고"의 일관성을 유지시켜주는 도구다.

> **Q.** 그럼 다시 정리: "ORM은 객첼랑 엔티티를 매핑시켜주는거고, 수단으로서 SQL을 자동으로 생성하는것인데, 이때 생성되는 SQL은 복잡한 구조가 아닌 단순한 구조라서 사용자가 요구하는 복잡한 쿼리는 작성이 불가능하다. 그래서 JPQL로 보다 복잡한 쿼리를 작성하고 이걸 JPA가 SQL로 번역해서 hibernate가 읽을 수 있게 해준다" 맞아?
>
> 거의 다 맞는데 두 군데 정정이 필요하고, 그중 하나는 이전에 이미 확인했던 내용(Q3)과 모순된다.
>
> - **정정 ①("객체랑 엔티티를 매핑")**: 엔티티가 곧 객체다(엔티티 = 자바 객체). 둘을 서로 다른 대상처럼 나열하면 안 되고, "엔티티(객체)와 테이블을 매핑"이 정확한 표현이다.
> - **정정 ②("생성되는 SQL은 단순한 구조라서...")**: 방향은 맞지만 정확히는 "SQL 자체가 단순하다"가 아니라 "JPA가 자동으로 추론할 수 있는 범위가 한정적"이라는 게 더 정확하다. `save()`처럼 자동 생성되는 SQL도 여러 컬럼을 다루는 등 구조가 단순하지만은 않을 수 있다. 핵심은 SQL의 복잡도가 아니라, JPA가 매핑 정보나 메서드 이름 규칙만 보고 "무엇을 조회하고 싶은지(업무 의도)"까지는 추론할 수 없다는 것이다.
> - **정정 ③("JPA가 SQL로 번역해서 hibernate가 읽을 수 있게 해준다")**: 이건 Q3에서 이미 확인한 내용과 정면으로 모순된다 — JPA는 명세(규칙)일 뿐 실제 동작(코드 실행)을 하지 않고, 실제 동작은 전부 Hibernate가 담당한다("JPA만 있고 구현체가 없으면 아무것도 동작 안 한다"). 방향이 반대다: JPA는 "JPQL이라는 쿼리 언어를 이런 문법으로 쓸 수 있어야 한다"는 규칙(스펙)만 정의하고, 그 JPQL을 실제로 파싱해서 dialect에 맞는 진짜 SQL로 번역하고 DB에 실행하는 건 Hibernate다.
>
> 정정된 최종 정리: ORM은 엔티티(객체)와 테이블을 매핑하고, 그 실행 수단으로 SQL을 자동 생성한다. 하지만 자동 생성은 매핑 정보에서 추론 가능한 범위까지만 가능해서, 개발자가 원하는 임의의 복잡한 조건은 자동으로 알아낼 수 없다. 그래서 JPQL로 그 조건을 엔티티 레벨에서 직접 명시하고, JPA가 아니라 Hibernate가 그 JPQL을 실제 SQL로 번역해서 DB에 실행한다.

> **Q.** 다시 정리: "ORM은 객체랑 테이블을 매핑 시켜주는 역할이고 그걸 위해서 SQL을 자동 생성하는데 이때는 자동 생성의 한계로 단순한 쿼리만 생성되기 때문에 사용자가 원하는 복잡한 쿼리를 위해서는 JPQL을 통한 직접 작성이 필요하고 이렇게 작성된 JPQL을 hibernate가 SQL로 변환시켜 실행 시켜준다" 맞아?
>
> 거의 완벽하게 맞다.
>
> - ORM = 객체와 테이블을 매핑
> - 그 실행 수단으로 SQL 자동 생성
> - 복잡한 쿼리는 JPQL로 직접 작성
> - 작성된 JPQL을 Hibernate가 SQL로 변환해서 실행
>
> 작은 뉘앙스 하나만 덧붙이면: "자동 생성의 한계로 단순한 쿼리만 생성된다"는 표현은 실용적으로는 맞는 요약이지만, 엄밀히는 "SQL 자체가 단순해서"가 아니라 "JPA가 매핑 정보만 보고 알아낼 수 있는 조건이 단순한 것(기본 CRUD, 필드 하나짜리 조건)까지로 한정돼 있어서"다. 결과적으로 커버되는 범위가 단순한 쿼리로 좁혀지는 것뿐이라, 정리한 흐름 자체는 문제없다.
>
> ORM → 자동 생성의 한계 → JPQL → Hibernate의 번역·실행까지 하나의 인과관계로 정리가 완료됐다.

> **Q.** 그럼 질문. ORM이 SQL을 자동생성 시켜줬잖아? 이후에 내가 복잡한 쿼리를 위해서 JPQL로 추가로 쿼리를 작성했을때 그 내용에 단순한 내용이 포함되서 자동으로 생성된 SQL 내용이랑 겹쳤어. 이 경우에는 문제없어?
>
> 문제없다. 다만 왜 문제가 없는지를 정확히 짚어야 한다 — "자동 생성된 SQL과 직접 쓴 JPQL이 서로 겹친다"는 개념 자체가 성립하지 않는다. 두 방식 모두 각각 독립된 Repository 메서드 하나에 묶여 있고, 그 메서드가 호출될 때마다 그 메서드 자신의 SQL만 독립적으로 번역·실행된다.
>
> - 예: `findByCategoryName(String name)`(자동 생성)과 `@Query("SELECT m FROM Menu m WHERE m.category.name = :name")`을 쓴 `findMenusInCategory(String name)`(직접 작성)이 사실상 같은 내용을 조회해도, 둘은 완전히 별개의 메서드다. 각자 자기 이름으로 호출될 때 각자의 SQL을 만들어서 각자 실행한다.
> - "자동 생성된 SQL"이 어딘가에 저장되어 있다가 새 JPQL과 합쳐지거나 충돌 검사를 하는 공유된 저장소(registry) 같은 건 없다. 매번 그 메서드가 호출되는 시점에 그 메서드 전용 쿼리가 실행될 뿐이다.
> - 그래서 내용이 겹쳐도 에러나 충돌은 안 나고, 그냥 똑같은 일을 하는 코드가 두 곳에 중복되어 있는 것뿐이다(기능적으로는 문제없지만, 유지보수 관점에서는 하나로 합치는 게 낫다).
>
> 유일하게 진짜 제약이 걸리는 부분은 자바 인터페이스 문법 자체의 규칙이다 — 같은 Repository 인터페이스 안에 메서드 시그니처(이름+파라미터)가 완전히 동일한 메서드 두 개는 만들 수 없다(자바 컴파일 에러). 이건 JPA/JPQL 때문이 아니라 그냥 자바 언어 규칙이고, 이름이나 파라미터가 조금이라도 다르면 내용이 겹쳐도 아무 문제 없이 공존한다.

> **Q.** 내가 의문이 드는게 그 부분이야. 자동으로 생성해줬는데 내가 쿼리를 직접 짤 수도있잖아 이건 어떻게 컨트롤해? JPA가 자동으로 CRUD를 만들어줬는데 특정 메서드만 뺄 수 있는거야? 아니면 그냥 어쩔 수 없이 중복 시켜야돼?
>
> 완전히 컨트롤 가능하다. 두 가지 경로가 있다.
>
> **① 애초에 중복을 만들 필요가 없다(선택의 문제)**: 직전 예시(`findByCategoryName` 자동 생성 vs 같은 내용의 `@Query`)는 사실 "어쩔 수 없이 겹친 것"이 아니라 둘 다 개발자가 직접 정의한 메서드다. 조건이 단순하면 메서드 이름 기반 쿼리 메서드만 만들고, 조건이 복잡하면(조인·정렬·집계 등) `@Query`로 JPQL만 쓴다. 처음부터 하나만 선택해서 만들면 중복 자체가 발생하지 않는다.
>
> **② `JpaRepository`가 기본 제공하는 CRUD(`save`, `findById`, `delete` 등)도 특정 메서드만 오버라이드 가능**: 부모(`JpaRepository`)가 제공하는 메서드와 완전히 동일한 시그니처(이름+파라미터)로 메서드를 다시 선언하면 그 메서드만 동작을 바꿀 수 있다.
>
> - 간단한 경우: 인터페이스에 `@Query`를 붙여 같은 이름의 메서드를 재정의.
> - 복잡한 경우(예: `save()` 동작 자체를 바꾸고 싶을 때): 커스텀 리포지토리 구현 패턴을 쓴다 — 1) `MenuRepositoryCustom` 인터페이스에 원하는 메서드 선언, 2) `MenuRepositoryImpl` 클래스에서 직접 구현, 3) `interface MenuRepository extends JpaRepository<Menu, Long>, MenuRepositoryCustom {}`처럼 둘 다 상속. Spring이 "이 메서드는 커스텀 구현체를 쓰고 나머지는 기본 CRUD를 쓴다"고 합쳐서 프록시를 만들어준다.
>
> 정리: 기본 CRUD 중 특정 메서드만 골라서 오버라이드할 수 있고, 새 조회 기능이 필요할 때도 자동 생성/직접 작성 중 하나만 선택하면 되므로, 애초에 중복이 강제되지 않는다.

> **Q.** 그러니까 내가 직접 선언해두면 자동으로 만들어져서 중복될일은 없다는거네?
>
> 맞다. Repository 인터페이스의 메서드 하나하나에 대해 Spring Data JPA는 딱 하나의 구현 방식만 선택해서 적용한다. 우선순위는 대략 다음과 같다.
>
> 1. 커스텀 구현체(`XxxRepositoryImpl`)에 같은 시그니처가 있으면 그걸 사용
> 2. 없으면 `@Query`가 붙어있는지 확인해서 있으면 그 JPQL을 사용
> 3. 둘 다 없으면 메서드 이름을 분석해서 자동으로 쿼리를 생성(`findByXxx` 규칙)
> 4. 그것도 아니면 `JpaRepository`가 기본 제공하는 상속 메서드(`save`, `findById` 등)를 그대로 사용
>
> 즉 "일단 자동으로 만들고 내가 만든 것도 추가로 덧붙이는" 방식이 아니라 위 순서대로 하나만 골라서 쓴다. `@Query`를 직접 써서 선언해두면 그 메서드는 애초에 이름 기반 자동 생성 대상에서 제외되고 직접 쓴 JPQL만 실행되므로, 같은 메서드에 자동 생성본과 직접 작성본이 동시에 존재해서 충돌하거나 둘 다 실행되는 일은 구조적으로 일어날 수 없다.

### Q11. 페이징과 정렬은 쿼리(DB) 레벨에서 처리된다

> **Q.** 페이징과 정렬, 이게 그러니까 쿼리를 통한 정렬 이라는거지?
>
> "정렬"은 맞는데, 이 섹션은 정렬만이 아니라 페이징 + 정렬 두 가지를 같이 다룬다. 그리고 중요한 포인트는 이게 쿼리(SQL) 레벨에서 처리된다는 것 — Java 메모리에서 데이터를 다 가져온 뒤에 정렬/자르기를 하는 게 아니다.
>
> - **정렬(Sort)**: `Sort.by("field").ascending()`처럼 Java 객체로 정렬 기준을 지정하면, JPA가 이걸 실제 SQL의 `ORDER BY field ASC`로 변환해서 DB가 정렬까지 끝낸 결과를 돌려준다.
> - **페이징(Pageable)**: `page`, `size`를 지정하면 SQL의 `LIMIT/OFFSET`으로 변환돼서, DB가 전체 데이터 중 필요한 구간만 잘라서 돌려준다.
> - 둘 다 자바 코드가 아니라 DB가 수행한다. 만약 이걸 안 쓰고 `findAll()`로 전체를 다 가져온 다음 자바에서 `Collections.sort()`나 `List.subList()`로 처리한다면, 불필요하게 전체 데이터를 메모리에 올려서 비효율적이다. `Pageable`/`Sort`는 이 작업을 SQL 단계로 밀어넣어 DB에서 효율적으로 처리하게 해주는 도구다.
>
> 정리: "쿼리를 통한 정렬"이라는 표현은 정확하지만, 정렬뿐 아니라 "쿼리를 통한 페이징"도 같은 원리로 같이 묶여 있다고 이해하면 된다.

> **Q.** 커서 기반 목록 조회랑은 어떤 연관이야?
>
> 지금까지 배운 `Pageable`(LIMIT/OFFSET) 방식과 커서 기반 조회는 같은 문제(대량 데이터를 나눠서 조회하기)를 푸는 다른 전략이다.
>
> **기존 방식(Offset 기반, `Pageable`)의 한계**: `PageRequest.of(page, size)` → SQL로는 `LIMIT size OFFSET (page * size)`.
>
> - 문제 1(성능): `OFFSET`이 커질수록(뒷페이지로 갈수록) DB는 건너뛸 행까지 일단 읽고 세어야 해서 페이지가 뒤로 갈수록 점점 느려진다.
> - 문제 2(정합성): 조회 도중 데이터가 추가/삭제되면 각 페이지의 기준(OFFSET)이 밀리면서 같은 항목이 중복으로 보이거나 하나가 통째로 누락될 수 있다.
>
> **커서 기반 조회의 해법**: "몇 번째 페이지냐"가 아니라 "직전에 마지막으로 본 항목이 뭐냐"를 기준으로 다음 요청을 보낸다.
>
> - SQL로는 `OFFSET` 없이 `WHERE id > :마지막으로_본_id ORDER BY id LIMIT size`처럼 쓴다.
> - 인덱스를 타고 바로 그 지점부터 읽기 때문에 뒤로 갈수록 느려지지 않고, 중간에 데이터가 바뀌어도 "그 이후 것들"만 가져오므로 중복/누락 문제가 없다.
> - 대신 "페이지 번호로 임의 점프"는 못 하고 앞/다음으로만 순차 이동 가능하다.
>
> **`Page<T>` vs `Slice<T>`와의 연결**: `Page<T>`는 전체 개수·전체 페이지 수까지 계산해야 해서 "페이지 번호 개념"이 있는 Offset 방식과 잘 맞는다. `Slice<T>`는 "다음이 있는지"만 알면 되고 count 쿼리가 필요 없어서 커서 기반 조회와 잘 맞는다(무한 스크롤 UI가 보통 커서 기반으로 구현되는 이유). Spring Data JPA에서 커서 기반은 `Pageable` 대신 직접 `WHERE id > :cursor` 조건을 넣은 커스텀 쿼리 + `Slice<T>`(또는 직접 구현한 응답 객체)로 구현하는 게 일반적이다.
>
> 정리: Offset 기반(`Pageable`)은 "몇 번째 페이지"를 기준으로 자르고, 커서 기반은 "마지막으로 본 위치"를 기준으로 자른다. 둘 다 최종적으로 SQL의 `LIMIT`을 쓰지만, 어떤 조건으로 "어디부터 잘라올지"를 결정하는 방식이 다르다.

> **Q.** 일단 순서대로 가보자. "문제 1(성능): OFFSET이 커질수록 DB는 건너뛸 행까지 일단 읽고 세어야 해서 페이지가 뒤로 갈수록 점점 느려진다. 문제 2(정합성): 조회 도중 데이터가 추가/삭제되면 각 페이지의 기준(OFFSET)이 밀리면서 같은 항목이 중복으로 보이거나 하나가 통째로 누락될 수 있다." 이거부터 좀 더 자세히 설명해줘
>
> **문제 1(성능) — 왜 뒷페이지로 갈수록 느려지나**: 핵심은 `OFFSET`이 "N번째 행으로 바로 점프"하는 기능이 아니라는 것이다. DB의 인덱스(B+Tree)는 "이 값이 어디 있나(정렬 순서상 위치)"는 빠르게 찾아주지만, "정렬된 결과 중 10,000번째부터 보여줘"라는 요청은 인덱스를 처음부터 순서대로 세면서 지나가야만(scan) 알 수 있다.
>
> - `LIMIT 20 OFFSET 20`(2페이지, 21~40번째): 앞의 20개를 세어서 건너뛰고 21~40번째를 반환 — 건너뛰는 비용이 작아서 빠르다.
> - `LIMIT 20 OFFSET 1000000`(5만 페이지째): 앞의 1,000,000개를 하나씩 세어서 건너뛴 뒤에야 원하는 20개를 반환한다.
> - 반환하는 건 항상 20개로 똑같은데, 내부적으로 읽고 세는 행의 수는 OFFSET 값에 비례해서 계속 늘어난다. 그래서 페이지 번호가 커질수록 쿼리 시간이 선형적으로 느려진다. 인덱스는 "특정 값 찾기"는 빠르게 해줘도 "몇 번째 항목인지 세기"는 결국 하나씩 지나가야 하는 별개의 문제다.
>
> **문제 2(정합성) — 왜 데이터가 밀리면 중복/누락이 생기나**: 최신순 정렬(id 내림차순)로 20개 항목(id 100~81)이 있고 페이지 크기 10인 예시.
>
> - 1페이지 조회(offset=0, limit=10) → id 100~91 반환(10개).
> - 2페이지 요청 전에 누군가 id=95(이미 1페이지에서 보여준 항목)를 삭제하면, 전체 목록은 19개로 줄고 그보다 뒤에 있던 모든 항목이 한 칸씩 앞으로 당겨진다.
> - 2페이지 조회(offset=10, limit=10) → 당겨진 목록 기준 10번째부터 반환하는데, 원래 2페이지 첫 항목이어야 할 id=90이 9번째 자리로 밀려버려 이번 조회 범위에서 빠진다. id=90은 1페이지 조회 때는 아직 안 걸렸고(11번째였음), 2페이지 조회 때는 이미 9번째로 밀려서 안 걸리니 결국 한 번도 화면에 안 보이고 통째로 누락된다.
> - 반대로 삭제 대신 새 항목이 앞쪽에 추가되면 정반대 현상이 일어난다 — 뒤의 항목들이 한 칸씩 밀려서, 2페이지 조회 시 이미 1페이지에서 봤던 항목이 다시 걸려서 중복으로 보인다.
>
> 정리: `OFFSET`은 "고정된 위치(숫자)"를 기준으로 자르는데, 그 사이에 데이터의 순서/개수가 바뀌면 그 "위치"가 가리키는 실제 항목이 달라져 버려서 생기는 문제다.

> **Q.** 그러니까 offset 방식은 DB에 값을 읽어서 반환해주는거다 맞아?
>
> 틀린 건 아니지만 너무 일반적인 표현이라 방금 설명한 핵심을 놓치고 있다. "DB에서 값을 읽어서 반환한다"는 Offset 방식이든 커서 방식이든 모든 조회 쿼리에 공통으로 해당하는 이야기라, Offset 방식만의 특징을 짚은 게 아니다.
>
> Offset 방식의 진짜 특징은 "요청한 구간을 반환하기 전에, 그 앞에 있는 행들을 순서대로 세어서 건너뛰는 과정이 반드시 필요하다"는 것이다.
>
> - 커서 방식(`WHERE id > :cursor LIMIT size`): 인덱스에서 조건(`id > 커서값`)에 맞는 지점으로 바로 진입해서 그 뒤로 필요한 개수만큼만 읽는다. 앞의 항목들을 세거나 건너뛰는 과정이 없다.
> - Offset 방식(`LIMIT size OFFSET n`): "몇 번째부터"라는 개념 자체가 인덱스에 없기 때문에, 처음부터 순서대로 n개를 세어서 지나쳐야만 그다음 지점을 알 수 있다.
>
> 정정된 표현: "Offset 방식은 원하는 구간에 도달하기 위해 그 앞의 모든 행을 세어서 건너뛰어야 하는 방식이다." 이 "건너뛰는 비용"이 있느냐 없느냐가 Offset과 커서 방식을 가르는 핵심 차이다.

> **Q.** 음 다시. offset 방식은 쿼리에서 지정한 구간을 읽어서 반환하는 방식인데 이때 지정한 구간을 처음부터 순서대로 읽어서 찾아내 반환해준다 맞아?
>
> 맞다. 정확히 이해했다 — 쿼리에서 지정한 구간(`LIMIT`/`OFFSET`)을 반환하는 방식이고, 그 구간을 찾기 위해 처음부터 순서대로 읽으면서(세면서) 지나가야 한다.
>
> 한 가지 강조해서 덧붙이면: 이 "처음부터 세는 과정"은 매 요청마다 매번 새로 일어난다. DB는 이전에 몇 페이지를 조회했었는지 기억하지 않기 때문에, 5페이지를 요청하든 6페이지를 요청하든 그 요청이 들어올 때마다 또다시 처음부터 앞의 행들을 세어서 건너뛴다. 그래서 "한 번 세어놓은 걸 다음 요청에 재사용"하는 게 아니라, 페이지를 요청할 때마다 매번 같은 비용을 반복해서 치르는 것이 Offset 방식의 특징이다. 반면 커서 방식은 매 요청이 "마지막으로 본 위치"라는 정보를 클라이언트가 직접 들고 와서 넘겨주기 때문에, DB 입장에서는 항상 그 지점부터 바로 시작할 수 있다.

> **Q.** 다시 정리하면 offset 방식은 쿼리에서 지정한 구간을 값을 db에서 순서대로 읽어 반환해주는데 이때 지정된 값이 클수록 그거에 비례해 반환시간이 늦어진다 맞아?
>
> 맞다. 정확한 정리다.
>
> - Offset 방식은 쿼리에서 지정한 구간의 값을 DB에서 처음부터 순서대로 읽어(세어)가며 찾아서 반환한다.
> - 그 지정된 값(OFFSET 숫자)이 클수록 세어야 하는 행의 수도 같이 늘어나서, 반환 시간이 그에 비례해 늦어진다.
>
> 이건 두 문제(성능/정합성) 중 성능 문제(문제 1)를 정확히 요약한 것이고, 앞서 짚은 정합성 문제(문제 2 — 데이터가 도중에 바뀌면 중복/누락 생김)는 이것과는 별개의 추가적인 단점으로 같이 기억해두면 된다. 이 두 가지가 합쳐져서 커서 기반 방식이 필요한 이유가 된다.

> **Q.** 오케이 그러면 다시 이어서 정리하면 "offset 방식은 지정한 구간을 값을 db에서 처음부터 읽어서 값을 찾아 반환해주는게 그 지정된 값이 클수록 반환 시간이 늦어지고 offset이 자체적으로 반환 지점을 기억하지 않기때문에 추가적인 요청시에도 계속 처음부터 읽는 문제가 발생한다, 이떄 조회중에 인덱스 값의 삭제, 추가가 이뤄질시에 db에서 순서가 바뀌어서 검색 결과에 특정 값이 누락되거나 중복된 값이 조회될 수 도있따" 맞아?
>
> 거의 완벽하고 표현 하나만 다듬으면 된다.
>
> **맞는 부분**: Offset은 지정한 구간을 찾기 위해 처음부터 읽어야 하고 값이 클수록 반환 시간이 늦어진다. Offset 자체가 위치를 기억하지 않아서 추가 요청마다 매번 처음부터 다시 읽는다. 조회 도중 데이터가 변경되면 특정 값이 누락되거나 중복 조회될 수 있다. 모두 맞다.
>
> **다듬을 표현**: "인덱스 값의 삭제, 추가가 이뤄질시에 db에서 순서가 바뀌어서"는 원인 진단이 살짝 부정확하다. 실제로 바뀌는 건 "순서(정렬 기준)"가 아니라 각 항목이 몇 번째에 위치하는지(count/offset 상 위치)다 — 정렬 기준(예: id 내림차순) 자체는 그대로 유지된다. "인덱스 값이 삭제/추가된다"보다는 "데이터(행) 자체가 삭제/추가된다"가 더 정확한 원인이고, 그 결과로 인덱스에 반영된 항목 개수가 바뀌면서 남아있는 각 항목들의 위치가 한 칸씩 밀리는 것이다.
>
> 정정된 문장: "조회 도중에 데이터(행)가 삭제되거나 추가되면, 남은 항목들의 위치(몇 번째인지)가 한 칸씩 밀리게 되어 검색 결과에 특정 값이 누락되거나 중복 조회될 수 있다."
>
> 이걸로 Offset 방식의 두 문제(성능 저하 + 정합성 문제)와 그 원인까지 정확히 정리됐다.

> **Q.** 그럼 커서 기반은 기존적으로 직전에 마지막으로 확인한 값이 뭔가를 기준으로하니까 offset 기반 정렬의 단점이 다 상쇄되는거네?
>
> 방향은 맞지만 "단점이 다 상쇄된다"는 표현은 조금 과하다. 정확히는 기존 두 문제는 해결하지만 그 대신 다른 걸 포기하는 트레이드오프다.
>
> **해결되는 것**
> - 성능 문제: `WHERE id > :마지막값`은 인덱스에서 그 조건에 맞는 지점으로 바로 진입하니 앞의 행들을 세어서 건너뛸 필요가 없다 — offset이 커질수록 느려지는 문제가 사라진다.
> - 정합성 문제: "몇 번째"라는 숫자가 아니라 "실제 마지막으로 본 값"을 기준으로 삼기 때문에, 중간에 데이터가 삭제/추가돼도 그 값 자체가 사라지지 않는 한 기준점이 흔들리지 않는다 — 중복/누락이 안 생긴다.
>
> **대신 포기하는 것(트레이드오프)**
> - 임의 페이지 점프 불가: "3페이지로 바로 가줘" 같은 요청을 못 한다. 오직 다음/이전으로만 순차 이동 가능하다(직전 값을 알아야 다음을 조회할 수 있으므로).
> - 전체 개수/전체 페이지 수를 알기 어려움: `Page<T>`처럼 "총 몇 개, 총 몇 페이지"를 자연스럽게 계산해주지 않는다(필요하면 별도의 count 쿼리를 추가로 돌려야 한다).
> - 정렬 기준이 고유(unique)해야 함: 커서로 쓰는 컬럼(보통 id)이 값이 겹치지 않아야 안전하다. 중복 가능한 값(예: 이름)만으로 정렬하면 같은 값을 가진 여러 행 중 어디까지 봤는지 구분이 안 돼서 커서 방식도 자체적으로 누락/중복 문제를 겪을 수 있다.
>
> 정리: 커서 기반은 Offset의 두 문제(성능 저하, 데이터 변경에 따른 정합성 깨짐)를 해결하지만 "페이지 임의 이동"과 "전체 개수 파악"이라는 편의 기능을 포기하는 대가를 치른다. 무조건 더 좋은 방식이 아니라, 무한 스크롤처럼 순차 이동만 필요한 UI에 적합한 방식으로 이해하는 게 정확하다.

> **Q.** 그러니까 임의로 설정한 페이지로 바로 이동하거나 전체 페이지 수 파악이 안된다는거지
>
> 맞다. 정확하다.
>
> - 임의로 지정한 페이지 번호로 바로 이동 불가(순차적으로 다음/이전만 가능)
> - 전체 개수/전체 페이지 수 파악 불가(별도 count 쿼리 없이는)
>
> 이 두 가지가 커서 기반 방식이 offset 대비 포기하는 대가다. 그래서 "페이지 번호 네비게이션(1,2,3...)"이 필요한 화면에는 Offset(`Page<T>`)이 맞고, "무한 스크롤"처럼 순차적으로만 계속 불러오면 되는 화면에는 커서 방식이 맞다.

> **Q.** 임의 페이지에 이동불가는 그러니까 예를 들어 내가 1페이지에서 바로 3페이지로 넘어가는걸 말하는거지?
>
> 맞다. 정확한 예시다.
>
> - Offset 방식: 3페이지가 필요하면 `OFFSET = (3-1) * size`를 그냥 계산해서 요청하면 된다. 1페이지, 2페이지를 실제로 조회한 적이 없어도 상관없이 바로 3페이지 몫을 계산해서 요청할 수 있다.
> - 커서 방식: 3페이지를 조회하려면 "2페이지의 마지막 항목 값(커서)"이 있어야 `WHERE id > 그값`으로 3페이지를 요청할 수 있다. 그런데 1페이지에서 2페이지를 건너뛰고 바로 3페이지로 가려고 하면 2페이지의 마지막 값을 아예 모르기 때문에 요청 자체를 만들 수가 없다.
>
> 그래서 커서 방식은 반드시 직전 페이지를 실제로 거쳐야만 그다음 페이지로 갈 수 있는 순차적인 구조이고, 임의로 건너뛰는 게 구조적으로 불가능하다.

> **Q.** 전체 개수 파악 안 되면 무한 스크롤에서 "다음 있는지"는 어떻게 알아?
>
> "전체 개수를 모른다"와 "다음이 있는지 안다"는 서로 모순되지 않는다. `Slice<T>`(그리고 커서 기반)는 전체 개수를 세는 대신 훨씬 가벼운 트릭을 쓴다.
>
> **트릭: 요청한 개수보다 1개 더 가져온다**
>
> - 사용자가 `size=10`을 요청하면, 실제 쿼리는 `LIMIT 11`(요청한 것보다 1개 더)로 날린다.
> - 결과가 11개 왔다면 → 화면에는 앞의 10개만 보여주고, 11번째가 존재했다는 사실 자체가 "다음 페이지가 있다"는 증거가 된다 → `hasNext = true`.
> - 결과가 10개 이하로 왔다면 → 더 가져올 게 없었다는 뜻이므로 → `hasNext = false`.
>
> **왜 이게 "전체 개수를 세는 것"보다 훨씬 가벼운가**: `COUNT(*)`는 조건에 맞는 전체 행을 다 훑어야 정확한 숫자가 나온다(테이블이 크면 비용이 큼). 반면 `LIMIT 11`은 정확히 11개만 가져오면 끝이라 전체를 셀 필요가 없다. 그래서 "전체가 몇 개인지"는 모르지만 "지금 이 페이지 다음에 하나라도 더 있는지"는 아주 저렴하게 알 수 있다.
>
> 무한 스크롤은 애초에 "총 몇 개 남았는지"를 화면에 보여줄 필요가 없고, "스크롤 내렸을 때 더 불러올 게 있는지(예/아니오)"만 알면 되기 때문에 이 `size+1` 트릭 하나로 충분하다. 이게 정리 노트의 "`Slice<T>`는 count 쿼리 생략 가능"이라는 말의 실제 구현 방식이다.

> **Q.** LIMIT 11은 내부적으로 자동으로 설정되는거야?
>
> 상황에 따라 다르다 — Spring Data JPA가 기본 제공하는 `Slice<T>` 반환 방식을 쓰면 자동이고, 직접 커서 쿼리를 짜는 경우는 본인이 직접 +1을 넣어야 한다.
>
> **자동으로 되는 경우(`Slice<T>` + `Pageable`)**: Repository 메서드를 `Slice<Menu> findByCategoryId(Long categoryId, Pageable pageable);`처럼 선언만 하면, `pageable = PageRequest.of(page, 10)`으로 호출해도 Spring Data JPA(`SimpleJpaRepository` 내부 구현)가 알아서 실제 SQL에 `LIMIT 11`(size+1)을 붙여서 실행하고, 11번째가 있었는지 확인해서 `hasNext()`를 계산해준 뒤 결과 리스트는 다시 10개로 잘라서 돌려준다. 개발자는 `size+1`이라는 숫자를 신경 쓸 필요가 전혀 없다.
>
> **직접 짜야 하는 경우(커서 기반 `@Query`)**: `@Query("SELECT m FROM Menu m WHERE m.id > :cursor ORDER BY m.id")`처럼 직접 JPQL을 쓰는 경우엔 그냥 개발자가 작성한 일반 쿼리라 Spring이 자동으로 개수를 조작해주지 않는다. 이 경우엔 `Pageable`을 `PageRequest.of(0, size + 1)`처럼 직접 +1 해서 넘기거나 쿼리 자체에 `LIMIT :size + 1`을 명시해서 직접 처리하고, 그 결과가 `size`보다 많이 왔는지를 서비스 코드에서 직접 검사해 `hasNext`를 계산해야 한다.
>
> 정리: "요청보다 1개 더 가져와서 다음 여부를 판단한다"는 원리 자체는 같지만, `Slice<T>`처럼 Spring Data JPA가 기본 제공하는 기능을 쓰면 그 +1 처리가 프레임워크 내부에서 자동으로 이뤄지고, 완전히 직접 만든 커서 쿼리라면 그 로직을 개발자가 손수 구현해야 한다.

> **Q.** offset 방식에서는 무한 스크롤을 못쓰나?
>
> 쓸 수는 있다. 다만 Offset의 두 단점(성능 저하, 정합성 문제)이 무한 스크롤에서 특히 더 아프게 드러나서 잘 안 쓰는 것이다. 그리고 짚어야 할 정정이 하나 있다.
>
> **정정**: 직전에 설명한 `Slice<T> + Pageable` 자동 방식은 사실 Offset 기반이다. Spring Data JPA의 `Pageable`/`PageRequest`는 원래부터 `OFFSET`을 쓰는 방식이고, `Slice<T>`는 거기서 "count 쿼리만 생략"해주는 것일 뿐, 커서 방식으로 자동 전환해주는 게 아니다. 진짜 커서 기반(`WHERE id > :cursor`)을 쓰려면 `@Query`로 직접 조건을 작성해야 하고, `Slice<T>`는 그 커서 쿼리에도 붙일 수 있고 기본 Offset 쿼리에도 붙일 수 있는, 둘과는 독립적인 "count 생략" 기능이다.
>
> **그래서 Offset으로 무한 스크롤을 만들면**: 기술적으로는 가능하다 — 스크롤 내릴 때마다 `page`를 1씩 늘려서 계속 다음 `OFFSET`을 요청하면 된다. 하지만 두 문제가 그대로 따라온다 — 스크롤을 오래 내릴수록(offset이 계속 커질수록) 매 요청이 점점 느려지고, 인스타그램 피드처럼 새 글이 계속 올라오는 데이터라면 스크롤 도중 항목이 밀려서 중복/누락이 자주 발생한다. 무한 스크롤은 보통 "오래, 깊게 스크롤"하고 "실시간으로 데이터가 계속 바뀌는" 상황(피드, 타임라인)에 쓰이기 때문에 이 두 단점이 최악의 조합으로 나타난다. 그래서 실무에서 무한 스크롤엔 커서 기반이 강하게 권장되는 것이지, Offset이 아예 못 쓰는 건 아니다.

> **Q.** 그럼 반대로 네이버나 구글에서 검색 페이지를 이미 보여주고 1~5 페이지 중에 내가 선택한 화면에 들어갈 수 있는건 offset 방식이겠네?
>
> 맞다. 정확한 적용이다.
>
> - 네이버/구글 검색 결과처럼 "1, 2, 3, 4, 5 페이지" 번호가 보이고 그중 아무 번호나 눌러서 바로 이동할 수 있는 UI는, "임의 페이지로 점프 가능"해야 하므로 Offset 방식(`Page<T>`)의 특징과 정확히 일치한다.
> - 반대로 커서 방식이었다면 지금 보고 있는 페이지에서 다음/이전만 가능하고, 안 본 페이지 번호로 바로 뛸 방법이 없었을 것이다.
> - 검색 결과는 보통 "전체 1,234개 결과" 같은 전체 개수도 같이 보여주는데, 이것도 `Page<T>`(count 쿼리로 전체 개수·전체 페이지 계산)의 특징과 맞아떨어진다.
>
> 정리: 번호를 눌러 임의 페이지로 이동 + 전체 결과 수 표시가 함께 나오는 UI는 Offset 기반(`Page<T>`)이고, 아래로 계속 스크롤하며 순차적으로만 불러오는 UI(SNS 피드 등)는 커서 기반(`Slice<T>` 또는 직접 구현)이라는 대응 관계로 기억하면 된다.

> **Q.** 그럼 결국 2개를 같이 활용한거네?
>
> 맞다 — 다만 "하나의 화면에서 두 방식을 동시에 섞어 쓴다"는 뜻이 아니라, 서비스 하나가 화면/기능별로 상황에 맞는 방식을 각각 골라서 함께 활용한다는 뜻으로 이해하면 정확하다.
>
> - 예를 들어 같은 검색 서비스라도, PC 검색 결과 페이지(번호 1~5 클릭해서 이동)는 Offset 방식을 쓰고, 같은 서비스의 모바일 무한 스크롤 피드나 채팅 메시지 목록(위로 스크롤해서 과거 메시지 더 불러오기)은 커서 방식을 쓴다.
> - 즉 "이 서비스는 Offset이다/커서다"라고 서비스 전체를 하나로 못박는 게 아니라, 화면의 요구사항(임의 페이지 이동이 필요한가? 실시간으로 데이터가 계속 바뀌는가? 순차 스크롤이면 충분한가?)에 따라 그때그때 적합한 방식을 선택하는 것이다.
>
> 그래서 "결국 2개를 같이 활용한다"는 정리가 맞다 — 한 가지 방식이 항상 정답인 게 아니라, 기능별로 트레이드오프를 따져서 골라 쓰는 도구 상자로 이해하면 된다.

### Q12. N+1 문제 심화 — 발생 원리와 두 해결책의 제약

> **Q.** [N+1 문제 및 Fetch Join / @EntityGraph 섹션] N+1 문제는 자주 나오니까 좀 더 구체적으로 알고싶어
>
> **1) 지연 로딩(LAZY)에서 왜 N+1이 생기나 — 구체적 트레이스**
>
> `Menu`가 `@ManyToOne(fetch = LAZY) private Category category;`를 가진 상황에서 `List<Menu> menus = menuRepository.findAll();`(쿼리 1번)로 100개를 가져온 뒤, 반복문에서 각 `m.getCategory().getName()`을 호출하면:
>
> - `findAll()` 자체는 SQL 1번(`SELECT * FROM menus`)만 나간다.
> - 각 `Menu`의 `category` 필드는 실제 값이 없는 지연 로딩 프록시 상태다. `getCategory().getName()`을 호출하는 순간 그 프록시가 초기화를 요청해 `SELECT * FROM categories WHERE id = ?`를 그때그때 날린다.
> - 메뉴가 100개면 최악의 경우 100번의 추가 쿼리가 나가 총 `1 + 100 = 101`번 실행된다 — 이게 N+1이다.
> - 다만 1차 캐시가 여기서도 작동한다: 여러 메뉴가 같은 카테고리를 공유하면 그 id는 최초 한 번만 DB를 타고 이후엔 1차 캐시에서 반환되므로, 실제 추가 쿼리 수는 "메뉴 개수"가 아니라 "서로 다른 카테고리의 개수"가 된다. 카테고리가 전부 제각각일 때만 진짜 N번이 다 나간다.
>
> **2) 즉시 로딩(EAGER)도 컬렉션에서는 왜 N+1이 생기나**
>
> `Category`가 `@OneToMany(fetch = EAGER) private List<Menu> menus;`인 경우, `categoryRepository.findAll()`을 호출하면 Hibernate는 컬렉션을 하나의 JOIN으로 자동으로 합쳐주지 않고, `categories`를 먼저 조회한 뒤(1번) 각 카테고리마다 그에 속한 메뉴 목록을 조회하는 쿼리를 즉시 추가로 날린다(N번). LAZY와의 차이는 "언제 터지느냐"뿐이다 — LAZY는 `getMenus()` 호출 시점에 지연해서 터지고, EAGER는 `findAll()` 즉시 한꺼번에 터진다. 총 쿼리 수(1+N)는 똑같거나, EAGER 쪽이 필요 없어도 무조건 다 가져오니 오히려 더 나쁠 수 있다.
>
> **3) 해결책 ① Fetch Join — 왜, 그리고 세 가지 제약이 왜 생기나**
>
> `SELECT m FROM Menu m JOIN FETCH m.category`는 SQL로 `SELECT m.*, c.* FROM menus m JOIN categories c ON m.category_id = c.id`처럼 번역돼, `Menu`와 `Category`를 한 번의 SQL로 함께 가져온다. 이후 `getCategory()`를 호출해도 이미 데이터가 채워져 있어 추가 쿼리가 안 나간다.
>
> - 제약 ①(컬렉션 + 페이징 위험): `JOIN FETCH m.allergies`처럼 컬렉션(1:N)을 Fetch Join하면 SQL 결과는 "메뉴 1개당 알레르기 개수만큼 행이 늘어난" 형태가 된다(메뉴 1개, 알레르기 3개 → 3행). 이 상태에서 `LIMIT 10`을 걸면 "메뉴 10개"가 아니라 "행 10개"만 잘려서 어떤 메뉴는 알레르기가 잘려나간 채로 나올 수 있다. 이를 막기 위해 Hibernate는 SQL의 LIMIT을 포기하고 전체 결과를 다 가져온 뒤 메모리에서 페이징을 흉내 낸다 — 데이터가 크면 메모리가 위험해진다.
> - 제약 ②(컬렉션 2개 동시 Fetch Join 불가, 카테시안 곱): `JOIN FETCH m.allergies JOIN FETCH m.reviews`처럼 컬렉션 두 개를 동시에 조인하면 결과 행 수가 "알레르기 개수 × 리뷰 개수"로 곱해져 폭증한다(알레르기 3개 × 리뷰 5개 = 메뉴 1개당 15행). 데이터가 왜곡되므로 Hibernate가 이를 막는다(예외 발생).
> - 제약 ③(1:N에서 중복 → DISTINCT 필요): 메뉴 1개에 알레르기가 3개면 조인 결과는 3행이고 각 행마다 같은 `Menu`가 반복해서 담긴다. `List<Menu>`로 받으면 같은 메뉴가 3번 중복돼서 들어간다. `SELECT DISTINCT m FROM Menu m JOIN FETCH m.allergies`처럼 `DISTINCT`를 붙여 중복 행을 걸러내야 한다.
>
> **4) 해결책 ② `@EntityGraph` — Fetch Join과 뭐가 다른가**
>
> `@EntityGraph(attributePaths = {"category"})`를 붙인 `findAll()`처럼, JPQL을 안 쓰고 어노테이션 하나로 "이 메서드 호출 시엔 `category`를 즉시(EAGER)로 취급해서 조인해와"라고 선언적으로 지정하는 방식이다. 내부적으로 Hibernate가 Fetch Join과 비슷한 JOIN SQL을 자동 생성한다.
>
> - 장점: 이미 있는 `findAll()`, `findById()` 같은 기존 메서드에도 그대로 적용 가능해서 매번 JPQL을 새로 쓸 필요 없이 코드 중복을 줄인다.
> - 단점: `attributePaths`에 필요 이상으로 많은 연관관계를 나열하면, 그 화면에서 안 쓸 데이터까지 매번 조인해서 가져오는 과잉 로딩이 생긴다.
>
> **5) 언제 뭘 쓰나**: 단순히 "이 연관관계, 접근할 때마다 매번 같이 로딩해줘"면 `@EntityGraph`(선언적, 간단)를 쓰고, 복잡한 WHERE/정렬/여러 조인 조건이 섞인 특정 쿼리라면 Fetch Join(JPQL로 직접 제어, 대신 위 세 가지 제약을 항상 염두에 둬야 함)을 쓴다.

> **Q.** N+1 문제 한번에 이해하기 좀 복잡한데;; 1) 지연 로딩 프록시 = 지연로딩도 알고 프록시도 아는데 이건 처음들어봐 2) eager, join, lazy, fetch 이게 다 무슨소리지? 3) 글로만 길게 있으니까 이해가 좀 힘들어
>
> 용어부터 하나씩 짧게 정리한다.
>
> **① 지연 로딩(LAZY) / 즉시 로딩(EAGER)**: 둘 다 "언제 데이터를 가져올지"를 정하는 설정이다. LAZY(지연) = "지금 당장은 안 가져오고, 진짜 필요할 때(그 필드를 실제로 건드릴 때)만 가져온다." EAGER(즉시) = "물어보지도 않았는데 처음부터 같이 가져온다."
>
> **② 프록시**: 예전에 Q6에서 배운 그 프록시다("진짜 객체 대신 앞에 서 있는 대리인 객체").
>
> **③ "지연 로딩 프록시" = ①+②를 합친 것**: LAZY로 설정된 필드는 조회하는 그 순간에는 진짜 데이터를 안 가져오고 빈 껍데기(프록시)만 일단 넣어둔다. 나중에 그 필드를 실제로 건드리면(`.getCategory().getName()`) 그제서야 그 프록시가 "지금 진짜 데이터를 가져와야겠다"고 판단해서 DB를 한 번 더 조회한다. 즉 "지연 로딩 프록시" = "지연 로딩되는 자리에 미리 넣어둔 가짜 대역"이라는 뜻이다.
>
> **④ JOIN**: SQL 문법이다. "두 테이블을 합쳐서 한 번에 같이 조회하는 것"(Entity 연관관계에서 `menus`와 `categories`를 `category_id`로 연결했던 그 개념).
>
> **⑤ FETCH**: "가져오다"라는 뜻의 일반 동사일 뿐이다. 고정된 하나의 의미가 있는 게 아니라 두 군데에 각각 쓰인다.
>
> - `fetch = LAZY` / `fetch = EAGER`: "언제 가져올지"를 지정할 때 쓰는 옵션 이름.
> - `JOIN FETCH`: JPQL 전용 문법 키워드. 그냥 `JOIN`은 조건 필터링용으로만 테이블을 합치고 연관 엔티티 객체 자체는 채워주지 않는데, `JOIN FETCH`는 "합친 김에 연관된 진짜 데이터까지 완전히 채워서 가져와라"는 명령이다.
>
> **하나로 이어보면**: 기본 상태에서 `Menu`의 `category` 필드는 LAZY라서 조회 시 프록시(가짜)만 들어있다. `getCategory()`를 건드리면 그 프록시가 추가로 DB를 조회하고, 메뉴가 여러 개면 이게 반복돼서 N+1이 생긴다. 해결책으로 `JOIN FETCH`를 쓰면 처음부터 `Menu`와 `Category`를 한 SQL로 같이(JOIN해서) 가져오게(FETCH) 되어, 프록시 없이 진짜 데이터가 바로 채워져서 추가 조회가 안 생긴다.

> **Q.** 그러니까 좀 풀어서 설명하면 메뉴의 카테고리 필드가 lazy 설정되어있어서 호출시에만 동작하는데 이떄는 프록시가 db에 메서드에 비해서 db를 추가조회한다고?
>
> 핵심은 맞는데 문장이 꼬여서 정확한 표현으로 다시 정리한다.
>
> 메뉴의 category 필드가 LAZY로 설정되어 있으면, 그 필드는 처음 조회될 때 실제 데이터 대신 프록시(가짜 대역)만 채워진다. 그리고 나중에 그 프록시에 대해 실제 데이터가 필요한 메서드를 호출하는 순간, 프록시가 "지금 진짜 데이터를 가져와야겠다"고 판단해서 DB에 추가 쿼리를 날린다.
>
> 한 가지 더 정밀하게 짚으면 `getCategory()`와 `getCategory().getName()`을 구분해야 한다.
>
> - `menu.getCategory()` — 그냥 그 필드에 들어있는 프록시 객체 자체를 반환하는 것뿐이다. 이 시점에는 아직 DB를 안 건드린다.
> - `menu.getCategory().getName()` — 여기서 `.getName()`처럼 프록시 안의 진짜 값을 요구하는 메서드를 호출하는 그 순간, 비로소 프록시가 "아직 빈 껍데기인데 진짜 값을 달라고 하네" 하고 그때 DB에 `SELECT * FROM categories WHERE id = ?`를 추가로 날린다.
>
> 즉 "호출 시에만 동작한다"는 표현은 정확히는 "필드에 접근하는 것 자체가 아니라, 그 필드 안의 진짜 값을 실제로 써야 하는 메서드를 호출하는 순간에 DB 추가 조회가 일어난다"는 뜻이다.

> **Q.** 그러니까 다시 정리하면 객체의 프록시가 대기 중인데 실제 원본을 호출할때 프록시가 원본 메서드를 호출하기 위해 쿼리를 메서드 만큼 날린다는거 아니야?
>
> 방향은 비슷한데 두 가지를 정정해야 한다 — 특히 "메서드 만큼 쿼리가 날아간다"는 부분이 N+1의 진짜 원인을 잘못 짚었다.
>
> **정정 ①: 같은 프록시에 대해서는 쿼리가 딱 1번만 날아간다**: 프록시는 최초로 진짜 데이터가 필요한 메서드가 호출되는 그 한 번의 순간에만 DB 쿼리를 날린다. 그 이후로 같은 프록시 인스턴스에 대해 `getName()`을 또 부르든 다른 getter를 또 부르든, 이미 초기화가 끝난 뒤라 진짜 객체에게 그냥 위임만 하고 DB는 다시 안 건드린다. 즉 "메서드를 부른 횟수만큼" 쿼리가 나가는 게 아니라 "그 프록시가 초기화됐는지 여부"만 중요하다 — 초기화 전이면 처음 한 번, 초기화 후엔 0번.
>
> **정정 ②: N+1의 "N"은 한 프록시가 여러 번 불려서 생기는 게 아니라, 서로 다른 프록시가 여러 개 있어서 생긴다**: `findAll()`로 메뉴 100개를 가져오면, 메뉴 100개 각각이 자기만의 독립된 `category` 프록시를 하나씩 갖고 있다(프록시 100개, 서로 다른 인스턴스). 반복문을 돌며 각 메뉴의 `getCategory().getName()`을 부르면, 그 100개의 서로 다른 프록시 각각이 자기 초기화를 위해 딱 1번씩 쿼리를 날린다. 그래서 "N"은 "한 프록시를 N번 호출해서 생기는 것"이 아니라 "N개의 서로 다른 프록시가 각각 1번씩 초기화 쿼리를 날려서 생기는 것"이다.
>
> 정리: "프록시가 원본 호출을 위해 쿼리를 메서드 횟수만큼 날린다"가 아니라, "프록시 1개당 최초 초기화 시 딱 1번만 쿼리를 날리고, 그런 프록시가 N개(메뉴 개수만큼) 있어서 총 N번의 추가 쿼리가 나간다"가 정확한 표현이다.

> **Q.** 그럼 다시 정리하면 프록시 1개당 쿼리는 한번만 날리고 원본의 메서드 호출 수 만큼 추가 쿼리가 나간다고?
>
> 거의 다 왔는데 뒷부분("원본의 메서드 호출 수만큼 추가 쿼리")이 아직 틀렸다. 한번 초기화되고 나면 그 뒤로는 메서드를 몇 번을 부르든 추가 쿼리가 0번이다.
>
> **정확한 흐름(프록시 1개 기준)**:
>
> 1. 초기화 전: 메서드를 불러도 아직 초기화 트리거가 안 걸렸으면 쿼리 0번(예: `getCategory()`만 호출한 경우).
> 2. 최초로 진짜 값이 필요한 메서드를 호출(예: `getName()`) → 이때 딱 1번 쿼리가 나가서 프록시가 초기화됨(진짜 데이터로 채워짐).
> 3. 그 이후로 같은 객체에 대해 `getName()`을 또 부르든 `getPrice()`를 부르든 100번을 부르든 → 추가 쿼리는 0번이다. 이미 메모리에 값이 다 채워져 있어서 그냥 값을 읽어오기만 하는(순수 자바 필드 접근) 것뿐이라 DB를 다시 건드릴 이유가 없다.
>
> **왜 "메서드 호출 수만큼"이 아닌가**: 쿼리를 발생시키는 건 "메서드를 몇 번 불렀는가"가 아니라 "아직 초기화가 안 된 상태에서 처음으로 진짜 값을 요구했는가"라는 한 번뿐인 전환 이벤트다. 초기화가 끝나는 순간 그 프록시는 사실상 평범한 객체와 다를 바 없어져서, 이후의 메서드 호출은 쿼리와 완전히 무관해진다.
>
> 정리: 프록시 1개당 쿼리는 딱 1번(최초 초기화 시점)만 나가고, 그 이후 메서드를 아무리 많이 호출해도 추가 쿼리는 0번이다. N+1의 "N"은 이 "1번짜리 초기화"가 서로 다른 N개의 프록시에서 각각 일어나기 때문에 생기는 것이지, 한 프록시에 대한 반복 호출 때문이 아니다.

> **Q.** 그러니까 쿼리는 프록시당 1번이다? 메소드 호출마다 프록시가 그만큼 생겨나는게 n+1이다?
>
> 첫 부분은 맞고, 뒷부분("메서드 호출마다 프록시가 생겨난다")은 정정이 필요하다 — 프록시는 메서드를 호출해서 생기는 게 아니라 최초 조회 시점에 이미 다 만들어져 있다.
>
> **정확한 타임라인**
>
> 1. `findAll()` 실행 → 쿼리 1번, 메뉴 100개 반환.
> 2. 이 순간 Hibernate는 각 메뉴 객체를 만들면서 그 안의 `category` 필드에 이미 프록시를 하나씩 채워 넣는다. 아직 아무 메서드도 안 불렀는데도 메뉴가 100개면 이 시점에 프록시도 이미 100개 만들어져 있다.
> 3. 그 뒤 반복문에서 `getCategory().getName()`을 부르면, 이미 존재하던 그 100개의 프록시가 각자 한 번씩 초기화되면서 쿼리를 1번씩 날린다(총 100번).
> 4. 최종: `1(최초 조회) + 100(프록시 100개 각각의 초기화 쿼리) = 101` → N+1.
>
> **정리**: "쿼리는 프록시당 1번" — 맞다. "메서드 호출마다 프록시가 생겨난다" — 아니다. 프록시는 부모 엔티티(메뉴)가 조회되는 시점에 이미 그 개수만큼(N개) 만들어져 있고, 메서드 호출은 이미 있는 프록시를 초기화시키는 트리거 역할만 한다. N+1의 "N"은 "메서드를 부른 횟수"가 아니라 "최초 조회로 가져온 부모 엔티티(=프록시)의 개수"다.

> **Q.** findAll() 실행 → 쿼리 1번, 메뉴 100개 반환. 아니 그러니까 하... findAll 실행했어? 그럼 객체에 대한 프록시 1개 그리고 대응하는 쿼리 1번 맞지? 그리고 findAll 하위에 메뉴 메서드 100개 반환 한다 맞아?
>
> 핵심 정정: `findAll()` 자체는 프록시를 안 만든다. 두 가지를 완전히 분리해서 봐야 한다 — ① 메뉴 자체(엔티티) vs ② 메뉴 안의 category 필드(프록시).
>
> **단계별로 다시**
>
> - 1단계: `findAll()` 실행 → 쿼리 1번만 나간다.
> - 2단계: 그 쿼리 결과로 메뉴(Menu) 100개가 반환된다. 이 메뉴 100개는 진짜(real) 객체다 — `findAll()`이 직접 조회한 대상이라 id/이름/가격 등 모든 필드가 이미 다 채워져 있다. 프록시가 아니다.
> - 3단계: 메뉴 100개 각각은 `category`라는 필드를 갖고 있고, 그 필드는 LAZY로 설정돼 있다. 그래서 Hibernate가 메뉴 객체를 만드는 바로 이 시점(2단계와 동시)에, 각 메뉴의 `category` 필드 자리에 프록시를 하나씩 끼워 넣는다. 메뉴가 100개니까 이때 만들어지는 프록시도 100개다.
> - 4단계(아직 발생 안 함): 여기까지는 반복문도 안 돌았고 `getName()`도 안 불렀다. 쿼리는 여전히 1번뿐이다.
> - 5단계: 반복문에서 각 메뉴의 `getCategory().getName()`을 부르면, 이미 3단계에서 만들어져 있던 그 100개의 프록시가 하나씩 초기화되면서 쿼리를 1번씩 날린다 → 추가로 100번.
> - 최종: `1(2단계) + 100(5단계) = 101`.
>
> **정리**: "findAll()이 프록시 1개랑 쿼리 1개를 만든다"가 아니다. `findAll()`은 프록시 없이 쿼리 1번으로 진짜 메뉴 100개를 만든다. 그 100개의 메뉴 각각이 자기 안에 별도의 category 프록시를 하나씩(총 100개) 갖게 되는 것이고, 이 프록시들이 나중에 초기화되면서 추가 쿼리 100번을 만든다.

> **Q.** 다시 구체적인 예시를 보여주고 다시 설명해. 지금 설명해서는 findAll이 그냥 호출 받은거 같은데 사실 거기서부터 이해안돼. 그리고 category는 또 어디서 튀어나온거야. getName 또 왜 있어. 실제 코드 바탕으로 다시 설명해 정확하게 이해가 안되잖아
>
> 처음부터 실제 코드로 다시 짠다. 세 가지 파일.
>
> **코드 1) Category 엔티티(`categories` 테이블 대응)**
> ```java
> @Entity
> public class Category {
>     @Id @GeneratedValue
>     private Long id;
>     private String name;
>
>     public String getName() {   // "getName"이 여기서 나온다 — 그냥 name 필드를 읽는 평범한 getter
>         return name;
>     }
> }
> ```
>
> **코드 2) Menu 엔티티(`menus` 테이블 대응)**
> ```java
> @Entity
> public class Menu {
>     @Id @GeneratedValue
>     private Long id;
>     private String name;
>
>     @ManyToOne(fetch = FetchType.LAZY)   // 이 필드의 "타입"이 Category다 — "category"가 여기서 나온다
>     @JoinColumn(name = "category_id")
>     private Category category;
>
>     public Category getCategory() {
>         return category;
>     }
> }
> ```
>
> **코드 3) Repository(자동 생성 CRUD를 상속만 받음)**
> ```java
> public interface MenuRepository extends JpaRepository<Menu, Long> {
>     // findAll()은 코드를 안 짜도 JpaRepository가 이미 만들어서 준다
> }
> ```
>
> **실제 실행 코드**
> ```java
> List<Menu> menus = menuRepository.findAll();
> for (Menu menu : menus) {
>     System.out.println(menu.getCategory().getName());
> }
> ```
>
> **실행 순서를 그대로 따라가면**
>
> 1. `menuRepository.findAll()` 호출 — 우리가 만든 메서드가 아니라 `JpaRepository`를 상속받아 이미 공짜로 받은 메서드(예전에 배운 자동 CRUD).
> 2. SQL `SELECT * FROM menus`가 딱 1번 나가고, 결과 100행이 `Menu` 자바 객체 100개로 변환된다. 이 `Menu` 객체들은 진짜 데이터다(id, name 다 채워짐) — `findAll()`이 직접 조회한 대상이기 때문.
> 3. `Menu` 클래스 안 `category` 필드의 타입이 `Category`다 — "Category가 어디서 나왔냐"의 답은 `Menu` 클래스에 원래 선언돼 있던 필드의 타입이라는 것이다. 이 필드가 `@ManyToOne(fetch = LAZY)`라서, 2번에서 `Menu` 객체를 만드는 그 순간 Hibernate는 진짜 `Category` 데이터 대신 `Category`인 척하는 빈 껍데기(프록시)를 만들어 `category` 필드에 넣어둔다. 메뉴가 100개니 프록시도 100개 생긴다.
> 4. 여기까지 쿼리는 여전히 1번뿐이고 반복문도 아직 안 돌았다.
> 5. `for` 반복문에서 첫 메뉴의 `menu.getCategory()`를 부른다 — 이건 2번의 `Menu` 클래스에 있는 평범한 getter라서 `category` 필드에 들어있는 것(3번에서 만든 프록시)을 그대로 반환할 뿐이다. 아직 DB 안 건드림.
> 6. 이어서 `.getName()`을 부른다 — "getName이 왜 있냐"의 답은 코드 1번 `Category` 클래스에 직접 정의한 평범한 getter라는 것이다. 그런데 지금 호출당하는 대상은 진짜 `Category`가 아니라 3번에서 만든 가짜(프록시)다. 이 프록시는 `getName()`이 불리는 순간 "나 아직 진짜 이름 값이 없네, 지금 가져와야겠다"고 판단해서 `SELECT * FROM categories WHERE id = ?`를 이때 처음으로 날린다.
> 7. 두 번째 메뉴로 넘어가면 그 메뉴는 자기만의 또 다른 프록시를 갖고 있으므로(3번에서 각자 따로 만들어짐) 똑같은 과정이 반복된다 — 또 쿼리 1번.
> 8. 메뉴 100개 전부에 대해 반복되면 쿼리가 100번 추가로 나간다.
>
> **최종**: 2번의 쿼리(1번) + 6~8번이 100개 메뉴 각각에 대해 반복되며 나가는 쿼리(100번) = 총 101번. 이게 N+1이다.

> **Q.** "SQL SELECT * FROM menus가 딱 1번 나가고, 결과 100행이 Menu 자바 객체 100개로 변환된다." 왜? 코드상에선 설정이 안되있는대?
>
> 실제로는 "설정 안 된 게" 아니라, SQL 문자열로 직접 안 썼을 뿐 다른 방식(어노테이션 + 제네릭 타입)으로 이미 설정돼 있는 것이다. 두 군데를 봐야 한다.
>
> **설정 ① — `@Entity` 클래스 자체가 "어느 테이블인지"를 이미 알려줌**: `@Entity`(+ 필요하면 `@Table(name="menus")`)를 붙이는 순간, 이 자바 클래스가 `menus` 테이블에 대응한다는 매핑 정보가 이미 등록된다. `@Id`, `@Column` 같은 어노테이션도 "어떤 필드가 어떤 컬럼에 대응하는지"를 이미 다 알려준다. 그래서 SQL을 직접 안 써도, Hibernate는 "Menu 객체를 다루고 싶으면 menus 테이블, id는 id 컬럼, name은 name 컬럼"이라는 걸 이 어노테이션들만 보고 이미 안다.
>
> **설정 ② — `JpaRepository<Menu, Long>`의 제네릭 타입이 "무슨 엔티티를 다룰지"를 알려줌**: `findAll()`은 사실 `SimpleJpaRepository<T, ID>`라는 클래스 안에 딱 한 번 범용적으로 이렇게 구현돼 있다(개념적으로): `SELECT e FROM T e` — 여기서 `T`는 고정된 값이 아니라 `<Menu, Long>`이라고 써넣은 그 자리다. `MenuRepository`가 `JpaRepository<Menu, Long>`을 상속하는 순간 이 `T` 자리에 `Menu`가 끼워져서 `SELECT m FROM Menu m`이 만들어지고, ①에서 확인한 매핑 정보를 이용해 최종적으로 `SELECT * FROM menus`라는 진짜 SQL로 번역된다.
>
> **"100행 → 100개 객체 변환"도 같은 원리**: 결과로 온 각 행(row)을 ①의 `@Column` 매핑 정보를 거꾸로 이용해서 "이 컬럼 값은 이 필드에 넣어라"고 하나씩 채워 넣어 `Menu` 객체를 만든다. 이것도 반복문을 직접 짜서 한 게 아니라, Hibernate가 어노테이션 정보를 보고 자동으로 해주는 것이다.
>
> 정리: "코드에 설정이 안 되어 있다"가 아니라, SQL 문자열 대신 어노테이션(`@Entity`, `@Column`)과 제네릭 타입(`<Menu, Long>`)이라는 형태로 이미 설정이 되어 있고, Hibernate가 그 설정을 읽어서 실제 SQL과 객체 변환을 대신 만들어주는 것이다.

> **Q.** 그러니까 방금 니 설명에서도 100행을 반환한다는 내용이 없다니까?
>
> 좋은 지적이다 — 사실 코드 어디에도 "100"이라는 숫자는 없다. 설명하면서 예시로 편의상 "메뉴 100개"라고 가정한 것뿐이지, `findAll()`이 몇 개를 반환할지는 코드에 전혀 설정되어 있지 않다.
>
> - `findAll()`의 뜻 자체가 "지금 이 테이블에 들어있는 행을 전부 다 가져와라"다. "몇 개"라는 숫자를 지정하는 부분이 원래 없다.
> - 그래서 실제로 몇 개가 반환되는지는 그 순간 DB의 `menus` 테이블에 실제로 몇 행이 들어있느냐에 의해서만 결정된다. 오늘은 100개일 수도, 내일 데이터가 추가되면 150개일 수도 있다.
> - 즉 "100"은 코드가 정한 숫자가 아니라 런타임에 DB 상태를 보고서야 알 수 있는 값이고, 설명을 구체적으로 하려고 "예를 들어 100개 있다고 하자"라고 임의로 잡은 예시 숫자였다.
>
> 정리: `@Entity`/`@Column`/제네릭 타입은 "어떤 테이블의 어떤 컬럼을 어떤 필드로 매핑할지"만 정해줄 뿐이고, "몇 개의 행이 나올지"는 그 어떤 어노테이션에도 없다 — 그건 순전히 그 시점의 실제 데이터 양에 달려 있다.
