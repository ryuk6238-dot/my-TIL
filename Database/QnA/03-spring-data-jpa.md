# Spring Data JPA 도입하기 — Q&A

### Q1. SQL과 테이블의 관계

> **Q.** SQL 이라는게 테이블 말하는거지?
>
> 아니다. SQL은 테이블 자체가 아니라 **테이블(관계형 데이터베이스)에 접근하기 위한 언어**다.
>
> - **테이블**은 실제 데이터가 행(row)과 열(column) 구조로 저장되는 대상. 정리 노트의 `tbl_menu`, `categories` 같은 것이 테이블이다.
> - **SQL**은 그 테이블에 대해 조회(SELECT), 삽입(INSERT), 수정(UPDATE), 삭제(DELETE) 같은 작업을 수행하기 위한 질의 언어(Query Language)다.
>
> 정리 노트의 "SQL 중심 기술"이라는 표현은 "테이블 자체"가 아니라, 개발자가 SQL 문장을 직접 작성해서 DB에 접근하는 방식(MyBatis, Spring JDBC 등)을 뜻한다. 반대로 JPA/Spring Data JPA는 SQL을 직접 쓰지 않고 엔티티 객체(자바 클래스)를 통해 테이블에 접근하며, SQL은 JPA가 내부적으로 자동 생성해준다.

> **Q.** 반대로 JPA/Spring Data JPA는 SQL을 직접 쓰지 않고 엔티티 객체(자바 클래스)를 통해 테이블에 접근하며, SQL은 JPA가 내부적으로 자동 생성해준다. 이게 noSQL 인가?
>
> 아니다. JPA/Spring Data JPA는 여전히 **관계형 데이터베이스(RDBMS)와 SQL**을 사용한다 — 그 SQL을 개발자가 직접 타이핑하지 않고 JPA가 대신 생성해줄 뿐이다.
>
> - **NoSQL**은 애초에 테이블·행·열 구조 자체를 쓰지 않는 별도의 데이터베이스 종류다(MongoDB의 document, Redis의 key-value, Cassandra의 wide-column 등). SQL 언어 자체가 필요 없는 구조다.
> - **JPA**는 "SQL을 안 쓴다"가 아니라 "SQL을 직접 작성하지 않아도 된다"는 것이다. 내부적으로는 여전히 PostgreSQL, MySQL 같은 RDBMS에 접속해서 진짜 SQL(`SELECT`, `INSERT` 등)을 실행하며, 그 SQL 문자열을 개발자 대신 JPA/Hibernate가 엔티티 정보를 보고 자동으로 만들어낸다.
>
> 즉 SQL을 누가 작성하느냐(개발자 vs JPA)의 차이일 뿐, 둘 다 관계형 DB + SQL 세계 안에 있다. NoSQL은 그 세계 바깥의 완전히 다른 데이터베이스 패러다임이다.

### Q2. Entity 클래스 기반 작성과 패러다임 불일치의 관계

> **Q.** "패러다임 불일치: 객체지향과 관계형 DB는 데이터를 표현하는 방식이 근본적으로 다르다. 객체의 상속 구조, 참조, 컬렉션 필드는 테이블로 그대로 표현되지 않아 매핑 문제가 발생한다." — 이 경우에는 내 기억에 entity 클래스를 기반으로 작성했던거 같은데
>
> 맞다. `Entity 설계 기초` 실습(Category.java)이나 `Spring Data JPA 시작하기` 실습(Menu.java)에서 실제로 **Entity 클래스를 먼저 작성 → `ddl-auto: create` 설정으로 JPA가 테이블 DDL을 자동 생성**하는 순서로 진행했다.
>
> - `@Entity`, `@Table(name = "categories")`, `@Id`, `@GeneratedValue`, `@Column(nullable = false, length = 30)` 같은 어노테이션으로 자바 클래스를 작성하면, 앱 실행 시 Hibernate가 그 정보를 읽어 `CREATE TABLE categories (...)` DDL을 자동 생성한다.
> - 이는 **객체 우선(code-first)** 방식이다. 반대로 테이블을 먼저 설계하고 Entity를 거기에 맞춰 작성하는 **테이블 우선(schema-first)** 방식도 있는데, 실무에서는 `ddl-auto: validate`/`none`을 쓰면서 스키마는 Flyway/Liquibase 같은 도구로 관리하고 Entity를 그 스키마에 맞춰 작성하는 경우가 더 흔하다.
>
> 패러다임 불일치와 모순되지 않는다. 패러다임 불일치는 "객체와 테이블의 구조가 원래 다르다"는 것이고, `@Entity`/`@Table`/`@Column`/`@OneToMany` 같은 JPA 어노테이션들이 바로 그 간극을 메우는 역할을 한다. Entity 클래스를 기반으로 작성했다는 것은, 그 어노테이션들이 "이 객체를 이런 테이블 구조로 번역해달라"고 JPA에게 지시하는 것이고, 실제 변환(매핑) 작업 자체가 패러다임 불일치를 해소하는 과정이다.

### Q3. ORM 등장 배경과 패러다임 불일치의 인과관계

> **Q.** "ORM은 이 불일치를 해소하기 위해 객체 ↔ 테이블 매핑을 자동 처리하는 기술. 생산성·가독성이 향상되지만, 내부 동작을 모르면 성능 저하나 예기치 못한 쿼리가 발생할 수 있다." 이거 좀 의문인게, 위에서 패러다임 불일치라는 문제가 생겨서 orm이라는 기술이 도입돼서 매핑을 도와주는건가?
>
> 맞다. 정확히 그 인과관계다.
>
> - 객체지향과 관계형 DB는 애초에 데이터를 표현하는 방식이 다르다(패러다임 불일치) → 개발자가 SQL을 직접 짜서 이 간극을 수작업으로 메워야 했다(SQL 중심 기술, JDBC/MyBatis) → 이 수작업이 반복적이고 번거로우니, 그 매핑 작업 자체를 자동화하는 기술로 ORM이 등장했다.
> - 정리 노트에도 "ORM(Object-Relational Mapping)은 객체와 테이블 사이의 매핑을 자동으로 처리하는 기술로, 위 문제(패러다임 불일치)를 해결하기 위해 등장했다"고 명시돼 있다.
> - 같은 흐름에서 JPA는 자바 진영에서 이 ORM 기능을 "표준화"한 명세이고, Hibernate는 그 명세를 실제로 구현한 라이브러리다. 즉 `패러다임 불일치(문제) → ORM(해결 기술의 개념) → JPA(자바 표준 명세) → Hibernate(구현체)` 순서로 이어지는 계보로 이해하면 된다.

> **Q.** 그럼 지금 학습 흐름대로면 기존에 SQL 중심 기술로는 spring의 객체 지향 방식과 DB의 데이터 매핑 문제가 생겼고 이를 해결하기 위한 ORM이 등장했다 로 이해하면 되나?
>
> 거의 맞지만 한 가지만 짚어야 한다 — "Spring의 객체지향 방식"이 아니라 "Java(객체지향 언어) 자체의 특성"이다. Spring은 프레임워크일 뿐이고, 패러다임 불일치는 Spring을 쓰든 안 쓰든 자바(또는 다른 OOP 언어)로 개발하면서 관계형 DB를 쓸 때 항상 존재하는 근본적인 문제다.
>
> 정리하면: **기존에 SQL 중심 기술(JDBC, MyBatis)로는 자바(객체지향)의 표현 방식과 관계형 DB(테이블 중심)의 표현 방식이 근본적으로 달라(패러다임 불일치) 매핑 문제가 있었고, 이를 자동으로 해결하기 위해 ORM이라는 기술이 등장했다.**
>
> - 패러다임 불일치는 "언어 vs DB" 차원의 문제(Java ↔ RDBMS)다.
> - Spring/Spring Data JPA는 그 위에서 "이 매핑 작업(ORM)을 자바 생태계에서 얼마나 편하게 쓸 수 있게 해주느냐"를 다루는 계층이다 — 문제의 원인이 아니라 해결책을 편리하게 제공하는 쪽이다.

> **Q.** "JPA(Java Persistence API)는 자바 진영의 ORM 표준 명세(인터페이스 규약)일 뿐이고" — 이게 무슨 말이지? 1) jpa가 ORM이라는거야? 2) JPA가 ORM의 역할을 한다는거야? 3) JPA가 ORM과 같은 역할을 한다는거야?
>
> 셋 다 애매하게 맞을 수 있어 헷갈리지만, 정확히는 ①도 ②도 아니고 ③에 가장 가까우면서도 조금 더 정밀하게 표현해야 한다. **JPA는 "ORM이 어떤 모습이어야 하는지"를 정의한 명세(규약)일 뿐, JPA 자체가 실제로 매핑 작업을 수행하지는 않는다.**
>
> - ① "JPA가 ORM이다" (X) — JPA는 ORM 자체(실제로 동작하는 기술/도구)가 아니다. 동작하는 실체가 없다.
> - ② "JPA가 ORM의 역할을 한다" (X, 미묘하게 틀림) — "역할을 한다"는 실제로 뭔가를 수행한다는 뜻인데, JPA 자체는 아무 동작도 하지 않는다. 실제 역할(매핑, SQL 생성)은 Hibernate 같은 구현체가 수행한다.
> - ③ "JPA가 ORM과 같은 역할을 한다" — 이것도 정확하진 않고, 더 정확히는 "JPA는 ORM이라는 개념/역할을 자바에서 수행하려면 어떤 인터페이스(`EntityManager`)와 어노테이션(`@Entity`, `@Id` 등)을 갖춰야 하는지 정해놓은 표준 문서"다.
>
> 비유: Java의 `List` 인터페이스가 "리스트가 뭘 할 수 있어야 하는지(add, get, remove...)"만 정의하고, 실제 동작은 `ArrayList`나 `LinkedList` 같은 구현체가 하는 것과 같다. `List` = JPA(규약만 정의), `ArrayList` = Hibernate(실제 구현체, 진짜 동작 수행). 정리 노트에도 "JPA는 하나의 인터페이스 규약이고, 이를 구현한 프레임워크(Hibernate, EclipseLink, DataNucleus 등)를 통해 실제 동작이 수행된다"고 되어 있다.

> **Q.** 이거만 재정리하면 그러니까 JPA가 ORM이 어떤 형태인지 정해주는 명세서 역할을 한다?
>
> 맞다. 정확한 이해다.
>
> - JPA = "ORM은 이런 인터페이스(`EntityManager`)와 이런 어노테이션(`@Entity`, `@Id`, `@Column`...)을 가져야 한다"고 정해놓은 명세서(규약)
> - Hibernate = 그 명세서대로 실제로 코드를 짜서 동작하게 만든 구현체
>
> 명세서 자체는 종이 위의 규칙일 뿐 아무것도 실행하지 않고, 그 규칙을 따라 실제로 SQL을 만들고 실행하는 건 Hibernate다.

> **Q.** "JPA는 자바 진영의 ORM 표준 명세(인터페이스 규약)일 뿐이고, 실제 동작은 구현체(대표적으로 Hibernate)가 담당한다." 이걸 다시 정리해보면 JPA는 ORM이 어떤 형태인지 정하는 명세서이고 하이버네이트는 JPA가 정해둔 명세서를 실제로 동작시키는 구현체다 맞아?
>
> 맞다. 그 정리 그대로다.
>
> - JPA = 명세서(규약) — 예: `EntityManager`, `@Entity` 같은 "이런 게 있어야 한다"는 규칙만 정의
> - Hibernate = 구현체 — 그 규칙을 실제 코드로 구현해서 SQL 생성, 영속성 컨텍스트 관리 같은 진짜 동작을 수행
>
> 이 관계는 "표준(JPA)과 그 표준을 따르는 제품(Hibernate)"의 관계와 같다. Hibernate 외에도 EclipseLink, DataNucleus 같은 다른 구현체도 있는데, 어떤 구현체를 쓰든 JPA라는 같은 명세를 따르기 때문에 코드(어노테이션, API 사용법)는 거의 동일하게 유지된다 — 이것이 JPA가 표준 명세로 존재하는 이유(벤더 독립성)이기도 하다.

> **Q.** 그럼 의문인게 hibernate가 없으면 jpa가 작동 안하는거야?
>
> 맞다. JPA만 있고 구현체가 없으면 아무것도 동작하지 않는다.
>
> - JPA는 인터페이스와 어노테이션 규약만 정의해놓은 API 모음(`jakarta.persistence` 패키지)일 뿐이라 그 자체로는 실행 가능한 코드가 없다. `EntityManager.persist()`를 호출해도 그 메서드의 실제 로직(SQL 생성, DB 연결, 트랜잭션 처리 등)은 JPA 안에 들어있지 않다.
> - 그래서 반드시 JPA 구현체(JPA Provider)가 클래스패스에 있어야 실제로 동작한다. Hibernate가 가장 널리 쓰이지만 EclipseLink나 OpenJPA 같은 다른 구현체로 대체해도 된다 — 핵심은 "Hibernate가 필수"가 아니라 "JPA 구현체 중 하나는 반드시 있어야 한다"는 것이다.
> - Spring Boot에서 `spring-boot-starter-data-jpa`를 추가하면 별다른 설정 없이 Hibernate가 기본 구현체로 자동 포함되기 때문에, 평소에는 "구현체를 별도로 골라야 한다"는 걸 의식하지 못할 뿐이다.
>
> 비유: `List item = new ArrayList<>();`에서 `ArrayList` 없이 `List` 인터페이스만으로는 객체를 만들 수 없는 것과 같은 원리다.

> **Q.** 음 그러니까 개념적으로 JPA 가 결국 API니까 그 호출?을 받아서 동작시킬 구현체가 필요한데 그게 hibernate 다 맞아?
>
> 맞다. 정확한 이해다.
>
> - JPA = API(호출 인터페이스) — "이런 메서드를 이런 이름으로 호출할 수 있다"는 규약만 존재(`EntityManager.persist(entity)`, `@Entity` 등)
> - 그 호출을 실제로 받아서 처리(동작)시키는 게 구현체 — 대표적으로 Hibernate
>
> API는 "무엇을 할 수 있는지(what)"만 정의하고, 구현체가 "어떻게 실제로 할지(how)"를 채워 넣는 구조다. 개발자는 JPA의 API(어노테이션, `EntityManager` 메서드)만 알고 코드를 짜면 되고, 그 뒤에서 실제로 SQL을 만들고 DB에 쏘는 건 Hibernate가 알아서 처리한다.

> **Q.** 아까 ORM은 JPA가 형태를 규정한다고 이해했는데 그럼 ORM은 무조건 JPA 하위에 존재하는거야? 다시 정리하면 JPA만의 기술/개념인거야? 아니면 좀 더 광범위하게 사용되는건데 JPA로 형태를 잡을 수 있다는거야?
>
> 반대다. JPA가 ORM의 하위 개념이 아니라, ORM이 훨씬 더 넓은 범위의 일반 개념이고 JPA는 그 ORM 개념을 자바 진영에서 표준화한 것이다.
>
> - ORM은 언어에 종속되지 않는 일반적인 기술/패턴이다. 자바뿐 아니라 Python(Django ORM, SQLAlchemy), Ruby(ActiveRecord), .NET(Entity Framework), JavaScript(TypeORM, Sequelize), PHP(Doctrine) 등 각 언어마다 JPA와 무관한 독자적인 ORM 도구가 있다.
> - JPA는 그 넓은 ORM 개념 중 "자바에서는 이런 인터페이스 형태로 ORM을 제공하자"고 정한 자바 전용 표준일 뿐이다.
> - 역사적으로도 순서가 증명된다: Hibernate는 2001년에 이미 독자적인 ORM 프레임워크로 등장했고, JPA는 그보다 나중인 2006년에 Hibernate 같은 기존 ORM들의 경험을 바탕으로 자바 표준으로 만들어졌다. 즉 ORM(Hibernate)이 먼저 있었고 JPA가 나중에 그걸 표준화한 것이지, JPA가 먼저 있고 ORM이 그 밑에 생긴 게 아니다.
>
> 정리: "ORM은 JPA로 형태를 잡을 수 있다"가 맞는 방향이다. ORM(광범위한 개념) ⊃ JPA(그중 자바 표준으로 형태를 규정한 하나의 사례).

> **Q.** 그럼 다시 정리해보면 ORM을 JAVA에서 사용하기 위해 JPA로 ORM의 형태를 규정해서 hebernate로 구현할 수 있도록 했다 가 맞겠네?
>
> 맞다. 정확한 최종 정리다 — "ORM을 Java에서 사용하기 위해 JPA로 ORM의 형태를 규정하고, Hibernate로 그걸 구현할 수 있도록 했다."
>
> 이 문장이 지금까지 나온 개념(패러다임 불일치 → ORM 등장 → JPA 표준화 → Hibernate 구현)을 정확히 압축한 결론이다.
>
> (역사적 순서만 참고로 덧붙이면) 실제로는 Hibernate가 2001년에 먼저 독자적인 ORM으로 나왔고, JPA가 2006년에 그걸 포함한 기존 ORM들의 설계를 참고해서 자바 표준 형태로 규정한 것이라, 시간 순서상으로는 "Hibernate 먼저 → JPA가 형태를 나중에 규정 → Hibernate가 그 규정에 맞춰 표준 구현체로 재정비"에 가깝다. 다만 지금 이해해야 할 개념적 구조(무엇이 무엇을 규정하고 구현하는가)로는 이 정리가 맞다.

### Q4. 영속성 컨텍스트 개념 — 생성 시점, Key-Value 관리, Thread-Safe, Request Scope

> **Q.** "영속성 컨텍스트(Persistence Context): 엔티티를 영구 저장하는 환경으로, 엔티티 매니저(EntityManager) 생성 시 함께 만들어지며 Key-Value로 엔티티를 관리한다. 엔티티 매니저는 Thread-Safe하지 않아 Web에서는 보통 Request Scope와 일치시킨다." 이게 개념적으로 헷갈리는데, 영속성 컨텍스트라는게 유저가 의도적으로 삭제하지 않으면 영구적으로 저장한다는거잖아? 1) 엔티티 매니저를 언제 어떻게 생성을 한다는거야? 플러그인과야? 아니면 패키지 구조적인거야? 2) 만들어 질때 키와 값으로 관리를 한다고했는데 그러면 엔티티매니저를 만들때 키 값을 설정해줘야한다는건가? 3) thread-safe가 뭐야 4) web에서 보통 request나 scope를 일으킨다는데 scope은 뭐야? 그리고 영속성 컨텍스트가 결국 엔티티라고 난 이해했는데 아무런 요청도 호출도 없는게 갑자기 왜 웹에서 호출을 받아?
>
> 핵심 오해부터 정정한다 — "영속성 컨텍스트 = 영구 저장(DB에 계속 남음)"이 아니다. "영속(persistent)"은 "DB에 영원히 저장됨"이 아니라 "지금 이 컨텍스트가 그 엔티티를 계속 추적/관리하고 있는 상태"라는 뜻이다. 영속성 컨텍스트 자체는 메모리 상의 임시 저장소이고, `EntityManager`가 종료되면 (커밋해서 DB에 반영되지 않았다면) 그 안의 내용은 다 사라진다. 진짜 영구 저장은 DB가 하고, 영속성 컨텍스트는 그 전 단계의 "작업 중인 메모리 공간(1차 캐시)"이다.
>
> **1) 엔티티 매니저는 언제 어떻게 생성되나** — 플러그인이나 패키지 구조 얘기가 아니라 객체 생성 시점의 문제다. 앱이 시작될 때 Spring이 `EntityManagerFactory`(무거운 객체, 앱 전체에 1개)를 먼저 만든다. 실제 요청 처리 중(`@Transactional` 메서드 시작 시점)에 그 공장에서 가벼운 `EntityManager` 인스턴스를 하나씩 자동으로 찍어내 스레드에 묶어준다. 개발자가 직접 생성 코드를 쓰지 않아도 Spring이 자동으로 처리한다.
>
> **2) Key-Value 관리가 직접 키를 설정해야 한다는 뜻인가** — 아니다, 자동이다. key는 그 엔티티의 `@Id` 필드 값이다. `entityManager.find(Menu.class, 1L)`처럼 조회하면 JPA가 내부적으로 `key=1L, value=menu객체` 형태로 1차 캐시(Map)에 자동 저장한다. 개발자는 `@Id`를 어떤 필드에 붙였는지만 정하면 되고 따로 키를 설정하는 코드는 없다.
>
> **3) Thread-Safe가 뭐야** — 여러 스레드가 동시에 같은 객체를 건드려도 데이터가 꼬이지 않고 안전하게 동작하는 성질. `EntityManager`는 내부에 "지금 관리 중인 엔티티 목록(1차 캐시)"이라는 상태를 갖고 있어서, 만약 사용자 A와 B의 요청이 같은 `EntityManager` 인스턴스를 동시에 쓴다면 두 요청의 데이터가 같은 내부 Map에서 뒤섞여 서로를 오염시킬 수 있다. 그래서 `EntityManager`는 "혼자만 써야 안전한" 객체다.
>
> **4) Scope란? 그리고 왜 "웹에서 호출을 받는다"는 표현이 이상한가** — 먼저 오해 정정: 영속성 컨텍스트가 스스로 뭔가를 "호출받는" 능동적인 존재가 아니다. `EntityManager` 안에 딸린 수동적인 저장 공간일 뿐이고, 그 `EntityManager`의 생명주기(생성~소멸 시점)가 "웹 요청 하나의 생명주기"와 맞춰져 있다는 뜻이다.
>
> - Scope = "이 객체 인스턴스가 얼마나 오래, 어떤 범위 동안 유효하냐"는 개념. 예: Singleton scope(앱 전체에서 인스턴스 1개, `EntityManagerFactory`가 이런 성격), Request scope(HTTP 요청 하나가 들어올 때마다 새 인스턴스를 만들고 응답 나가면 버림).
> - "Web에서는 Request Scope와 일치시킨다"의 의미: 클라이언트가 요청을 보내면 Controller → Service → Repository로 흘러가는 그 한 번의 요청-응답 사이클 동안만 새 `EntityManager`(와 그 안의 영속성 컨텍스트)를 만들어 쓰고, 응답을 돌려준 뒤 닫는다. 다음 요청이 오면 완전히 새로운 `EntityManager`를 또 만든다.
> - 이렇게 하는 이유가 바로 3번의 Thread-Safe 문제 때문이다. 요청마다 별도의 `EntityManager`를 쓰면 동시에 여러 사용자가 요청을 보내도 서로의 데이터가 섞이지 않는다.
>
> 정리: 영속성 컨텍스트는 "영구 저장소"가 아니라 "한 트랜잭션/요청 동안만 살아있는 임시 작업 공간"이고, 그 생명주기를 웹 요청 하나의 생명주기와 맞춰서(Request Scope) 매 요청마다 새로 만들고 버리는 것이다.

> **Q.** 그러니까 천천히 정리해보면 일단 영속성 컨텍스트는 엔티티를 영구적으로 저장하는게 아니야 생성된 엔티티에 대한 지속적인 관찰 상태를 말하는거고 키,값은 spring에서 자동으로 설정한다. 엔티티 매니저는 thread-safe하지 않아서 동시에 같은 객체를 건들면 데이터가 꼬이므로 엔티티 매니저 혼자 사용해야한다 까지 맞아?
>
> 거의 다 맞고, 한 군데만 정정한다.
>
> 1. "영속성 컨텍스트는 엔티티를 영구적으로 저장하는게 아니다" — 맞다.
> 2. "생성된 엔티티에 대한 지속적인 관찰 상태를 말하는거고" — 정확하다. "관찰(추적)하고 관리하는 상태"라는 표현이 맞다(변경 감지, 동일성 보장이 다 이 "관찰" 덕분에 가능).
> 3. "키,값은 spring에서 자동으로 설정한다" — 살짝 정정 필요. 이건 Spring이 아니라 JPA(정확히는 구현체인 Hibernate)가 하는 일이다. Spring의 역할은 `EntityManager`를 언제 만들고 언제 닫을지(생명주기, Request Scope 관리)이고, JPA/Hibernate의 역할은 그 `EntityManager` 내부에서 `@Id` 값을 key로 삼아 1차 캐시(Map)에 엔티티를 저장하는 실제 동작이다. 즉 "Request Scope로 EntityManager를 관리해주는 건 Spring", "그 안에서 Key-Value로 엔티티를 캐싱하는 건 JPA/Hibernate"로 역할이 나뉜다.
> 4. "엔티티 매니저는 thread-safe하지 않아서 동시에 같은 객체를 건들면 데이터가 꼬이므로 엔티티 매니저 혼자 사용해야한다" — 맞다.
>
> 최종 정리: 영속성 컨텍스트는 영구 저장소가 아니라 생성된 엔티티에 대한 지속적인 추적/관찰 상태이며, 그 안의 Key-Value 캐싱은 JPA/Hibernate가 자동으로 처리한다(Spring은 EntityManager의 생명주기·스코프만 관리). 엔티티 매니저는 Thread-Safe하지 않아서 동시에 같은 인스턴스를 여러 스레드가 건드리면 데이터가 꼬이므로, 요청마다 하나씩 독립적으로 사용해야 한다.

> **Q.** "엔티티 매니저는 Thread-Safe하지 않아 Web에서는 보통 Request Scope와 일치시킨다." 이 부분 thread-safe 하지 않다까지는 이해했는데 그 다음이 이해가 안돼 무슨말이야
>
> 인과관계를 구체적 시나리오로 풀면 이렇다: "Thread-Safe 하지 않다" → "여러 스레드가 하나의 EntityManager를 같이 쓰면 위험하다" → "그러니까 스레드(=웹 요청)마다 EntityManager를 따로따로 만들어서 쓰자" → 이 "따로따로 만든다"가 바로 Request Scope다.
>
> **Request Scope로 안 만들면(나쁜 예)**: `EntityManager`를 앱 전체에서 딱 1개(싱글턴)로 만들어 모든 요청이 공유한다고 하자. 웹 서버는 동시에 여러 요청을 처리하려고 요청마다 별도 스레드를 배정한다(사용자 A=스레드1, 사용자 B=스레드2, 동시 실행). 두 스레드가 같은 EntityManager 인스턴스를 동시에 건드리면, 스레드1의 1차 캐시에 스레드2가 조회한 엔티티가 섞이거나, 스레드1이 커밋 안 한 변경사항을 스레드2가 실수로 함께 flush 해버릴 수 있다. 결과적으로 "A가 조회했는데 B의 DB 변경이 섞여 나온다" 같은 데이터 오염이나 예외가 발생한다.
>
> **Request Scope로 만들면(실제 방식)**: 요청이 들어올 때마다(스레드가 새로 배정될 때마다) 그 요청 전용의 새 EntityManager를 하나 만든다. 스레드1과 스레드2는 각자 자기만의 EntityManager를 가지므로 서로 마주칠 일이 없다. 요청 처리가 끝나 응답을 보내면 그 EntityManager는 버려진다(닫힌다). 다음 요청이 오면 또 새로 만든다.
>
> 즉 "Request Scope와 일치시킨다"는 "EntityManager를 공유하지 않기 위해 요청 하나당 정확히 하나씩 만들고 그 요청이 끝나면 버린다"는 뜻이다. Thread-Safe 하지 않은 문제를 "공유를 아예 안 시켜버림으로써" 회피하는 전략이며, Spring이 `@Transactional`을 통해 이 과정을 자동으로 처리해준다.

> **Q.** 아 그러니까 thread-safe 하지 않으니까 데이터가 꼬일 위험이 있어서 Scope request 형태으로 맞춰서 한번에 하나의 엔티티 매니저만 만들어 위험을 방지한다 맞아?
>
> 거의 맞지만 "한 번에 하나의 엔티티 매니저만 만들어"라는 표현은 오해될 수 있어 정정한다. 핵심은 "전체에서 하나만"이 아니라 "요청마다 각자 하나씩, 서로 공유는 안 한다"는 것이다.
>
> - 동시에 여러 요청이 들어오면 그 순간에도 EntityManager는 여러 개가 동시에 존재한다(요청 A용 1개, 요청 B용 1개, 요청 C용 1개... 동시 요청 수만큼).
> - 다만 각 EntityManager는 딱 그 요청 하나만 전담하고 절대 다른 요청과 공유되지 않는다.
>
> 정확한 정리: Thread-Safe 하지 않아서 데이터가 꼬일 위험이 있기 때문에, 요청(스레드)마다 EntityManager를 하나씩 독립적으로 만들어(Request Scope) 서로 공유되지 않게 함으로써 위험을 방지한다. "한 번에 하나만"이 아니라 "요청 하나당 하나씩, 절대 공유 안 함"이 정확한 뉘앙스이며, 나머지 논리 흐름(Thread-Safe 문제 → 공유하면 위험 → Request Scope로 격리)은 정확하다.

> **Q.** "엔티티 생명주기: 비영속(new) → 영속(managed) → 준영속(detached)/삭제(removed), 준영속 → 병합(merge)으로 다시 영속화 가능. 1차 캐시: @Id를 key로 하는 영속성 컨텍스트 내부 캐시... 쓰기 지연(Write-Behind): INSERT/UPDATE/DELETE SQL을 즉시 보내지 않고... 변경 감지(Dirty Checking): 영속 상태 엔티티는 최초 스냅샷과 현재 상태를 flush 시점에 비교해..." 이거 다 영속성 컨텍스트의 특징인거야?
>
> 맞다. 넷 다 영속성 컨텍스트를 이해하는 핵심 요소들이지만, 구분을 좀 더 정확히 하면 다음과 같다.
>
> - 엄밀히 "영속성 컨텍스트의 기능/메커니즘"인 것(3개): 1차 캐시(영속성 컨텍스트가 내부에 갖고 있는 Map 구조 자체 → 컨텍스트의 구성 요소), 쓰기 지연(SQL을 모아뒀다가 한꺼번에 보내는 내부 동작 방식 → 컨텍스트가 하는 일), 변경 감지(스냅샷과 현재 상태를 비교해 자동으로 UPDATE를 만드는 내부 동작 → 컨텍스트가 하는 일).
> - 성격이 조금 다른 것(1개): 엔티티 생명주기(비영속/영속/준영속/삭제/병합)는 영속성 컨텍스트가 "하는 일"이라기보다, 어떤 엔티티가 지금 이 영속성 컨텍스트에 의해 관리되고 있는지 아닌지를 구분하는 상태 분류다. "영속(managed)" 상태라는 것 자체가 "이 엔티티가 지금 영속성 컨텍스트 안에 들어와서 1차 캐시·변경 감지·쓰기 지연의 적용을 받고 있다"는 뜻이라, 나머지 세 개념이 작동하기 위한 전제 조건(이 엔티티가 영속 상태인가?)을 정의하는 것에 가깝다.
>
> 정리: 1차 캐시·쓰기 지연·변경 감지는 영속성 컨텍스트의 "기능"이고, 엔티티 생명주기는 그 기능들이 "언제 적용되는지"를 결정하는 엔티티의 "상태"다. 넷 다 서로 뗄 수 없이 연결되어 있어 "영속성 컨텍스트의 특징"으로 함께 이해해도 실질적으로 문제없다.

> **Q.** 그럼 의문인게 바로 위에서는 jpa, ORM 그리고 hibernate 설명했잖아? 이건 결국 db관리랑 그걸 구현하는 구현부의 조합인데 왜 바로 영속성 컨텍스트가 나오지?
>
> 갑자기 튀어나온 게 아니라, 사실 "JPA/Hibernate가 정확히 어떻게(How) 일을 하는지"를 설명하는 부분이 바로 영속성 컨텍스트다. 지금까지의 흐름은 이렇게 이어진다.
>
> 1. 문제: 패러다임 불일치(객체 vs 테이블)
> 2. 해결 기술 개념: ORM
> 3. 자바의 ORM 표준: JPA(명세, "이런 인터페이스를 써야 한다"는 규약 — 그중 하나가 `EntityManager`)
> 4. 그 명세의 실제 구현체: Hibernate
>
> 여기까지는 "누가(Who) 무엇을(What) 하는가" — 개념·역할·계보에 대한 설명이었다. 이제 노트는 "그래서 실제로 어떻게(How) 동작하는가?"로 넘어가고, 그 답이 영속성 컨텍스트다.
>
> Hibernate가 SQL을 자동 생성해주는 일을 어떻게 해내는지 뜯어보면 그 중심에 영속성 컨텍스트라는 내부 저장 공간이 있다. JPA가 규정한 `EntityManager` 인터페이스를 Hibernate가 실제로 구현하는데, 그 `EntityManager`가 내부적으로 관리하는 것이 바로 영속성 컨텍스트다. 구조: `JPA(EntityManager라는 인터페이스를 규정) → Hibernate(EntityManager를 실제로 구현) → 그 EntityManager 내부의 "영속성 컨텍스트"라는 작업 공간에서 1차 캐시·쓰기 지연·변경 감지 메커니즘으로 실제 SQL 자동 생성이 이루어짐`.
>
> 정리: 영속성 컨텍스트는 JPA/ORM/Hibernate와 다른 주제가 아니라 "Hibernate가 ORM을 실제로 어떻게 수행하는지"에 대한 내부 동작 원리다. 앞부분(JPA/ORM/Hibernate)이 "정의와 역할" 설명이었다면, 뒷부분(영속성 컨텍스트)은 "그 역할을 실제로 수행하는 메커니즘" 설명이라 자연스러운 다음 단계다.

> **Q.** 그러니까 JPA로 ORM을 규칙에 맞게 만들고 호출을 받고 hibernate가 수행하는데에 내부적으로 ORm을 수행하는 방식이 영속성 컨텍스트다 맞아? hibernate 내부적으로 엔티티 매니저를 만들어서 수행한다?
>
> 둘 다 맞다.
>
> 1. "JPA로 ORM을 규칙에 맞게 만들고 호출을 받고 hibernate가 수행하는데, 그 내부적으로 ORM을 수행하는 방식이 영속성 컨텍스트다" — 맞다. JPA가 규칙(인터페이스)을 정하고, 개발자는 그 규칙대로 호출하고(`entityManager.persist()` 등), 실제로 그 호출을 받아 처리하는 Hibernate가 내부적으로 영속성 컨텍스트라는 메커니즘을 통해 ORM 작업(매핑·SQL 생성·캐싱)을 수행한다.
> 2. "hibernate 내부적으로 엔티티 매니저를 만들어서 수행한다?" — 맞다. `EntityManager`는 JPA가 정의한 인터페이스이고, Hibernate는 그 인터페이스의 실제 구현 클래스(Hibernate 용어로는 `Session`)를 제공한다. JPA는 인터페이스만 정의(틀만 제공)하고, Hibernate는 그 인터페이스를 구현한 실제 객체를 만들어내며(Spring이 요청하면 Hibernate가 진짜 인스턴스를 생성), 그 인스턴스(EntityManager) 안에 영속성 컨텍스트가 함께 생성되어 1차 캐시·쓰기 지연·변경 감지가 그 안에서 이루어진다.
>
> 정리: JPA(규칙) → Hibernate가 그 규칙에 맞는 EntityManager를 실제로 생성 → 그 EntityManager가 내부에 영속성 컨텍스트를 두고 ORM 작업을 실질적으로 수행하는 구조다.

### Q5. Spring Data JPA의 계층 순서와 주요 기능

> **Q.** [Spring Data JPA 시작하기 섹션] 그러니까 spring data jpa는 흐름적으로는 jpa -> hibernate -> spring data jpa 흐름으로 동작하고 실제로 설정할 때는 의존성 하나로 일괄 구성이 가능하고 주요기능으로는 기본적인 CRUD 자동 생성, 커스텀 쿼리, 페이징 정렬 등이 있다 맞아?
>
> 전체적으로 맞지만 "흐름"이라는 표현에서 한 가지 뉘앙스를 정확히 짚어야 한다.
>
> **"JPA → Hibernate → Spring Data JPA" 순서**는 계층 구조(역할 정의)로서는 맞다. 정리 노트의 표에도 정확히 이 순서로 나와 있다.
>
> | 구분 | 역할 | 예시 |
> | --- | --- | --- |
> | JPA | 표준 명세 | `@Entity`, `EntityManager.persist()` |
> | Hibernate | JPA의 구현체 | 내부에서 SQL 실행 처리 |
> | Spring Data JPA | JPA를 추상화하여 자동화 | `MyRepository extends JpaRepository` |
>
> 다만 "흐름(동작 순서)"이라는 표현으로 오해하면 안 되는 부분이 있다 — 실제로 코드가 호출될 때(런타임)는 반대 방향으로 흐른다:
>
> ```
> 개발자가 Repository 메서드 호출
>   → Spring Data JPA (프록시가 요청을 가로챔)
>     → JPA API (EntityManager 메서드를 내부적으로 호출)
>       → Hibernate (실제로 SQL 만들어서 DB 실행)
> ```
>
> 즉 "누가 누구 위에 얹혀 있는가"의 계층 순서는 JPA(맨 아래, 표준) → Hibernate(그 위, 구현) → Spring Data JPA(맨 위, 추상화)가 맞지만, 실제 호출은 위(Spring Data JPA)에서 아래(Hibernate)로 내려간다.
>
> 나머지도 다 맞다: 의존성 하나(`spring-boot-starter-data-jpa`)로 Spring Data JPA + Hibernate + JPA가 자동 설정되고, 주요 기능은 CRUD 자동 구현·메서드 이름 기반 쿼리·`@Query`/QueryDSL/Native Query를 통한 커스텀 쿼리·`Pageable`/`Sort` 기반 페이징·정렬이 맞다(추가로 Spring 트랜잭션·예외 변환과의 통합도 있지만 핵심은 다 짚었다).

### Q6. 프록시와 프록시 객체란

> **Q.** 프록시는 정확히 뭐고 프록시 객체는 뭔데
>
> 정리 노트에 "프록시"가 두 군데(Repository 자동 구현, 지연 로딩)에서 나오는데, 일반적인 개념부터 잡고 그 두 가지에 각각 적용한다.
>
> **프록시(Proxy)란**: "진짜 객체 대신 앞에 서서 요청을 받아주는 대리인 객체"다. 프록시는 진짜 객체와 똑같은 모양(같은 인터페이스/타입)을 하고 있어서, 사용하는 쪽은 이게 진짜인지 대리인인지 신경 쓰지 않고 똑같이 사용할 수 있다. 내부적으로는 요청을 그냥 진짜 객체에게 그대로 전달하거나(위임, delegation), 전달하기 전/후에 추가 작업을 끼워 넣는다(로깅, 권한 체크, 지연 로딩, 트랜잭션 처리 등).
>
> 비유: 연예인(진짜 객체) 대신 스케줄을 관리하는 매니저(프록시). 팬(사용하는 쪽)은 매니저에게 연락하지만 실제 공연은 연예인이 한다. 매니저는 필요할 때만 연예인을 실제로 움직이게 하고, 그 사이에 일정 조율 같은 부가 작업도 처리한다.
>
> **프록시 객체**는 이 대리인 역할을 하는 실제 인스턴스를 말한다. 런타임에 자동으로 생성되며, 보통 직접 `new`로 만들지 않는다.
>
> **정리 노트에 나온 두 가지 프록시**
>
> 1) **Repository 프록시**(`Spring Data JPA 시작하기` 섹션): `public interface MenuRepository extends JpaRepository<Menu, Long> {}`처럼 인터페이스만 작성하면, Spring Boot 실행 시 Spring Data JPA가 이 인터페이스를 보고 런타임에 진짜 구현 클래스(프록시 객체)를 자동으로 만들어 빈으로 등록한다. 이 프록시는 내부적으로 `SimpleJpaRepository`를 상속받아 실제 CRUD 로직을 수행하며, 개발자는 그 프록시 객체를 인터페이스 타입으로 주입받아 쓴다.
> 2) **지연 로딩 프록시**(`JPA 활용 시 주의 사항` 섹션): `@ManyToOne(fetch = FetchType.LAZY) private Category category;`처럼 지연 로딩 설정 시, 처음 `Menu`를 조회하면 `category` 필드에는 진짜 `Category` 객체가 아니라 프록시 객체가 들어간다. 겉보기엔 `Category`처럼 생겼지만 속은 비어있고, `menu.getCategory().getName()`처럼 실제로 이 프록시를 건드리는 순간 영속성 컨텍스트에 초기화를 요청해 DB 조회를 트리거한 뒤, 그 뒤로는 진짜 `Category` 객체에게 요청을 위임한다. 이게 지연 로딩이 실제로 구현되는 방식이다.
>
> 공통점: 두 경우 모두 직접 만들지 않은 대리인 객체가 실제 동작을 대신 처리해주고, 그 과정에서 자동화(Repository 구현 자동화 / DB 접근 지연)를 실현한다는 점에서 같은 원리다.

> **Q.** 그럼 프록시는 객체와 객체 사이를 나누는 완충제 같은거네?
>
> "사이에 낀다"는 부분은 맞지만 "완충제"라는 표현은 뉘앙스가 다르다.
>
> - 완충제의 이미지: 두 물체가 직접 부딪히지 않게 충격을 흡수함(수동적, 보호 목적)
> - 프록시의 실제 역할: 요청을 가로채서 능동적으로 판단·처리함(이 요청을 그냥 넘길지, 추가 작업을 할지, 아직 처리하지 말고 미룰지 등을 결정)
>
> 더 정확한 비유는 "완충제"보다 "중개인/대리인/문지기(gatekeeper)"에 가깝다.
>
> - Repository 프록시: `findAll()` 호출을 가로채서 "아 이건 내가 대신 SQL 만들어서 처리해줄게"라고 능동적으로 일을 대신 해줌
> - 지연 로딩 프록시: `category.getName()` 호출을 가로채서 "잠깐, 아직 실제 데이터가 없네? 지금 DB에서 가져와야겠다"라고 판단해서 필요한 시점에 개입
>
> 즉 "사이에 낀 존재"라는 직관은 정확하지만, 그 역할은 "충격을 완화시켜주는 수동적 존재"가 아니라 "중간에서 요청을 통제하고 대신 처리해주는 능동적 대리인"이라는 점이 핵심 차이다.

> **Q.** 객체와 객체 사이의 중개인으로 인지하면 될까?
>
> 맞다. "객체와 객체 사이의 중개인"으로 인지하면 정확하다.
>
> - 호출하는 쪽(클라이언트)과 실제 일을 하는 진짜 객체(Real Subject) 사이에서
> - 프록시가 중개인으로 끼어들어 요청을 가로채 판단하고
> - 필요하면 진짜 객체를 대신 움직이거나, 대신 처리하거나, 처리 시점을 조절한다
>
> 이렇게 이해하면 Repository 프록시(Spring Data JPA가 개발자 대신 CRUD 구현을 중개)와 지연 로딩 프록시(실제 DB 조회 시점을 중개)를 모두 같은 원리로 설명할 수 있다.

> **Q.** 그럼 살짝 복습으로 전에 배운 DTO랑 비슷한 역할 아닌가? DTO는 내부 로직와 외부 데이터 사이에 껴서 내부 로직을 외부로 부터 보호하는거잖아
>
> 비슷해 보이지만 작동 방식이 근본적으로 다르다. "무언가 사이에 껴서 보호한다"는 큰 그림은 비슷하지만 "어떻게" 보호하는지가 다르다.
>
> 공통점(표면적 유사성): 둘 다 "진짜/내부 것"과 "바깥/외부 것" 사이에 끼어서 경계 역할을 한다. Proxy는 클라이언트 ↔ 진짜 객체 사이, DTO는 외부(API 응답/요청) ↔ 내부(Entity/도메인 로직) 사이.
>
> 결정적 차이(가로채서 판단하는가 vs 그냥 모양만 다른 데이터인가):
>
> | | Proxy | DTO |
> | --- | --- | --- |
> | 정체 | 진짜 객체와 같은 타입을 흉내 낸 대리인 | 진짜 객체와 완전히 다른, 더 단순한 데이터 클래스 |
> | 동작 방식 | 메서드 호출을 가로채서(intercept) 판단·위임·지연 | 그냥 필드만 있는 정적인 데이터 덩어리(능동적 판단 없음) |
> | 예시 | `category.getName()` 호출 시 "지금 DB 조회해야겠다" 판단 | `new MenuResponse(menu.getId(), menu.getName(), ...)`처럼 미리 값을 복사해서 새 객체를 만듦 |
> | 목적 | 호출 시점/방식을 통제(지연 로딩, 자동 구현) | 노출할 데이터의 모양(shape)을 통제(Entity 구조 숨기기, 무한루프 방지) |
>
> Proxy는 "행동(behavior)"을 대신 처리한다 — 요청이 오면 그 순간 판단해서 움직인다. DTO는 "데이터(data)"의 모양만 다르게 포장한다 — Entity의 연관관계, 지연 로딩 필드, 내부 구조를 그대로 노출하면 무한루프나 `LazyInitializationException`이 터지니까 필요한 값만 뽑아서 새로운 단순한 객체로 옮겨 담는 것뿐이고, 호출을 가로채거나 지연시키는 능동적 동작은 없다.
>
> 한 줄 정리: DTO가 "내부 로직을 보호한다"는 표현은 정확하지만, 그 보호 방식은 프록시처럼 "요청을 가로채서 통제"하는 게 아니라 "애초에 내부 구조를 노출하지 않고 별도의 단순한 사본을 만들어 건네주는 것"이다. GoF 디자인 패턴으로 분류하면 Proxy는 호출을 가로채는 구조적 패턴, DTO는 단순 데이터 전달 객체(패턴이라기보다 관례)로 성격이 다르다.

### Q7. SQL과 PostgreSQL의 관계

> **Q.** [정리 노트의 "PostgreSQL에서는 일반적으로..." 문장 관련] SQL이 db에서 사용하는 언어니까 postgreSQL은 SQL의 종류지?
>
> 아니다, 관계가 반대다. PostgreSQL은 SQL의 "종류"가 아니라, SQL이라는 언어를 사용하는 여러 RDBMS(관계형 데이터베이스 관리 시스템) 제품 중 하나다.
>
> - SQL: 관계형 데이터베이스를 다루기 위한 언어(표준) 그 자체. 특정 회사나 제품이 아니라 국제 표준(ANSI/ISO SQL)이다.
> - PostgreSQL, MySQL, Oracle, SQL Server, SQLite, MariaDB 등: 그 SQL 언어를 이해하고 실행해주는 각각의 소프트웨어 제품(DBMS)이다.
>
> 비유: SQL은 "영어"라는 언어이고, PostgreSQL·MySQL·Oracle은 각자 조금씩 다른 억양/사투리로 그 영어를 구사하는 "화자들"이다. 기본 문법(SELECT, INSERT, WHERE...)은 다 공유하지만 제품마다 세부 문법이나 고유 함수가 조금씩 다르다.
>
> 정리 노트에도 이미 힌트가 있었다 — `application.yaml`의 `dialect: org.hibernate.dialect.PostgreSQLDialect` 부분. 여기서 "dialect(방언)"이라는 단어 자체가 "SQL이라는 하나의 언어에 여러 제품별 사투리가 있다"는 것을 보여준다. PostgreSQL이 "SQL의 한 종류"라면 dialect라는 개념 자체가 말이 안 되고, "SQL이라는 큰 언어 안에서 PostgreSQL이 자기만의 사투리(dialect)를 쓴다"고 봐야 정확하다(`GenerationType.IDENTITY` 전략이 PostgreSQL 10+ 에서 쓰이는 것도 이런 제품별 차이의 예시).

### Q8. Java-SQL 타입 매핑에서 dialect의 역할

> **Q.** "방언(dialect)에 따라 실제 SQL 타입은 달라질 수 있다." 이렇게 나와있는데 어떤 SQL 타입이든 JAVA로 바꿔준다는거지?
>
> 방향이 살짝 반대로 이해됐다. "어떤 SQL 타입이든 Java로 바꿔준다"가 아니라, "같은 Java 타입이라도 어떤 DB(dialect)를 쓰느냐에 따라 실제 생성되는 SQL 타입이 달라질 수 있다"는 뜻이다.
>
> 방향은 Java → SQL이다. 정리 노트의 표를 보면 `LocalDateTime`(Java 타입, 고정) → `timestamp`(PostgreSQL에서 생성되는 SQL 타입). "방언에 따라 달라진다"는 건 이 Java → SQL 변환의 "목적지(결과물)"가 DB 제품마다 다르다는 뜻이다. 같은 `LocalDateTime` 필드라도 PostgreSQL이면 `timestamp`로, 다른 DBMS면 이름이나 세부 정의가 다른 타입으로 생성될 수 있다. 즉 출발점(Java 타입)은 고정인데 도착점(실제 SQL 타입 이름)이 방언마다 달라진다.
>
> 정확한 그림: `Java 타입(String, LocalDateTime, int...) → (JPA가 변환, 이때 "어떤 dialect를 쓰느냐"가 변환 규칙을 결정) → DB 제품별 실제 SQL 타입(PostgreSQL의 varchar/timestamp, 다른 DB의 다른 표현...)`.
>
> 참고로 이건 테이블을 생성할 때(DDL)의 방향(Java → SQL)이고, 반대로 데이터를 조회할 때는 SQL 결과(SQL 타입) → Java 객체로 다시 변환되는 과정도 있는데, 이때도 마찬가지로 dialect가 "이 DB의 이 타입을 Java의 어떤 타입으로 읽어들일지"를 결정한다. 두 방향 모두 dialect가 "번역 규칙"을 제공하는 것이지, "SQL 타입을 무조건 Java로 바꿔준다"는 단방향 얘기가 아니다.

> **Q.** 그럼 타입 매핑은 어떻게 결정되는거지? 내가 MySQL을 쓸지 PostgreSQL을 쓸지 어떻게 알아? 의존성에서 나뉘나?
>
> 세 가지 설정이 함께 작동해서 결정된다. 의존성이 관련은 있지만 그게 전부는 아니다.
>
> 1) 의존성(Dependency) — "어떤 DB에 연결할 수 있는 능력"을 결정. `runtimeOnly 'org.postgresql:postgresql'`(PostgreSQL용 JDBC 드라이버) 또는 `runtimeOnly 'com.mysql:mysql-connector-j'`(MySQL용). 이 드라이버가 없으면 애초에 그 DB에 연결 자체가 불가능하다.
>
> 2) `application.yaml`의 접속 정보 — "실제로 어떤 DB에 연결할지" 결정. `spring.datasource.url`(예: `jdbc:postgresql://localhost:5432/menudb`)과 `driver-class-name`(예: `org.postgresql.Driver`)이 "지금 이 순간 실제로 접속할 DB가 PostgreSQL이다"라고 명시한다.
>
> 3) `hibernate.dialect` — "그 DB에 맞는 SQL 문법을 어떻게 생성할지" 결정. `spring.jpa.properties.hibernate.dialect: org.hibernate.dialect.PostgreSQLDialect`가 Q8의 "타입 매핑 규칙"을 결정하는 부분이다. 최신 Hibernate(6.x, Spring Boot 3.x 이상)는 접속된 JDBC 커넥션 정보를 보고 dialect를 자동 감지할 수 있어 이 설정을 생략해도 동작하는 경우가 많지만, 명시적으로 지정해두는 게 안전하고 관례적이다.
>
> 정리: "의존성에서 나뉘나?"는 부분적으로 맞다 — 의존성(드라이버)이 "연결 가능한 DB 종류"를 정하고, `url`/`driver-class-name`이 "실제로 연결할 DB"를 정하고, `dialect`가 "그 DB에 맞는 SQL 타입/문법 변환 규칙"을 정한다. 이 세 가지가 함께 맞아떨어져야 PostgreSQL이든 MySQL이든 제대로 동작한다.

### Q9. "Entity 연관관계 매핑" 섹션이 다루는 대상

> **Q.** [Entity 연관관계 매핑 섹션] 이거 자체가 기본적으로 엔티티랑 테이블의 매핑을 말하는거지?
>
> 살짝 정정이 필요하다. "Entity ↔ 테이블"의 매핑(1개 클래스 ↔ 1개 테이블)은 이미 앞 섹션(`Entity 설계 기초`)에서 다룬 내용이고, "Entity 연관관계 매핑"은 그것과는 다른, 한 단계 더 나아간 개념이다.
>
> | | Entity 설계 기초 | Entity 연관관계 매핑 |
> | --- | --- | --- |
> | 다루는 대상 | 엔티티 1개 ↔ 테이블 1개 | 엔티티와 엔티티 사이의 관계(= 테이블과 테이블 사이의 외래키 관계) |
> | 핵심 어노테이션 | `@Entity`, `@Table`, `@Id`, `@Column` | `@ManyToOne`, `@OneToMany`, `@JoinColumn`, `mappedBy` |
> | 예시 | `Menu` 클래스 → `menus` 테이블(각 필드 → 각 컬럼) | `Menu`가 `Category`를 참조 → `menus.category_id`라는 외래키(FK)로 연결 |
>
> - Entity 설계 기초: "`Menu`라는 자바 클래스 하나를 `menus`라는 테이블 하나에 어떻게 매핑할까?"(필드 하나하나를 컬럼에 매핑)
> - Entity 연관관계 매핑: "`Menu`와 `Category`처럼 서로 다른 엔티티(=테이블) 두 개가 서로를 참조할 때, 그 관계를 자바 필드(`private Category category;`)로 어떻게 표현하고 그게 DB의 외래키로 어떻게 연결되는가?"
>
> 즉 "연관관계 매핑"은 "엔티티 하나를 테이블 하나로 바꾸는 것"이 아니라, "엔티티들 사이의 관계(참조)를 테이블들 사이의 관계(외래키)로 어떻게 표현하는가"를 다루는 것이다. `Menu.category` 필드에 `@ManyToOne @JoinColumn(name = "category_id")`를 붙이는 예시가 이를 보여준다 — 자바 객체의 "참조(reference)"가 DB의 "외래키(FK)"로 번역되는 과정이다.

> **Q.** 기본 개념부터 차근차근해야할거 같은데, 일단 내가 지금 이해한건 엔티티 연관관계 매핑 이라는게 엔티티랑 엔티티 사이의 매핑을 다루는거고 이게 다중성을 띌 수 있다? 그리고 엔티티를 참조할때는 외래키가 필요하다는거만 이해했어
>
> 세 가지 모두 맞다. 이어서 나머지 핵심 개념(방향성, 연관관계의 주인)을 순서대로 붙인다.
>
> **개념 ① 다중성 구체화**: "다중성을 띈다"는 관계를 맺는 두 엔티티가 각각 몇 개씩 연결되는지를 말하며 4가지뿐이다.
>
> | 관계 | 뜻 | 예시 |
> | --- | --- | --- |
> | 1:1 | 서로 딱 하나씩 | 주문 1개 ↔ 결제 1건 |
> | 1:N | 하나가 여러 개를 가짐 | 카테고리 1개 ↔ 메뉴 여러 개 |
> | N:1 | 여러 개가 하나를 가리킴 | 메뉴 여러 개 ↔ 카테고리 1개 |
> | N:M | 서로 여러 개씩 | 메뉴 N개 ↔ 알레르기정보 N개 |
>
> 카테고리-메뉴 예시에서 "카테고리 입장에서는 1:N", "메뉴 입장에서는 N:1"인데, 이는 같은 관계를 어느 쪽에서 바라보느냐의 차이일 뿐 결국 하나의 관계다.
>
> **개념 ② 외래키를 자바 코드로 표현**: `@ManyToOne @JoinColumn(name = "category_id") private Category category;`처럼 Menu 쪽에 필드를 선언하면 "menus 테이블에 category_id라는 외래키 컬럼을 만들어라"는 뜻이 된다. 즉 DB의 외래키 = 자바 클래스의 참조 필드(`private Category category`)로 표현된다.
>
> **개념 ③(새로 추가) 방향성(단방향 vs 양방향)**: Menu가 Category를 필드로 갖고 있으면 `Menu → Category` 방향으로만 참조 가능하다(단방향). 반대로 Category에서도 `@OneToMany(mappedBy = "category") private List<Menu> menus;`를 추가하면 양쪽이 서로 참조하는 양방향이 된다. 양쪽 다 필드를 가지면, DB의 외래키 컬럼(category_id)을 실제로 어느 쪽 코드가 책임지고 관리하는지(연관관계의 주인)를 정해야 하는 다음 문제로 자연스럽게 이어진다.

> **Q.** 일단 외래키 개념부터. 내가 이해하기론 a가 b를 참조할려면 a가 b의 외래키를 컬럼으로 만들어야된다는거지?
>
> 핵심은 맞지만 표현을 정확히 다듬어야 한다. 정확한 표현: "A가 B를 참조하려면, A의 테이블에 B의 기본키(PK)를 가리키는 외래키 컬럼을 만들어야 한다."
>
> "B의 외래키"라는 표현이 헷갈릴 수 있다 — 외래키 컬럼은 B가 아니라 A의 테이블에 생긴다. 다만 그 컬럼 안에 들어가는 값은 B의 기본키(PK) 값이다.
>
> 구체적 예시: `@ManyToOne @JoinColumn(name = "category_id") private Category category;`에서 Menu(A)가 Category(B)를 참조할 때, 외래키 컬럼(`category_id`)이 생기는 곳은 `menus` 테이블(A, 참조하는 쪽에 생김)이고, 그 컬럼에 저장되는 값은 `categories` 테이블(B, 참조당하는 쪽)의 `id` 값이다. `categories` 테이블(B)에는 외래키 컬럼이 생기지 않는다.
>
> 정리: "A가 B를 참조" = A 테이블에 "B를 가리키는" 외래키 컬럼을 만들고, 그 컬럼 값으로 B의 PK를 저장하는 것. "B의 외래키를 만든다"보다는 "A에, B를 향한 외래키를 만든다"가 더 정확한 표현이다.

> **Q.** 양방향 관계에서는 A B가 서로의 외래키를 칼럼으로 추가한건가?
>
> 아니다. 양방향이어도 실제 DB에 외래키 컬럼이 생기는 건 한쪽뿐이다. 이게 바로 "연관관계의 주인" 개념이다.
>
> 예시: `@ManyToOne @JoinColumn(name = "category_id") private Category category;`(Menu 쪽, 외래키 컬럼을 실제로 만드는 "주인")과 `@OneToMany(mappedBy = "category") private List<Menu> menus;`(Category 쪽, 조회 편의용, 실제 컬럼은 안 만듦). 결과적으로 `menus` 테이블에는 `category_id` 컬럼이 생기지만, `categories` 테이블에는 메뉴 관련 컬럼이 전혀 생기지 않는다.
>
> Category의 `List<Menu> menus`는 DB에 저장되는 실제 데이터가 아니라 JPA가 자바 객체 레벨에서만 만들어주는 가상의 편의 기능이다. `category.getMenus()`를 호출하면 JPA가 내부적으로 `SELECT * FROM menus WHERE category_id = ?` 쿼리를 대신 날려서 결과를 `List<Menu>`로 채워주는 것뿐이고, `categories` 테이블 자체에는 그 정보를 저장할 컬럼이 없다.
>
> 정리: 연관관계의 주인(`@JoinColumn`을 가진 쪽, 여기선 Menu)은 실제 외래키 컬럼을 만들고 관리하는 쪽이고, 주인이 아닌 쪽(`mappedBy`를 가진 쪽, 여기선 Category)은 컬럼은 안 만들고 반대 방향 조회만 가능하게 해주는 쪽이다. "A와 B가 서로의 외래키를 컬럼으로 추가한다"가 아니라 "둘 중 하나만 진짜 외래키 컬럼을 갖고, 나머지 하나는 그 컬럼을 거꾸로 조회하는 기능만 가진다"가 정확하다.

> **Q.** "@ManyToOne: 가장 흔한 관계(N:1)" 그럼 이 경우에는 a가 b c의 외래키를 가지고 있는경우?
>
> N:1이 뜻하는 바를 살짝 다르게 이해했다. "A가 B와 C의 외래키를 둘 다 가지고 있는 경우"는 N:1 관계 하나가 아니라, 완전히 독립된 N:1 관계가 두 개 있는 것이다.
>
> N:1에서 N과 1이 가리키는 건 "엔티티 종류 개수"가 아니라 "행(row)의 개수"다. `@ManyToOne @JoinColumn(name = "category_id") private Category category;`에서 N(여러 개)은 "Menu라는 같은 종류의 엔티티가 여러 행(row) 있다"는 뜻이고, 1(하나)은 "그 여러 Menu 행들이 결국 Category라는 같은 엔티티의 한 행을 가리킨다"는 뜻이다(`Menu(id=1,category_id=1)`, `Menu(id=2,category_id=1)`, `Menu(id=3,category_id=1)` 전부 `Category(id=1)` 하나를 가리키는 구조). 즉 N:1은 "한 엔티티의 여러 행이 다른 한 엔티티의 한 행을 참조"하는 것이지, "한 엔티티가 서로 다른 두 종류의 엔티티(B, C)를 참조"하는 게 아니다.
>
> 만약 A가 진짜로 B와 C 둘 다 참조하고 싶다면, 그건 가능하지만 N:1 관계 하나가 아니라 N:1 관계 두 개가 된다. 예: `Order`가 `Customer`와 `ShippingAddress`를 둘 다 참조하면, `@ManyToOne @JoinColumn(name="customer_id") private Customer customer;`(Order→Customer 방향의 N:1 관계 1)와 `@ManyToOne @JoinColumn(name="shipping_address_id") private ShippingAddress address;`(Order→ShippingAddress 방향의 N:1 관계 2)로, `orders` 테이블에 외래키 컬럼이 두 개(`customer_id`, `shipping_address_id`) 생기지만 이는 서로 독립적인 두 개의 N:1 관계다. 각각의 `@ManyToOne`은 항상 "하나의 대상 엔티티"만 가리킨다.

> **Q.** 그러니까 N이 말하는게 엔티티 내부적으로 가지고 있는 행의 수 라는거지? 그러면 a(행 3개)가 b(행1개)의 외래키를 가지고 있으면 이건 N:1이라는거지?
>
> 중요한 오해가 있다. N:1은 "지금 이 순간 테이블에 실제로 몇 개 행이 들어있나"를 세는 게 아니다. "여러 개의 A 행이 같은 B 행 하나를 가리키는 것이 구조적으로 허용되는가"를 말하는 것 — 데이터의 스냅샷(현재 몇 개 들어있는지)이 아니라 관계의 설계 규칙(구조)이다.
>
> `Category` 테이블에 지금 딱 1개의 행만 있어도, 그건 우연히 지금 데이터가 1개인 것뿐이지 관계의 종류를 결정하는 게 아니다. 내일 카테고리를 5개 더 추가해도 관계의 종류(N:1)는 그대로다. N:1을 결정하는 건 "여러 개의 Menu가 같은 Category 하나를 공유하는 게 구조적으로 허용되는가"다.
>
> 진짜 기준은 외래키 컬럼에 UNIQUE 제약이 있는가 없는가다.
>
> - N:1 예(`menus.category_id`에 UNIQUE 제약 없음): 여러 메뉴가 같은 `category_id` 값을 가질 수 있음(허용됨). `(1,'김치찌개',1)`, `(2,'된장찌개',1)`처럼 category_id=1이 중복돼도 괜찮다.
> - 반대로 1:1 예(예: `payments.order_id`에 UNIQUE 제약 있음): 같은 `order_id`를 두 개의 payment 행이 가질 수 없다(구조적으로 막혀있음).
>
> 두 예시 모두 "A쪽 행이 3개, B쪽 행이 1개"인 경우가 우연히 생길 수 있지만, N:1인지 1:1인지는 행 개수가 아니라 "중복이 허용되는가(UNIQUE 제약의 유무)"로 결정된다.
>
> 정정된 정의: N:1은 "A의 외래키 컬럼에 같은 B 값이 여러 번 나올 수 있도록(중복 허용) 설계되어 있어서, 여러 A 행이 같은 B 행 하나를 공유할 수 있는 구조"를 말한다. 지금 실제로 몇 개의 행이 들어있는지는 무관하다.

> **Q.** menu 엔티티가 있어 category 엔티티의 외래키를 가지고 있어. 그럼 menu가 category를 참조할 수 있잖아? 이상태에서 category에 있는 id를 중복으로 사용하게 N:1이라는거라고?
>
> 맞다. "Category의 id를 여러 Menu 행이 중복으로(=재사용해서) 참조할 수 있는 상태"가 바로 N:1이다.
>
> 예: `Category(id=1, name='찌개류')` 하나에 대해 `Menu(id=1, category_id=1)`, `Menu(id=2, category_id=1)`, `Menu(id=3, category_id=1)`처럼 `category_id=1`이라는 값이 여러 Menu 행에서 반복(중복) 사용된다. 이게 가능한 이유는 `menus.category_id` 컬럼에 UNIQUE 제약이 없기 때문이다(DB가 "이 값 또 써도 돼"라고 허락). 그래서 "여러(N) 개의 Menu가 하나(1)의 Category를 공유(중복 참조)할 수 있다" → N:1.
>
> 대조로 `menus.category_id`에 UNIQUE 제약을 걸면, category_id=1을 이미 Menu(id=1)이 썼으면 Menu(id=2)는 절대 그 값을 또 쓸 수 없게 되어 "하나의 Category당 딱 하나의 Menu만 연결 가능"해지고, 이건 N:1이 아니라 1:1이 된다.
>
> 결론: "외래키 값(Category의 id)을 여러 참조하는 쪽(Menu) 행이 중복해서 쓸 수 있게 허용된 상태"가 N:1이라는 이해가 정확하다.

> **Q.** 위 예시에서 unique 제약설정해서 1:1까지 이해했어. 그러면 N:M은 어떻게 생기는거지? 서로를 참조하는건 오류잖아? 그러면 추측건데 A에 있는 n개의 카테고리에 b의 id를 m개 참조하는거야?
>
> "서로 참조가 문제"라는 직관은 맞는 방향이다. 외래키 컬럼 하나는 딱 하나의 값만 저장할 수 있는데, N:M은 "A 하나가 여러 B를 가질 수 있고, B 하나도 여러 A에 속할 수 있는" 관계다. Menu에 allergy_id 컬럼을 하나 추가하면 그 메뉴는 알레르기 정보 하나밖에 못 가지고(컬럼 하나=값 하나), Allergy에 menu_id를 추가해도 반대로 같은 문제가 생긴다. 그래서 N:M은 A나 B 어느 쪽에도 직접 외래키를 추가하는 방식으로는 표현이 안 된다. ("A n개가 B의 id를 m개 참조"처럼 한 컬럼에 여러 id를 몰아넣는 방식은 DB에서 불가능하다.)
>
> 실제 해법은 A와 B 사이에 제3의 **중간 테이블(Join Table)**을 만들고, 그 테이블이 A와 B를 각각 N:1로 참조하게 만드는 것이다.
>
> 예: `Menu`, `menu_allergy`(중간 테이블: menu_id, allergy_id), `Allergy`. `menu_allergy`의 한 행 = "이 메뉴에 이 알레르기 정보가 있다"는 하나의 조합. `menu_id=1`(김치찌개)이 여러 행(`menu_id=1,allergy_id=1`과 `menu_id=1,allergy_id=2`)에 걸쳐 중복 등장하면 김치찌개가 여러 알레르기를 가질 수 있고(N:1: 중간테이블→Menu), `allergy_id=1`(갑각류)도 여러 행에 걸쳐 중복 등장하면 갑각류가 여러 메뉴에 속할 수 있다(N:1: 중간테이블→Allergy).
>
> 즉 N:M은 "N:1 관계 두 개를 중간 테이블로 이어붙인 것"이다. 중간 테이블 자체는 A와도 N:1, B와도 N:1 관계를 맺고 있고, 그 두 개가 합쳐져서 결과적으로 "A와 B가 N:M"처럼 보이는 것이다. 정리 노트에서 `@ManyToMany`를 실무에서 잘 안 쓰고, 이 중간 테이블을 아예 엔티티(`OrderCoffee` 같은)로 직접 만들어서 N:1 + 1:N으로 푸는 방식을 권장한다고 한 것이 바로 이 원리다.

> **Q.** (글로 보니까 하나도 이해가 안 된다는 반응에 이어) 학생-수업 예시로 다시 설명. 그러니까 다시 정리를 하면 엔티티가 기본적으로 하나의 값만 가지니까 한 값에 2개를 쓸려면 추가적인 엔티티를 만들어서 각 엔티티에 어떤 값을 넣을지 정하는 엔티티를 추가해서 한 값이 각각 1개의 값을 가진 결과를 2개 만들어낸다고?
>
> 맞다. 정리한 논리 그대로다.
>
> 1. 한 컬럼(값)은 딱 하나의 값만 담을 수 있다(컬럼 하나 = 값 하나 원칙)
> 2. "철수 → [수학, 영어]"처럼 하나가 여러 값을 가지려는 상황이 생긴다
> 3. 이걸 해결하려고 중간에 새로운 표(엔티티)를 하나 추가한다
> 4. 그 표는 "철수-수학", "철수-영어"처럼 한 줄에 딱 한 쌍(조합)만 적어서, 여러 줄로 나눠 표현한다
>
> 즉 "하나의 칸에 여러 값을 억지로 넣는 것"을 "한 줄에 값 하나씩만 있는 여러 줄"로 쪼개서 풀어낸 것이다.
>
> | 학생 | 수업 |
> | --- | --- |
> | 철수 | 수학 |
> | 철수 | 영어 |
> | 영희 | 수학 |
>
> "철수가 2과목 듣는다"는 하나의 사실이 위 표에서는 "철수"가 등장하는 줄이 2개로 표현된다. 한 줄 안에서는 항상 "학생 1명 + 수업 1개"라는 1:1 짝만 있고, 그 짝을 여러 줄 반복해서 "여러 개를 가진다"는 걸 흉내 내는 것이다.
>
> 이 "중간 표"가 바로 앞서 말한 "중간 테이블(Join Table)/중간 엔티티"다. 이 표는 학생 쪽으로도, 수업 쪽으로도 각각 N:1 관계를 맺고 있고, 그 둘이 합쳐진 결과가 N:M이라고 부르는 것이다.
