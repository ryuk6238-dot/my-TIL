# 객체지향 프로그래밍의 이해 — Q&A

### Q1. OOP(객체지향 프로그래밍)란 무엇인가

> **Q.** oop가 뭐야?
>
> OOP(객체지향 프로그래밍)는 프로그램을 절차(함수 흐름) 중심이 아니라, 상태(필드)와 행동(메서드)을 함께 가진 독립적인 **객체(Object)**들이 서로 메시지를 주고받으며 협력하는 방식으로 만드는 프로그래밍 패러다임이다. 객체는 **클래스**라는 설계도로부터 만들어진다.
>
> 절차지향이 "이 기능을 어떻게 구현할까?"를 묻는다면, 객체지향은 "누가 이 책임을 맡아야 하지?"를 묻는다. 즉 기능 중심이 아니라 **책임 중심 사고**다.
>
> 예를 들어 학생 성적 관리 프로그램에서, 절차지향은 이름·점수 배열을 두고 for문을 돌리지만, 객체지향은 `Student` 클래스를 만들어 각 학생을 객체로 다룬다. 새로운 과목이 추가되면 절차지향은 배열과 반복문 로직을 모두 고쳐야 하지만, 객체지향은 `Student` 클래스에 필드 하나를 추가하고 `getAverage()`만 수정하면 모든 객체에 자동 반영된다. 이것이 OOP가 유지보수와 확장에 유리한 이유다.

### Q2. static의 정확한 의미

> **Q.** static 이 정적 메소드? 이렇게 배운걸로 기억하는데 맞아?
>
> 절반만 맞다. `static`은 메소드뿐 아니라 필드, 초기화 블록, 중첩 클래스에도 붙일 수 있는 키워드이며, 핵심은 "메소드/필드가 인스턴스가 아니라 클래스 자체에 속한다"는 것이다. 클래스가 메모리에 로드될 때 메소드 영역에 단 한 번 만들어지고, 그 클래스로 생성되는 모든 인스턴스가 이를 공유한다. 그래서 인스턴스를 만들지 않아도 `클래스이름.메소드()`로 바로 호출할 수 있고, static 메소드 내부에서는 `this`가 없어 인스턴스 필드/메소드에 접근할 수 없다.
>
> **Q.** 맞다면 정확히 이게 뭘 의미하는거지? '동적'의 반대 의미니까 static으로 선언된건 메소드가 변하지않는다는 의미인가?
>
> 아니다. "값이 변하지 않는다"는 뜻이 아니다. 예를 들어 `public static double VAT_RATE = 0.1;`처럼 static 필드도 `final`이 붙어 있지 않으면 얼마든지 값이 바뀔 수 있다. 불변으로 만들고 싶으면 `static final`처럼 `final`을 별도로 붙여야 한다.
>
> '정적'이 정확히 반대하는 개념은 "동적 바인딩(dynamic binding)"의 반대인 **정적 바인딩(static binding)**이다. 일반(인스턴스) 메소드는 오버라이딩이 가능해서 실제 어떤 클래스의 구현이 실행될지 런타임에 결정되지만(동적 바인딩), static 메소드는 오버라이딩 대상이 아니라서 컴파일 시점에 이미 어떤 메소드를 호출할지 고정된다. 즉 "정적"은 "실행 중에 변하지 않는 값"이 아니라 "클래스 레벨에 고정되어 있고, 호출 대상이 컴파일 타임에 확정된다"는 의미로 이해해야 한다.

> **Q.** 음 그러니까 인스턴스는 new할때 마다 새로운 인스턴스를 만들어내지만 static으로 선언해두면 컴파일 시점에서 같은 메서드 중에서는 1개의 인스턴스만 취한다는거지?
>
> 두 가지가 섞여 있다. 첫째, static 멤버가 만들어지는 시점은 "컴파일 시점"이 아니라 "**클래스 로딩 시점**"이다(클래스가 처음 사용되어 JVM에 로드될 때, 즉 런타임의 한 시점). 컴파일 시점에 정해지는 것은 메모리 생성이 아니라 "이 메소드 호출이 정적 바인딩이냐 동적 바인딩이냐"라는 *호출 방식의 결정*이며, 이는 별개의 개념이다.
>
> 둘째, "같은 메서드 중에서 1개의 인스턴스만 취한다"는 표현이 핵심 오해다. static은 "여러 인스턴스 중 하나를 대표로 고르는 것"이 아니라, 애초에 **인스턴스와 무관한 것**이다. 인스턴스 필드/메소드는 `new`로 객체를 만들 때마다 그 개수만큼 힙에 복제되어 생기지만(0개 만들면 0개 존재), static 필드/메소드는 인스턴스를 몇 개 만들든, 심지어 하나도 만들지 않아도 클래스가 로드되는 순간 이미 존재한다. 즉 `Order.VAT_RATE`는 `order1`, `order2` 같은 인스턴스가 생기기 전에도 이미 존재할 수 있고, `order1.VAT_RATE`처럼 인스턴스를 통해 접근해도 실제로는 인스턴스가 가진 값이 아니라 클래스가 가진 값 하나를 빌려서 보는 것뿐이다.

> **Q.** 음 그러니까 static이 클래스 로딩 시점에서 여러 인스턴스가 있어서 상관없이 공통된 1개의 메서드를 가져온다?
>
> 거의 맞다. "가져온다"보다는 "이미 그렇게 존재한다"가 더 정확한 표현이다. static 멤버는 인스턴스가 몇 개든(심지어 0개든) 클래스 로딩 시점에 이미 딱 1개만 만들어져서 존재하고 있고, 인스턴스들은 그 존재하는 것을 그냥 같이 바라보는(공유하는) 것이지, 어딘가에서 "가져오는" 능동적 동작이 있는 것은 아니다.
>
> 정리하면: 인스턴스 필드/메소드는 `new` 할 때마다 힙에 새로 찍혀 나와 인스턴스 개수만큼 여러 벌 존재하지만, static 필드/메소드는 클래스 로딩 시점에 메소드 영역에 미리 1벌만 만들어져서 인스턴스가 몇 개든(0개여도) 상관없이 그 1벌을 공통으로 공유한다.

> **Q.** 그럼 이어서 그렇게 미리 만들어진 메서드를 사용하게 되면 여러개 만들어져있는 인스턴스들은 의존관계가 없으니까 GC가 자동으로 삭제시켜주는거야?
>
> 아니다, 그 연결은 잘못됐다. GC는 "static과 관련 있냐 없냐"로 판단하는 게 아니라, 각 인스턴스가 어딘가에서 여전히 참조되고 있는지(도달 가능성, reachability)로만 판단한다.
>
> GC는 GC 루트(스택의 지역변수, static 필드, 실행 중인 스레드 등)에서 출발해 참조를 따라갔을 때 도달 가능한 객체는 살아있다고 마킹하고, 도달 불가능한 객체만 회수한다. `order1`, `order2`, `order3`이 각각 static 메소드를 호출한다고 해서 그 인스턴스와 static 멤버 사이에 의존 관계가 생기거나 없어지는 것이 아니다. `order1.someStaticMethod()`처럼 인스턴스를 통해 static 메소드를 호출해도 `order1` 변수는 여전히 그 인스턴스를 가리키고 있고, 그 변수가 스코프 안에 살아있는 한 GC 대상이 되지 않는다.
>
> 오히려 반대에 가까운 경우가 있다. 앞서 정리한 메모리 누수 원인 중 하나가 "static 필드로 인한 참조"였는데, static 필드는 그 자체가 GC 루트 역할을 하기 때문에 어떤 객체를 static 필드에 담아두면 그 클래스가 언로드되기 전까지 절대 GC되지 않는다. 즉 static은 GC를 유발하는 쪽이 아니라, 잘못 쓰면 오히려 GC를 막아 메모리 누수를 일으키는 쪽에 더 가깝다.
>
> 정리: 인스턴스가 GC되는지 여부는 static 메소드 사용 여부와는 무관하고, 순전히 그 인스턴스를 가리키는 살아있는 참조가 남아있는지로 결정된다.

### Q3. 힙(Heap)은 메모리 영역인가, 인스턴스 자체인가

> **Q.** 힙(Heap)이라는게 new로 생성된 인스턴스들을 저장하는 메모리를 지칭하는거야?, 아니면 jvm에 저장된 인스턴스 자체를 지칭하는거야?
>
> 힙은 "메모리 영역(공간)"을 가리키는 말이다. 인스턴스 자체를 부르는 이름이 아니라, `new`로 생성된 인스턴스들이 저장되는 공간이 힙이다.
>
> 비유하면 힙은 창고(공간)이고, 인스턴스(객체)는 그 창고 안에 놓인 물건이다. `Student s = new Student();`를 실행하면, JVM이 힙(창고) 안에 `Student` 객체 하나가 들어갈 자리를 마련해 실제 데이터(필드 값들)를 채우고(이것이 "인스턴스가 힙에 생성된다"는 말의 의미), 그 자리의 주소(참조값)를 `s`라는 변수에 담아 스택(Stack)에 저장한다.
>
> 그래서 "힙에 인스턴스가 있다"라고 할 때, 힙은 그 인스턴스를 담고 있는 메모리 공간을 뜻하고 인스턴스(객체)는 그 공간 안에 실제로 채워진 데이터 덩어리를 뜻한다. `new`할 때마다 같은 힙이라는 공간 안 서로 다른 위치에 여러 인스턴스가 계속 쌓이며, GC는 이 힙이라는 공간을 뒤져 더 이상 참조되지 않는 인스턴스(물건)를 치워주는 역할을 한다.

### Q4. MapStruct가 setter를 대체할 수 있는가

> **Q.** 필드는 private + getter/setter로 접근 이 부분 나중에 mapstructer로 대체 setter를 대체 가능한거 아닌가?
>
> "대체"라기보다 역할이 다른 것에 가깝다. JavaBean 규약(getter/setter)은 하나의 클래스가 자기 자신의 필드를 어떻게 외부에 공개하느냐에 대한 캡슐화 규칙이고, MapStruct는 서로 다른 두 객체(예: Entity ↔ DTO) 간에 값을 옮겨 담는 매핑 코드를 컴파일 시점에 자동 생성해주는 라이브러리로, 층위가 다르다.
>
> MapStruct가 매핑을 하려면 결국 대상(target) 객체에 값을 넣을 방법이 필요한데, 보통 setter(`target.setName(value)`, 대상이 mutable이면 기본 사용), 생성자(all-args constructor), 빌더(Builder) 중 하나를 쓴다. 즉 MapStruct는 `target.setName(source.getName())` 같은 반복 매핑 코드를 직접 안 써도 되게 자동 생성해주는 것이지, setter라는 개념 자체를 없애주는 것은 아니다. 대상 클래스가 여전히 mutable하고 setter를 갖고 있다면 MapStruct는 내부적으로 그 setter를 호출한다.
>
> 다만 DTO/엔티티를 `private final` 필드 + 생성자(또는 `@Builder`)로만 설계하면, MapStruct가 setter 없이 생성자나 빌더를 통해 매핑해줄 수 있다. 정리하면 MapStruct는 setter 호출 코드를 손으로 안 써도 되게 해주는 도구이고, setter 개념 자체를 대체하려면 대상 클래스를 불변(생성자/빌더 기반)으로 설계해야 한다 — "MapStruct + 불변 객체 설계"의 조합이 setter를 실질적으로 안 쓰게 만드는 방법이지, MapStruct 혼자만으로 setter가 사라지는 것은 아니다.
>
> **Q.** 다시 정리해보면 mapstructer 내부적으로 setter가 동작한다가 맞는말이겠네?
>
> 조건부로만 맞다. "MapStruct는 항상 내부적으로 setter를 쓴다"는 틀렸고, 정확히는 "대상 클래스가 setter를 갖춘 mutable 클래스일 때만 그 setter를 호출한다"가 맞는 표현이다.
>
> MapStruct는 대상 클래스를 보고 가능한 방법 중 하나를 골라 매핑 코드를 생성한다: 대상 클래스에 setter가 있으면 `target.setName(source.getName())`처럼 setter를 호출하는 코드를, all-args 생성자만 있고 setter가 없으면 `new Target(source.getName(), ...)`처럼 생성자를 호출하는 코드를, 빌더(`@Builder`)를 쓰면 `Target.builder().name(source.getName()).build()`처럼 빌더 체이닝 코드를 생성한다. 즉 setter 호출은 MapStruct의 고정된 동작 방식이 아니라 대상 클래스의 설계에 MapStruct가 맞춰주는 것이며, 대상 클래스를 불변(생성자/빌더)으로 설계하면 그 경우엔 setter가 아예 호출되지 않는다.

### Q5. @FunctionalInterface와 람다의 관계

> **Q.** @FunctionalInterface 이걸 직접 써본적이 없는게 설명대로면 interface로 여러 메서드를 정의할게 아니면 람다식을 활용해 1개 메서드만 간단하게 정의할수 있게해주는 건가?
>
> 거의 맞지만 한 가지를 짚어야 한다: `@FunctionalInterface`가 "람다를 쓸 수 있게 해주는" 것이 아니다. 람다를 쓸 수 있는 조건은 오직 "추상 메소드가 정확히 1개인 인터페이스"라는 것 하나뿐이며, 어노테이션을 안 붙여도 추상 메소드가 1개면 이미 람다로 구현할 수 있다.
>
> `@FunctionalInterface`는 컴파일러에게 "이 인터페이스는 추상 메소드가 1개여야 한다"고 검증을 부탁하는 안전장치일 뿐이다. 나중에 누가 실수로 추상 메소드를 하나 더 추가하면 그 순간 컴파일 에러가 발생해 람다 계약이 깨졌음을 바로 알려준다. 즉 문서화 + 실수 방지 목적이며, 없어도 동작 자체에는 지장이 없다.
>
> "여러 메서드를 정의할게 아니면"이라는 표현도 다듬으면: 인터페이스 안에 `default`/`static` 메소드는 몇 개든 있어도 상관없고, 오직 추상 메소드(구현부 없는 메소드)가 딱 1개여야 한다는 조건만 지키면 된다. 정리하면, 추상 메소드가 1개인 인터페이스는 익명 클래스로 장황하게 구현하지 않고 람다식으로 간결하게 구현할 수 있으며, `@FunctionalInterface`는 그 '1개' 조건이 앞으로도 깨지지 않도록 컴파일러가 지켜주는 표식일 뿐이다.

> **Q.** 근데 경험상 이렇게 추상 메서드를 하나만 구분할 경우가 많지도 않았고 1개만 딱 필요로 하는경우도 없었거든 차라리 서비스 메서스 내부에서 추가하지 @FunctionalInterface를 사용하는 특별한 목적이 있나?, 단순히 람다식의 조건을 지켜주는 목적이야?
>
> 정확한 통찰이다. `@FunctionalInterface`/람다의 진짜 목적은 "추상 메소드 1개 조건을 지키는 것" 자체가 아니라, 그 조건 덕분에 "동작(로직)을 데이터처럼 파라미터로 넘길 수 있게 되는 것"이다. 서비스 클래스 안에 메소드를 하나 추가하면 그 로직은 컴파일 시점에 고정되어 항상 똑같이 실행되지만, 함수형 인터페이스를 파라미터 타입으로 받으면 호출하는 쪽에서 그때그때 다른 로직을 끼워 넣을 수 있다 — 즉 메소드가 필요로 하는 동작 자체를 외부에서 주입하는 것이며, 이는 전략 패턴(Strategy Pattern)을 클래스 계층 없이 간단하게 구현하는 방법이다.
>
> 예를 들어 `list.sort(Comparator.comparing(Student::getScore))`나 `list.stream().filter(s -> s.getScore() > 80)`처럼, `sort()`나 `filter()`는 "정렬한다"/"거른다"는 알고리즘 자체는 고정돼 있지만 어떤 기준으로 할지는 매번 달라져야 한다. 이를 서비스 메소드 안에 직접 넣으면 기준이 바뀔 때마다 오버로딩이나 if문을 계속 늘려야 하지만, 함수형 인터페이스로 받으면 호출부가 원하는 로직을 그 자리에서 람다로 던져주면 된다.
>
> "직접 정의할 일이 별로 없었다"는 경험도 자연스럽다. 이미 JDK가 범용 함수형 인터페이스(`Function<T,R>`, `Predicate<T>`, `Consumer<T>`, `Supplier<T>`, `Comparator<T>`, `Runnable` 등)를 `java.util.function`에 만들어 놨기 때문에, 실무에서는 새 함수형 인터페이스를 직접 정의하기보다 이미 있는 함수형 인터페이스를 매개변수로 받는 메소드(Stream API, `Comparator.comparing`, Spring의 `JdbcTemplate.query(sql, rowMapper)`, `TransactionTemplate.execute(status -> {...})` 등)를 쓰는 경우가 훨씬 흔하다. 즉 이미 이 패턴을 계속 사용해왔을 가능성이 크고, 다만 그것이 "함수형 인터페이스를 구현하는 람다"라는 것을 의식하지 못했을 뿐이다.
>
> 정리: `@FunctionalInterface`의 형식적 역할은 "1개 조건 강제"가 맞지만, 그 조건이 존재하는 진짜 이유는 "메소드가 실행할 로직을 호출자가 원하는 대로 갈아 끼울 수 있게(파라미터화) 하려는 것"이다. 로직이 항상 고정이면 서비스 메소드 안에 그냥 넣는 것이 맞고, 로직이 호출부마다 달라져야 하면 함수형 인터페이스 파라미터가 필요하다.

### Q6. this() 생성자 체이닝을 @Builder로 생략할 수 있는가

> **Q.** this()를 통한 생성자 간 호출이 가능하다. 이걸 @build로 생략 가능한거였나?
>
> `@Builder`(Lombok)가 `this()` 자체를 없애주는 것이 아니라, `this()`로 여러 생성자를 체이닝해야 했던 상황 자체를 만들지 않게 해주는 것에 가깝다.
>
> 기존 방식은 파라미터 조합마다 생성자를 늘리고, 중복 초기화를 피하려고 `this()`로 서로 연결한다(예: `Order()` → `this("NONE", new ArrayList<>())`, `Order(orderId)` → `this(orderId, new ArrayList<>())`). 이렇게 필드 조합이 늘어날 때마다 생성자를 계속 오버로딩하는 것을 **텔레스코핑 생성자(telescoping constructor) 문제**라고 부르며, 필드가 늘어나면 조합이 기하급수적으로 늘어나 관리가 힘들어진다.
>
> `@Builder`를 적용하면 생성자를 여러 개 만들고 `this()`로 엮을 필요 없이, 딱 하나의(보통 all-args) 생성자를 Lombok이 내부적으로 만들고 필요한 필드만 골라 체이닝으로 채우면 된다(`@Builder.Default`로 기본값 지정, `Order.builder().orderId("ORD001").build()`처럼 필요한 필드만 설정). 즉 `@Builder`는 "`this()` 문법을 생략해주는 기능"이 아니라 "애초에 여러 생성자 조합을 오버로딩할 필요 자체를 없애는 다른 생성 패턴(빌더 패턴)"이다.
>
> 정리: 파라미터 조합에 따라 생성 로직이 완전히 달라야 하는 경우(단순 기본값 설정이 아닌 경우)는 `@Builder`만으로 부족해 여전히 커스텀 생성자 + `this()`가 필요할 수 있지만, 대부분의 "선택적 필드/기본값" 상황에서는 `@Builder`가 그 자리를 대체한다.

### Q7. 다형성의 "런타임 결정"이 실제로 무엇을 가리키는가

> **Q.** 하나의 타입(인터페이스)에 대해 여러 구현을 연결할 수 있는 능력. 실제 실행될 메소드는 런타임에 결정된다(동적 바인딩). 이거 좀 의문인데? 예를 들어 CRUD를 인터페이스로 구현해놨어 이걸 상속 받은 service 메서드는 상속 받아올때 interface의 어떤 메서드를 가져오는지 명시를 해놔야하잖아. 근데 여기 설명은 '실제 실행될 메소드는 런타임에 결정'이라는 말은 안맞는말 아닌가? 내가 이미 인터페이스에서 내가 쓸 메서드를 결정해서 service에 사용을 한거잖아?
>
> "어떤 메서드를 호출할지"와 "그 메서드의 어떤 구현(몸체)이 실행될지"는 서로 다른 두 가지 결정이며, 이 둘을 구분해야 한다.
>
> 1) 어떤 메서드를 호출할지는 컴파일 타임에 결정된다. `CrudRepository` 인터페이스에 `save()`가 있다는 것을 보고 `repo.save(entity);`라고 코드에 적으면, 컴파일러는 "`repo`의 선언된 타입(`CrudRepository`)에 `save()`라는 시그니처가 있는가"만 확인한다. "이미 인터페이스에서 쓸 메서드를 결정했다"는 것은 바로 이 부분이며 맞는 말이다.
>
> 2) 그 `save()`가 실제로 어느 클래스의 코드로 실행될지는 런타임에 결정된다. `repo` 변수에 실제로 `JpaUserRepository`가 들어있는지 `MyBatisUserRepository`가 들어있는지는 서비스 코드 안에는 적혀 있지 않고, 외부에서(예: Spring이 어떤 빈을 주입하느냐) 결정된다. `repo.save(entity);`라는 똑같은 한 줄이, 프로그램이 실제로 돌아갈 때 `repo`에 무엇이 들어있느냐에 따라 다른 클래스의 `save()`를 실행하며, 이 선택은 JVM이 그 줄을 실행하는 순간 실제 객체의 클래스를 보고 결정한다(vtable 조회, 동적 디스패치).
>
> 즉 `UserService`의 소스코드만 봐서는 결국 어떤 클래스의 로직이 실행될지 알 수 없다. 컴파일할 때는 "`save`라는 이름의 메소드를 호출하라"는 명령만 새겨두고, 정확히 어느 클래스의 몸체인지는 실행 시점까지 미뤄둔다. 그래서 같은 `UserService` 코드가 재컴파일 없이도 다른 구현체(JPA→MyBatis 등)와 잘 동작할 수 있는 것이 다형성의 실제 이점이다.
>
> 정리: 결정한 것은 호출할 메서드 이름(시그니처)이고, "런타임 결정"이 가리키는 것은 그 이름에 대응하는 실제 실행 코드(구현체)가 무엇이냐이다. 둘은 완전히 다른 층위의 결정이다.
>
> **Q.** 음 그러니까 설명에서 말하는건 '인터페이스에 특정메서드를 상속받은것까지는 코드상에서 인식한 상태이고 실제 실행 시점에 들어가야 구체적으로 상속 받은 인터페이스 내부에 어떤 메서드를 적용시킬지 결정된가는거지?
>
> 큰 흐름은 맞다. 다만 표현 두 군데를 다듬으면 정확해진다.
>
> 첫째, "상속받은"보다는 "구현(implements)한"이 정확한 용어다. Java에서는 클래스가 클래스를 물려받는 것은 `extends`(상속), 클래스가 인터페이스의 메소드 시그니처를 구현하는 것은 `implements`(구현)로 구분한다.
>
> 둘째, "인터페이스 내부에 어떤 메서드를 적용시킬지"가 아니라 "그 인터페이스를 구현한 여러 클래스 중 어떤 클래스의 구현체가 실행되는지"이다. 인터페이스 안에는 `save()`라는 메소드가 딱 하나(시그니처)만 있으므로, "여러 메서드 중 하나를 고르는 것"이 아니라 `save()`라는 하나의 이름표에 대해 그것을 구현한 여러 클래스들(예: `JpaUserRepository`, `MyBatisUserRepository`) 중 실제로 어떤 클래스의 몸체가 실행되느냐가 런타임에 정해지는 것이다.
>
> 정확히 정리하면: "어떤 인터페이스의 메소드를 구현했다(코드상 `implements`로 명시)"까지는 컴파일 시점에 확정되어 있고, 실제로 프로그램이 그 메소드 호출 지점을 실행할 때가 되어야 "그 인터페이스를 구현한 여러 클래스 중 정확히 어떤 클래스의 구현체가 실행되는지"가 결정된다.
