# 컬렉션 프레임워크와 Stream API — Q&A

### Q1. 배열의 한계 절에서 말하는 "배열"이 List를 가리키는 것인지

> **Q.** 여기서 말하는 배열이 list()를 말하는거지?
>
> 아니다. 여기서 "배열"은 `List`가 아니라 Java의 원시 배열 타입(`int[]`, `String[]` 등, `int[] numbers = new int[3]`처럼 쓰는 것)을 가리킨다. 문서 구조 자체가 "배열의 한계"(원시 배열 이야기) → "컬렉션의 필요성"(그 한계를 해결하는 것이 `List` 등 JCF)으로 대비시켜 설명하는 것이라, `List`는 배열이 아니라 배열의 한계를 극복하기 위해 JCF가 제공하는 구현체 중 하나다.
>
> - 배열: 크기 고정, 인덱스 수동 관리, 런타임 타입 체크만 가능
> - `List`(`ArrayList` 등): 내부적으로 동적 배열/노드 연결을 사용해 크기가 자동 확장되고, `add()`/`remove()` 같은 유틸리티 메서드를 제공하며, 제네릭으로 컴파일 시점 타입 체크가 가능

> **Q.** int[], String[] 이거의 정의가 int 타입으로 배열할거다, string타입으로 배열할거다가 맞나?
>
> 맞다. `타입[]`은 "이 배열엔 해당 타입의 값들만 순서대로 담겠다"는 선언이다. `int[]`는 int 타입 값들을 담는 배열이고, `String[]`는 String 타입 값들을 담는 배열이다.
>
> 다만 한 가지 미묘한 차이가 있다: `int`처럼 기본형(primitive)의 배열은 배열 칸에 값 자체가 저장되지만(`int[]`는 정수값이 바로 들어있음), `String`처럼 참조형(reference type)의 배열은 배열 칸에 객체가 아니라 그 객체를 가리키는 참조(주소)가 저장된다(`String[]`는 각 칸이 String 객체를 가리키는 참조).

> **Q.** 그러니까 배열은 자바 기능이고 jcf에서 제공하는 list나 map은 jcf가 있어서 사용이 가능하다?
>
> 맞다. 배열(`[]`)은 자바 언어 자체의 문법 요소로, JVM 차원에서 직접 지원되기 때문에 별도 import 없이 바로 쓸 수 있다. 반면 `List`, `Map`, `Set`은 언어 문법이 아니라 `java.util` 패키지의 JCF가 제공하는 인터페이스/클래스라서, `import java.util.List;`처럼 반드시 import를 해야 쓸 수 있는 표준 라이브러리 코드다. 즉 배열은 "언어가 기본 제공하는 기능", `List`/`Map`은 "그 위에 표준 라이브러리(JCF)가 얹어서 제공하는 기능"이며, 배열의 한계(고정 크기 등)를 극복하기 위해 JCF가 만들어졌다.

> **Q.** java.util 패키지가 jcf를 임포트(상속)하는게 맞아?
>
> 아니다. JCF는 java.util 패키지가 별도로 가져오는 대상이 아니라, java.util(및 일부는 java.util.concurrent) 패키지 안에 있는 `Collection`, `List`, `Set`, `Map`과 그 구현체들(`ArrayList`, `HashMap`, `HashSet` 등)을 통틀어 부르는 이름이다. 즉 **JCF ⊂ java.util**(java.util 패키지 안에 JCF가 포함된 관계)이지, java.util이 JCF를 import하거나 상속하는 관계가 아니다.
>
> 또한 import와 상속은 서로 다른 개념이다.
> - **import**: 다른 패키지의 클래스/인터페이스를 전체 경로(`java.util.List`) 없이 짧은 이름(`List`)으로 쓸 수 있게 해주는 컴파일 타임 문법. 타입 간 관계를 만드는 게 아니라 단순히 "가져다 쓰겠다"는 선언이다.
> - **상속(`extends`/`implements`)**: 한 타입이 다른 타입의 멤버를 물려받는 타입 간의 관계다(예: `ArrayList`는 `List` 인터페이스를 `implements`한다).
> - 패키지 자체는 import도 상속도 하지 않는다. 패키지는 클래스·인터페이스들을 묶어놓은 이름공간(namespace)일 뿐이다.

> **Q.** 음 내 기억에 java.util.'*';이게 jcf 전체를 import하는걸로 기억하는데 맞아? 방금 니 설명대로면 이걸로 jcf 내부에 있는 인터페이스들을 다 사용 가능하도록 하는거잖아
>
> 거의 맞지만 정확히 짚을 부분이 있다. `import java.util.*;`는 "java.util 패키지 바로 아래에 있는 모든 타입"을 가져오는 와일드카드 import다. JCF의 핵심 인터페이스·클래스(`List`, `Set`, `Map`, `Collection`, `ArrayList`, `HashMap`, `HashSet` 등)가 대부분 java.util 바로 아래에 있어서, 결과적으로 이걸 쓰면 JCF 대부분을 개별 import 없이 쓸 수 있게 되는 건 맞다.
>
> 다만 두 가지 정정이 필요하다.
> - "JCF를 import한다"는 표현은 정확하지 않다. `java.util.*`는 JCF만 콕 집어 가져오는 게 아니라 java.util 패키지에 있는 모든 것을 가져온다. 여기엔 `Scanner`, `Random`, `Optional`, `Date`, `StringTokenizer`처럼 JCF가 아닌 것들도 섞여 있다. JCF는 java.util 안에서 "컬렉션 관련된 것들"만 가리키는 부분집합 이름일 뿐이다.
> - 하위 패키지는 포함되지 않는다. `java.util.*`는 java.util 바로 아래 타입만 가져오고, `java.util.concurrent`(예: `ConcurrentHashMap`) 같은 하위 패키지는 포함하지 않아 따로 import해야 한다.
>
> 정리하면, `import java.util.*;`를 쓰면 JCF의 대부분(핵심 인터페이스·구현체)이 자동으로 딸려오긴 하지만, "JCF를 import하는 문법"이 따로 있는 게 아니라 그냥 java.util 패키지 전체를 가져오는 문법이고 JCF는 그 안에 포함된 것뿐이다.

> **Q.** 아 jcf가 java.util에 포함된다고 내가 이해한게 맞아?
>
> 맞다. JCF는 별도의 패키지나 실체가 아니라, java.util 패키지 안에 있는 `Collection`, `List`, `Set`, `Map`과 그 구현체들(`ArrayList`, `HashMap`, `HashSet` 등)을 묶어서 부르는 개념적인 이름이다. 즉 "JCF ⊂ java.util"(java.util이 JCF를 포함하는 더 큰 범위)이라는 이해가 맞다.
>
> 다만 엄밀히 말하면 `ConcurrentHashMap`처럼 동시성 환경을 위한 컬렉션들은 `java.util.concurrent`라는 하위 패키지에 있는데, 이것도 넓은 의미의 "컬렉션 프레임워크"에 포함시켜 이야기하기도 한다. 지금 배우는 `List`/`Set`/`Map`의 핵심 부분은 전부 java.util 바로 아래에 있다.

### Q2. List/Set/Map 핵심 특징 요약이 맞는지

> **Q.** 음 그러면 간단하게 정리하면 list, arraylist 는 중복허용, 자동 확장, 순서 보장 / set, hashset 은 중복 불허, 확장 안됨, 순서 미보장 / map,hashmap 은 키,값 한쌍, 중복 불허, collection 계열이 아니라서 .stream을 바로 사용 불가 맞아?
>
> `List`/`ArrayList`와 `Map`/`HashMap` 정리는 맞지만, `Set`/`HashSet`의 "확장 안됨"은 틀렸다. `HashSet`은 내부적으로 `HashMap`을 기반으로 동작하는데, 이 해시 테이블도 요소가 일정 비율(load factor)을 넘으면 자동으로 내부 배열 크기를 늘리고 재배치(rehash)한다. 즉 `HashSet`도 `ArrayList`처럼 요소를 추가하면 크기가 자동으로 늘어난다. `List`와 `Set`의 진짜 차이는 "확장 여부"가 아니라 **중복 허용 여부와 순서 보장 여부**다.
>
> 정정한 요약:
> - **List/ArrayList**: 중복 허용, 크기 자동 확장, 순서 보장
> - **Set/HashSet**: 중복 불허, 크기 자동 확장(내부 해시테이블 리해시), 순서 미보장
> - **Map/HashMap**: 키 중복 불허, 크기 자동 확장, (키 기준) 순서 미보장
>
> `Map`/`HashMap`은 키-값 한 쌍으로 저장하고, 키는 중복을 허용하지 않으며, `Collection` 인터페이스를 구현하지 않아 `.stream()`을 바로 쓸 수 없고 `entrySet()`을 거쳐야 한다는 설명은 맞다.

> **Q.** HashSet은 내부적으로 HashMap을 기반으로 동작하는데 그러면 hashmap이 hashset의 상위 개념인거야?
>
> 아니다. "상위 개념"(상속 관계, IS-A)이 아니라 내부 구현에서 갖다 쓰는 관계(컴포지션, HAS-A)다. 02장(OOP)에서 다룬 상속 vs 컴포지션 구분이 여기에도 그대로 적용된다.
>
> - 실제 자바 소스에서 `HashSet`은 `HashMap`을 상속(`extends`)하지 않는다. `HashSet`은 `AbstractSet`을 상속하고 `Set` 인터페이스를 구현(`implements`)한다.
> - 대신 `HashSet` 내부에 `private HashMap<E, Object> map;` 필드로 `HashMap` 인스턴스를 하나 갖고 있다(HAS-A). `add(e)`를 호출하면 실제로는 내부적으로 `map.put(e, 더미값)`을 호출하는 식으로, 넣으려는 요소를 키로 하고 의미 없는 상수 객체(`PRESENT`)를 값으로 해서 `HashMap`에 위임 저장한다.
>
> 정리: `HashSet` **is-a** `Set`(인터페이스 구현)이고, `HashSet` **has-a** `HashMap`(내부 구현 도구로 활용, 컴포지션)이다. `HashMap`이 `HashSet`의 부모 타입이라서가 아니라, 중복 없는 키만 있는 `HashMap`을 값은 신경 쓰지 않고 쓰면 곧 `Set`이 된다는 아이디어로 내부 구현에 재사용한 것이다.

> **Q.** 음 그러니까 hashset이 동작할때 hashmap을 활용해서 (키, 값) 구조에서 키를 배제하고 '값'만 누적하는 방식으로 동작한다? 내가 이해한게 맞아?
>
> 방향이 정반대다. HashSet에 넣는 요소(예: `"Kim"`)는 내부 `HashMap`의 **키(key)**로 저장되고, **값(value)**엔 아무 의미 없는 상수 객체 하나(`PRESENT`)가 들어가서 모든 요소가 이 똑같은 더미 값을 공유한다. 즉 배제되는 건 "값" 쪽이지 "키" 쪽이 아니다.
>
> 이렇게 하는 이유는, `HashMap`은 키는 중복을 허용하지 않지만 값은 중복을 허용하기 때문이다. `Set`이 필요로 하는 것이 정확히 "요소 중복 금지"인데, 이것이 `HashMap`의 "키 중복 금지" 규칙과 같다. 그래서 `Set`을 새로 구현하는 대신, 넣으려는 요소를 키로 쓰고 값은 의미 없는 상수로 채운 `HashMap`을 재활용하면 공짜로 `Set`이 만들어진다(`equals()`/`hashCode()` 기반 중복 판단 로직도 `HashMap`의 키 비교 로직을 그대로 물려받는다).
>
> 정리: 키 = 실제 저장하려는 요소(중요), 값 = 무시되는 더미(배제되는 쪽).

> **Q.** "Map은 Collection을 구현하지 않으므로 바로 .stream()을 호출할 수 없고, entrySet()(Set<Map.Entry<K, V>> 반환)을 거쳐야 스트림으로 변환할 수 있다" 이 방식이 반대로 hashmap에서 hashset으로 반환해서 동작하는건가?
>
> 방향에 대한 직관은 맞지만, "HashMap이 내부적으로 새 HashSet을 만들어서 반환한다"는 아니다. `entrySet()`은 `Map` 데이터를 복사해 새 `HashSet`을 만드는 게 아니라, `HashMap` 내부의 해시 테이블을 그대로 가리키면서 그 데이터를 `Set<Map.Entry<K,V>>`처럼 보이게 해주는 경량 뷰(view) 객체를 반환한다. 실제 타입은 `java.util.HashSet`이 아니라 `HashMap` 내부에 정의된 별도의 `EntrySet` 헬퍼 클래스(`Set` 인터페이스만 구현)다.
>
> 그래서 이건 뷰지 복사본이 아니다. `entrySet()`으로 얻은 `Set`을 순회 중 원본 `Map`이 바뀌면 그 변화가 그대로 반영되고, 반대로 이 `Set`에서 요소를 지우면(`remove()`) 원본 `Map`에서도 지워진다. 이는 아까 `HashSet`이 `HashMap`을 내부 저장소로 그대로 갖다 쓰던 것(새 객체를 만들어 값을 더미로 채우는 컴포지션)과 다른 점이다.
>
> 더미 값이 필요 없는 이유: `HashSet`은 원래 값이 없는 구조(요소 하나만 저장)라서 `Map`의 값 자리를 채울 더미가 필요했지만, `Map.Entry<K,V>`는 키와 값을 이미 한 쌍으로 갖고 있는 객체라서 그 자체로 `Set`에 담을 "요소"가 완성된다. 그래서 더미 값 없이도 `Map.Entry` 객체들의 집합으로 자연스럽게 `Set`을 만들 수 있다.
>
> 정리: "반대 방향"이라는 직관은 맞지만, `HashSet`이 `HashMap`을 소유(has-a)해서 저장소로 쓰는 것과 달리, `entrySet()`은 `Map` 자신의 데이터를 그대로 노출하는 뷰를 제공하는 것이라 구현 방식 자체는 다르다.

> **Q.** 음 그러면 다시 정리하면 hashmap -> hashset으로 갈려면 hashmap의 구성을 set처럼 보이게 감싸서 처리한가는거야?
>
> 방식 자체는 맞지만 "HashSet"이라는 표현은 정정이 필요하다.
>
> - 맞는 부분: `HashMap`의 `entrySet()`은 내부 데이터를 복사하지 않고, 기존 해시 테이블 구조를 그대로 둔 채 그 위에 `Set` 인터페이스의 규격(`size()`, `iterator()`, `contains()` 등)을 구현한 어댑터/뷰로 감싸서 "Set처럼 보이고 동작하게" 만든다.
> - 정정할 부분: 그 결과로 나오는 것은 `java.util.HashSet` 인스턴스가 아니다. `HashSet`은 `HashMap`을 필드로 갖고 새로 저장 공간을 만드는 독립적인 구체 클래스인 반면, `entrySet()`이 반환하는 것은 `HashMap` 내부에 별도로 정의된 `EntrySet`이라는 전용 뷰 클래스다. 이 클래스는 `Set` 인터페이스만 구현할 뿐, `HashSet`이라는 구체 클래스와는 무관하다.
>
> 즉 "타입 규격(`Set` 인터페이스)에 맞춰 감싼다"는 방식은 맞지만, "`HashSet`이라는 구체 클래스로 변환한다"는 아니다. 코드에서도 `Set<Map.Entry<K,V>> es = map.entrySet();`처럼 `Set` 인터페이스 타입으로 받지 `HashSet` 타입으로 받지 않는다는 게 그 증거다.

### Q3. List/Set/Map을 각각의 대표 구현체(ArrayList/HashSet/HashMap)와 묶어서 설명한 이유, 그리고 구현체 간 차이

> **Q.** 위에 정리된게 list,arraylist / set,hashset / map,hashmap 이렇게 되어있는데 각각 다른 요소인데 왜 차이점은 설명안하고 묶어서 설명하고 넘어가? 서로 차이점을 짚고넘어가야 정확한 사용처를 구분할거 아니야
>
> `List`/`Set`/`Map`과 `ArrayList`/`HashSet`/`HashMap`은 애초에 같은 레벨의 다른 개념이 아니라서 묶여서 설명됐다.
>
> - `List`, `Set`, `Map`은 **인터페이스**다. "이런 기능(계약)을 제공해야 한다"는 명세일 뿐 그 자체로는 객체를 만들 수 없다(`new List<>()` 불가능).
> - `ArrayList`, `HashSet`, `HashMap`은 그 인터페이스를 구현한 **여러 구체 클래스 중 하나**다.
>
> 이번 챕터(노션 원본 "JCF 주요 인터페이스 활용")가 애초에 각 인터페이스마다 가장 대표적인 구현체 하나씩만(List→ArrayList, Set→HashSet, Map→HashMap) 소개하는 구성이라, 그 범위를 그대로 요약하다 보니 "구현체 간 비교"가 빠졌다.
>
> 실제로 "정확한 사용처"를 구분하려면 같은 인터페이스를 구현한 여러 클래스끼리의 차이를 알아야 한다(이번 챕터 원본엔 없던 내용).
>
> - **List 계열**
>   - `ArrayList`: 내부가 배열이라 인덱스 접근(`get(i)`)이 빠름(O(1)), 중간 삽입/삭제는 뒤 요소를 밀어야 해서 느림(O(n))
>   - `LinkedList`: 내부가 이중 연결 리스트라 양 끝 삽입/삭제가 빠름(O(1)), 인덱스 접근은 앞에서부터 순회해야 해서 느림(O(n))
> - **Set 계열**
>   - `HashSet`: 해시 테이블 기반, 순서 보장 안 함, 삽입/조회가 평균 O(1)로 제일 빠름
>   - `LinkedHashSet`: 해시 테이블 + 연결 리스트로 삽입 순서를 기억함
>   - `TreeSet`: 레드-블랙 트리 기반, 항상 정렬된 상태를 유지(O(log n))
> - **Map 계열**
>   - `HashMap`: 해시 테이블 기반, 순서 보장 안 함, 제일 빠름
>   - `LinkedHashMap`: 삽입 순서를 기억
>   - `TreeMap`: 키 기준으로 항상 정렬됨(O(log n))
>
> 정리: "언제 어떤 걸 쓸지"는 `List` vs `Set` vs `Map`(인터페이스 레벨, 어떤 형태의 자료구조가 필요한가)을 고른 다음, 그 안에서 구현체끼리(예: 순서가 필요하면 `LinkedHashSet`, 정렬이 필요하면 `TreeMap`, 빠른 삽입/삭제가 잦으면 `LinkedList`) 골라야 정확해진다.

### Q4. "지연 평가"와 "지연 연산"이 다른 개념인지

> **Q.** 지연 평가: filter()/map() 같은 중간 연산은 정의만 해서는 실행되지 않고 — 이거 '지연연산'이랑 다른 개념이야?
>
> 다른 개념이 아니라 같은 것을 가리키는 말이다. 다만 정확한 용어를 짚으면:
>
> - **지연 평가(Lazy Evaluation)**가 프로그래밍 언어/CS에서 쓰이는 정식 용어다. "식(expression)의 계산(평가)을 필요한 시점까지 미룬다"는 뜻이고, Stream API 관련 자료에서도 이 용어(Lazy Evaluation)를 그대로 쓴다.
> - "지연 연산"은 별도로 정의된 기술 용어가 아니라, 같은 개념(계산을 미룬다)을 좀 더 풀어서 부르는 구어적인 표현이다. "평가(evaluation)"는 식을 계산해서 값을 만들어내는 것을 정확히 가리키는 반면, "연산(operation)"은 더 넓은 의미(사칙연산, 메서드 호출 등 모든 계산 행위)라서, "지연 연산"이라고 하면 뜻은 통하지만 학술적으로 표준화된 용어는 아니다.
>
> 정리: 개념은 동일하고, 자바/Stream API 문맥에서는 "지연 평가"가 맞는 정식 용어다.

> **Q.** "최종 연산: ... 한 번 소비된 스트림은 재사용할 수 없다"에서 스트림 재사용이 불가능하다는게 한 로직의 플로우중에 2번은 사용이 안된다는거야? 아니면 하나의 스트림식에서 결과를 호출하는 forEach() 등을 한번만 사용하라는거야?
>
> 두 번째 해석에 더 가깝지만, "로직 흐름에서 몇 번 쓰냐"가 아니라 딱 하나의 `Stream` 객체(인스턴스)에 대한 규칙으로 이해하는 것이 정확하다.
>
> ```java
> List<String> names = List.of("Tom", "Jerry");
>
> Stream<String> s = names.stream();   // Stream 객체 하나 생성
> s.forEach(System.out::println);      // 최종 연산 호출 → 이 순간 s는 소비(소모)됨
>
> s.forEach(System.out::println);      // IllegalStateException:
>                                       // stream has already been operated upon or closed
> ```
>
> 한 번 최종 연산이 호출된 그 스트림 객체(`s`)는 이후 어떤 연산(최종이든 중간이든)을 다시 호출하려 해도 예외가 발생한다. 하지만 원본 컬렉션(`names`) 자체는 소비되지 않으므로, 아래처럼 새 스트림을 다시 뽑으면 얼마든지 반복해서 쓸 수 있다.
>
> ```java
> names.stream().forEach(System.out::println); // OK
> names.stream().forEach(System.out::println); // OK, 매번 새 Stream 객체라서 문제없음
> ```
>
> 정리: "한 로직 플로우 안에서 2번은 못 쓴다"가 아니라, 같은 소스에서 필요한 만큼 새 스트림을 만들어 여러 번 처리하는 것은 문제없다. 정확히는 하나의 스트림 인스턴스에 대해 최종 연산은 딱 한 번만 호출할 수 있다는 규칙이며, 보통 `.stream()...forEach()`처럼 한 번에 체이닝해서 쓰기 때문에 이 문제를 잘 못 느끼지만 스트림을 변수에 저장해두고 재사용하려 할 때 이 규칙에 걸린다.

### Q5. map()에 "여러 개를 하나로 합치는" 동작이 있는지

> **Q.** flatMap() 이게 평면화 하는건 이해했는데 map()을 사용했을때 하나의 로직으로 합쳐주는 내용이 안보여 내가 잘못 기억하는건가?
>
> 그 "합쳐주는" 동작은 `map()`이 아니라 `flatMap()`의 것이다. 기억이 섞인 것으로 보인다.
>
> - **`map()`**: 순수하게 1:1 변환만 한다. 스트림 요소 하나를 받아서 다른 값/타입 하나로 바꿔줄 뿐, 여러 개를 하나로 합치는 동작은 전혀 없다(예: `"Alice"` → `5`(길이). 요소 개수는 변하지 않음).
> - **`flatMap()`**: 요소 하나하나가 컬렉션/스트림처럼 여러 개를 담고 있을 때, 그 안의 것들을 다 꺼내서 하나의 스트림으로 합쳐(평면화)준다(예: `List<List<String>>` → `List<String>`. 요소 개수가 달라질 수 있음).
>
> 그래서 "합쳐준다"는 표현은 `flatMap()`에만 해당하는 특징이고, `map()`은 그런 병합 기능이 없는 것이 맞다. 요약본에 `map()` 설명에서 "합쳐주는 내용"이 안 보이는 것은 정상이다 — 애초에 없는 기능이기 때문이다.
>
> 비유하면: `map()`은 "각 상자 안 내용물을 딴 걸로 바꿔치기", `flatMap()`은 "상자 안에 또 상자가 들어있을 때 그 속 내용물을 다 꺼내 큰 바구니 하나에 담기"다.

> **Q.** 니가 지금 내 질문을 잘못 이해한거 같거든. 내 질문은 flatmap이 map()의 중복 사용시 합쳐준다는 내용이 왜 빠졌는가를 물어본거야. 일단 합쳐주는건 맞다는거지?
>
> 맞다. `flatMap()`은 확실히 "합쳐준다(병합/평면화)"는 게 맞다. 그리고 그게 왜 필요한지가 정확히 "`map()`을 쓰면 생기는 중첩 구조" 때문이다.
>
> `flatMap()`은 사실 두 단계가 합쳐진 연산이다.
> 1. 매핑(map): 각 요소를 스트림(또는 컬렉션)으로 변환
> 2. 평면화(flatten/병합): 그렇게 나온 여러 개의 스트림을 하나로 이어붙임
>
> ```java
> List<List<String>> nested = List.of(
>     List.of("Apple", "Banana"),
>     List.of("Cat", "Dog")
> );
>
> // map()만 쓰면 -> Stream<List<String>> (여전히 중첩된 상태, 안 합쳐짐)
> Stream<List<String>> notFlattened = nested.stream().map(list -> list);
>
> // flatMap()을 쓰면 -> Stream<String> (하나로 합쳐짐/평면화됨)
> Stream<String> flattened = nested.stream().flatMap(list -> list.stream());
> ```
>
> `map()`만 반복해서(중첩해서) 써도 결과는 여전히 `Stream<Stream<...>>` 같은 중첩된 상태로 남고 자동으로 합쳐지지 않는다. `flatMap()`이 하는 일이 바로 그 중첩 결과를 자동으로 풀어서 하나의 평평한 스트림으로 합쳐주는 것이고, 이것이 `map()`과의 결정적 차이다.
>
> 정리: flatMap()이 합쳐주는 것은 맞고, 그 이유는 "`map()`을 (중첩해서든 반복해서든) 쓰면 결과가 중첩된 채로 쌓이는데, `flatMap()`은 그 매핑 + 병합(평면화)을 한 번에 해준다"는 것이다.

### Q6. 코딩테스트에서 배열과 JCF를 동시에 쓰는 이유

> **Q.** 코딩테스트에서는 배열이랑 jcf를 동시에 사용하는경우가 많던데 이건 왜지? 간단 배열에서의 한계점을 jcf로 해결한거잖아
>
> JCF가 배열의 한계를 해결한 건 맞지만, 완전히 대체(상위 호환)한 게 아니라 트레이드오프 관계라서 그렇다.
>
> - **성능 문제(오토박싱/언박싱)**: `int[]` 등은 기본형 값 자체를 메모리에 연속으로 저장하지만, `ArrayList<Integer>` 같은 JCF는 제네릭이 참조형만 받을 수 있어 `int` 값을 `Integer` 객체로 감싸는 오토박싱을 거친다. 그러면 값마다 객체 헤더 등 부가 메모리가 붙고, 값을 꺼낼 때마다 언박싱을 거쳐야 하고, 배열처럼 메모리에 연속으로 붙어있지 않아 캐시 지역성도 떨어진다. N이 크고 시간 제한이 빡빡한 문제(DP 테이블, 방문 배열, 누적합 배열 등)에서는 이 차이가 실행 시간에 크게 영향을 줘서 `int[]`를 쓴다.
> - **다차원 데이터**: 그래프/그리드 탐색(DFS, BFS) 문제에서 `int[][]`는 `List<List<Integer>>`보다 선언과 접근이 간단하고 메모리 오버헤드도 적다.
> - **크기가 미리 정해져 있을 때**: 크기를 미리 알 때는 `ArrayList`의 "필요하면 자동으로 커진다"는 장점이 의미가 없고 내부 재할당·복사 비용만 남으므로, 처음부터 크기를 정한 배열이 낫다.
> - **반대로 배열이 못 하는 것을 JCF가 채움**: 배열은 인덱스 기반이라 "키로 빠르게 찾기"(`HashMap`), "정렬 상태 유지"(`TreeMap`/`TreeSet`), "우선순위 꺼내기"(`PriorityQueue`, 다익스트라·그리디에 필수), "양쪽 끝 삽입/삭제"(`Deque`, BFS·슬라이딩 윈도우에 필수) 같은 기능을 스스로 구현하기 어렵다.
>
> 정리: JCF는 배열의 한계(고정 크기, 부족한 유틸리티) 일부를 해결해주지만, 그 대가로 오토박싱 오버헤드와 메모리 비용을 지불한다. 그래서 코딩테스트에서는 숫자를 빠르게 대량으로 다뤄야 하는 부분(DP, 방문 체크 등)은 배열을, 탐색/우선순위/키 기반 조회가 필요한 부분(그래프 인접 리스트, 힙, 해시 조회 등)은 JCF를 상황에 맞게 섞어 쓰는 것이 정석이다.

### Q7. 람다 문법이 .stream()에서 자주 활용되는지

> **Q.** 람다 문법이 .stream에서 자주 활용된다고 이해하는게 맞나?
>
> 맞는 이해지만, "스트림 전용"은 아니라는 점만 덧붙인다.
>
> - 왜 자주 같이 쓰이나: `filter()`, `map()`, `forEach()`, `sorted()`, `reduce()` 등 스트림의 대부분 메서드가 파라미터로 함수형 인터페이스(`Predicate`, `Function`, `Consumer`, `Comparator` 등)를 받는다. 람다는 이런 함수형 인터페이스를 그 자리에서 간결하게 구현하는 문법이라, 스트림 코드에서 거의 항상 람다(또는 메서드 참조)가 등장하게 된다.
> - 다만 람다가 스트림 전용 문법은 아니다. 람다는 "함수형 인터페이스를 구현하는 범용 문법"이라서 스트림 밖에서도 쓴다. 예: `new Thread(() -> doWork())`처럼 `Runnable` 구현, `list.sort((a, b) -> ...)`처럼 스트림 없이 정렬할 때의 `Comparator`, `Optional.ifPresent(v -> ...)`, 버튼 클릭 리스너 등.
>
> 정리: "스트림에서 람다가 자주 쓰인다"는 맞지만, 정확히는 "함수형 인터페이스가 필요한 모든 곳에서 람다가 쓰이고, 스트림이 그 함수형 인터페이스를 가장 많이 요구하는 대표적인 API라서 특히 자주 보이는 것"이다.

### Q8. 고급 Collector(그룹화·집계)가 DB 테이블 단 정보처리와 별개인지

> **Q.** 고급 Collector 이 부분 결론적으로 객체에 대한 연산이라서 테이블 단에서 정보처리하는거랑은 별개지?
>
> 맞다. 서로 다른 레이어(계층)에서 동작하는 별개의 처리다. 다만 "완전히 무관하다"기보다는 "역할이 다르다"고 이해하는 것이 더 정확하다.
>
> - **Stream의 고급 Collector**(`groupingBy()`, `partitioningBy()`, `summarizingInt()` 등): 이미 자바 애플리케이션 메모리(JVM 힙)에 올라와 있는 객체들의 컬렉션(`List<Employee>` 등)을 대상으로 동작한다. 즉 DB에서 데이터를 다 가져와서(또는 API 응답, 파일 읽기 등으로 이미 객체화된 데이터를) 자바 코드 안에서 그룹화·집계하는 것이다.
> - **SQL의 `GROUP BY` / 집계 함수**(`SUM`, `AVG`, `COUNT` 등): 데이터베이스 엔진이 테이블(디스크/DB 서버)에 저장된 행(row)을 대상으로, 자바 애플리케이션에 데이터가 넘어오기도 전에 DB 서버에서 직접 그룹화·집계를 수행한다.
>
> 실행되는 위치(자바 애플리케이션 vs DB 서버)와 대상(이미 로드된 객체 vs 테이블 행)이 다르다는 점에서 "별개"라는 이해가 맞다.
>
> 다만 실무적으로 연결되는 지점도 있다.
> - 개념은 유사: 둘 다 "묶어서(그룹화) 통계를 낸다"는 같은 목적이라, SQL의 `GROUP BY` + 집계함수 = Stream의 `groupingBy()` + `summarizingInt()` 조합과 거의 1:1로 대응된다.
> - 성능 관점에서는 보통 DB 쪽이 유리: 데이터가 대량이면, 자바로 다 끌고 와서 Stream으로 집계하는 것보다 SQL에서 미리 집계해서 필요한 결과만 받아오는 것이 네트워크 전송량과 메모리 사용 면에서 훨씬 효율적이다.
> - Stream 쪽이 유리한 경우: 이미 다른 이유로 객체가 메모리에 올라와 있고, SQL로 표현하기 어려운 복잡한 후처리(예: 여러 API 응답을 합쳐서 그룹화)가 필요할 때는 Stream Collector가 더 적합하다.
>
> 정리: 실행 계층은 별개(자바 객체 연산 vs DB 테이블 연산)지만, 하는 일(그룹화/집계)의 개념은 평행하고, 실무에서는 상황에 따라 둘 중 하나 또는 둘을 조합해서 쓴다.

> **Q.** 음 그러니까 stream은 이미 객체화된 데이터의 복잡한 연산처리에 더 유리하고 테이블에서는 대용량 데이터 처리에 더 유리하다?
>
> 큰 방향은 맞지만 "복잡한 연산"과 "대용량"이라는 표현을 조금 더 정확히 다듬어야 한다.
>
> - Stream이 유리한 이유는 "연산이 복잡해서"라기보다, ① 이미 메모리에 데이터가 올라와 있거나, ② SQL로 표현하기 어려운 로직(여러 소스의 데이터를 합치는 비즈니스 로직, 복잡한 조건 분기 등)을 처리해야 할 때다. Stream이 복잡한 연산을 더 잘하는 게 아니라, DB가 할 수 없거나 하기 애매한 종류의 처리를 자바 코드에서 유연하게 할 수 있다는 의미에 가깝다.
> - DB가 유리한 이유도 단순히 "데이터가 많아서"보다는, 원본 데이터가 있는 곳(DB)에서 미리 집계해서 필요한 결과만 네트워크로 가져오면 전송량·메모리 사용이 줄고 DB의 인덱스·쿼리 최적화 엔진을 활용할 수 있기 때문이다. 데이터가 많을수록 이 이점이 커지므로 "대용량일 때 특히 더 유리하다"는 표현은 정확하다.
>
> 정리: "Stream = 이미 있는 데이터에 대한 유연한/커스텀 처리에 유리", "DB = 원본 데이터 자체를 효율적으로 줄여서(전송량·메모리 절감) 집계하는 데 유리, 특히 데이터가 많을수록 그 이점이 커진다"로 이해하면 정확하다.

### Q9. 외부 API + DB + Stream을 연계하는 파이프라인 설계가 맞는 방향인지

> **Q.** 그러면 둘을 연계하는게 좋은 방향이겠네? 예를 들어 외부 api를 db에서 들어온 정보를 집계해서 각 테이블로 정리하고, 정리된 테이블 데이터를 객체로서 stream으로 필요한 연산(전체 수, 각 키워드의 수, 특정한 정보를 포함한 정보 수, 중복 검사 등)을 처리하고, 특히 중복 검사를 거쳐서 중복된 기사가 있다면 테이블 단에서 해당 정보를 삭제하는 로직, 코드상에서 정의한 객체에 외부 api 정보를 매핑, 재정의된 객체의 수만큼 외부 api를 batch로 가져오는 로직을 만들 수도 있을 것 같은데 이 방향이 맞아?
>
> 전체 그림(외부 API → 매핑 → DB 저장 → 집계/중복검사 → 정리)은 맞는 방향이며 실무에서 흔히 쓰는 ETL/수집 파이프라인 패턴이다. 다만 두 지점은 "DB vs Stream 역할 분담" 원칙에 비춰 다듬을 여지가 있다.
>
> - **"전체 수", "각 키워드의 수"는 오히려 DB(SQL) 쪽이 더 유리하다.** 단순 집계는 테이블 전체를 객체로 불러와 Stream으로 세는 것보다 `COUNT()`, `GROUP BY`(JPQL/QueryDSL의 `count()`, `groupBy()`)로 DB에서 바로 뽑는 것이 데이터 이동량과 메모리 사용 면에서 훨씬 효율적이다. 데이터가 많아질수록 이 차이는 커진다.
> - **중복 검사는 "무엇을 기준으로 중복을 판단하냐"에 따라 최적 위치가 달라진다.**
>   - 단순 기준(같은 외부 기사 URL/ID)이면, 저장할 때부터 DB에 유니크 제약(unique constraint)을 걸고 `INSERT ... ON CONFLICT DO NOTHING`(또는 저장 전 `existsBy...()` 체크)으로 애초에 중복이 안 들어가게 막는 것이 더 간단하고 안전하다. "일단 저장하고 나중에 Stream으로 찾아서 지우는" 방식은 그 사이 다른 프로세스가 같은 데이터를 또 넣는 동시성 문제(race condition)에 취약할 수 있다.
>   - 복잡한/유사도 기준 중복(제목이 비슷하지만 완전히 같지 않은 기사 등 SQL로 표현하기 어려운 로직)이면, 객체로 불러와 Stream으로 비교하고 중복으로 판단된 ID들을 모아서 DB에 삭제 쿼리를 날리는 패턴이 맞는 접근이다. 이 경우도 전체 테이블이 아니라 비교 범위를 좁혀서(예: 최근 N일 이내 기사만) 가져오는 것이 성능에 좋다.
> - **외부 API 응답 → 코드에서 정의한 객체로 매핑**: 정확히 맞는 표준 패턴(DTO/엔티티 매핑)이다.
> - **재정의된 객체 수만큼 외부 API를 batch로 가져오기**: 방향이 맞고, 실제로 외부 API 대부분이 요청당 rate limit·페이지네이션 제한이 있어 이런 배치 처리가 필요하다. 추가로 고려할 것: 배치 요청 실패 시 재시도(retry) 전략, 같은 요청을 두 번 보내도 결과가 같도록 하는 멱등성(idempotency), 실패한 배치만 나중에 재처리할 수 있게 상태를 남기는 것.
>
> 정리: 전체 그림은 맞는 방향이고, "이미 메모리에 있는 객체에 대한 커스텀/복잡한 로직은 Stream, 단순 집계나 대량 데이터 필터링은 DB"라는 원칙을 각 단계마다 적용하면 더 정교해진다. 특히 "전체 수/키워드별 수"는 SQL로, "복잡한 유사도 기반 중복검사"는 Stream으로 나누는 것이 지금까지의 원칙과 가장 잘 맞는다.
