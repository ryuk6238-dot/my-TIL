# Java 프로그래밍 시작하기 — Q&A

### Q1. OS, 바이트코드, JVM, 그리고 Java의 플랫폼 독립성(WORA)

**Q. OS가 정확히 뭐지?**
OS(Operating System, 운영체제)는 하드웨어(CPU, 메모리, 디스크, 입출력장치)와 응용 프로그램 사이에서 컴퓨터 자원을 관리하고 프로그램이 실행될 환경을 제공하는 시스템 소프트웨어다. 주요 역할은 프로세스/스레드 스케줄링(CPU 관리), 메모리 관리, 파일 시스템 관리, 입출력 장치 제어, 사용자 인터페이스 제공 등이다. 예: Windows, macOS, Linux.

**Q. 자바의 강점이 여러 OS에 호환되는 것이고, 그게 자바 파일을 컴파일로 바이트코드로 변환해 각 OS에 맞게 변환이 가능하기 때문이다 맞아?**
거의 맞지만 정정이 필요하다: **바이트코드 자체가 OS마다 다르게 변환되는 게 아니라, 바이트코드는 모든 OS에서 완전히 동일하고 그것을 실행하는 JVM이 OS마다 다르게 구현되어 있는 것**이다. 컴파일(`javac`)은 한 번만 수행되어 OS와 무관하게 항상 동일한 `.class`를 만들고, 실행 시점에 각 OS용으로 만들어진 JVM이 이 동일한 바이트코드를 해석해서 그 OS의 시스템 콜로 바꿔 실행한다.

**Q. 그럼 자바 파일이 컴파일을 통해 여러 OS에서 동일하게 쓰는 바이트코드로 변환되고, 이걸 JVM이 실행 시점에 해당 OS에 맞게 변환해주는 거라고?**
맞다. 컴파일 시 동일한 바이트코드 생성 → 실행 시 JVM이 OS별로 변환 실행, 이 두 단계가 Java 플랫폼 독립성(WORA)의 핵심 메커니즘이다.

**Q. JVM이 정확히 뭔지 설명해줘. 자바 버추얼 머신 약자는 기억하는데 넓은 개념의 java로 알고 있어.**
JVM(Java Virtual Machine)은 바이트코드를 실제로 읽어서 실행하는 가상 머신이다. 클래스 로더(바이트코드 적재), 실행 엔진(인터프리터+JIT 컴파일러), 메모리 관리(힙/스택, GC), OS 연동(동일 바이트코드를 각 OS 시스템 콜로 변환)이 주요 역할이다. "넓은 개념의 java"라는 이해는 정정이 필요하다: JVM은 Java 전체를 아우르는 넓은 개념이 아니라 JDK/JRE/JVM 중 바이트코드를 실행하는 가장 안쪽의 구체적인 실행 엔진(컴포넌트)이며, 오히려 Java 바이트코드 규격만 지키면 Kotlin/Scala/Groovy 같은 다른 언어도 JVM 위에서 실행 가능하다.

**Q. 그래서 자바랑 호환되는 언어들에서 자바 프레임워크가 JVM을 통해서 가능한 건가?**
맞다. Kotlin/Scala/Groovy 같은 JVM 호환 언어도 컴파일하면 Java와 동일한 형식의 바이트코드로 변환되고, JVM은 바이트코드가 어떤 언어에서 왔는지 신경 쓰지 않고 클래스/메서드 호출 규약만 맞으면 그대로 실행한다. 그래서 Spring 같은 Java 프레임워크를 Kotlin 코드에서도 자기 라이브러리처럼 호출할 수 있다(반대 방향도 가능). JVM이 번역해주는 게 아니라, 애초에 같은 바이트코드 포맷으로 컴파일되기 때문에 언어 간 경계 없이 상호 호출이 가능한 것이다. (예: Spring Boot의 Kotlin 공식 지원, Gradle의 Kotlin DSL)

**Q. (JVM 설명 중 언급된) GC가 뭐야?**
GC(Garbage Collection)는 JVM이 힙 메모리에서 더 이상 어디서도 참조되지 않는 객체를 자동으로 찾아 회수하는 기능이다. 개발자가 직접 메모리를 해제(`free`/`delete`)하지 않아도 되게 해주는 것이 핵심 목적이며, 동작 원리는 참조가 끊긴(도달 불가능) 객체를 표시(mark)한 뒤 실제로 제거(sweep)하는 방식이다. 대표 GC 종류로 Serial/Parallel/G1(Java 9+ 기본)/ZGC 등이 있고, GC가 도는 동안 애플리케이션 스레드가 멈추는 현상을 Stop-the-World라 부른다.

**Q. 힙 메모리는?**
힙(Heap)은 JVM이 `new`로 생성한 객체(인스턴스)와 배열을 저장하는 메모리 영역이다. 스택에는 그 객체를 가리키는 참조(주소)만 저장되고 실제 데이터는 힙에 있다. 메서드 호출마다 생겼다 사라지는 스택과 달리, 힙의 객체는 여러 메서드/스레드에서 공유될 수 있고 프로그램 실행 중 계속 유지되며 생명주기가 더 길다. 더 이상 참조되지 않는 객체는 스스로 사라지지 않고 힙에 남아있다가 GC가 주기적으로 회수한다. 힙이 부족한 채로 객체를 계속 생성하면 `OutOfMemoryError: Java heap space`가 발생하며, `-Xms`/`-Xmx` 옵션으로 힙 크기를 조절할 수 있다.

**Q. 그러니까 JVM 내부에서 객체 정보를 저장하는 메모리를 힙이라고 하고, 힙에서 사용하지 않는 객체 정보를 자동으로 회수해서 처리하는 게 GC라는 건가?**
큰 흐름은 맞지만 한 가지 표현이 정확하지 않다: GC는 "사용하지 않는 것 같은" 객체가 아니라, **어디서도 참조되지 않아 더 이상 도달할 수 없는(unreachable) 객체**를 찾아 회수하는 것이다. GC의 판단 기준은 실제 사용 여부가 아니라 순전히 참조 관계(누가 이 객체를 가리키고 있는가)이며, 참조가 하나도 남지 않은 객체만 회수 대상이 된다. 그래서 실제로는 안 쓰는 객체라도 어딘가에 참조가 남아있으면 GC가 회수하지 못하는데, 이것이 자바에서도 발생할 수 있는 메모리 누수의 원인이다.

### Q2. 기본 자료형 중 int만 주로 쓰게 되는 이유

**Q. 변수 중에선 기존 자료형 변수 중에선 int 말고 써본 적이 없는데 왜지? 제일 기본적인 타입이라서 그런가?**
맞는 방향이다. Java에서 정수 리터럴의 기본 타입이 `int`라서(`long`을 쓰려면 `10L`처럼 명시 필요), 정수가 필요한 대부분의 상황(반복문 카운터, 인덱스, 개수 등)에서 자연스럽게 `int`를 쓰게 된다. `byte`/`short`는 메모리 절약 외 이점이 없고(연산 시 내부적으로 `int`로 자동 승격되어 계산되므로 속도 이득도 없음) 대량 배열처럼 메모리가 실제 문제가 되는 특수한 경우에만 쓴다. `long`은 값의 범위가 `int`(약 ±21억)를 넘어설 때(타임스탬프, 대용량 카운트 등), `float`/`double`은 소수점이 필요할 때, `char`는 문자 하나, `boolean`은 참/거짓 플래그처럼 각자 명확히 다른 목적이 있을 때만 쓴다. 즉 int가 정수의 default 타입으로 지정돼 있고, 나머지 타입은 각자 특수한 상황(범위 초과, 메모리 절약, 소수점, 문자, 논리값)에서만 쓰기 때문이다.

### Q3. switch의 분기 선택 방식과 fall-through

**Q. switch는 분기마다 선택이 필수인 거야? if→else처럼 자동으로 넘어가는 건 불가능해?**
switch는 오히려 "하나만 선택"을 강제하지 않는 쪽이다. if-else는 각 분기마다 조건을 다시 평가해서(첫 조건이 거짓이면 다음 조건을 검사) 넘어가지만, switch는 `switch(변수)`로 값을 딱 한 번만 평가해서 일치하는 case를 찾고 그 지점부터 코드를 순서대로 쭉 실행한다. `break`가 없으면 아래 case들은 값이 일치하는지 다시 검사하지 않고 무조건 이어서 실행되는데 이것이 fall-through다. 정리하면: (1) 분기마다 선택이 필수는 아니다 — break가 없으면 오히려 자동으로 다음 case까지 계속 넘어가고, `default`도 `else`처럼 생략 가능한 선택사항이다. (2) if→else처럼 조건을 재평가하며 넘어가는 것은 불가능하다 — switch는 값 하나를 한 번만 비교해 진입점만 찾는 구조라 case마다 조건을 재검사하는 개념 자체가 없다. 참고로 Java 14부터의 화살표 문법(`case X -> ...`)은 반대로 fall-through가 없어서 매치된 case 하나만 실행되고 자동으로 빠져나온다(if-else의 배타적 선택에 더 가까움).

**Q. 아 그러니까 switch는 변수값 하나에 대한 여러 가지 조건을 평가해서 최종 변수에 대입하는 건가?**
두 가지 정정이 필요하다. (1) "조건을 평가"하는 게 아니라, 변수의 값 하나를 각 case에 적힌 상수 값과 단순히 "같은지(equality)"만 비교하는 것이다 — if-else처럼 `x > 10` 같은 임의의 조건식을 평가하는 게 아니라 오직 일치 여부만 확인한다. (2) "최종 변수에 대입"이 기본 동작이 아니다 — 전통적인 switch문은 값에 따라 다른 코드 블록을 실행하는 것이지 대입이 목적이 아니다. 다만 Java 14부터의 switch 표현식(`case X -> 값;`, `yield` 사용)은 결과를 변수에 대입할 수 있게 해주는 별도의 선택적 기능이다. 정리: switch는 변수값 하나를 case의 상수들과 일치하는지만 확인해서 일치하는 지점의 코드를 실행하는 구조다.

**Q. 아 그럼 다시, switch는 변수에 대해 case 값이 동일한지 확인하는 거네?**
맞다. switch는 변수(switch 대상 값)가 각 case에 적힌 값과 동일한지(equality)만 확인해서, 일치하는 case의 코드를 실행하는 구조다.

### Q4. while과 do-while의 관계, 그리고 while이 거짓으로 시작할 수 있는 이유

**Q. do-while은 while의 연장선인 거야? 최초 조건을 무시하고 실행하는? 근데 의문인 게 while이 참/거짓에 따라 움직이는 거 아니야? 그러면 while문 시작 전에 기본적으로 '참'으로 선언해두면 되는 거 아닌가? 애초에 거짓으로 while문을 시작할 이유가 뭐지?**
do-while은 while의 연장선이 맞지만, "조건을 무시"하는 게 아니라 "조건을 검사하는 시점"이 다른 것이다. while은 조건을 먼저 검사한 뒤 몸통을 실행해서 처음부터 조건이 거짓이면 한 번도 실행되지 않고, do-while은 몸통을 먼저 한 번 실행한 뒤 조건을 검사해서 최소 1회 실행이 보장된다.

"while을 항상 참으로 시작하면 되지 않나"는 오해다. while의 조건은 개발자가 고정으로 선언해두는 값이 아니라 실행 시점의 실제 상태(변수 값, 사용자 입력, 파일 내용 등)에 따라 자연스럽게 정해지는 값이다. 예를 들어 `while (n > 0)`에서 사용자 입력으로 `n`이 이미 0이 들어왔다면 반복문이 애초에 한 번도 돌면 안 되는 게 맞는 동작이고, 파일을 한 줄씩 읽는 `while (line != null)`도 파일이 비어있으면 처음부터 조건이 거짓인 게 정상이다. 즉 "거짓으로 시작할 이유"는 "처리할 데이터/조건이 처음부터 없을 수도 있는 실제 상황"을 정확히 반영하기 위해 while이 존재하는 것이며, 무조건 참으로 시작하게 만들면 정말 0번 실행해야 하는 상황에서도 억지로 1번 실행하는 버그가 생긴다. 반대로 do-while은 몸통이 무조건 최소 1번은 실행되어야 함이 확실한 특수 상황(예: 메뉴를 한 번 보여주고 계속할지 묻는 경우)에 쓴다.

**Q. 음 그러니까 최초 1회 무조건 실행해보고 조건이 거짓인지를 판단할 수 있게 보장하는 거야?**
맞다. do-while은 조건을 아예 평가하지 않은 채로 몸통을 최소 1회 무조건 실행하고, 그 다음에서야 조건을 검사해서 계속 반복할지를 판단하는 구조다. 조건이 처음에 참이었을지 거짓이었을지와 무관하게 1회 실행은 이미 보장된 상태에서, 그 이후 반복 여부만 조건으로 결정한다.

**Q. 굳이 쓸 필요는 없지만 while 상단에 if로 참/거짓 판단을 대체할 수도 있겠네?**
맞는 발상이다. `if (true) { body(); } while (condition) { body(); }` 처럼 짜면 do-while과 동일한 효과(최소 1회 실행 + 이후 조건 반복)를 낼 수 있다. 다만 이 방식은 몸통(body) 코드가 `if`와 `while` 두 곳에 중복되어, 로직 수정 시 두 군데를 다 고쳐야 하고 하나만 고치면 버그가 생길 위험이 있다. `do-while`은 몸통을 한 곳에만 쓰면서도 같은 동작을 표현할 수 있어서, 이 코드 중복 없이 같은 결과를 안전하게 얻을 수 있는 문법적 지름길이다.

**Q. 구체적인 조건이 필요하면 상단에 if로 참/거짓 구분하면 되고, 그럴 필요 없이 바로 변수값 판단이 필요하면 do-while을 쓰면 된다는 거지?**
이 정리는 정정이 필요하다. "조건이 구체적이냐 아니냐"가 기준이 아니다 — if든 do-while이든 결국 똑같은 조건식(boolean 값)을 검사하는 것이라 조건의 종류로 나뉘지 않는다. 실제 기준은 하나뿐이다: "이 반복문이 0번 실행되는 경우도 정상적으로 허용해야 하는가?" 0번 실행이 정상일 수 있다면(조건이 처음부터 거짓이면 아예 안 돌아도 되는 경우) `while`을 쓰고, 무조건 최소 1번은 실행돼야 한다면(조건과 무관하게) `do-while`을 쓴다. 앞서 얘기한 `if(true){body();} while(...){body();}` 트릭은 "조건이 구체적일 때 쓰는 대안"이 아니라 do-while이 하는 일을 do-while 없이 흉내 낸 것뿐이며(코드 중복이라는 단점 포함), if를 위에 쓰느냐 do-while을 쓰느냐는 조건의 성격과 무관하게 "최소 1회 실행 보장"이라는 같은 목적을 달성하는 서로 다른 방법일 뿐이다.

**Q. while문이 안 돌아도 되면 그냥 while 쓰고 무조건 최소 1번 돌아야 하면 do-while이라는 거잖아? 그럼 반대로 최소 1번 돌아야 하는데 그 값이 '거짓'일 때는 코드상에서 '거짓'을 요구한다는 거야? 그리고 최소 1번 보장으로 접근하면 break로 1회 반복 후 정지로 조절도 가능하잖아**
앞부분 정리는 맞다. do-while이 "거짓을 요구"하는 것은 아니지만(조건이 참이든 거짓이든 항상 잘 동작함), do-while이 while과 실제로 다른 결과를 만들어내는 상황은 정확히 "조건이 처음에 거짓인 경우"뿐이다 — 조건이 처음부터 참이면 while도 첫 검사에서 바로 통과해 실행하므로 do-while과 결과가 완전히 같아지고, 조건이 처음부터 거짓일 때만 while은 0번, do-while은 1번 실행이라는 실질적 차이가 생긴다. 그래서 do-while을 굳이 쓰는 실질적 의미는 "조건이 처음에 거짓일 수도 있는 상황"을 염두에 둔 것이라는 감각은 정확하다.

break를 이용한 방식도 맞다: `while (true) { body(); if (!condition) break; }`는 코드 중복 없이 do-while과 완전히 동일한 동작을 만드는 잘 알려진 패턴이며, 이전에 얘기한 `if(true){body();} while(...){body();}` 방식보다 더 깔끔한 대안이다(몸통 코드가 한 곳에만 있음). do-while은 결국 이 패턴을 언어 차원에서 문법으로 축약해놓은 것이다.

**Q. 음 그러니까 다시 정리하면 do-while을 쓰는 경우는 '무조건 최소 1번 while문의 동작의 보장'인데, 여기서 요구하는 구체적인 답이 참이든 거짓이든 상관없이 '최소 1번'을 요구하는 거니까 성립하는 것이고, 굳이 '거짓'에 집착할 필요 없다는 거네?**
정확하다. do-while을 쓰는 기준은 조건이 참이냐 거짓이냐가 아니라, 그냥 "이 몸통이 조건값과 무관하게 무조건 최소 1번은 실행되어야 하는가" 하나뿐이다. 앞서 "거짓일 때 차이가 난다"고 한 것은 do-while을 쓰는 기준이 아니라 while과 do-while이 실제로 다른 결과를 내는 경우가 언제인지를 설명한 부수적인 내용일 뿐이며, 실제로 do-while을 선택할 때는 조건이 참일지 거짓일지 신경 쓸 필요 없이 "최소 1회 실행이 필요한가?"만 보면 된다.

### Q5. 배열.length는 얕은 복사인가?

**Q. 배열.length <- 이건 코딩 테스트에서 자주 봤어. 이건 배열의 길이만 요구하는 거니까 얕은 복사인가?**
`.length`는 복사와 전혀 관계가 없다. 그냥 배열 객체가 이미 가지고 있는 "길이"라는 값(정수) 하나를 읽어오는 것뿐이다. 얕은 복사/깊은 복사는 배열(또는 그 요소들)을 새로 복제하느냐에 대한 개념인데, `.length`는 아무것도 복제하지 않고 기존 배열 객체의 메타데이터(크기)를 조회만 하는 것이라 복사라는 개념 자체가 적용되지 않는다. 코딩테스트에서 `arr.length`를 자주 보는 건 반복문 조건(`for (int i = 0; i < arr.length; i++)`)이나 크기 검증 등에 필요해서 가장 자주 쓰이는 배열 속성 조회이기 때문이지, 복사와는 무관하다.

### Q6. API란 정확히 무엇인가

**Q. "유용한 API"라고 설명에 되어 있는데 정확히 API가 뭔지 설명해줘**
API(Application Programming Interface)는 프로그램이 다른 프로그램/라이브러리/시스템과 상호작용할 수 있도록 미리 정해둔 규칙과 호출 창구다. 핵심은 "내부가 어떻게 동작하는지는 몰라도 이렇게 호출하면 이런 결과가 나온다"는 약속(인터페이스)만 정의해둔 것이라는 점이다. 이 파일의 `Arrays.toString(arr)`, `Arrays.sort(arr)` 맥락에서 API는 Java가 미리 만들어 제공하는 라이브러리(클래스/메서드)를 뜻하며, 개발자가 정렬/문자열 변환 알고리즘을 직접 구현하지 않고도 정해진 메서드를 호출하기만 하면 되게 해준다. 더 넓게는 웹의 REST API도 같은 개념(서버가 "이 주소로 이렇게 요청하면 이런 데이터를 준다"고 정해둔 규칙)이며, 스케일만 다를 뿐이다(`Arrays.sort()`는 한 프로그램 안의 API, REST API는 서로 다른 시스템 간 네트워크 API).
