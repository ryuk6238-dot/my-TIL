# 컬렉션 프레임워크와 Stream API

> Java 기초 학습 기록 — 노션 내용 정리 예정

## 개념 정리

### 1. 배열의 한계와 JCF의 필요성

- **배열의 한계**: 생성 시 크기를 고정해야 해서 요소가 넘치면 더 큰 배열을 만들어 복사해야 하고(고정 크기), 삽입·삭제·탐색을 인덱스 기준으로 직접 관리해야 하며(한정된 기능), 런타임에만 타입 불일치를 감지할 수 있어 제네릭만큼 컴파일 시점 안전성을 보장하지 못한다(타입 안정성 문제).
- **컬렉션의 필요성**: `List` 계열은 내부적으로 동적 배열/연결 구조를 사용해 요소 추가 시 자동으로 공간을 확장하고(동적 크기 관리), 삽입·삭제·검색·정렬 같은 기능을 기본 제공하며(풍부한 유틸리티 메서드), 제네릭 기반 선언으로 컴파일 시점 타입 체크가 가능하다(타입 안정성).
- **JCF(Java Collections Framework)의 구조**
  - **Collection 계열**: 모든 컬렉션의 상위 인터페이스인 `Collection`(`add()`, `remove()`, `size()` 등 공통 기능 정의) 아래, 순서가 있고 인덱스 접근·중복을 허용하는 `List`(`ArrayList`, `LinkedList`)와, 중복을 허용하지 않고 `hashCode()`/`equals()`로 동일성을 판단하는 `Set`(`HashSet`, `LinkedHashSet`)이 있다.
  - **Map 계열**: 키-값 쌍으로 데이터를 저장하는 `Map`(`HashMap`, `LinkedHashMap`, `TreeMap`). `Collection`의 하위 인터페이스는 아니지만 JCF에서 함께 관리되는 자료구조로 취급한다.
- **JCF의 장점**: 표준화된 인터페이스로 구현체를 교체해도 코드 변경 범위가 작고, 상황(삽입/삭제·탐색 빈도, 정렬 필요성 등)에 맞는 구현체를 선택할 수 있으며, 제네릭으로 타입 안정성을 얻고, `Collections`나 각 컬렉션에 내장된 유틸리티 메서드로 정렬·최소/최대 탐색·필터링을 단순화할 수 있다.

### 2. JCF 주요 인터페이스 활용

- **List / ArrayList**: 순서가 있고 인덱스로 접근하며 중복을 허용한다. 내부적으로 동적 배열을 사용해 요소 추가 시 자동으로 크기를 확장하고, 인덱스 기반 랜덤 액세스가 빠르다. 주요 메서드: `add()`, `get(index)`, `remove(index/Object)`, `size()`, `clear()`.
- **Set / HashSet**: 중복을 허용하지 않고 순서를 보장하지 않는다. 해시 테이블 기반으로 저장되며, `hashCode()`와 `equals()`로 중복 여부를 판단한다(예: `"Alice".hashCode()`를 배열 길이로 나눈 나머지를 버킷 인덱스로 사용). 주요 메서드: `add()`(중복 시 무시), `remove()`, `contains()`, `size()`, `clear()`.
- **Map / HashMap**: 키-값 쌍을 저장하며 키는 중복을 허용하지 않는다(같은 키로 `put()`하면 값을 덮어씀). 해시 테이블 기반으로 키를 통해 값을 효율적으로 조회한다. 주요 메서드: `put(k, v)`, `get(key)`, `remove(key)`, `containsKey(key)`, `keySet()`.
  - `Map`은 `Collection`을 구현하지 않으므로 바로 `.stream()`을 호출할 수 없고, `entrySet()`(`Set<Map.Entry<K, V>>` 반환)을 거쳐야 스트림으로 변환할 수 있다. `entrySet()`을 쓰면 key·value를 함께 다룰 수 있다는 장점도 있다.
- **조합 실습**: 학생 관리 프로그램처럼 `List`(전체 목록 관리)·`Set`(이름 중복 체크)·`Map`(이름→점수 매핑)을 함께 조합해 쓰는 것이 실무에서 흔한 패턴이다.

### 3. 함수형 인터페이스와 람다 표현식

- **일반 클래스 vs 함수형 인터페이스 구현체**: 일반 클래스는 여러 메서드와 상태(필드)를 가지고 상속·다형성으로 복합 구조를 만들 수 있는 반면, 함수형 인터페이스 구현체는 **단 하나의 추상 메서드(SAM, Single Abstract Method)**만 가지며 "객체"라기보다 로직 하나를 일시적으로 담아 전달하는 용도로 쓰인다. 자바는 메서드 포인터를 언어 차원에서 지원하지 않는 대신, 함수형 인터페이스+람다로 이를 대체한다.
- **`@FunctionalInterface`**: 붙이면 컴파일러가 추상 메서드가 정확히 하나인지 검증해준다. `default`/`static` 메서드는 몇 개든 있어도 이 카운트에 포함되지 않는다.
- **람다 문법**: `(매개변수 목록) -> { 실행 블록 }` 형태. 파라미터 타입은 추론 생략 가능하고, 실행 블록이 한 줄에 `return`뿐이면 중괄호와 `return`을 생략할 수 있다. 단, 여러 줄 블록에서 반환값이 필요하면 `return`을 생략할 수 없다.
- **변수 캡처와 effective final**: 람다가 외부 지역 변수를 참조(캡처)하려면 그 변수가 **effective final**(실질적으로 재할당되지 않는 변수)이어야 한다. 이유는 ① 지역 변수는 메서드 종료 시 스택에서 사라지지만 람다는 메서드 종료 후에도 살아남을 수 있어 값이 안전하게 복사(캡처)될 보장이 필요하고, ② 비동기·멀티스레드 환경에서 캡처한 변수가 중간에 바뀌면 동시성 문제가 생길 수 있으며, ③ 인스턴스/static 필드는 힙·클래스 영역에 있어 람다와 생존 기간을 공유하므로 자유롭게 변경 가능하지만 지역 변수는 그렇지 않기 때문이다.
  - 람다의 `this`는 람다를 감싼 외부 객체를 가리키는 반면, 익명 클래스의 `this`는 익명 클래스 자신을 가리킨다는 차이가 있다.
- **메서드 참조(`::`)**: 이미 존재하는 메서드 하나만 호출하는 람다를 더 간결하게 표현. 정적 메서드 참조(`ClassName::staticMethod`), 인스턴스 메서드 참조(`instance::instanceMethod`), 생성자 참조(`ClassName::new`) 세 가지가 대표적이다.
- **`java.util.function`의 주요 함수형 인터페이스**
  - **`Predicate<T>`**: `boolean test(T t)` — 조건 판별(필터링에 사용, `filter()`의 인자).
  - **`Function<T, R>`**: `R apply(T t)` — 입력을 다른 타입/값으로 변환(`map()`의 인자).
  - **`Consumer<T>`**: `void accept(T t)` — 입력을 소비만 하고 반환값 없음(`forEach()`의 인자).
  - **`Supplier<T>`**: `T get()` — 인자 없이 값을 생성해 반환.

### 4. Stream API 기초

- **Stream이란**: Java 8부터 도입된, 컬렉션 요소를 데이터가 흐르는 한 줄기 흐름처럼 다루며 반복·필터링·매핑 등을 함수형 스타일로 처리하는 API. 원본 데이터를 변경하지 않고(불변성 유지), 연산은 최종 연산이 호출될 때 비로소 실행된다(**지연 평가, lazy evaluation**).
- **스트림 파이프라인 구성 요소**
  - **데이터 소스**: 리스트, 배열, 파일 등에서 스트림 생성.
  - **중간 연산(Intermediate Operation)**: 스트림을 반환해 여러 번 체이닝 가능. 예: `filter()`, `map()`, `sorted()`, `distinct()`.
  - **최종 연산(Terminal Operation)**: 스트림을 소모하며 결과(실제 값/컬렉션)를 생성, 한 번만 호출 가능. 예: `forEach()`, `collect()`, `count()`, `reduce()`. 한 번 소비된 스트림은 재사용할 수 없다.
- **지연 평가**: `filter()`/`map()` 같은 중간 연산은 정의만 해서는 실행되지 않고, `forEach()` 같은 최종 연산이 호출되는 순간 전체 파이프라인이 한 번에 실행된다. 덕분에 불필요한 연산을 건너뛸 수 있어 효율적이다.
- **기본 연산 3종**
  - **`filter(Predicate)`**: 조건을 만족하는 요소만 남기는 중간 연산.
  - **`map(Function)`**: 각 요소를 다른 타입/값으로 변환하는 중간 연산.
  - **`forEach(Consumer)`**: 각 요소에 부수 효과(출력 등)를 적용하는 최종 연산. 내부 반복이라 `continue`/`break`를 직접 쓸 수 없으므로 조건 분기가 필요하면 `filter()`와 조합한다.
  - 세 연산 모두 익명 클래스 또는 람다로 함수형 인터페이스를 구현해 전달할 수 있으며, `Map` 데이터를 다루려면 `entrySet().stream()`을 거쳐야 한다.

### 5. Stream API의 고급 연산

- **`distinct()`**: 중복 요소를 제거하는 중간 연산. 객체의 `equals()`/`hashCode()`가 올바르게 구현되어 있어야 중복 판단이 정확하다.
- **`sorted()`**: 스트림을 정렬하는 중간 연산. 인자 없이 쓰면 `Comparable` 기반 오름차순 정렬이고, `Comparator`(예: `Comparator.comparingInt(...).thenComparing(...)`, 커스텀 `Comparator` 구현체)를 넘기면 사용자 정의 정렬이 가능하다.
- **`flatMap()`**: `List<List<T>>` 같은 다차원(중첩) 구조를 각 요소를 스트림으로 변환한 뒤 하나로 이어붙여 1차원 스트림으로 평면화하는 중간 연산.
- **`peek()`**: 스트림 요소를 중간에 확인(로깅)하기 위한 중간 연산. 주로 디버깅 목적이며, 파이프라인 자체에 변화를 주는 부수 효과 용도로는 권장되지 않는다.
- **`collect()` 기본 활용**: 스트림 요소를 원하는 형식으로 모으는 최종 연산으로, 보통 `Collectors`의 정적 메서드를 사용한다. `Collectors.toList()`/`toSet()`으로 리스트·집합을 만들고, `Collectors.joining(구분자)`로 문자열을 이어붙일 수 있다. 더 복잡한 그룹화·통계 집계는 다음 절에서 다룬다.

### 6. 데이터 분석과 리포트 생성 (고급 Collector)

- **`groupingBy(분류함수)`**: 분류 함수가 반환하는 키를 기준으로 요소를 묶어 `Map<키, List<요소>>` 형태로 수집한다. `groupingBy()` 결과에 다시 `groupingBy()`를 중첩하면 다단계(예: 직책 → 부서) 그룹화도 가능하다.
- **`partitioningBy(Predicate)`**: 조건의 참/거짓 두 그룹으로만 데이터를 분할해 `Map<Boolean, List<T>>`를 반환한다.
- **통계/집계 Collector**
  - `summingInt()`/`summingLong()`/`summingDouble()`: 합계.
  - `averagingInt()`/`averagingLong()`/`averagingDouble()`: 평균(항상 `double` 반환).
  - `maxBy(Comparator)` / `minBy(Comparator)`: `Comparator` 기준 최댓값/최솟값을 `Optional`로 반환.
  - `summarizingInt()`/`summarizingLong()`/`summarizingDouble()`: 개수·합계·평균·최댓값·최솟값을 한 번에 구해 `IntSummaryStatistics` 등으로 반환.
  - `reducing(초기값, 누적함수)`: 합계·평균처럼 기본 제공되지 않는 커스텀 누적 로직이 필요할 때 사용.
- **다단계 그룹화 + 통계 조합**: `groupingBy(분류함수, summarizingInt(...))`처럼 다운스트림 Collector를 함께 넘기면 "부서별 급여 합계·평균·최대·최소" 같은 리포트를 한 번에 생성할 수 있다.
- **실무 활용 예시**: 월별 매출 분석(`groupingBy(매출월)` + `summingInt`/`averagingDouble`), 카테고리별 판매량 집계, 유저 등급별 사용 시간 분석(`groupingBy` + `averagingDouble`, 필요 시 `partitioningBy`로 VIP/일반 분리), 부서+직급+지역처럼 다단계 조건 그룹화 등. 공통 흐름은 `filter() → groupingBy() → 집계(Collector) → 결과 포맷팅`이며, 이 핵심 로직만 스트림으로 깔끔하게 표현해두면 유지보수·확장성이 좋아진다.
