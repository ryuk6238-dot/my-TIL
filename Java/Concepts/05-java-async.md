# Java 비동기 처리하기

> Java 기초 학습 기록 — 노션 내용 정리 예정

## 개념 정리

### 1. 비동기 처리의 개념과 필요성

- **동기 vs 비동기**: 작업 간 순서와 제어 흐름을 기준으로 구분한다. 동기는 호출한 쪽이 결과가 나와야만 다음 일을 하고(순차 처리, 예측·디버깅이 쉽지만 느린 작업이 있으면 전체가 멈춰 보임), 비동기는 결과와 상관없이 다음 일을 계속하고 결과는 나중에 확인한다(여러 작업을 동시에 진행해 전체 처리 시간을 단축).
- **블로킹 vs 논블로킹**: 호출한 주체(스레드)가 대기 상태에 들어가느냐를 기준으로 구분한다. 블로킹은 자원이 준비될 때까지 호출 스레드가 멈춰서 다른 작업을 못 하고, 논블로킹은 자원이 준비되지 않아도 즉시 제어권을 반환해 호출자가 다른 작업을 계속할 수 있다.
  - "비동기 = 논블로킹"은 항상 참이 아니다. 예를 들어 `Future.get()`은 비동기로 수행된 작업이지만 `get()` 호출 순간 블로킹되고(비동기+블로킹), `CompletableFuture.thenApply(...)` 체이닝은 결과가 오면 자동 실행되므로 호출 스레드가 블로킹되지 않는다(비동기+논블로킹).
- **동기 처리가 필요한 실제 시나리오**: ① 순서·의존성이 중요한 트랜잭션(계좌 이체처럼 "잔액 확인 → 차감 → 이력 기록"이 반드시 이전 단계 결과를 받아야 다음 단계로 넘어갈 수 있는 경우, 하나라도 실패하면 전체를 롤백해야 하는 경우), ② 결과 없이는 다음 로직을 진행할 수 없는 요청·응답(로그인 인증처럼 인증 결과가 나오기 전에는 다음 화면·로직으로 넘어갈 수 없는 경우), ③ 아주 짧고 가벼운 연산(단순 계산이나 캐시 조회처럼 작업 자체가 스레드 생성·컨텍스트 전환 오버헤드보다 훨씬 빨라, 비동기로 만들어도 이득이 없고 오히려 코드만 복잡해지는 경우).
- **비동기 처리가 필요한 실제 시나리오**: ① I/O 바운드 작업(파일 다운로드, API 호출처럼 연산보다 대기 시간이 훨씬 긴 작업), ② 대용량 트래픽 처리(요청을 병렬로 처리해 동시 접속자 수를 늘림), ③ 사용자 응답성 향상(오래 걸리는 작업을 백그라운드로 돌려 UI가 멈추지 않게 함).
- **실무 팁**: 비동기 처리가 항상 성능을 높이는 것은 아니다. CPU 집약적 작업이나 단순 계산은 스레드 생성 오버헤드가 더 클 수 있으므로 작업 특성을 보고 적용해야 한다.

### 2. Java 스레드의 기본 개념과 생성

- **프로세스 vs 스레드**: 프로세스는 실행 중인 프로그램의 인스턴스로 OS가 독립적인 메모리 공간을 보장하며 고유 PID를 갖고 다른 프로세스와 메모리를 공유하지 않는다(통신은 IPC). 스레드는 프로세스 내 작업 단위로 같은 프로세스의 다른 스레드와 메모리를 공유한다(데이터 공유가 쉽지만 동시성 문제 야기 가능). 모든 Java 프로그램은 최소 하나의 메인 스레드에서 실행되고, 추가 스레드를 만들어 멀티스레드 프로그래밍을 구현한다.
- **Thread 클래스 상속 방식**: `run()`을 오버라이드해 작업을 정의하고 `start()`로 새 스레드에서 실행한다. `run()`을 직접 호출하면 새 스레드가 생성되지 않고 현재 스레드에서 실행되므로, 병렬 실행을 위해서는 반드시 `start()`를 호출해야 한다.
- **Runnable 인터페이스 구현 방식**: Java는 다중 상속이 불가능하므로, 다른 클래스를 상속할 수 있는 유연성을 위해 `Thread` 상속보다 `Runnable` 구현이 권장된다. `Runnable`은 함수형 인터페이스라 람다식으로 간결하게 작성할 수 있고, 이미 정의된 메서드를 실행하고 싶으면 정적/인스턴스 메서드 참조(`ClassName::method`, `instance::method`)도 활용할 수 있다.

### 3. 스레드 제어와 생명주기 관리

- **스레드 제어 메서드**
  - `start()`: 새 스레드를 생성하고 `run()`을 실행한다. 같은 객체에 두 번 호출하면 `IllegalThreadStateException`이 발생한다.
  - `sleep()`: 현재 스레드를 지정 시간만큼 정지시키는 정적 메서드로, `InterruptedException`을 던질 수 있다.
  - `join()`: 다른 스레드의 종료를 대기해 스레드 간 순서를 제어한다. 타임아웃 버전(`join(ms)`)으로 무한 대기를 방지할 수 있다.
  - `interrupt()`: 스레드에 중단 신호를 보내는 메서드다. 강제 종료가 아니라 **협력적 중단**을 위한 메커니즘이라, 스레드가 `isInterrupted()`나 `sleep()`의 `InterruptedException`으로 신호를 확인하고 스스로 정리·종료해야 한다.
- **스레드 생명주기 6단계** (`Thread.State`)
  1. **NEW**: 객체만 생성, 아직 `start()` 호출 전 (`isAlive()` false).
  2. **RUNNABLE**: `start()` 이후 실행 중이거나 실행 대기 큐에서 스케줄러 할당을 기다리는 상태.
  3. **BLOCKED**: `synchronized` 진입 시 모니터 락을 다른 스레드가 보유해 대기하는 상태(락 경합으로 발생, CPU 미사용).
  4. **WAITING**: `Object.wait()`, `join()`(타임아웃 없음), `LockSupport.park()` 등으로 진입하는 무기한 대기. 외부의 `notify()`/`unpark()`/`interrupt()` 신호가 와야 복귀한다.
  5. **TIMED_WAITING**: `sleep(ms)`, `wait(ms)`, `join(ms)` 등 지정 시간만 대기하며, 시간이 지나면 자동으로 RUNNABLE로 돌아온다.
  6. **TERMINATED**: `run()`이 정상/예외로 종료된 상태. 다시 `start()` 할 수 없다.
- **핵심 용어**
  - **모니터 락(Monitor Lock)**: 객체가 가진 잠금 장치. `synchronized` 블록/메서드에 진입하려면 해당 객체의 모니터 락을 먼저 확보해야 하며, 락을 가진 스레드만 실행하고 나머지는 대기한다.
  - **`synchronized`**: 모니터 락을 사용하도록 해주는 키워드로, "한 번에 하나의 스레드만 실행"을 자바가 자동으로 보장(락 획득/해제)해준다.
  - **락 경합(Lock Contention)**: 여러 스레드가 같은 모니터 락을 동시에 차지하려고 경쟁하는 상황으로, 대기 스레드가 많아질수록 처리 속도가 느려진다.
  - **레이스 컨디션(Race Condition)**: 락이 없어서 여러 스레드가 같은 자원에 동시에 접근할 때 실행 순서에 따라 결과가 달라지는 상황. 재현이 불규칙해 버그로 이어지기 쉽다.
  - **임계 영역(Critical Section)**: 여러 스레드가 동시에 접근하면 문제가 생기는 공유 자원/코드 구간으로, 반드시 동기화 장치(모니터 락, `synchronized`, `ReentrantLock` 등)로 보호해야 한다.

### 4. 멀티스레드 환경의 문제점과 해결책

- **Race Condition의 원인**: `count++` 같은 단순 증가도 "읽기 → 계산 → 쓰기" 3단계로 나뉘기 때문에, 이 사이에 다른 스레드가 끼어들면 두 스레드가 같은 값을 읽고 각자 계산해 저장하면서 증가 횟수가 실제보다 적게 반영되는 비결정적 결과가 나온다.
- **해결책 - `synchronized`**: 임계 영역(읽기→계산→쓰기)을 `synchronized (lock) { ... }`로 감싸면 한 번에 하나의 스레드만 그 블록에 들어갈 수 있어 값이 정확하게 누적된다. 단, 동기화는 정확성을 높이지만 스레드가 번갈아 대기하므로 실행 시간이 길어질 수 있다.
- **스레드 안전한 컬렉션**: `ConcurrentHashMap`, `BlockingQueue` 등은 내부적으로 동시성을 안전하게 처리해주므로, 직접 `synchronized`를 걸지 않고도 멀티스레드 환경에서 안전하게 공유 자료구조를 다룰 수 있다.

### 5. Executor 프레임워크 소개

- **직접 스레드 생성의 문제점**: 매번 새 스레드를 만들면 스레드당 약 1MB의 스택 메모리 할당과 컨텍스트 스위칭 비용이 들고(생성 비용), 요청이 몰리면 스레드가 무제한 생성되어 `OutOfMemoryError`나 크래시로 이어질 수 있으며(수 제어 어려움), 대기 작업의 우선순위 처리도 어렵다(큐잉 부재).
- **Executor 추상화의 이점**: "무엇을 실행할 것인가(작업, Task)"와 "어떻게 실행할 것인가(실행 방식, Execution Policy)"를 분리한다. 동일한 작업을 단일 스레드 순차 처리, 스레드 풀 병렬 처리 등 다양한 전략으로 바꿔 끼울 수 있고, 스레드 풀로 스레드를 재사용해 생성/소멸 비용을 절감한다.
- **`Executor` vs `ExecutorService`**: `Executor`는 `execute(Runnable)` 하나만 제공해 완료 여부·결과를 알 수 없다. `ExecutorService`는 이를 확장해 `submit()`(Future 반환), `shutdown()`/`shutdownNow()`(종료), `invokeAll()`/`invokeAny()`(일괄 처리), `isShutdown()`/`isTerminated()`(상태 확인)를 추가로 제공한다.
- **실무 팁**: `ExecutorService`의 워커 스레드는 기본적으로 non-daemon이라, `shutdown()`/`shutdownNow()`를 호출하지 않으면 JVM이 종료되지 않고 계속 대기하거나 메모리 누수가 생길 수 있다. 사용 후 반드시 명시적으로 종료해야 한다.

### 6. 다양한 스레드 풀 유형과 활용

- **`SingleThreadExecutor`**: 단일 워커 스레드로 작업을 FIFO 순서로 순차 실행한다. 상태를 공유하거나 순서가 중요한 작업(로그 기록, 시퀀스 생성 등)에 적합하다.
- **`execute()` vs `submit()`**: `execute()`는 Runnable을 실행만 하고 결과를 반환하지 않는 "발사 후 망각(fire-and-forget)" 방식이라 예외는 로그로만 확인된다. `submit()`은 Future를 반환해 완료 상태·결과를 받을 수 있고, 예외는 `get()` 시 `ExecutionException`으로 전달된다.
- **`FixedThreadPool`**: 고정된 스레드 수로 예측 가능한 성능을 제공하지만, 작업량이 급증하면 큐에 작업이 누적되고 작업이 적으면 유휴 스레드가 자원을 낭비한다. 서버 요청 처리처럼 가장 일반적으로 쓰인다.
- **`CachedThreadPool`**: 필요할 때 스레드를 동적으로 생성/재사용하고 60초간 미사용 스레드는 자동 제거한다. 짧고 예측 불가능한 버스트 트래픽에 유리하지만 무제한 증가 위험이 있다.
- **`ScheduledThreadPool`**: 지연 실행(`schedule()`), 시작 시간 기준 고정 주기 반복(`scheduleAtFixedRate()`), 이전 작업 종료 후 일정 지연 반복(`scheduleWithFixedDelay()`)을 지원한다. 모니터링·메트릭 수집·배치 처리 등에 쓰이며, Spring의 `@Scheduled`도 유사한 개념을 사용한다.
- **`ThreadPoolExecutor` 커스텀 구성**: `corePoolSize`(기본 유지 스레드 수)·`maximumPoolSize`(최대 스레드 수)·`workQueue`(대기 큐)·`RejectedExecutionHandler`(큐와 풀이 모두 가득 찼을 때의 거부 정책)를 직접 지정해 세밀하게 제어할 수 있다.
- **실무 팁**: 스레드 풀 크기는 작업 특성(CPU 바운드는 코어 수에 근접, I/O 바운드는 더 많은 스레드)을 고려해 결정해야 한다.

### 7. Future와 Callable 인터페이스

- **Runnable의 한계**: `void` 반환이라 결과를 전달할 수 없고, 체크 예외를 던질 수 없으며, 완료 시점을 확인하기 어렵다. 이를 해결하기 위해 제네릭 기반으로 타입 안전한 결과를 반환하는 **`Callable<T>`**가 도입되었다.
- **Future**: 비동기 작업 결과의 플레이스홀더 역할을 하는 객체("미래에 결과가 도착할 것이라는 계약서"). `get()`은 블로킹 호출로 작업이 끝날 때까지 대기하며, `get(timeout, unit)`으로 타임아웃을 걸고 `TimeoutException` 시 `cancel(true)`로 작업을 취소할 수 있다.
- **`invokeAll()` / `invokeAny()`**: `invokeAll()`은 제출한 모든 작업이 끝날 때까지 대기하고 Future 리스트를 반환한다(가장 오래 걸리는 작업 기준). `invokeAny()`는 가장 먼저 끝난 작업의 결과만 반환하고 나머지는 취소한다(여러 대안 중 하나만 성공하면 될 때 유용).
- **Future의 한계**: `get()`이 블로킹이라 논블로킹 비동기 프로그래밍에 부적합하고, 완료 시 자동 호출되는 콜백을 등록할 수 없으며, 한 작업의 결과를 다음 작업의 입력으로 잇는 파이프라인 구성이 어렵다. 이 한계를 극복하기 위해 Java 8에서 **CompletableFuture**가 도입되었다.

### 8. 실전 비동기 패턴 (Producer-Consumer, Fork-Join)

- **Producer-Consumer 패턴**: 생산자가 데이터를 만들고 소비자가 처리하는 패턴으로, 두 역할의 처리 속도 차이를 조절해 전체 처리량을 최적화한다. `BlockingQueue`(`LinkedBlockingQueue`, `ArrayBlockingQueue` 등)를 쓰면 큐가 가득 차면 `put()`이 자동 대기하고, 큐가 비면 `take()`가 자동 대기해 별도 동기화 코드 없이 안전하게 구현할 수 있다(예: 카페의 캐셔=생산자, 바리스타=소비자).
- **Fork-Join 프레임워크**: 분할 정복(Divide and Conquer) 알고리즘을 병렬로 실행하는 데 특화된 프레임워크다. `RecursiveTask`(결과 반환)/`RecursiveAction`(결과 없음)를 상속해 작업이 임계값(threshold)보다 크면 절반으로 나눠 `fork()`(비동기로 한쪽 실행)하고 다른 쪽을 직접 계산한 뒤 `join()`으로 합친다. 대용량 배열 합계 계산 같은 CPU 집약적 작업에 효율적이다.

### 9. CompletableFuture 기초와 생성

- **등장 배경**: Future는 완료 시점을 능동적으로 감지할 콜백 메커니즘이 없어 작업 파이프라인 구성이 비효율적이었다. CompletableFuture는 Stream API와 유사한 함수형 스타일(`map`↔`thenApply`, `thenCompose`, `thenCombine` 등)로 비동기 워크플로우를 선언적으로 표현할 수 있게 해준다.
- **생성 방법**: `runAsync()`는 반환값이 없는 작업(로깅, 알림 전송 등 부수 효과 목적)을, `supplyAsync()`는 값을 반환하는 작업(API 호출, 계산, DB 조회 등)을 비동기로 실행한다. 기본적으로 `ForkJoinPool.commonPool()`을 쓰지만, 두 번째 인자로 커스텀 `Executor`를 넘기면 작업 성격별로 전용 스레드 풀을 분리할 수 있다.
  - **부수 효과(Side Effect)**: 함수가 결과를 반환하는 것 외에 외부 상태를 바꾸거나 관찰 가능한 변화를 일으키는 행위(콘솔 출력, 파일 수정, 네트워크 요청 등). 순수 함수와 대비되는 개념이다.
- **기본 처리 메서드 3종**
  - `thenApply()`: Stream의 `map()`과 동일하게 이전 결과를 받아 새 값으로 **변환**한다(동기적 변환).
  - `thenAccept()`: 이전 결과를 받아 **소비**하지만 새 값을 반환하지 않는다(부수 효과 발생 목적).
  - `thenRun()`: 이전 결과와 **무관하게** 실행되는 후속 작업(정리·로깅 등 하우스키핑).
  - 체이닝 메서드는 모두 새 CompletableFuture 인스턴스를 반환하므로 원본 결과는 보존되며 여러 브랜치로 분기할 수 있다.

### 10. 비동기 작업 조합과 연결

- **`thenCompose()`**: 이전 작업의 결과를 **다음 비동기 작업의 입력**으로 사용할 때 쓴다. `thenApply()`가 동기적 변환이라면 `thenCompose()`는 비동기적 변환이며, 중첩된 `CompletableFuture<CompletableFuture<T>>`를 평탄화(flatten)한다. 회원가입(ID 생성 → 프로필 생성 → 환영 이메일)처럼 단계 간 의존성이 있는 순차 워크플로우에 적합하고, 예외가 발생하면 체인 전체가 중단된다.
- **`thenCombine()`**: 서로 **독립적인 두 작업**이 모두 끝나면 그 결과들을 조합해 새 값을 만든다(예: 가격 조회와 할인 조회를 병렬로 실행 후 할인가 계산). 순차 처리보다 전체 대기 시간이 단축된다.
- **`allOf()` / `anyOf()`**: `allOf()`는 여러 작업이 **모두** 끝날 때까지 대기한다(상품 상세 페이지처럼 이미지·설명·리뷰가 모두 필요한 경우). `anyOf()`는 **가장 빨리** 끝난 작업 하나의 결과만 쓰고 나머지는 무시한다(여러 견적 중 가장 빠른 응답 채택).

### 11. 예외 처리와 회복 전략

- **비동기 예외의 특성**: 예외가 발생한 스레드와 처리하는 스레드가 다를 수 있고, 여러 작업이 병렬로 실행될 때 일부 실패가 전체 워크플로우에 미치는 영향을 제어해야 한다.
- **`exceptionally()`**: 예외 발생 시 **대체값**을 제공해 워크플로우를 복구한다(Fallback 패턴). 결제 API 실패 시 "점검 중입니다" 같은 안전한 대체 응답을 줄 수 있다.
- **`handle()`**: 성공(`result`)과 실패(`exception`)를 **모두 받아** 단일한 결과 타입으로 변환한다. 성공/실패 여부와 무관하게 일관된 응답 형태를 보장해야 할 때 쓴다.
- **`whenComplete()`**: 결과를 **바꾸지 않고** 완료 시점에 부수 작업(로깅, 모니터링)만 수행한다. 핵심 비즈니스 로직과 횡단 관심사(Cross-cutting Concern)를 분리하는 AOP적 개념으로 볼 수 있다.
- **체이닝에서의 예외 전파**: 체인 중간에서 예외가 발생하면 그 지점부터 나머지 단계는 건너뛰고, 예외 처리 메서드가 나올 때까지 예외가 전파된다(**fail-fast 원칙** — 문제를 최대한 빨리 드러내 잘못된 상태가 퍼지지 않게 함). 예외 처리 메서드는 너무 일찍 두면 후속 예외를 놓치고, 너무 늦게 두면 복구 기회를 잃으므로 체인의 적절한 위치에 배치해야 한다.

### 12. 실전 활용 패턴과 모범 사례

- **타임아웃 처리**: `orTimeout()`은 시간 초과 시 `TimeoutException`으로 **실패** 처리한다(엄격한 SLA가 중요할 때). `completeOnTimeout()`은 시간 초과 시 **기본값**(예: 캐시 데이터)으로 완료시킨다(사용자 경험이 우선일 때).
  - **SLA(Service Level Agreement)**: 서비스 제공자와 사용자가 합의한 가용성·응답 시간 등 품질 보장 기준.
- **대량 데이터 처리 최적화**: CPU 바운드 작업은 병렬 스트림이, I/O 바운드 작업은 CompletableFuture가 적합하며, 둘을 조합해(`parallelStream()` + `thenCombine()`/`allOf()`) 대량 SKU의 가격·재고 조회 같은 작업을 최적화할 수 있다. 실무에서는 rate limit·메모리·대역폭을 고려해 보통 50~200개 단위로 배치 처리한다.
- **복합 비즈니스 워크플로우**: 전자상거래 주문 처리처럼 순차 단계(`thenCompose`로 장바구니 검증 → 재고 예약 → 결제 → 배송 정보 생성, `orTimeout`으로 결제 타임아웃 설정)와 병렬 후속 처리(`allOf` + `runAsync`로 이메일·SMS·CRM 업데이트 동시 실행), 그리고 `whenComplete`(모니터링)·`handle`(최종 응답)·`exceptionally`(실패 응답)를 종합적으로 조합한다.
- **성능 최적화**: 작업 특성(CPU 집약적/I·O 집약적/혼합형)에 맞춰 전용 스레드 풀 크기를 다르게 설정해야 한다(예: CPU 집약적은 코어 수만큼, I/O 집약적은 더 많은 스레드). 체인이 길어지거나 순환 참조가 생기면 메모리 누수가 발생할 수 있어 주의가 필요하다.
