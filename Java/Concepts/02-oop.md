# 객체지향 프로그래밍의 이해

> Java 기초 학습 기록 — 노션 내용 정리 예정

## 개념 정리

### 1. 객체지향 프로그래밍의 개념과 필요성

- **객체(Object)**: 현실 세계에서 인지 가능한 모든 대상(사물, 사람, 개념)을 프로그래밍에서 표현한 것. **상태(state)와 행동(behavior)을 가진 독립적인 단위**.
- **클래스(Class)**: 객체를 만들기 위한 설계도. 객체는 클래스로부터 생성된 실체(인스턴스).
- **메시지 / 협력**: 객체 간의 상호작용은 메서드 호출(메시지 전달)로 이루어지며, 여러 객체가 협력하여 하나의 프로그램을 완성한다.
- **절차지향 vs 객체지향**: 절차지향은 "기능을 어떻게 구현할까?"(절차 중심)를 묻는 반면, 객체지향은 "누가 이 기능을 담당해야 하지?"(책임 중심)를 묻는다. 소프트웨어를 독립적 단위(객체)로 나누고 메시지를 주고받으며 협력하게 만든다.
- **장점**: 유지보수성(책임을 맡은 객체만 수정), 확장성(상속·인터페이스로 구현체 추가 용이), 재사용성(공통 객체·라이브러리화).
- **단점**: 초기 설계 부담(객체 분할·협력 설계 실패 시 복잡도 증가), 학습 곡선.

### 2. Java의 클래스와 객체

- **필드(Fields)**: 인스턴스 변수(객체마다 독립된 값)와 클래스 변수(`static`, 모든 인스턴스가 공유).
- **생성자(Constructor)**: 객체 생성 시 필드를 초기화. 기본 생성자, 오버로딩된 생성자, `this()`를 통한 생성자 간 호출이 가능하다.
- **메소드와 오버로딩/가변인자**: 메소드 시그니처는 이름+파라미터 목록으로 결정된다(접근제어자·반환타입·파라미터명은 시그니처에 영향 없음). 가변인자(`...`)는 내부적으로 배열로 처리되며, 오버로딩과 함께 쓰면 호출이 모호해질 수 있어 주의가 필요하다. 호출 우선순위는 **고정 파라미터 > 박싱/언박싱 > varargs**.
- **static 키워드**: 인스턴스 없이 클래스 이름으로 호출 가능한 static 메소드, 클래스 로딩 시 1회 실행되는 static 초기화 블록, 클래스 이름 없이 호출하게 해주는 static import. 싱글톤 패턴은 `private` 생성자 + `static` 필드/메소드로 구현한다.

  **"클래스에 속한다" vs "인스턴스에 속한다" 시각화**

  static 멤버는 클래스가 로드될 때 메소드 영역에 **딱 하나만** 만들어져서 모든 인스턴스가 같은 것을 공유하고, 인스턴스(비-static) 멤버는 `new`로 객체를 만들 때마다 힙에 **각자 따로** 만들어진다. 그래서 static 필드를 한 인스턴스에서 바꾸면 다른 모든 인스턴스에서도 바뀐 값이 보이지만, 인스턴스 필드는 서로 완전히 독립적이다.

  ```mermaid
  flowchart TB
      subgraph CLASS["Order 클래스 (메소드 영역) — 딱 1개, 모든 인스턴스가 공유"]
          SF["static double VAT_RATE = 0.1"]
      end

      subgraph HEAP["힙(Heap) — new 할 때마다 인스턴스별로 새로 생성"]
          I1["order1\norderId = 'A001'\nisPaid = false"]
          I2["order2\norderId = 'A002'\nisPaid = true"]
          I3["order3\norderId = 'A003'\nisPaid = false"]
      end

      I1 -.같은 걸 참조.-> SF
      I2 -.같은 걸 참조.-> SF
      I3 -.같은 걸 참조.-> SF
  ```

  - `orderId`, `isPaid`는 인스턴스 필드라서 `order1`, `order2`, `order3`이 각자 독립된 값을 가진다 (한쪽을 바꿔도 다른 쪽엔 영향 없음).
  - `VAT_RATE`는 static 필드라서 `Order` 클래스 자체에 단 하나만 존재하며, `order1.VAT_RATE`든 `order2.VAT_RATE`든 결국 같은 메모리를 가리킨다 — 즉 어느 인스턴스를 거쳐 접근해도 실제로는 "클래스"가 가진 값 하나를 보는 것이다.
- **JVM 메모리 구조**
  - **메소드 영역**: 클래스 바이트코드, 상수풀, static 필드 등 (모든 스레드 공유)
  - **힙(Heap)**: `new`로 생성된 모든 객체 인스턴스, GC 대상
  - **스택(Stack)**: 스레드별 지역변수·매개변수·리턴주소가 쌓이는 스택 프레임
  - **PC 레지스터 / 네이티브 메소드 스택**
  - 객체 생성 과정: 클래스 로딩 확인 → 힙에 공간 할당 → 필드 기본값 초기화 → 생성자 실행 → 스택에 참조 저장
- **가비지 컬렉션(GC)**: Mark and Sweep(도달 가능한 객체 마킹 후 나머지 제거), Generational GC(Young/Old 영역으로 나눠 효율화), Stop-the-world(GC 중 스레드 일시 정지).
- **메모리 누수 원인**: 컬렉션에 넣고 제거하지 않는 경우, static 필드의 장기 참조, 잘못된 객체 풀 사용, 리스너/콜백 미해제. 대응책은 명시적 제거, try-with-resources, WeakReference, 모니터링.

### 3. 객체지향 4대 핵심 개념

**추상화(Abstraction)**
- 복잡한 현실을 단순화해 필요한 속성·행위만 모델링하는 것. 인터페이스, 추상 클래스, 컴포지션으로 구현한다.
- 이점: 중복 코드 감소, 도메인 구조 명확화, 확장성 확보(새 구현체만 추가).
- 주의점: 과도하게 세분화된 추상화(불필요한 클래스 분할)는 오히려 유지보수를 어렵게 하므로, 실제 비즈니스 로직 차이가 있을 때만 추상화 단위를 나눠야 한다.

**상속(Inheritance)**
- 부모(상위) 클래스의 속성/메소드를 자식(하위) 클래스가 물려받아 재사용하는 기법. `extends`, `super` 키워드 사용. **IS-A 관계**를 코드로 표현(예: `BusinessUser`는 `User`이다).
- 장점: 공통 코드 재사용, 확장성, 다형성 기반 제공.
- 단점: 깊은 상속 계층의 복잡성, 강한 결합도, IS-A 관계가 아닌데 상속을 쓰는 오버엔지니어링 위험.
- **컴포지션(Composition)**: "A는 B를 가지고 있다"는 **HAS-A 관계**. 전체-부분 생명주기가 일치하거나 IS-A 관계가 불명확할 때 상속 대신 사용. 결합도를 낮추고 구현체 교체를 유연하게 하므로, 단순 기능 재사용 목적이라면 상속보다 컴포지션을 우선 고려하는 것이 원칙이다.

**다형성(Polymorphism)**
- 하나의 타입(인터페이스)에 대해 여러 구현을 연결할 수 있는 능력. 실제 실행될 메소드는 런타임에 결정된다(**동적 바인딩**).
- **오버라이딩**(부모 메소드 재정의) vs **오버로딩**(동일 이름, 다른 파라미터).
- **업캐스팅**: 자식 객체를 부모 타입으로 참조(안전). **다운캐스팅**: 부모 타입 참조를 자식 타입으로 변환(`ClassCastException` 위험이 있어 `instanceof`로 확인 필요).
- 인터페이스와 결합하면 새로운 구현체 추가 시 기존 코드(예: `OrderService`) 수정 없이 확장 가능해진다.

**캡슐화(Encapsulation)**
- 객체 내부 데이터·로직을 외부로부터 보호하고 필요한 부분만 공개하는 **정보 은닉**. 데이터 무결성 보장, 결합도 감소, 유지보수성 향상, 보안 강화가 목적.
- **접근 제어자**: `private`(같은 클래스) < `package-private`(같은 패키지) < `protected`(패키지+상속) < `public`(전체 공개).
- **Java Bean 규약**: 기본 생성자 제공, 필드는 private + getter/setter로 접근, `getXxx`/`setXxx`/`isXxx` 명명 규칙, 직렬화 가능.
- 내부 상태(예: 계좌 잔액)는 공개 메소드(`deposit`, `withdraw`)를 통해서만 검증을 거쳐 변경하도록 설계해야 안전하다.
- **불변 객체(Immutable Object)**: 생성 후 상태가 변경되지 않는 객체(예: `String`). 모든 필드가 `final`이며 수정 메소드를 제공하지 않는다. 멀티스레드 환경에서 동기화 부담 없이 안전하게 공유 가능.

**4가지 개념과 구현 수단의 관계**: `abstract class`, `interface`, `composition` 각각이 추상화·상속·다형성·캡슐화를 실현하는 정도가 다르며, 실제 설계에서는 이들을 조합해서 사용한다.

### 4. SOLID 원칙

OOP의 4대 특성을 실무적으로 잘 지키기 위한 5가지 설계 지침. (OOP 원칙이 "철학"이라면 SOLID는 "실천 방법론".)

- **SRP (단일 책임 원칙)**: 클래스는 단 하나의 변경 이유만 가져야 한다. 예: 사용자 데이터 관리(`UserRepository`), 서비스 로직(`UserService`), 인증/인가(`AuthService`)로 책임 분리.
- **OCP (개방-폐쇄 원칙)**: 확장에는 열려 있고 변경에는 닫혀 있어야 한다. 새 결제 수단 추가 시 기존 `if-else`를 고치는 대신, `Payment` 인터페이스를 구현한 새 클래스만 추가하면 되도록 설계.
- **LSP (리스코프 치환 원칙)**: 부모 타입 자리에 자식 타입을 넣어도 프로그램이 정상 동작해야 한다. (`Square`가 `Rectangle`을 상속하면서 `setWidth`/`setHeight` 계약을 깨는 예시로 위반 사례를 설명 — `Shape` 인터페이스로 재설계하여 해결.)
- **ISP (인터페이스 분리 원칙)**: 클라이언트가 사용하지 않는 메소드에 의존하지 않도록 인터페이스를 기능별로 잘게 나눈다.
- **DIP (의존성 역전 원칙)**: 고수준 모듈이 저수준 모듈의 구체 구현이 아니라 추상화(인터페이스)에 의존해야 한다. 스프링의 의존성 주입(DI)이 대표적 구현 방식.

### 5. 내부 클래스와 익명 클래스

- **내부 클래스 종류**: 정적 중첩 클래스(`static`, 외부 인스턴스 불필요, 외부의 static 멤버만 접근), 비정적 내부 클래스(외부 인스턴스를 통해서만 생성, 외부 인스턴스 멤버 접근 가능), 지역 내부 클래스(메소드 내부에서만 유효, 참조하는 지역변수는 effectively final이어야 함).
- **익명 클래스**: 인터페이스/추상 클래스를 이름 없이 즉석에서 구현하는 문법(`new 타입() { ... }`). 한 번만 쓰는 구현체에 적합하며, 내부의 `this`는 익명 클래스 자기 자신을 가리킨다.
- **함수형 인터페이스와 람다**: 추상 메소드가 하나뿐인 인터페이스(`@FunctionalInterface`)는 람다식(`(파라미터) -> {...}`)으로 간결하게 구현 가능. 람다 내부의 `this`는 람다를 감싼 외부 객체를 가리킨다는 점이 익명 클래스와 다르다. 추상 메소드가 여러 개거나 상태가 필요하면 익명 클래스를 사용해야 한다.

### 6. Enum (열거 타입)의 활용

- **정의**: 미리 정의된 상수 집합을 타입 안전하게 표현하는 특별한 클래스. `static final` 상수보다 컴파일 시 유효성 검사, 가독성, 유지보수성이 뛰어나다.
- **기본 메소드**: `values()`(모든 상수 배열), `ordinal()`(선언 순서 인덱스), `name()`(상수 이름 문자열).
- **필드/생성자/메소드 추가**: enum도 클래스처럼 각 상수마다 고유 데이터(필드)와 행위(메소드)를 가질 수 있다. enum 생성자는 상수 초기화 시 자동 호출되며 항상 `private`(또는 패키지 접근)이다.
- **switch문과 결합**: enum을 `switch`에 사용하면 타입 안전하게 분기 처리할 수 있고, 정의되지 않은 값은 컴파일 단계에서 걸러진다.
- 상태와 행위를 함께 정의할 수 있어 객체지향적 설계와 유사하며, `EnumSet`/`EnumMap`으로 효율적인 집합 연산도 가능하다.

### 7. 예외 처리

- **Error vs Exception**: `Error`는 시스템적 치명적 오류(복구 거의 불가, 예: `OutOfMemoryError`), `Exception`은 개발자 실수나 외부 요인(대부분 복구 가능). 모든 오류/예외는 `Throwable`을 상속한다.
- **Checked Exception**: 컴파일 시점에 처리(`try-catch`/`throws`)가 강제되는 예외(`IOException`, `SQLException` 등, 주로 외부 요인). **Unchecked Exception**(`RuntimeException` 계열)은 컴파일러가 강제하지 않으며 주로 프로그래밍 로직 오류(`NullPointerException`, `ArrayIndexOutOfBoundsException` 등)에서 발생 — 클라이언트가 복구 가능하면 Checked, 코드 수정이 필요한 로직 오류면 Unchecked를 사용한다.
- **try-catch-finally**: try(위험 코드) → catch(구체적 타입부터 순서대로 처리) → finally(예외 발생 여부와 무관하게 항상 실행, 주로 자원 정리).
- **try-with-resources**: `AutoCloseable`/`Closeable` 자원을 자동으로 `close()`시켜주는 구문(Java 7+). `finally`로 직접 자원을 닫는 것보다 안전하고 간결하다.
- **베스트 프랙티스**
  - **Fail-Fast**: 문제를 가능한 빨리 감지해 즉시 예외를 던져 오류 전파를 막는다.
  - **예외 삼키기(Swallowing) 금지**: catch 블록에서 아무 처리 없이 무시하면 디버깅이 불가능해지므로, 반드시 로깅하거나 재던진다.
  - **예외 전환(Chaining/Wrapping)**: 저수준 예외(`SQLException`)를 도메인 예외(`DataAccessException`)로 감싸 원인(cause)을 보존한 채 재포장한다.
  - **의미 있는 메시지와 로깅**: 구체적인 예외 메시지와 예외 객체를 함께 로깅해 원인 추적을 쉽게 한다.

### 8. UML을 활용한 객체지향 설계 시각화

- **UML**: 객체지향 시스템을 설계·문서화·시각화하기 위한 표준 언어. 시각화, 명세화, 구축(코드 변환), 문서화 기능을 가진다.
- **클래스 다이어그램**: 클래스의 필드/메소드와 접근 범위(`+` public, `-` private, `#` protected, `~` package-private)를 표현하는 정적 구조 다이어그램. 클래스 간 관계는 연관(실선), 의존(점선 화살표), 집합(빈 마름모, 느슨한 생명주기), 합성(채워진 마름모, 강한 생명주기), 일반화(빈 삼각형, 상속), 구현(점선+빈 삼각형, 인터페이스 구현)으로 구분된다.
- **시퀀스 다이어그램**: 객체(생명선) 간 메시지 교환을 시간 순서로 표현해 협력 흐름을 시각화한다.
- **작성 도구**: Mermaid(Markdown 기반, GitHub 지원), PlantUML(텍스트 기반), draw.io, Lucidchart 등.
