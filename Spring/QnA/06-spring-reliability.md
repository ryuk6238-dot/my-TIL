# Spring 안정성 높이기 — Q&A

### Q1. 외부 시스템 연동 실패가 왜 "우리가 직접 제어할 수 없는 영역"인가

> **Q.** 외부 시스템 연동 실패: 결제·소셜 로그인·이메일 발송 등 우리가 직접 제어할 수 없는 영역 — 이게 왜 우리가 직접 제어할 수 없다는거지? 백엔드 로직만드로는 간섭이 불가능하다는거야?
>
> "우리가 직접 제어할 수 없다"는 건 백엔드 로직으로 개입이 아예 불가능하다는 뜻이 아니라, 장애가 발생하는지 여부 자체를 우리 쪽에서 결정할 수 없다는 의미다.
>
> 구분해서 보면:
>
> - 우리가 통제 가능한 영역: 우리 서버 안에서 도는 코드, DB 스키마, 비즈니스 로직 — 버그가 나면 우리가 고치면 끝이다.
> - 우리가 통제 불가능한 영역: 결제 게이트웨이(토스페이먼츠, 카카오페이 등), 소셜 로그인 제공자(구글, 카카오), 이메일 발송 서비스(SendGrid 등)는 다른 회사가 운영하는 서버다. 그 서버가 지금 이 순간 살아있는지, 응답 속도가 얼마나 걸릴지, 자기들 쪽 버그로 500 에러를 뱉는지, API 스펙을 갑자기 바꾸거나 요청 한도(rate limit)를 초과시켰는지는 전부 상대방 인프라 안에서 벌어지는 일이라 우리 백엔드 코드로는 원인을 고칠 수도, 발생 자체를 막을 수도 없다. 우리가 할 수 있는 건 그쪽에 HTTP 요청을 보내고 응답(또는 무응답)을 받는 것뿐이다.
>
> 그래서 노션 원문에서도 "타임아웃 설정, 재시도 로직, 대체 수단 제공"을 대비책으로 제시한다 — 장애를 막는 게 아니라, 장애가 났을 때 우리 서비스가 어떻게 반응할지는 우리가 통제할 수 있다는 뜻이다. 예를 들어 결제 API가 타임아웃되면 무한정 기다리지 않고 일정 시간 후 실패 처리 + 재시도, 소셜 로그인이 다운되면 이메일/비밀번호 로그인 같은 대체 수단 안내, 이메일 발송이 실패하면 회원가입 자체는 막지 않고 나중에 비동기로 재시도하는 식이다.
>
> 즉 "간섭 불가능"이 아니라 "원인 발생 지점에 대한 통제권이 없다 → 그러니 우리 쪽 대응 전략(타임아웃/재시도/폴백)을 미리 설계해둬야 한다"는 논리다.

> **Q.** 음 그러니까 우리가 에러를 발생시킬 수 없나는 뜻이지?
>
> 정확히 그 뜻이다.
>
> - 에러가 "발생하는지 여부"는 우리 쪽 결정이 아니다 — 결제사 서버가 다운되든, 응답이 느리든, 자기들 버그로 500을 뱉든, 그건 전적으로 상대방 인프라 사정이다. 우리 백엔드 코드가 아무리 잘 짜여 있어도 저쪽 서버가 죽는 것 자체를 막을 방법은 없다.
> - 대신 우리는 그 에러에 어떻게 반응할지만 결정할 수 있다. 즉 에러 발생 자체는 우리 손을 떠난 일이고, 에러 이후의 대응(타임아웃 처리, 재시도, 대체 수단 제공, 로깅)만 우리가 설계 가능한 영역이다.
>
> 비유하자면: 택배 기사가 배송 중 사고가 나는 걸 내가 막을 순 없지만, "사고 나면 다른 기사를 보낸다"는 대응 매뉴얼은 내가 만들 수 있는 것과 같은 구조다.

### Q2. 예외 추상화/변환 — "예외에 공통 로직을 설정할 수 있다"는 뜻인가

> **Q.** 예외 추상화/변환 이게 그러니까 예외를 공통로직 설정 가능하다는거지?
>
> 거의 맞지만, 정확히는 "공통 로직을 설정할 수 있다"는 결과이고 핵심은 "서로 다른 기술의 예외들을 하나로 통일(변환)한다"는 것이다.
>
> 무슨 일이 벌어지는지:
>
> - JDBC를 직접 쓰면 DB 벤더마다 오류 코드가 다 다르다. Oracle은 `ORA-00001`, MySQL은 `1062`처럼 벤더별로 제각각인 `SQLException`이 던져진다.
> - Spring은 이 벤더별 오류 코드를 내부적으로 분석해서, `DuplicateKeyException`, `DataIntegrityViolationException`처럼 의미가 명확한 Spring 표준 예외(`DataAccessException` 계층)로 바꿔서 던져준다. 이게 예외 변환(Exception Translation)이고, 그 결과로 만들어지는 통일된 예외 체계가 예외 추상화다.
>
> 그래서 왜 좋은가 (= "공통 로직" 부분):
>
> - 원래대로면 "Oracle 오류코드면 A처리, MySQL 오류코드면 B처리"처럼 벤더마다 다른 catch 로직을 짜야 했을 것이다.
> - 하지만 Spring이 벤더별 차이를 흡수해서 `DuplicateKeyException` 하나로 통일해주니까, 개발자는 DB가 Oracle이든 MySQL이든, JPA든 MyBatis든 상관없이 동일한 catch 블록 하나만 작성하면 된다. 즉 기술이 바뀌어도 재사용 가능한 하나의 공통 예외 처리 로직을 짤 수 있게 되는 것이다.
>
> 정리하면: 예외 자체에 공통 로직을 심는다는 뜻이 아니라, 기술마다 제각각인 예외를 하나의 표준 예외 체계로 변환해줘서, 그 결과 우리가 짜는 예외 처리 코드는 기술 독립적인 공통 로직이 될 수 있다는 것이다.

> **Q.** 음 그러니까 db벤더 마다 오류 코드가 다르게 나오는게 이걸 공통 예외롤 처리해서 유지보수성을 높일 수 있다? 맞아?
>
> 정확히 맞다. 유지보수성이 왜 올라가는지 구체적으로 짚으면:
>
> - 코드 중복 감소: 벤더별 오류 코드마다 분기 처리를 안 해도 되니, catch 블록 하나로 끝난다.
> - 기술 변경에 강해짐: DB를 Oracle → PostgreSQL로 바꾸거나, JDBC → JPA로 마이그레이션해도, 예외 처리 코드(`catch (DuplicateKeyException e)` 등)는 그대로 재사용된다. 벤더/기술이 바뀌는 건 Spring이 알아서 흡수해준다.
> - 결합도 감소: 비즈니스 로직이 특정 DB 벤더의 세부 오류 코드에 의존하지 않게 되어, 서비스 코드가 인프라 세부사항으로부터 분리된다.
>
> 정리하면: 벤더마다 다른 오류 코드 → Spring이 공통 예외로 변환 → 개발자는 그 공통 예외 하나만 처리하면 됨 → 기술이 바뀌어도 코드를 안 고쳐도 되니 유지보수성이 올라간다는 흐름이 맞다.

> **Q.** 근데 DB 벤더가 뭐야
>
> "벤더(vendor)"는 그냥 제조사/공급사라는 뜻이다. 그러니까 DB 벤더 = 데이터베이스 소프트웨어를 만들어서 파는(또는 배포하는) 회사/주체를 말한다.
>
> 예를 들면 Oracle(Oracle Database를 만드는 회사), MySQL(원래 MySQL AB가 만들었고 지금은 Oracle이 소유), PostgreSQL(특정 회사가 아니라 오픈소스 커뮤니티가 개발/배포), Microsoft SQL Server(Microsoft), MariaDB(MySQL에서 갈라져 나온 오픈소스 프로젝트) 등이 있다.
>
> 이 회사/프로젝트마다 자기들만의 방식으로 DB를 구현했기 때문에, 똑같은 "중복 키 오류" 상황이라도 내부적으로 뱉는 에러 코드가 다 다르다. Oracle은 `ORA-00001`, MySQL은 `1062`(에러 번호) 같은 식이다.
>
> 즉 "DB 벤더마다 오류 코드가 다르다"는 말은, DB 제조사가 회사마다 다르다 보니 그 회사들이 각자 정한 오류 코드 체계도 서로 다르다는 뜻이다.

> **Q.** 아 그러니까 다른 db종류 뭐 이렇게 생각해보되겠네?
>
> 그렇게 생각해도 충분하다. "DB 벤더가 다르다" ≈ "쓰는 DB 종류(제품)가 다르다"로 이해하면 된다. Oracle DB, MySQL, PostgreSQL, SQL Server가 다 서로 다른 DB 종류이고, 그 각각을 만든/배포한 주체를 부를 때 "벤더"라는 단어를 쓰는 것뿐이다.
>
> 정리: "DB 벤더가 다르다" = "쓰는 DB 제품(종류)이 다르다" — 같은 말이다. "벤더"라는 단어는 좀 더 공식적/기술적인 자리에서 "그 제품을 만든 회사"라는 뉘앙스를 강조할 때 쓰는 표현일 뿐, 실질적으로는 "DB 종류"라고 생각하고 넘어가도 무방하다.

### Q3. Logback이 로그 메시지를 생성해서 출력해주는 것인가

> **Q.** 기본 로깅 프레임워크로 Logback을 사용하며 logback이라는게 로그 메세지를 생성해서 출력해주는거야?
>
> 큰 틀에서는 맞다. 조금 더 구조적으로 보면 Logback은 로그 메시지를 만들고 내보내는 파이프라인 전체를 담당하는 프레임워크다.
>
> 세 가지 구성요소가 협업하는 구조:
>
> - Logger: 코드에서 `log.info("주문 완료")` 처럼 호출하면, 이 메시지를 "생성"하는 역할
> - Layout/Encoder: 그 메시지를 어떤 형식으로 보여줄지 결정 (`%d{HH:mm:ss} [%thread] %level - %msg%n` 같은 패턴)
> - Appender: 형식이 정해진 로그를 실제로 어디에 "출력"할지 결정 (콘솔, 파일, 나중엔 Kafka나 외부 로그 수집 시스템 등)
>
> 그러니까 흐름은 `Logger가 메시지 생성 → Encoder가 형식 적용 → Appender가 출력`이다.
>
> 하나 더 알아두면 좋은 점: 코드에서는 사실 Logback을 직접 부르는 게 아니라 SLF4J(Simple Logging Facade for Java)라는 인터페이스를 통해 호출한다. Logback은 그 SLF4J 뒤에서 실제로 동작하는 "구현체"다. Spring Boot는 `spring-boot-starter-web`만 추가해도 Logback이 기본으로 내장되어 있어서 별도 설정 없이 바로 `LoggerFactory.getLogger(...)`로 로깅을 쓸 수 있다.

> **Q.** Encoder가 형식 적용 여기서 말하는 형식은 로그레벨을 말하는거야?
>
> 아니다. 로그 레벨은 그 형식(패턴) 안에 포함되는 여러 정보 중 하나일 뿐이다. Encoder가 결정하는 "형식"은 로그 한 줄이 어떤 정보들을 어떤 순서/모양으로 담을지에 대한 전체 틀(pattern)을 말한다.
>
> 예를 들어 이런 패턴이 있다고 하면:
>
> ```
> %d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n
> ```
>
> 여기 들어가는 각 조각이 다 다른 정보다:
>
> - `%d{...}` → 시각 (언제 찍힌 로그인지)
> - `[%thread]` → 스레드 이름 (어느 스레드에서 실행 중이었는지)
> - `%-5level` → 로그 레벨 (ERROR/WARN/INFO 등, 질문하신 부분)
> - `%logger{36}` → 로거 이름 (보통 클래스 이름, 어디서 찍힌 로그인지)
> - `%msg` → 실제 로그 메시지 내용
> - `%n` → 줄바꿈
>
> 즉 로그 레벨은 이 패턴을 구성하는 여러 토큰 중 하나(`%level`)일 뿐이고, Encoder가 하는 일은 "시각+스레드+레벨+로거이름+메시지를 이 순서, 이 모양으로 한 줄에 조립해라"는 전체 포맷을 정하는 것이다. 그래서 실제 출력은 이렇게 나온다:
>
> ```
> 2024-01-15 10:30:45.123 [http-nio-8080-exec-1] INFO  c.e.service.UserService - 사용자 생성 완료
> ```

> **Q.** 로그 메세지의 패턴이라고 생각하는게 맞을까?
>
> 정확히 그렇게 생각하면 된다. Encoder가 적용하는 "형식"이 바로 로그 메시지의 패턴(pattern) 자체다. 실제로 Logback 설정 파일에서도 이 부분을 `<pattern>...</pattern>` 태그로 정의한다:
>
> ```xml
> <encoder>
>     <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
> </encoder>
> ```
>
> 그러니까 "형식 적용" = "이 패턴대로 로그 한 줄을 조립해라"라고 이해하면 된다. "형식"과 "패턴"은 여기서 사실상 같은 말을 가리키는 것이다.

### Q4. Bean Validation이 그래서 뭔가

> **Q.** Bean Validation이 그래서 뭔데
>
> Bean Validation은 자바 객체(주로 DTO)의 필드 값이 조건을 만족하는지 어노테이션 하나로 선언적으로 검증할 수 있게 해주는 자바 표준 스펙이다. (정식 이름은 JSR 380 / Jakarta Bean Validation)
>
> 왜 필요한가:
>
> - 원래는 이런 검증을 if문으로 직접 짜야 했다:
>   ```java
>   if (email == null || email.isEmpty()) throw new IllegalArgumentException("이메일 필수");
>   if (!email.contains("@")) throw new IllegalArgumentException("이메일 형식 오류");
>   ```
> - 이런 코드가 여러 API·여러 개발자마다 제각각 짜이면 검증 기준이 들쭉날쭉해지고, 프론트엔드 검증만 믿으면 개발자 도구로 우회당할 위험도 있다.
>
> Bean Validation은 이걸 어노테이션으로 대체한다:
>
> ```java
> public class UserRequest {
>     @NotBlank(message = "이메일은 필수입니다")
>     @Email(message = "올바른 이메일 형식이 아닙니다")
>     private String email;
>
>     @Min(1) @Max(150)
>     private Integer age;
> }
> ```
>
> 그리고 컨트롤러에서 `@Valid`만 붙이면 이 규칙들이 요청이 들어올 때 자동으로 검사된다:
>
> ```java
> @PostMapping("/users")
> public ResponseEntity<?> create(@Valid @RequestBody UserRequest request) { ... }
> ```
>
> 검증에 실패하면 Spring이 알아서 `MethodArgumentNotValidException`을 던지고, 컨트롤러 로직은 아예 실행되지도 않는다.
>
> 한 줄 요약: if문으로 흩어져 있던 "이 값이 유효한가?"라는 검증 로직을, `@NotBlank`, `@Email`, `@Min` 같은 표준 어노테이션으로 필드 위에 선언만 해두면 Spring이 알아서 검사해주는 것 — 그게 Bean Validation이다.

> **Q.** 그러니까 원래 if문으로 길게 검사해야했던걸 어노테이션으로 간단하게 검사할 수 있게 하는게 bean validation 이다 맞아?
>
> 정확하다. 그게 핵심 요지다. Bean Validation = "if문으로 길게 써야 했던 검증 로직을, 어노테이션 한 줄로 선언만 하면 되게 만들어주는 것". 원래대로면 각 필드마다 null 체크, 형식 체크, 범위 체크를 코드로 일일이 짰어야 했는데, `@NotBlank`, `@Email`, `@Min(1)` 처럼 어노테이션만 필드 위에 붙이면 Spring이 알아서 저 if문들을 대신 실행해준다. 코드량도 줄고, 어떤 필드에 어떤 규칙이 있는지 한눈에 보이니 가독성도 좋아진다.

> **Q.** 그럼 질문 이건 아무대나 쓸 수 있어?
>
> 완전히 "아무데나"는 아니고, 몇 가지 조건이 있다.
>
> 1. 타입이 맞아야 한다. 어노테이션마다 적용 가능한 타입이 정해져 있다.
>    - `@Email`, `@NotBlank`, `@Pattern` → `String`에만
>    - `@Min`, `@Max`, `@Positive` → 숫자 타입(`Integer`, `Long`, `BigDecimal` 등)에만
>    - `@Past`, `@Future` → 날짜 타입(`LocalDate`, `LocalDateTime` 등)에만
>
>    `String` 필드에 `@Positive`를 붙이는 것처럼 타입이 안 맞으면 컴파일이나 런타임에 오류가 난다.
>
> 2. 누군가 "검증해라"라고 트리거를 걸어줘야 한다. 어노테이션을 필드에 붙이기만 하면 아무 일도 안 일어난다. 반드시 다음 중 하나로 검증을 발동시켜야 실제로 체크된다.
>    - 컨트롤러에서 `@Valid @RequestBody UserRequest request` → 요청 들어올 때 자동 검증
>    - 서비스 메서드에서 `@Validated` 클래스 + `@Valid` 파라미터 → 메서드 호출 시 검증
>    - 중첩 객체는 상위 필드에 `@Valid`를 붙여야 하위까지 재귀 검증됨 (`@Valid private Address address;`)
>    - 컬렉션은 `List<@Valid UserDto>`처럼 타입 파라미터에 붙여야 요소별 검증됨
>
>    즉 어노테이션만 붙어있고 저 트리거가 하나도 없으면, 그냥 무시되는 "장식"에 불과하다.
>
> 3. 관례적으로는 DTO에 쓰지, 엔티티에는 잘 안 쓴다. 기술적으로는 `@Entity` 클래스에도 붙일 수 있지만, 그러면 JPA가 저장/수정 시점에 자동으로 검증을 걸어버려서 타이밍이 애매해지고 부분 수정(PATCH) 같은 상황에서 문제가 생기기 쉽다. 그래서 보통은 요청/응답용 DTO에만 붙이고, 엔티티는 그대로 둔다.
>
> 요약: "타입 맞는 필드"에 붙이고, "`@Valid`/`@Validated`로 트리거를 걸어준 곳"에서만 실제로 동작한다 — 아무 클래스, 아무 곳에나 붙인다고 저절로 검증되는 건 아니다.

> **Q.** 그러니까 사용은 타입이 일치하고 @vaild,@Vaildated 로 트리커를 걸어서 동작시켜야 사용이 가능하다 맞아?
>
> 정확히 맞다. 그 두 조건이 핵심이다: (1) 타입이 일치해야 어노테이션이 유효하게 동작하고, (2) `@Valid` 또는 `@Validated`로 트리거를 걸어야 실제로 검증이 실행된다. (철자는 `vaild`가 아니라 `valid`다.) 이 두 조건이 충족되지 않으면 어노테이션은 그냥 필드 위에 붙어있는 표시일 뿐, 아무 검증도 일어나지 않는다.

> **Q.** 관례적으로 DTO에 사용한다고 설명했잖아? 내가 기억하기로는 DTO는 객체 재정의하는 서비스,인터페이스 사이에 존재하는 완충제로 기억하거든 맞아?
>
> 관례적으로 방향은 맞는데, 조금 더 정확히 짚으면 DTO(Data Transfer Object)는 정확히는 "내부 도메인 모델(Entity)"과 "외부에 노출되는 표현(API 요청/응답)" 사이의 경계에 존재하는 객체다. "서비스와 인터페이스 사이"라기보다는, 엔티티(DB와 맞닿은 내부 구조)와 클라이언트가 실제로 주고받는 데이터 구조 사이의 완충제라고 보는 게 더 정확하다.
>
> 왜 완충제가 필요한가:
>
> - Entity를 그대로 API 응답에 내보내면 위험하다.
>   - 클라이언트가 `id`, `createdAt`, `passwordHash` 같은 내부 필드까지 그대로 받아보거나, 심지어 요청 본문에 그런 필드를 실어서 조작을 시도할 수 있음
>   - JPA 연관관계(양방향 매핑, 지연 로딩)가 얽혀있으면 직렬화 과정에서 무한 루프나 예외가 날 수 있음
>   - DB 구조가 바뀔 때마다 API 스펙까지 같이 흔들리게 됨 (Entity와 API가 강하게 결합)
> - 그래서 DTO를 하나 더 두고, "이 API는 딱 이 필드들만 주고받는다"는 계약(contract)을 명시적으로 만드는 것이다. Entity가 어떻게 바뀌든 DTO 매핑 코드만 손보면 되니, 내부 구조와 외부 인터페이스가 분리된다.
>
> 그래서 Bean Validation을 DTO에 붙이는 이유:
>
> - DTO가 "외부에서 들어오는 입력값을 받는 지점"이기 때문에, 여기서 `@NotBlank`, `@Email` 같은 검증을 걸어야 신뢰할 수 없는 외부 입력이 시스템 내부(Entity, DB)로 넘어가기 전에 걸러진다.
> - 반대로 Entity에 검증을 걸면, "이미 내부로 들어온 데이터"에 대한 검증이라 방어선으로서 의미가 늦어지고, JPA 저장 타이밍과 얽혀 애매해진다.
>
> 한 줄 요약: DTO는 "서비스↔인터페이스"보다는 "내부 도메인(Entity)↔외부 인터페이스(API)" 사이의 완충제이고, 그 경계가 바로 외부 입력을 검증해야 하는 지점이라 Bean Validation이 DTO에 붙는 게 자연스럽다.

> **Q.** 음 그러니까 다시 정리하면 DTO가 "외부에서 들어오는 입력값을 받는 지점"이기 때문에 사용하고, 사용할려면 타입을 일치하는 bean validation을 사용, @valid, @Validation을 트리거로 사용해 작동한다 맞아?
>
> 거의 맞는데, 두 가지만 다듬는다.
>
> 1. DTO를 쓰는 이유는 "외부 입력을 받는 지점"이라서만은 아니다. DTO는 원래 Entity와 API 사이를 분리하기 위해 존재하고(요청뿐 아니라 응답에도 쓰임), 그중 "요청을 받는 DTO"가 마침 외부 입력이 처음 들어오는 지점이라서 거기에 Bean Validation을 거는 게 자연스러운 것이다. 즉 "DTO를 쓰는 이유"와 "그 DTO에 Bean Validation을 붙이는 이유"는 살짝 다른 얘기다.
> 2. `@Validation`이 아니라 `@Validated`다 (오타).
>
> 정리하면:
>
> - DTO는 Entity(내부)와 API(외부) 사이의 완충제 역할을 한다.
> - 그중에서도 요청(request)을 받는 DTO는 외부에서 들어오는 신뢰할 수 없는 입력값을 처음 받는 지점이라서, 여기에 Bean Validation을 걸어 나쁜 데이터가 시스템 내부로 들어오는 걸 막는다.
> - Bean Validation을 실제로 쓰려면 ① 필드 타입에 맞는 어노테이션(`@NotBlank`→String, `@Min`→숫자 등)을 붙이고, ② `@Valid`(컨트롤러) 또는 `@Validated`(서비스)로 트리거를 걸어야 실제 검증이 동작한다.
>
> 이 흐름이 맞다.

### Q5. "계층별 검증 전략"이 DTO 대신 Controller/Service 사용을 말하는 것인가

> **Q.** 계층별 검증 전략 여기서 설명하는건 dto 말고 controller, service 단에서 사용을 말하는거지?
>
> 맞다. "계층별 검증 전략"은 DTO를 대체하는 게 아니라, "검증을 어느 계층(Controller vs Service)에서 담당할 것인가"에 대한 역할 분담 얘기다. DTO는 그대로 존재하고, 그 DTO를 놓고 Controller와 Service가 각각 다른 종류의 검증을 나눠서 맡는 구조다.
>
> Controller 계층 — 형식적 검증 (1차 방어선):
>
> - DTO에 붙은 `@NotBlank`, `@Email` 같은 Bean Validation 어노테이션을 `@Valid`로 트리거
> - "필수값이 비었나", "이메일 형식이 맞나", "파일 크기가 초과했나" 같은 값 자체의 형식만 확인
> - DB 조회 없이 필드값만 보고 판단 가능한 검증
>
> Service 계층 — 비즈니스 규칙 검증:
>
> - 형식은 맞지만 DB 조회나 다른 데이터와 비교해야만 판단 가능한 규칙을 검증
> - 예: 이메일이 형식은 맞는데 이미 DB에 존재하는지(중복 체크), 이 사용자가 이 작업을 할 권한이 있는지, 주문 상태가 취소 가능한 상태인지
> - 이런 건 `@Email` 같은 필드 어노테이션 하나로는 표현이 안 되니까, Service 코드 안에서 직접 `if (userRepository.existsByEmail(...))` 식으로 검증하거나, `@Validated` + 커스텀 Validator를 쓴다
>
> 즉 정리하면: DTO는 "검증 규칙이 선언되는 대상 객체"로 계속 존재하고, "계층별 검증 전략"은 그 위에서 "형식 검증은 Controller가, 비즈니스 규칙 검증은 Service가 맡는다"는 책임 분담 얘기다. DTO 얘기가 빠진 게 아니라, DTO를 누가(어느 계층이) 어떤 기준으로 검증하느냐의 문제다.

> **Q.** Service 계층 — 비즈니스 규칙 검증. 의도는 이해하는데 이런건 구체적인 if문이 더 적절하지 않나?
>
> 맞다, 의도를 정확히 파악했다. Service 계층의 비즈니스 규칙 검증은 실제로 어노테이션보다 명시적인 if문 + 예외 던지기가 더 적절하고, 실무에서도 그렇게 짜는 게 일반적이다.
>
> 왜 Bean Validation 어노테이션이 아니라 if문이 더 적합한가:
>
> 1. DB 조회가 필요하기 때문: `@NotBlank` 같은 어노테이션은 필드 값 자체만 보고 판단하는 "정적" 검증이다. 하지만 "이메일이 이미 DB에 있는지" 확인하려면 리포지토리를 호출해야 하는데, 이건 어노테이션 하나로 표현하기엔 부자연스럽다. (기술적으로는 Spring Bean을 주입받는 커스텀 `ConstraintValidator`를 만들면 가능하긴 하지만, 거의 안 쓴다.)
> 2. 검증 시점과 순서가 중요하기 때문: "이메일 중복 체크 → 나이 정책 체크 → 사용자 저장" 처럼 여러 단계가 순서대로 실행되어야 하는 경우, 어노테이션은 이런 흐름 제어가 안 된다. if문이면 순서를 코드로 명확히 통제할 수 있다.
> 3. 가독성: `@Valid` 하나로 숨겨진 검증이 여러 개 실행되는 것보다, Service 메서드 안에 명시적으로 `if (userRepository.existsByEmail(...)) throw new DuplicateEmailException(...)` 이렇게 써두는 게 "이 메서드가 어떤 규칙을 지키는지" 한눈에 보인다.
>
> 실제 코드는 이런 식이다:
>
> ```java
> private void validateBusinessRules(UserRegistrationRequest request) {
>     userRepository.findByEmail(request.getEmail())
>         .ifPresent(existingUser -> {
>             throw new UserAlreadyExistsException(request.getEmail(), existingUser.getCreatedAt());
>         });
>
>     if (isBlockedEmailDomain(request.getEmail())) {
>         throw new BlockedEmailDomainException(...);
>     }
> }
> ```
>
> 정리: Controller의 "형식 검증"은 어노테이션이 잘 맞고, Service의 "비즈니스 규칙 검증"은 DB 조회·순서 제어·가독성 때문에 명시적인 if문 + 도메인 예외 던지기가 더 적절하다는 판단이 맞다.

> **Q.** 결론은 어쨌든 @bean validation은 간단한 검증을 위한거네?
>
> 결론적으로는 맞다. 다만 "간단하다"의 의미를 조금 더 정확히 짚으면, Bean Validation은 "필드 값 자체만 보고 판단 가능한, 외부 의존성이 없는(stateless) 검증"에 적합하다.
>
> - 적합: 형식 체크(`@Email`), 필수값(`@NotBlank`), 범위(`@Min/@Max`), 날짜(`@Past/@Future`) — 그 필드 값 하나만 보면 판단이 끝나는 것들
> - 부적합: DB 조회가 필요한 것(중복 체크), 여러 필드/다른 테이블과 비교해야 하는 것(권한, 상태 전이), 순서가 중요한 것(A 확인 후 B 확인)
>
> 그러니까 "간단하다"는 건 로직의 복잡도보다는 "이 값 하나만으로 자기 완결적으로 판단 가능한가"가 기준이다. 아무리 복잡한 정규식(`@Pattern`)을 쓰더라도 필드 값만 보고 판단되면 Bean Validation 영역이고, 아무리 단순해 보여도 DB를 한 번이라도 봐야 하면 Service의 if문 영역으로 넘어간다.

### Q6. 커스텀 Validator는 가능하지만 왠만해선 잘 안 만드는 것인가

> **Q.** 커스텀 Validator 이거 배울때 가능은 한데 왠만해선 잘 안만든다고 배웠거든 맞아?
>
> 완전히 동의하긴 어렵고, 어떤 종류의 커스텀 Validator냐에 따라 다르다.
>
> ① 외부 의존성(DB/API)이 필요한 커스텀 Validator → 맞음, 잘 안 만듦. Spring Bean을 주입받아 DB 조회하는 `ConstraintValidator` 같은 경우다. 사업자등록번호 실존 여부를 외부 API로 확인하거나, 이메일 중복을 DB로 확인하는 것 같은 건 기술적으로 만들 순 있지만, Service 계층 if문으로 처리하는 게 훨씬 자연스러워서 실무에서 잘 안 쓴다.
>
> ② 순수 형식/계산 로직만 있는 커스텀 Validator → 오히려 꽤 씀. 한국 휴대폰 번호 형식(`010-1234-5678`), 사업자등록번호 체크섬 계산, 비밀번호 복잡도 규칙, "시작일이 종료일보다 빨라야 한다" 같은 클래스 레벨 검증 등. 이런 건 외부 조회 없이 그 객체(필드값)만 보고 판단 가능하기 때문에, 기본 어노테이션(`@Pattern`, `@Email`)만으로는 표현이 안 되는 도메인 특화 규칙을 캡슐화하는 데 실제로 자주 쓴다. 반복되는 검증 로직을 어노테이션 하나로 재사용할 수 있다는 이점이 크다.
>
> 정리하면: "DB나 외부 API를 호출해야 하는 커스텀 Validator"는 잘 안 만든다는 게 맞고, "필드 값만으로 판단되는 도메인 특화 커스텀 Validator"는 오히려 실무에서 꽤 쓰인다. 배운 내용은 아마 전자(DB/API 의존형)를 두고 한 얘기였을 가능성이 높다.

### Q7. Spring Actuator는 상태 체크를 위한 것인가

> **Q.** Spring Actuator 이게 그러니까 상태체크를 위한거지?
>
> 큰 방향은 맞는데, "상태 체크"는 Actuator가 하는 일 중 하나이고 실제로는 조금 더 넓은 범위를 담당한다.
>
> Actuator = 운영 중인 애플리케이션의 상태와 성능 지표를 외부에서 들여다볼 수 있게 해주는 모니터링 엔드포인트 모음. 크게 3가지 축으로 나뉜다:
>
> 1. 상태 체크 (`/actuator/health`) — 질문하신 부분. 앱이 살아있는지, DB 연결은 정상인지, 디스크 공간은 충분한지 등을 `UP`/`DOWN`으로 보여줌. 로드밸런서나 쿠버네티스가 "이 인스턴스로 트래픽 보내도 되나?" 판단할 때 씀.
> 2. 애플리케이션 정보 (`/actuator/info`) — 버전, 빌드 시각, 커밋 해시 같은 메타 정보. "지금 운영 중인 게 정확히 어떤 버전인지" 확인용.
> 3. 성능 지표 수집 (`/actuator/metrics`) — 상태 체크와는 결이 다른, JVM 메모리 사용량, HTTP 요청 수·응답시간, GC 시간 같은 수치 데이터. 여기서 나온 지표를 Prometheus 같은 외부 도구로 넘겨서 그래프로 시각화하거나 임계치 알림을 걸 수 있음.
>
> 정리하면: "상태 체크"는 Actuator가 제공하는 기능 중 가장 대표적인 하나(`/health`)일 뿐이고, 전체적으로는 "상태 확인 + 메타 정보 + 성능 지표 수집"을 아우르는 운영 모니터링 도구라고 보는 게 더 정확하다.

### Q8. 커스텀 HealthIndicator는 "연결 상태"를 체크하는가 "서비스 여부"를 체크하는가

> **Q.** HealthIndicator 인터페이스를 구현해 카카오페이 같은 중요 외부 시스템의 생존 여부를 /actuator/health 응답에 추가할 수 있다 — 이게 그러니까 연결된 외부 api의 연결된 상태를 체크한다는거야? 아니면 외부 서비스의 서비스 여부를 확인한다는거야?
>
> 둘 중 하나로 딱 나뉘는 게 아니라, 사실상 이 둘이 합쳐진 하나의 신호를 체크하는 것이다.
>
> 어떻게 동작하는지 보면:
>
> ```java
> @Component
> public class ExternalApiHealthIndicator implements HealthIndicator {
>     @Override
>     public Health health() {
>         boolean apiAlive = checkExternalApi();   // 실제로 외부 API를 호출해봄
>         if (apiAlive) {
>             return Health.up().withDetail("externalApi", "Available").build();
>         } else {
>             return Health.down().withDetail("externalApi", "Unavailable").build();
>         }
>     }
> }
> ```
>
> `checkExternalApi()`는 보통 카카오페이 쪽에 실제로 HTTP 요청을 한 번 날려보고, 정상 응답이 오는지를 확인하는 방식으로 구현된다. (카카오페이가 제공하는 헬스체크용 엔드포인트를 부르거나, 가벼운 조회성 API를 하나 부르는 식으로.)
>
> "연결 상태"냐 "서비스 여부"냐로 나누기 어려운 이유:
>
> - 네트워크가 끊겨서 요청 자체가 안 나가도 → 실패 → `DOWN`
> - 네트워크는 정상인데 카카오페이 서버가 다운되어 응답이 안 와도 → 실패 → `DOWN`
> - 카카오페이 서버는 살아있는데 자기들 내부 오류로 500을 뱉어도 → 실패 → `DOWN`
>
> 우리 입장에서는 이 셋을 구분할 방법이 없다. 그냥 "지금 이 순간 저쪽에 요청을 보냈을 때 정상 응답을 받았는가"만 알 수 있다. 그래서 정확히 말하면: "연결이 되는가"와 "서비스가 살아있는가"를 따로 체크하는 게 아니라, "지금 실제로 통신을 시도해봤을 때 성공하는가"라는 하나의 통합된 신호를 체크하는 것이다. 원인(네트워크 문제인지, 상대 서버 문제인지)은 이 체크만으로는 알 수 없고, 그건 나중에 로그나 상세 원인 분석으로 따로 파고들어야 하는 부분이다.

> **Q.** 그럼 내부적으로 어떤 이유로 외부 API에 연결이 안되는건지는 내가 예외처리 할 수 있는거겠네?
>
> 정확히 그렇다. HealthIndicator의 `UP`/`DOWN`은 모니터링 대시보드용으로 단순화된 신호일 뿐이고, 실제로 외부 API를 호출하는 코드 쪽(Service 계층)에서는 예외 타입을 구분해서 원인별로 다르게 처리할 수 있다.
>
> 실제 호출 코드에서는 예외 타입으로 원인을 구분 가능하다:
>
> ```java
> try {
>     return paymentClient.charge(request);
>
> } catch (ConnectException | UnknownHostException e) {
>     // 연결 자체가 안 됨 — 네트워크/DNS 문제
>     log.error("결제 서버 연결 실패", e);
>     throw new PaymentSystemTemporarilyUnavailableException("결제 시스템에 연결할 수 없습니다", e);
>
> } catch (SocketTimeoutException e) {
>     // 연결은 됐는데 응답이 안 옴 — 타임아웃
>     log.warn("결제 서버 응답 지연", e);
>     throw new PaymentRetryableException("일시적 지연, 재시도 필요", e);
>
> } catch (HttpServerErrorException e) {
>     // 상대방이 응답은 했는데 자기들 서버 오류(5xx)
>     log.error("결제 게이트웨이 내부 오류 - 즉시 점검 필요", e);
>     throw new PaymentSystemException("결제 시스템 오류", e);
>
> } catch (HttpClientErrorException e) {
>     // 상대방이 응답했는데 우리 요청 자체가 잘못됨(4xx, 예: 잘못된 카드정보)
>     throw new InvalidPaymentMethodException("결제 정보를 확인해주세요");
> }
> ```
>
> 정리하면:
>
> - `HealthIndicator`: "지금 이 순간 저쪽이 정상 응답하는가"만 UP/DOWN 이진값으로 압축해서 보여줌 (모니터링 요약용)
> - 실제 호출 코드: `ConnectException`(연결 자체 실패), `SocketTimeoutException`(응답 지연), `HttpServerErrorException`(상대 서버 오류), `HttpClientErrorException`(우리 요청 문제) 등으로 세밀하게 나눠서 예외 처리 가능
>
> 이게 Q1에서 얘기했던 "장애 발생 자체는 못 막지만, 어떻게 대응할지는 우리가 설계할 수 있다"는 원칙이 실제로 코드 레벨에서 구현되는 방식이다 — 타임아웃이면 재시도, 서버 오류면 알림+서킷브레이커, 연결 실패면 대체 결제수단 안내 하는 식으로.
