# Spring Batch — Q&A

### Q1. batch는 개념이고 Spring Batch는 프레임워크인가

> **Q.** batch 라는게 framework 라는거지?
>
> 아니요, 정확히는 구분이 필요합니다. **batch(배치)**는 특정 프레임워크가 아니라 "대량의 데이터를 실시간이 아니라 정해진 시점/주기에 한꺼번에 처리하는 방식"을 가리키는 일반적인 처리 패턴/개념이고, 언어나 프레임워크와 무관하게 존재합니다. **Spring Batch**가 그 배치 처리 패턴을 Spring 생태계 안에서 구현할 수 있게 해주는 구체적인 프레임워크로, Job/Step/청크 처리/재시작/skip·retry 같은 배치 처리에 공통으로 필요한 기능을 프레임워크 레벨에서 표준 제공합니다. 정리하면 "batch"는 개념(패턴), "Spring Batch"는 그 개념을 구현한 프레임워크입니다.

> **Q.** 음 그러니까 spring batch는 프레임워크라는거 잖아? 그럼 앞에 'spring'이 붙어있는게 spring framework의 하위 개념인거야?
>
> 정확히는 "하위 개념"이라기보다 **"Spring이라는 큰 우산(포트폴리오) 아래 있는 별도의 프로젝트"**에 가깝습니다. **Spring Framework**는 IoC/DI 컨테이너, AOP, 트랜잭션 추상화 같은 핵심 기능을 제공하는 진짜 "코어" 프레임워크이고, **Spring Batch, Spring Security, Spring Data, Spring Cloud, Spring Boot** 등은 전부 Spring Framework 위에 얹혀서(그 DI 컨테이너, 트랜잭션 관리 같은 코어 기능을 가져다 쓰면서) 각자의 특화된 문제(배치 처리, 인증/인가, 데이터 접근, 분산 시스템, 자동 설정 등)를 해결하는 개별 프로젝트다. 각각 별도의 이름·버전·의존성(jar)을 가지고 있어서, Spring Batch를 쓴다고 Spring Security가 딸려오거나 하지 않는다. 그래서 "Spring 하위 개념"보다는 "Spring Framework를 기반으로 만들어진, Spring 생태계(family)에 속한 독립적인 프레임워크"라고 이해하는 게 더 정확하다. 이름에 'Spring'이 붙는 이유는 같은 생태계 소속이라는 걸 나타내기 위함이지, Spring Framework 내부의 한 구성요소라는 뜻은 아니다.

> **Q.** 그럼 spring이라는 환경에 속하는 대용량 처리에 특화된 프레임워크라고 이해하면 돼?
>
> 거의 맞지만 "대용량"보다는 **"일괄(batch) 방식으로 처리하는 데"** 특화된 게 핵심이다. Spring이라는 생태계에 속해있고, 대량의 데이터를 실시간이 아니라 정해진 시점에 한꺼번에(chunk 단위로) 읽고 가공하고 쓰는 배치 처리 패턴에 특화되어 있으며, 그 과정에서 필요한 재시작, skip/retry, 실행 이력 관리 같은 기능을 표준으로 제공하는 프레임워크다. "대용량"은 배치 처리에서 흔히 동반되는 특징이긴 하지만, 핵심은 데이터 양 자체보다 "일괄로, 청크 단위로, 재시작 가능하게 처리하는 방식"이라는 점이다. 그래서 "Spring 생태계에 속한, 대량 데이터의 일괄(batch) 처리에 특화된 프레임워크"라고 이해하면 정확하다.

> **Q.** 음 내가 배울때는 대용량 데이터 처리를 좀 더 중요하게 배웠던거 같은데 그럼 니 말은 batch의 동작 특징으로 chunk 단위로 일어나는 일괄 처리가 좀 더 핵심적인 개념이고 대용량 데이터 처리는 부가적인 효과라는거야?
>
> 앞선 설명을 정정한다. "chunk 처리가 핵심, 대용량은 부가효과"라는 위계는 맞지 않고, 실제로는 목적과 수단의 관계다. 대용량 데이터 처리 자체가 Spring Batch의 존재 이유(목적)다 — 수백만 건을 한 번에 메모리에 올려서 처리하면 OOM이 나거나, 처리 도중 실패하면 처음부터 다시 해야 하는 문제가 생기기 때문에, Spring Batch는 이런 대용량 데이터를 안전하고 효율적으로, 실패해도 복구 가능하게 처리하기 위해 만들어졌다. chunk 지향 처리(일괄 처리 방식)는 그 목적을 실현하기 위한 핵심 메커니즘이다 — 전체를 한 번에 메모리에 올리지 않고 일정 단위씩 읽고 커밋함으로써 메모리 사용량을 제한하고, 실패 시 마지막 커밋 지점부터 재시작 가능하게 만든다. 그래서 대용량 처리는 부가적 효과가 아니라, 대용량 데이터를 감당하기 위해 chunk 단위 처리라는 방식을 택한 것이며, 둘은 우열 관계가 아니라 목적-수단 관계로 뗄 수 없이 붙어있다.

> **Q.** 그럼 다시 정리해서 spring batch의 목적은 대용량 데이터 처리이고 이 목적을 이루기 위해서 채택한 방식이 chunk 단위의 일괄 처리다 맞아?
>
> 맞다. Spring Batch는 대용량 데이터를 안전하고 효율적으로, 실패해도 복구 가능하게 처리하기 위해 만들어진 프레임워크(목적)이고, 그 목적을 이루기 위해 채택한 핵심 방식이 chunk 단위의 일괄 처리 — 정해진 개수만큼 읽고 가공한 뒤 한 번에 커밋하는 방식(수단)이다.

> **Q.** job: 배치 처리의 최상위 단위. 하나 이상의 Step으로 구성 — 내가 프로젝트에서 사용할때는 job + step / read - write - process 방식으로 돌아갔던걸로 기억하는데 맞아?
>
> Job + Step 구조는 맞다. 다만 Step 내부의 처리 순서는 "Read → Write → Process"가 아니라 **"Read → Process → Write"**다. `ItemReader`가 데이터를 한 건씩 읽고 → `ItemProcessor`가 그 건을 가공/변환하고 → chunk 크기만큼 모이면 `ItemWriter`가 한 번에 쓴다. Write는 항상 Process 다음이고, 건별이 아니라 청크 단위로 일어난다는 점이 포인트다.

> **Q.** 내가 썼는대로 아직 정확히 구분이 안되는데 job + step 이랑 read - process - write 는 어떤 관계야? 할때 메서드 명을 무슨job, 무슨 write 이렇게 했던건 기억나는데
>
> 서로 다른 레벨의 개념이다. Job/Step은 "배치 작업을 어떻게 조직하느냐"의 구조적 단위이고(Job 안에 Step이 하나 이상), Read/Process/Write는 Job·Step과 나란한 개념이 아니라 **Step 하나를 chunk 지향 방식으로 만들 때 그 Step 내부에서 실제로 실행되는 처리 단계**다. 즉 Read-Process-Write는 Step의 "내용물"이다.
>
> ```
> Job (myJob)
>  └─ Step (myStep)          ← Job의 하위 단위
>       └─ Reader → Processor → Writer   ← Step "내부"에서 일어나는 처리 흐름
> ```
>
> Java Config로 쓰면 `myJob()`, `myStep()`은 구조(조직) 레벨의 빈이고, `myReader()`/`myProcessor()`/`myWriter()`는 그 `myStep()`을 구성하는 재료로 `.reader()`/`.processor()`/`.writer()`에 끼워 넣는 관계다:
>
> ```java
> @Bean
> public Job myJob(Step myStep) {
>     return jobBuilderFactory.get("myJob").start(myStep).build();
> }
>
> @Bean
> public Step myStep(ItemReader<A> reader, ItemProcessor<A, B> processor, ItemWriter<B> writer) {
>     return stepBuilderFactory.get("myStep")
>         .<A, B>chunk(100)
>         .reader(reader)
>         .processor(processor)
>         .writer(writer)
>         .build();
> }
>
> @Bean
> public ItemReader<A> myReader() { ... }
>
> @Bean
> public ItemProcessor<A, B> myProcessor() { ... }
>
> @Bean
> public ItemWriter<B> myWriter() { ... }
> ```
>
> "무슨job, 무슨write" 네이밍 기억이 정확히 이 계층 구조(Job/Step은 조직 단위, Reader/Processor/Writer는 Step 내부 구성 요소)를 가리키고 있는 것이다.

> **Q.** Job(설계도) → JobInstance(파라미터로 구체화된 실행 단위) → JobExecution(실제 시도 기록) → 그 안의 여러 StepExecution(단계별 실행 기록). 단위나 기록의 목적은 뭐야? 로직상에서 활용가능한 객체로써 남기는거야? 아니면 개발자가 확인을 위해?
>
> 둘 다지만, "프레임워크 로직이 실제로 사용하는 객체"가 우선이고 "개발자 확인용"은 부산물에 가깝다. `JobRepository`가 이 메타데이터(JobInstance/JobExecution/StepExecution)를 DB에 저장해두고, Spring Batch 프레임워크 자신이 실행할 때마다 이걸 실제로 참조해서 판단한다 — 같은 파라미터로 이미 성공한 JobInstance가 있으면 중복 실행을 막고, 실패한 Job을 재시작하면 마지막 StepExecution이 어디까지 처리했는지 보고 그 이후부터 이어서 처리한다. 각 JobExecution/StepExecution에는 `ExecutionContext`라는 키-값 저장소가 붙어있어 "지금까지 몇 건 처리했는지", "다음에 읽을 위치가 어디인지" 같은 상태를 실제로 저장했다가 재시작 시 꺼내 쓰므로, 단순 기록이 아니라 재시작 로직이 작동하기 위해 반드시 필요한 상태 저장소다. 부가적으로는 이 메타데이터 테이블(`BATCH_JOB_EXECUTION` 등)을 직접 조회하거나 관리 도구/actuator로 모니터링·디버깅하는 데도 쓰이고, 코드에서 `@BeforeStep`/`@AfterStep` 리스너에 `StepExecution`을 주입받아 처리 건수 같은 정보를 로직에서 직접 활용할 수도 있다. 정리하면 사람이 보려고 남기는 로그성 기록이 아니라, Spring Batch가 재시작·중복 방지 같은 핵심 동작을 하기 위해 실제로 읽고 쓰는 런타임 상태 객체이고, 그걸 개발자도 모니터링용으로 함께 활용할 수 있는 구조다.

> **Q.** 그럼 단위나 기록을 바탕으로 batch의 재시도 등에 활용하기 위해서 라고 이해하는게 맞겠네?
>
> 방향은 맞지만 "재시도(retry)"가 아니라 **"재시작(restart)"**이 정확한 용어다. 재시도(retry)는 청크 처리 중 아이템 하나에서 일시적 오류가 났을 때 그 아이템을 몇 번 다시 시도하는 것(Step 내부, 아이템 레벨)이고, 재시작(restart)은 Job 전체가 실패했을 때 처음부터가 아니라 마지막으로 성공한 지점부터 다시 실행하는 것(Job/Step 레벨)이다. Job/JobInstance/JobExecution/StepExecution 메타데이터는 바로 이 재시작을 가능하게 하기 위한 근거 데이터다. 정리하면 이 단위·기록들은 실패 시 처음부터 다시 하지 않고 이어서 재시작할 수 있게, 또 같은 파라미터로 중복 실행되는 걸 막고 실행 이력을 추적할 수 있게 하기 위한 것이다.

> **Q.** chunk 단위는 임의로 변경할 수 있어?
>
> 그렇다. Step을 만들 때 `.chunk(100)`처럼 숫자(커밋 간격, commit interval)를 직접 지정하며, 상수로 고정할 수도 있고 설정 파일 값을 주입받아 환경별로 다르게 줄 수도 있다. chunk를 크게 잡으면 커밋 횟수가 줄어 성능은 좋아지지만 메모리 사용량이 커지고 실패 시 롤백/재처리 범위도 커지며, 작게 잡으면 메모리는 절약되지만 커밋 오버헤드가 늘어나므로, 데이터 크기·처리 로직 무게·장애 재처리 비용을 감안해 값을 정한다. 고정 개수 대신 커스텀 `CompletionPolicy`를 넘겨 "일정 시간 경과" 같은 동적 기준으로 청크를 끊는 것도 가능하다. 즉 chunk 크기는 상황에 맞게 임의로 설정/조정 가능한 파라미터다.

> **Q.** 그럼 step 마다 다른 청크 단위 설정도 가능하겠네?
>
> 그렇다. chunk 크기는 Step 단위로 설정하는 값이라, 하나의 Job 안에 여러 Step이 있으면 각 Step을 만들 때마다 독립적으로 `.chunk(n)` 값을 다르게 줄 수 있다. 예를 들어 가벼운 단순 적재 Step은 `.chunk(500)`으로 크게, 외부 API 호출 등 무거운 처리를 하는 Step은 `.chunk(50)`으로 작게 잡는 식으로, 각 Step의 처리 특성(로직 무게, 메모리 사용량, 실패 시 재처리 비용)에 맞춰 서로 다른 chunk 크기를 독립적으로 설정하는 게 일반적이다.

> **Q.** 그럼 응용해서 예를 들어 첫시도에서 100 단위로 했다가 실패시 재시도할때 200으로 변경하는등의 가변적인 설정은 가능해?
>
> 가능은 하지만 프레임워크가 기본 제공하는 기능은 아니고 직접 커스터마이징해야 하는 영역이다. 기본적으로 chunk 크기는 Step 정의 시 고정으로 박아두는 값이라 Spring Batch가 "몇 번째 재시도인지"를 보고 자동으로 바꿔주지는 않는다. 직접 구현하면 (1) `@StepScope` + late binding으로 chunk 크기를 JobParameter처럼 외부 주입받게 하는 방법 — 다만 재시작(restart)이 성립하려면 같은 JobInstance로 인식되어야 하고 이는 보통 JobParameters가 동일해야 유지되므로, chunk 크기를 바꾸는 파라미터는 "identifying하지 않는(non-identifying) 파라미터"로 넘겨야 같은 JobInstance로 인식되면서 값만 바뀔 수 있다. (2) 커스텀 `CompletionPolicy`를 만들어 이전 StepExecution의 실패 이력이나 ExecutionContext 정보를 읽어 동적으로 청크 크기를 결정하는 방법. 다만 실무에서 흔히 쓰는 패턴은 아니며, 보통 "재시도를 더 안전하게" 하려는 목적이라면 chunk 크기를 동적으로 바꾸기보다 skip/retry 정책(아이템 레벨)을 튜닝하거나 애초에 안전한 chunk 크기를 고정해두는 방식으로 해결한다.

> **Q.** 그럼 굳이 커스텀하지말고 1번 batch/chunk(100) 실패시 다음 2번 batch/chunk(200)으로 넘기는 건?
>
> 그건 커스텀 없이 표준 기능만으로 가능하다. 앞서 말한 방식은 "같은 Step"을 재시작할 때 값을 바꾸려는 것이라 non-identifying 파라미터 같은 편법이 필요했지만, 이건 애초에 chunk 크기가 다른 별개의 Step 두 개를 만들어두고 1번 Step이 실패하면 2번 Step으로 흐름을 넘기는 방식이라 Spring Batch가 표준으로 지원하는 조건부 흐름 제어(Flow Control)로 그대로 구현된다.
>
> ```java
> @Bean
> public Job myJob(Step step1, Step step2) {
>     return jobBuilderFactory.get("myJob")
>         .start(step1)              // chunk(100)로 정의된 Step
>             .on("FAILED").to(step2)  // step1 실패하면 step2로
>         .from(step1).on("*").end()   // step1 성공하면 그대로 종료
>         .end()
>         .build();
> }
>
> @Bean
> public Step step1(...) {
>     return stepBuilderFactory.get("step1").<A,B>chunk(100)...build();
> }
>
> @Bean
> public Step step2(...) {
>     return stepBuilderFactory.get("step2").<A,B>chunk(200)...build();
> }
> ```
>
> step1의 종료 상태(exit status, 여기선 FAILED)에 따라 다음에 어떤 Step으로 갈지 조건 분기할 수 있고, 각 Step은 각자 원하는 chunk 크기를 독립적으로 고정해서 가지면 된다. 동일 Step 재시작 시 값 변경 같은 편법 없이, 서로 다른 chunk 설정을 가진 별개 Step을 실패 조건으로 연결하기만 하면 되는 훨씬 자연스럽고 표준적인 방법이다.

> **Q.** 내가 springboot 프로젝트 중에 batch를 사용해서 대용량 데이터 처리를 했는데 다른 방법이 있었어? 기본적으로 spring framework 사용중이라서 spring batch를 사용하는게 내부적으로 추가적인 코드 작성없이 batch에 설정되어있는 로직들?을 사용가능하잖아
>
> Spring Batch 외에도 여러 대안이 있다.
>
> - **직접 페이징/커서 처리**: `JdbcTemplate`/MyBatis의 `fetchSize` + 커서 스트리밍이나 `Pageable` 반복 조회로 청크 처리. 단순하지만 재시작·skip/retry를 전부 손으로 구현해야 해서 Spring Batch가 이미 해주는 걸 재발명하는 셈
> - **Spring Batch 확장 기능**: Multi-threaded Step, Partitioning, Remote Chunking으로 스케일 아웃. Batch를 버리는 게 아니라 그대로 쓰면서 병렬화하는 정석 경로
> - **메시지 큐 파이프라인**: Kafka/RabbitMQ로 여러 컨슈머가 병렬 처리. 수평 확장은 쉽지만 Job 실행 이력·재시작 지점 관리는 직접 구현해야 함
> - **리액티브 스택**: WebFlux + R2DBC로 백프레셔 기반 스트림 처리
> - **DB 네이티브 벌크**: `INSERT ... SELECT`, `LOAD DATA INFILE` 등으로 애플리케이션 레이어를 아예 거치지 않는 방식. 순수 이관이면 제일 빠름
> - **분산 처리 프레임워크**: 수백만 건을 넘어서는 진짜 빅데이터 규모라면 Apache Spark
>
> 정리하면, Spring 생태계 안에서 재시작성·트랜잭션·skip/retry 같은 배치 고유 기능이 필요하면 Spring Batch(+파티셔닝/멀티스레드 확장)가 여전히 정답에 가깝고, 순수 처리량·확장성이 핵심이면 메시지 큐 파이프라인이나 DB 네이티브 벌크 연산이 대안이 된다.

> **Q.** ItemProcessor<I, O> 여기 질문. 가공, 변환이 가능하다고 설명이 나와있는데 여기서 말하는 가공이라는게 null로 변환시키는걸 말하는거야? 프로세스 단계에서 보다 복잡한 필터링이나 연산 로직같은게 들어가도돼?
>
> null 반환은 "가공"의 일부가 아니라 필터링을 위한 특별한 규칙이다. `process()`가 null을 리턴하면 Spring Batch가 그 아이템을 writer로 넘기지 않고 버린다(스킵) — 조건에 안 맞는 데이터를 결과에서 제외하는 용도다.
>
> 그 외에 null이 아닌 걸 리턴하는 한 `process()` 안에서는 다음과 같은 로직을 자유롭게 넣을 수 있다:
>
> - **타입/형태 변환**: Entity → DTO
> - **필드 가공**: 문자열 정규화, 단위 변환
> - **연산**: 여러 필드를 조합한 파생값 계산 (예: 단가×수량 → 총액)
> - **외부 조회 결합**: 다른 테이블/API 조회 후 값 채우기
> - **검증 후 필터링**: 조건에 안 맞으면 null 반환
> - **체이닝**: `CompositeItemProcessor`로 여러 Processor 연결
>
> 즉 `I`를 받아 `O`를 만드는 과정의 비즈니스 로직 전부가 가공이고, 그중 "이 아이템은 결과에서 아예 빼겠다"는 결정만 null 반환이라는 특수 규약으로 처리되는 구조다. 복잡한 연산 로직을 넣는 건 전혀 문제없고, 오히려 ItemProcessor의 정상적인 용도다.

> **Q.** 검증 후 필터링: 조건에 안 맞으면 null 반환 — 이렇게 처리되면 writer 과정이 생략되는거잖아? 최종적으로 step 과정에서는 문제가 없어?
>
> writer 단계 자체가 생략되는 게 아니라, 그 아이템 하나만 writer로 넘어가는 리스트에서 빠지는 것이다. Step 레벨에서는 전혀 문제없이 정상 동작하도록 설계돼 있다.
>
> - **카운트가 분리되어 있음**: `StepExecution`은 `readCount`/`writeCount`/`filterCount`를 각각 따로 관리한다. 필터링된 아이템은 `readCount`엔 포함되지만 `writeCount`엔 안 잡히고, 대신 `filterCount`로 집계된다
> - **커밋 타이밍은 read 기준**: 청크 경계(commit interval)는 reader가 읽은 건수를 기준으로 발생하지 writer로 넘어간 건수 기준이 아니라서, 필터링이 일어나도 커밋 자체는 정상 진행된다
> - **한 청크가 전부 필터링돼도 안전함**: 청크 내 모든 아이템이 null로 걸러져 writer에 넘길 게 없어도, writer는 빈 리스트로 호출되고(대부분의 표준 Writer는 빈 입력을 안전하게 no-op 처리) 트랜잭션은 정상 커밋된다. 에러나 예외로 취급되지 않는다
> - **skip과 다름**: 예외 기반 skip은 skip-policy 설정이 필요하지만, null 필터링은 별도 설정 없이 Spring Batch가 기본으로 지원하는 정상 경로다
>
> 결론적으로 걱정할 문제는 없고, filterCount로 정상 집계되며 Step은 그대로 완료된다.

> **Q.** 음 그러니까 다시 정리하면 process 과정에서 null이 발생해도 step 레벨에서 확인하는건 count이기 때문에 각각 집계에는 문제가 없어서 정상적으로 동작한다?
>
> 거의 맞지만 한 가지는 정정이 필요하다. count는 Step이 정상 여부를 판단하는 기준이 아니라, 그냥 결과를 기록하는 통계다.
>
> - Step의 성공/실패는 read/write/filter count가 서로 맞아떨어지는가로 판단하는 게 아니라, **처리 도중 예외가 발생했는가**로 판단된다. null 필터링은 예외를 던지지 않는 정상 경로이기 때문에 애초에 Step 입장에서 문제 삼을 일이 없다
> - readCount/writeCount/filterCount는 그 정상적인 흐름이 끝난 뒤 "몇 건이 어떻게 처리됐는지"를 사후적으로 기록해두는 통계일 뿐이지, Step이 그 숫자들을 검증(reconcile)해서 통과/실패를 가르는 게 아니다
>
> 정확히는 "Step은 애초에 필터링을 예외 상황이 아닌 정상 경로로 취급하기 때문에 문제없이 진행되고, 그 결과 각 카운트에는 필터링된 만큼의 차이가 정확히 반영될 뿐"이라고 이해하는 게 맞다. count가 문제를 막아주는 안전장치가 아니라, count는 그냥 결과를 보여주는 창구다.

> **Q.** 그럼 process 내부적으로 예외를 던지도록 작성하는건 가능해?
>
> 가능하다. `process()`는 일반 Java 메서드라 그 안에서 예외를 던지는 것 자체엔 제약이 없다. 다만 null 반환(필터링)과는 의미와 처리 흐름이 완전히 다르다.
>
> - **기본 동작(설정 없을 때)**: 예외가 발생하면 그대로 전파되어 해당 청크의 트랜잭션이 롤백되고 Step이 FAILED 상태로 종료된다. 별도 설정이 없으면 예외 하나가 전체 Step(보통 Job까지)을 실패시킨다
> - **`.faultTolerant().skip(SomeException.class).skipLimit(n)`**: 지정한 예외가 나면 그 아이템만 건너뛰고(skip) Step은 계속 진행된다. `skipCount`로 집계되고, `SkipListener`를 붙이면 스킵된 아이템을 별도로 로깅/기록할 수 있다
> - **`.faultTolerant().retry(SomeException.class).retryLimit(n)`**: 예외가 나면 지정한 횟수만큼 그 아이템의 처리를 재시도한 뒤, 그래도 실패하면 skip 정책이 있으면 skip, 없으면 최종 실패로 처리된다
>
> null 반환과의 핵심 차이는 "의도"다: null 반환은 "이 아이템은 원래 결과에서 빠져야 한다"는 정상적인 비즈니스 판단(filterCount)이고, 예외 던지기는 "이 아이템을 처리하다가 문제가 생겼다"는 에러 상황(skipCount/재시도 대상)이며 fault-tolerant 설정이 없으면 Step 전체를 죽인다. 그래서 단순 조건 필터링엔 null을, 데이터 이상·외부 호출 실패 같은 진짜 예외 상황엔 예외 던지기 + skip/retry 정책을 쓰는 식으로 구분해서 쓴다.

> **Q.** 그러니까 정상적으로 아이템에 대한 스킵을 원하면 null 필터링이 맞고 프로세스의 재시도를 원하면 예외 처리가 맞다는거야?
>
> 정확히는 아니다. 두 가지 정정이 필요하다.
>
> - **null 필터링은 Batch 용어로 "skip"이 아니라 "filter"다.** Spring Batch는 이 둘을 별도 통계(`filterCount` vs `skipCount`)와 별도 개념으로 구분한다. Batch가 공식적으로 말하는 skip은 예외 기반 메커니즘(`skipCount`, `SkipPolicy`, `SkipListener`)만을 가리키는 용어다
> - **예외 처리 = retry 전용이 아니다.** `.faultTolerant()`로 예외를 다루면 retry와 skip을 각각, 또는 둘을 조합해서 쓸 수 있다. 실무에서 흔한 패턴은 "먼저 N번 재시도 → 그래도 실패하면 스킵"이다
>
> 정리하면 다음과 같다.
>
> - **아이템을 결과에서 정상적으로 제외**하고 싶다 → null 반환(filter)
> - **처리 중 에러가 났을 때 그 아이템을 포기하고 넘어가고 싶다** → 예외 + `.skip()`
> - **처리 중 에러가 났을 때 몇 번 다시 시도해보고 싶다** → 예외 + `.retry()`
>
> 이 셋은 서로 배타적이지 않고, 예외 상황에선 retry와 skip을 함께 설정해 "재시도 후 그래도 안 되면 스킵"으로 조합하는 게 일반적이다.

> **Q.** 그럼 추가적으로 process에서 예외처리로 재시도를 하면 프로세스만 재시도 되는거야?
>
> 그렇다. process()에서 발생한 예외로 인한 재시도는 그 아이템의 process() 호출만 재시도된다. 청크 전체나 다른 아이템들이 다시 처리되는 게 아니다.
>
> - **reader는 다시 안 불림**: 이미 읽어서 메모리에 들고 있는 아이템이라, 재시도해도 reader를 다시 호출하지 않는다. 오직 그 아이템에 대해 `process()`만 다시 실행된다
> - **다른 아이템들은 영향 없음**: 같은 청크 안에서 이미 처리 완료된 다른 아이템들은 재처리되지 않는다. 재시도는 실패한 그 아이템 하나에 국한된다
> - **결과 분기**: 재시도 중 성공하면 그 아이템은 정상적으로 청크에 포함되어 writer로 넘어가고, `retryLimit`까지 재시도해도 계속 실패하면 skip 정책이 있는 경우 그 아이템만 skip(`skipCount`) 처리되고 나머지는 정상 진행되며, skip 정책이 없거나 skip 한도를 넘으면 예외가 전파되어 Step이 실패하고 해당 청크 트랜잭션이 롤백된다
>
> 참고로 이건 `process()`에서 예외가 난 경우고, `write()` 단계에서 예외가 나면 청크 전체가 한 번에 write되기 때문에 어떤 아이템이 문제인지 특정할 수 없어서, Spring Batch가 그 청크를 아이템 단위로 하나씩 다시 처리(scan)하며 원인을 좁혀나가는 별도 메커니즘이 있다.

> **Q.** 방금 내가 질문한거 자체가 트랜잭션 롤백인거야? 아니면 batch 의 자체적인 특징인거야?
>
> 둘 다 관련되어 있는데 구분이 필요하다.
>
> - **트랜잭션 롤백 자체는 일반적인 Spring 트랜잭션 특징**이다. 청크 하나가 하나의 트랜잭션 경계로 묶여 있고, 그 안에서 예외(write() 실패)가 발생하면 해당 트랜잭션이 롤백되는 건 Spring 트랜잭션 관리의 기본 동작이지 Batch만의 특별한 기능이 아니다. `@Transactional` 메서드에서 런타임 예외가 나면 롤백되는 것과 원리가 같다
> - **롤백 이후 아이템 단위로 다시 나눠서 처리(scan)하는 건 Spring Batch 고유의 기능**이다. 일반 트랜잭션 롤백은 "그냥 되돌리고 예외를 위로 던진다"에서 끝나지만, Batch의 fault-tolerant 프레임워크는 롤백된 뒤 그 청크를 실패로 끝내지 않고 청크 크기를 1로 줄인 것처럼 아이템 하나씩 다시 read→process→write 해보면서 원인 아이템을 특정하고, 문제 없는 아이템들은 각자 커밋하고 문제 있는 아이템만 skip하는 복구 로직을 자체적으로 얹어놓은 것이다
>
> 정리하면 롤백이 일어난다는 사실 자체는 Spring의 일반 트랜잭션 특징이고, 그 롤백 이후에 벌어지는 scan(아이템 단위 재처리·격리) 동작이 Spring Batch가 그 위에 추가한 고유 기능이다.

> **Q.** 예외처리 후 재시도 하는게 즉 트랜잭션 롤백 spring transaction의 특징이잖아? 내가 궁금한거 한 job - step의 흐름 중에서 트랜잭션이 걸리는 범위야. 프로젝트 특징별로 트랜잭션의 범위가 임의로 조정될 수 가 있나? 아니면 spring batch가 정해둔 양식이 있는거야? 아까 답변도 process 단에서 예외 + 재시도 시에는 process만 재시도 된다는건 process 단에만 트랜잭션이 걸려있다는 거잖아? 이렇게 되면 read - process - writer 각각 트랜잭션이 걸려있다는거야? 그런데 또 아까 답변을 보면 writer 단에서 예외처리 시에는 청크 전체에 대한 재시도를 한다고 했잖아
>
> read/process/write 각각에 독립적인 트랜잭션이 걸려있는 게 아니라, **"한 청크(read+process+write 전체) = 한 트랜잭션"**이 chunk 지향 Step의 기본 구조다.
>
> - **process 재시도는 트랜잭션과 무관한, 메서드 호출 레벨의 재시도다.** 아직 write()가 호출되기 전이라 DB에 아무것도 반영된 게 없는 상태라서, 그 아이템의 process() 호출을 인메모리에서 다시 시도하는 것뿐이고 "process 전용 트랜잭션"이 따로 있는 게 아니다. 최종 커밋은 여전히 청크의 모든 아이템이 처리·기록된 뒤 딱 한 번 일어난다
> - **writer 실패 시 청크 전체가 롤백되는 건 하나의 청크 트랜잭션이 실패했기 때문**이다. 배치로 한 번에 쓰다 보니 어느 아이템이 원인인지 알 수 없어서, 롤백 이후 그 청크를 아이템 하나씩(사실상 청크 크기 1처럼) 다시 read된 데이터로 process→write 해보며 원인을 특정하고 정상인 것들은 개별 커밋, 문제 있는 것만 skip하는 복구 로직(scan)을 얹은 것이지, process/write마다 트랜잭션이 따로 있어서가 아니다
>
> **범위 조정 가능 여부**: "청크 = 트랜잭션 경계"라는 구조 자체는 chunk 지향 Step에서 고정된 기본 설계이고, process/write를 각각 별도 트랜잭션으로 쪼개는 설정은 지원하지 않는다. 다만 조정 가능한 건 있다:
>
> - **chunk 크기(commit interval)**: `.chunk(n)` 값을 바꾸면 한 트랜잭션에 몇 건이 들어가는지가 바뀐다. `chunk(1)`이면 사실상 아이템마다 트랜잭션이 걸리는 것과 비슷해진다
> - **트랜잭션 속성**: `.transactionAttribute(...)`나 커스텀 `PlatformTransactionManager`로 격리 수준, 타임아웃, propagation 같은 트랜잭션 "동작 방식"은 조정 가능하다 (범위 자체가 아니라 속성)
> - **Tasklet 기반 Step**: chunk 지향이 아니라 `Tasklet`을 직접 구현하면 execute() 안에서 트랜잭션 경계를 스스로 다르게 설계할 수도 있다 (chunk 처리를 안 쓰는 다른 방식이라 일반적이진 않음)
>
> 정리하면 "read-process-write 각각 트랜잭션이 걸린다"는 이해는 틀렸고, 청크 전체가 하나의 트랜잭션이며 그 범위 자체는 chunk 지향 Step의 고정 양식이고, chunk 크기나 트랜잭션 속성만 조정 가능한 파라미터다.

> **Q.** 다시 정리하면 process 단에서의 재시도는 process가 인메모리에서의 자체적인 재시도고, writer에서의 재시도는 spring transaction의 롤백이다. 그리고 한 청크 read-process-writer 전체에 트랜잭션을 걸어 청크에 대한 재시도를 하는거 spring batch의 청크 지향 구조다 맞아?
>
> 거의 맞지만 두 군데는 정정이 필요하다.
>
> - **process 재시도 = 인메모리 자체 재시도.** 이건 맞다
> - **"writer에서의 재시도는 트랜잭션 롤백이다"는 순서가 섞여있다.** 롤백과 재시도는 같은 게 아니라 롤백 → (그다음) 재시도의 순차 관계다: write() 예외 → 청크 트랜잭션 롤백(일반 Spring 트랜잭션 특징) → 그 롤백 이후에 아이템 단위로 다시 처리해보는 scan 재시도가 이어짐(Batch가 얹은 별도 기능). 롤백 자체가 재시도인 게 아니라, 롤백은 실패를 되돌리는 것이고 재시도(scan)는 그 뒤에 벌어지는 복구 시도다
> - **"청크 전체에 트랜잭션 걸고 청크에 대한 재시도를 하는 게 chunk 지향 구조다"도 하나로 뭉치면 부정확하다.** "청크 = 트랜잭션 경계"인 건 chunk 지향 Step의 기본/고정 구조(항상 적용됨)이고, "실패 시 아이템 단위로 재시도(scan)해서 복구하는 것"은 `.faultTolerant()` + skip/retry 정책을 명시적으로 설정해야만 동작하는 옵션 기능이다. 이 설정이 없으면 청크가 실패하는 순간 재시도 없이 그냥 Step이 FAILED로 끝난다
>
> 정리하면 청크 단위 트랜잭션 경계는 chunk 지향 구조 자체의 고정된 특성이고, 실패 후 재시도/scan은 그 위에 올라가는 별도의(기본값이 아닌, 설정해야 켜지는) fault-tolerant 기능이다.

> **Q.** batch에서 제공하는 scan 기능이 예외처리로 인한 실패시에 batch에서 스캔해둔 이전 내용으로 복구 시켜준다는거야?
>
> 아니다. "이전에 저장해둔 내용으로 복구"하는 게 아니다.
>
> - scan은 백업/스냅샷 복구가 아니라, 이미 읽어서 메모리에 들고 있던 그 청크의 아이템들을 하나씩 다시 실행해보는 것이다. 청크 트랜잭션이 롤백됐다는 건 그 청크에서 DB에 반영된 게 아무것도 없다는 뜻이라, 애초에 "복구할 이전 상태" 자체가 존재하지 않는다
> - 정확한 동작은 실패한 청크를 구성했던 아이템들(이미 read된 상태로 메모리에 있는 것들)을 하나씩 다시 process() → write() 해보면서, 성공하는 아이템은 개별적으로 커밋하고 실패하는(예외를 던지는) 그 아이템만 skip 정책에 따라 건너뛰는 것이다
> - 즉 "미리 스캔해서 저장해둔 데이터로 되돌린다"가 아니라, 같은 원본 아이템들을 한 번 더, 이번엔 청크 단위가 아니라 아이템 단위로 훑으면서(scan) 어느 게 문제인지 걸러내는 재실행 과정이다. "scan"이라는 이름도 이 "하나씩 훑는다"는 동작에서 온 것이지 저장된 스냅샷을 가리키는 게 아니다
>
> 정리하면 scan은 복구(restore)가 아니라 재실행을 통한 원인 격리(isolation)다 — 실패했던 청크의 원본 아이템들을 다시, 이번엔 하나씩 처리해서 누가 문제였는지 가려내고 정상인 것만 살려서 커밋하는 방식이다.

> **Q.** 그럼 다시 정리하면 writer 단에서 예외로 인한 실패시 트랜잭션 롤백으로 read 단으로 돌리고 spring batch의 기능인 scan으로 예외 발생원인을 찾는다가 맞아?
>
> 거의 맞는데 "read 단으로 돌린다"는 표현은 정확하지 않다.
>
> - 롤백은 DB 반영을 되돌리는 것이지, reader를 다시 호출해서 read 단계로 돌아간다는 뜻이 아니다. 이 청크는 write에서 실패했으니 애초에 DB에 커밋된 게 없어서 롤백이 되돌릴 실질적인 변경 자체가 없는 경우가 많다
> - reader는 다시 호출되지 않는다. 실패한 청크의 아이템들은 이미 그 시도에서 read되어 메모리에 들고 있는 상태이고, scan은 그 메모리에 있는 동일한 아이템들을 재사용해서 하나씩 process→write를 다시 시도하는 것이다. 원본 소스(DB 등)에서 다시 읽어오는 게 아니다
>
> 정확한 흐름은: (1) write() 실패 → 그 청크의 트랜잭션 롤백(DB 반영 취소, 대개 애초에 커밋된 게 없음) → (2) 이미 메모리에 있는 그 청크의 원본 아이템들을 재사용 → (3) scan 기능이 그 아이템들을 하나씩 process→write 하며 원인 아이템을 특정 → (4) 정상 아이템은 개별 커밋, 원인 아이템은 skip. 즉 "롤백 → read로 되돌아감 → scan"이 아니라 "롤백(DB 취소)과 scan(메모리에 있는 아이템을 하나씩 재실행)이 함께 일어나는 것"이고, read 단계 자체가 다시 실행되는 건 아니다.

> **Q.** 내가 기억하는 트랜잭션 롤백은 한 트랜잭션의 대한 전체 재시도로 기억하는데? 한 청크는 read - process - writer 아니야?
>
> 두 가지로 나눠서 봐야 한다.
>
> - **"트랜잭션 롤백 = 전체 재시도"는 정확한 이해가 아니다.** 롤백은 트랜잭션 안에서 일어난 DB 변경을 취소하는 것, 그게 전부다. 재시도는 완전히 별개의 결정이고, 트랜잭션 매니저가 아니라 Spring Batch의 fault-tolerant 로직(RetryTemplate, scan)이 정한다. 롤백만 되고 재시도/skip 설정이 없으면 그냥 Step이 실패로 끝난다. "롤백 = 재시도"라는 등식 자체가 성립하지 않는다
> - **한 청크는 read-process-write로 구성되는 게 맞다**, 이 전체가 하나의 트랜잭션에 묶이는 것도 맞다. 다만 write 실패 후 Batch의 scan이 재시도할 때는 reader를 다시 호출하지 않고, 이미 읽어서 메모리에 들고 있던 아이템들(Chunk 객체)을 그대로 재사용해서 process→write만 아이템 단위로 다시 수행한다. "롤백됐으니 read부터 전부 다시 한다"가 아니라, Batch가 일부러 read 결과를 캐싱해뒀다가 재사용하도록 설계해놓은 것이다
>
> 정리하면 트랜잭션 롤백은 DB 변경 취소일 뿐 그 자체가 재시도를 의미하지 않고, 청크는 read+process+write로 구성되는 게 맞지만 실패 후 재시도(scan)는 그중 read는 재사용하고 process+write만 아이템 단위로 다시 수행하는 방식이다.

> **Q.** read -> process 에서의 예외 발생시에는 그럼 read로 돌아가서 재시도하는거야?
>
> 아니다, read로 돌아가지 않는다. 앞서 설명한 것과 같은 원리다.
>
> - process() 예외로 재시도가 일어날 때도, 이미 읽어서 메모리에 들고 있는 그 아이템 자체에 대해 process()만 다시 호출한다. reader가 다시 불려서 read 단계로 돌아가는 게 아니다
> - 이유는 writer 실패 때와 동일하다: 아이템은 이미 그 청크 시도에서 read되어 메모리에 있는 상태라 굳이 소스에서 다시 읽어올 필요가 없다
> - process 예외 재시도는 그 아이템의 process() 호출만 반복하는 것이고, 성공하면 이어서 write 단계로 진행된다
> - retryLimit까지 실패하면 skip 정책에 따라 그 아이템만 skip되고, 나머지 아이템들은 같은 메모리에 있던 것들이므로 정상적으로 이어서 처리된다
>
> 즉 read는 청크당 한 번만 일어나고, process/write 단계에서 벌어지는 재시도·scan은 전부 그 한 번 읽어온 결과를 재사용하는 구조다. read 단계 자체가 반복 호출되는 경우는 없다(다음 청크로 넘어갈 때를 제외하고).

> **Q.** read는 그 청크에서 사용한 데이터를 캐싱해두는 곳이라서 그런건가?
>
> 방향은 맞지만 "read의 역할이 캐싱"이라기보다는 결과적으로 그렇게 활용되는 것에 가깝다.
>
> - read의 본래 목적은 "다음 처리할 아이템들을 소스에서 가져오는 것"이다. 캐싱을 위해 존재하는 단계가 아니다
> - 다만 청크가 진행되는 동안 그 청크에서 읽은 아이템들은 어차피 process→write로 넘어가야 하니 당연히 메모리에 들고 있는 상태가 되고, process/write 단계에서 실패가 나서 재시도할 때 Spring Batch는 이 이미 메모리에 있는 아이템들을 그냥 재사용하도록 만들어져 있다
> - 여기엔 단순 효율성 이상의 더 중요한 이유가 있다: 많은 Reader(예: DB 커서 기반 `JdbcCursorItemReader`, 파일 스트림 기반 reader)는 한 번 읽으면 되돌릴 수 없는 상태를 가진 스트림이다. 커서는 한 번 지나가면 다시 그 위치로 못 돌아가고, 다시 read()를 호출하면 그다음 데이터를 가져오거나 잘못된 결과를 줄 수 있다. 그래서 실패 시마다 reader를 다시 호출해버리면 아이템을 건너뛰거나 중복 소비하는 문제가 생길 수 있어, 이를 막기 위해 Batch는 실패한 청크의 아이템들을 재사용하도록 설계되어 있다
>
> 정리하면 read는 캐싱하려고 존재하는 단계는 아니지만, 그 청크가 처리되는 동안 읽은 아이템들이 자연스럽게 메모리에 남아있고, Batch는 (특히 재시도 불가능한 stateful reader의 특성 때문에) 이걸 재사용하도록 설계했기 때문에 결과적으로 캐시처럼 동작하는 것이다.

> **Q.** 메타데이터 테이블은 앱 실행시 자동으로 테이블을 만드나?
>
> 테이블 종류(DB)에 따라 다르다 — 기본값 기준으로는 실제 운영 DB에서는 자동 생성되지 않는다.
>
> - Spring Boot의 Batch 자동 설정에는 `spring.batch.jdbc.initialize-schema` 프로퍼티가 있고 기본값은 `embedded`다. 이 값은 DataSource가 임베디드 DB(H2, HSQLDB, Derby)로 감지될 때만 메타데이터 테이블(`BATCH_JOB_INSTANCE`, `BATCH_JOB_EXECUTION`, `BATCH_STEP_EXECUTION` 등)을 자동 생성해준다는 뜻이다
> - MySQL, PostgreSQL 같은 실제 프로덕션 DB를 쓰면 기본 설정으로는 자동 생성이 안 된다. 자동 생성을 원하면 `spring.batch.jdbc.initialize-schema=always`로 명시적으로 설정해야 한다
> - 또는 `spring-batch-core` jar 안에 DB별로 들어있는 스키마 스크립트(`schema-mysql.sql`, `schema-postgresql.sql` 등)를 직접 찾아서 수동으로 실행하는 방식도 흔히 쓴다. 운영 DB에선 마이그레이션 도구(Flyway, Liquibase)로 관리하는 경우가 많다
> - 이건 Spring Boot의 자동 설정 기능이고, Spring Batch 자체(Boot 없이 순수 Spring으로 쓸 때)는 테이블을 자동으로 만들어주지 않는다 — 스키마 스크립트를 직접 실행하거나 `DataSourceInitializer` 빈을 손수 등록해야 한다
>
> 정리하면 개발 중 임베디드 DB로 테스트할 땐 자동 생성되어 편하지만, 실제 배포 환경에서는 `initialize-schema=always`를 켜거나 스키마를 직접 적용해야 메타데이터 테이블이 준비된다.

> **Q.** 예외 처리 전략: Skip / Retry — 스킵이나 재시도를 무조건 설정해놔야하는건가?
>
> 아니다, 무조건 설정해야 하는 건 아니다. `.faultTolerant()`로 켜는 선택적(optional) 기능이다.
>
> - **기본값(설정 안 하면)**: read/process/write 어디서든 예외가 발생하면 그 즉시 청크가 실패하고 Step이 FAILED로 끝난다. 재시도도 스킵도 자동으로 일어나지 않는다
> - **오히려 일부러 설정 안 하는 경우도 많다**: 데이터 정합성이 중요한 배치(금액 계산, 정산 처리 등)에서는 "이상 데이터가 하나라도 나오면 즉시 멈추고 조사하자(fail-fast)"는 게 더 안전한 전략일 수 있다. 이런 경우엔 skip/retry를 켜지 않는 게 의도된 설계다
> - **skip이 유용한 경우**: 외부에서 들어오는 데이터(CSV 업로드, 외부 API 연동 등)처럼 일부 불량 레코드가 섞여있는 게 당연히 예상되는 상황. 몇 건의 이상 데이터 때문에 전체 배치를 실패시키고 싶지 않을 때 쓴다
> - **retry가 유용한 경우**: 일시적인 장애(DB 커넥션 순간 끊김, 외부 API 타임아웃 등) — 재시도하면 성공할 가능성이 있는 상황에만 의미가 있다. 코드 버그나 데이터 자체의 문제라면 재시도해도 계속 실패하므로 부적합하다
> - **켤 때 주의할 점**: `skip(Exception.class)`처럼 모든 예외를 무조건 스킵하게 설정하면 진짜 버그까지 조용히 삼켜버릴 수 있으니 스킵/재시도 대상 예외는 구체적으로 지정하는 게 좋다. `skipLimit`으로 상한을 걸어둬야 데이터 대부분이 잘못된 극단적 상황에서 대량 스킵이 눈에 안 띄고 지나가는 걸 막을 수 있다
>
> 정리하면 skip/retry는 "데이터 품질이 원래 들쭉날쭉하고 일부 실패를 감수할 수 있는 배치"에는 켜는 게 맞고, "정합성이 중요해서 이상 발생 시 바로 멈춰야 하는 배치"에는 오히려 안 켜는 게 맞는, 상황에 따라 선택하는 옵션이다.

> **Q.** @Scheduled 가 batch를 설정된 시간에 트리거로 사용된다가 맞는 이해인가? 애초에 scheduler가 batch에만 활용되는건 아니잖아. 그럼 스케쥴러를 걸어둔 하단의 메서드를 설정된 시간에 실행시켜준다로 이해하는게 맞나?
>
> 맞다, 정확히 이해하고 있다.
>
> - `@Scheduled`는 Spring Batch와 무관한, Spring Framework의 범용 스케줄링 기능이다. cron 표현식이나 fixedRate/fixedDelay로 지정한 시점/주기에 그 메서드를 실행시켜주는 것뿐이고, 이메일 발송·캐시 정리·헬스체크 등 배치와 무관한 어떤 메서드에도 똑같이 쓸 수 있다
> - Spring Batch는 자체적인 스케줄링 기능이 없다. Job은 누군가 `JobLauncher.run(job, jobParameters)`를 호출해줘야 실행되는데, 그 "누군가"가 될 수 있는 방법 중 하나가 `@Scheduled`인 것뿐이다. 실무 패턴은 `@Scheduled` 메서드 본문 안에서 `jobLauncher.run(...)`을 호출하는 식이다:
>
> ```java
> @Scheduled(cron = "0 0 1 * * *")
> public void runBatchJob() {
>     jobLauncher.run(myJob, jobParameters);
> }
> ```
>
> - 즉 `@Scheduled`가 Batch 전용 트리거라서 특별한 연동이 있는 게 아니라, 그 메서드 안에서 호출되는 로직이 우연히 Batch Job 실행인 것뿐이다. "스케줄러를 걸어둔 하단의 메서드를 설정된 시간에 실행시켜준다"는 이해가 정확하다
> - 참고로 실제 서비스에서는 `@Scheduled` 대신 Quartz, 외부 스케줄러(AWS EventBridge, k8s CronJob 등)로 Batch Job을 트리거하는 경우도 많은데, 이것도 결국 "Batch를 실행하는 트리거는 외부에서 갈아 끼울 수 있다"는 같은 원리다.

> **Q.** 스케쥴러 말고도 Quartz? 다른 방법들도 있는데 스케쥴러를 우선 고려하는 이유? 내가 할때도 그렇고 보통 스케쥴러를 사용하던데 왜지?
>
> `@Scheduled`가 기본으로 많이 쓰이는 이유는 "단순한 요구사항엔 그게 충분하고, 추가로 짊어질 게 없기 때문"이다. Quartz나 외부 스케줄러가 못하는 걸 하는 게 아니라, 대부분의 배치는 그렇게까지 복잡한 기능이 필요 없어서 더 무거운 도구를 안 쓰는 것이다.
>
> **`@Scheduled`가 기본 선택이 되는 이유**
>
> - **추가 의존성/인프라가 필요 없다**: Spring을 쓰고 있으면 이미 포함된 기능이라 `@EnableScheduling` + 애노테이션 하나로 끝난다. Quartz는 `JobDetail`/`Trigger`/`Scheduler` 빈을 따로 구성해야 하고, 영속성이 필요하면 별도 DB 테이블(JobStore)까지 설정해야 해서 진입장벽이 높다
> - **대부분의 배치 요구사항은 단순하다**: "매일 새벽 1시에 한 번 실행" 같은 요구사항엔 cron 표현식 하나로 완전히 충분하다. Quartz의 고급 기능(misfire 처리, 동적 스케줄 변경, 클러스터 조율 등)은 안 쓸 기능인 경우가 많다
>
> **Quartz/외부 스케줄러가 필요해지는 시점**
>
> - **앱을 여러 인스턴스로 띄울 때(수평 확장)**: `@Scheduled`는 인스턴스마다 독립적으로 트리거가 발동한다. 서버를 3대 띄우면 같은 배치가 3번 동시에 실행되는 문제가 생긴다. Quartz는 JDBC JobStore로 클러스터 전체에서 "이번엔 한 노드만 실행"하도록 조율해줄 수 있다 — 이게 Quartz를 쓰는 가장 흔한 이유다
> - **스케줄을 런타임에 동적으로 바꿔야 할 때**: 관리자 화면에서 스케줄 주기를 코드 재배포 없이 바꾸고 싶다면 Quartz가 이런 동적 트리거 관리에 유리하다
> - **misfire(놓친 실행) 처리가 필요할 때**: 앱이 꺼져있던 사이 실행 시각이 지나가버렸을 때 어떻게 할지(바로 실행/스킵/누적 실행 등)를 세밀하게 제어하고 싶다면 Quartz가 이런 정책을 명시적으로 지원한다
>
> 외부 스케줄러(k8s CronJob, AWS EventBridge)를 쓰는 이유는 조금 다른데, 스케줄링을 앱 프로세스 자체에서 완전히 분리해서 배포/운영을 독립적으로 관리하고 싶을 때, 그리고 다중 인스턴스 중복 실행 문제를 Quartz의 클러스터링 없이 인프라 레벨에서 해결하고 싶을 때 선택한다.
>
> 정리하면 `@Scheduled`가 기본값인 이유는 "단일 인스턴스로 돌아가는 단순한 주기 실행"엔 그게 제일 가볍고 충분하기 때문이고, 다중 인스턴스 중복 실행 방지나 동적 스케줄 관리 같은 요구가 생기면 그때 Quartz나 외부 스케줄러로 넘어가는 게 일반적인 흐름이다.
