# Spring Batch

## 개념 정리

### 1. Spring Batch란, 왜 쓰는가

- **배치(Batch) 처리**: 실시간 요청-응답이 아니라, 대량의 데이터를 정해진 시점(또는 주기)에 한꺼번에 읽어서 가공하고 저장하는 처리 방식. 예: 매일 새벽 정산 집계, 대량 회원 등급 갱신, 외부 시스템에서 받은 CSV를 DB로 적재.
- **왜 직접 반복문으로 안 짜고 Spring Batch를 쓰는가**: 대량 데이터를 다루다 보면 중간에 실패했을 때 어디서부터 다시 시작할지(재시작), 일부 데이터만 실패했을 때 건너뛸지 재시도할지(skip/retry), 트랜잭션 단위를 어떻게 나눌지(청크 커밋), 처리 이력을 어떻게 남길지(메타데이터) 같은 문제가 공통으로 반복된다. Spring Batch는 이 문제들을 프레임워크 레벨에서 표준화해서 제공한다.
- **Spring Batch가 제공하는 핵심 가치**: 대용량 처리에 필요한 트랜잭션 관리, 청크 단위 처리, 실패 시 재시작(restart), 로깅/추적을 위한 메타데이터 저장, skip/retry 정책 등을 선언적으로 설정할 수 있다.

### 2. 핵심 도메인 모델

- **Job**: 배치 처리의 최상위 단위. 하나 이상의 `Step`으로 구성되며, "회원 정산 배치"처럼 하나의 배치 작업 전체를 의미한다.
- **Step**: `Job`을 구성하는 독립적인 실행 단계. 하나의 `Job` 안에 여러 `Step`을 순차적으로(또는 조건 분기하며) 배치할 수 있다(예: 1단계로 파일을 읽어 DB에 적재하고, 2단계로 집계 테이블을 갱신).
- **JobParameters**: `Job` 실행 시 전달하는 파라미터(예: 처리 대상 날짜). 같은 `Job`이라도 파라미터가 다르면 별개의 실행으로 취급되는 기준이 된다.
- **JobInstance**: `Job` + `JobParameters`의 조합으로 식별되는 논리적 실행 단위. 예를 들어 "2024-01-01 정산"과 "2024-01-02 정산"은 같은 `Job`이지만 서로 다른 `JobInstance`다.
- **JobExecution**: `JobInstance`를 실제로 한 번 "시도"한 기록. 같은 `JobInstance`라도 첫 실행이 실패해서 재시작하면 새로운 `JobExecution`이 생기지만, `JobInstance`는 그대로 유지된다(성공할 때까지 같은 `JobInstance`에 여러 `JobExecution`이 붙을 수 있음).
- **StepExecution**: 각 `Step`이 특정 `JobExecution` 안에서 실행된 기록. 처리 건수, 성공/실패 여부, 커밋 횟수 같은 실행 통계를 담는다.
- **관계 정리**: `Job`(설계도) → `JobInstance`(파라미터로 구체화된 실행 단위) → `JobExecution`(실제 시도 기록) → 그 안의 여러 `StepExecution`(단계별 실행 기록).

### 3. Step의 두 가지 처리 방식

- **Chunk 지향 처리(Chunk-oriented Processing)**: 데이터를 한 건씩 읽되(`ItemReader`), 지정한 개수(chunk size)만큼 모이면 그 묶음 단위로 가공(`ItemProcessor`)하고 한 번에 쓰기(`ItemWriter`)와 커밋을 수행하는 방식. 예를 들어 chunk size가 100이면 100건을 읽고 처리한 뒤 한 번에 커밋하고, 다음 100건으로 넘어간다. 대량 데이터를 다룰 때 기본이 되는 패턴이다.
  - 장점: 커밋 단위를 작게 유지해서 메모리 사용량을 제어할 수 있고, 실패 시 마지막으로 성공한 청크 이후부터 재시작할 수 있다.
- **Tasklet 방식**: `ItemReader`/`Processor`/`Writer` 3단계로 나누기 애매한, 한 번에 실행하고 끝나는 단순 작업(예: 임시 테이블 정리, 파일 이동)에 사용. `execute()` 메서드 하나에 로직을 직접 구현한다.
- **선택 기준**: 대량의 반복 가능한 데이터 처리는 Chunk 지향, 단발성/부수적인 작업은 Tasklet.

### 4. ItemReader / ItemProcessor / ItemWriter

- **ItemReader\<T\>**: 데이터 소스(DB, 파일, 큐 등)에서 한 건씩 데이터를 읽어오는 인터페이스. 더 이상 읽을 데이터가 없으면 `null`을 반환해 종료를 알린다. `JdbcCursorItemReader`, `JpaPagingItemReader`, `FlatFileItemReader`(CSV 등) 같은 구현체를 상황에 맞게 선택한다.
- **ItemProcessor\<I, O\>**: 읽어온 데이터 한 건을 가공/변환/필터링하는 인터페이스. `process()`가 `null`을 반환하면 해당 아이템은 `ItemWriter`로 전달되지 않고 스킵된다. 생략 가능(읽은 데이터를 그대로 쓰기만 한다면).
- **ItemWriter\<T\>**: 가공된 데이터를 chunk 단위로 모아서 한 번에 저장(DB insert, 파일 출력 등)하는 인터페이스. 건별이 아니라 청크(리스트) 단위로 호출되는 것이 핵심.
- **파이프라인 흐름**: `Reader`가 한 건씩 읽음 → chunk size만큼 모일 때까지 각 건을 `Processor`가 가공 → chunk가 다 차면 `Writer`가 한 번에 쓰고 트랜잭션 커밋 → 다음 chunk 반복.

### 5. 메타데이터와 재시작(Restart)

- **메타데이터 테이블**: Spring Batch는 `BATCH_JOB_INSTANCE`, `BATCH_JOB_EXECUTION`, `BATCH_STEP_EXECUTION` 등 별도의 메타데이터 테이블에 실행 이력(언제 시작/종료했는지, 성공/실패, 처리 건수 등)을 저장한다. 이 테이블들은 Job/Step을 직접 실행하지 않고도 "무엇이 언제 어떻게 실행됐는지"를 추적할 수 있게 해준다.
- **재시작(Restart)**: 같은 `JobParameters`로 실패한 `Job`을 다시 실행하면, Spring Batch는 메타데이터를 참고해 실패 지점(마지막으로 커밋된 chunk) 이후부터 이어서 처리할 수 있다. 이미 성공적으로 끝난 `JobInstance`는 기본적으로 같은 파라미터로 재실행할 수 없다(중복 실행 방지) — 재실행하려면 파라미터를 바꾸거나 별도 설정이 필요하다.
- **왜 중요한가**: 대량 데이터 처리 중 중간에 서버가 죽거나 특정 건에서 예외가 나도, 처음부터 전부 다시 처리하지 않고 이어서 처리할 수 있어야 실무에서 쓸 수 있다.

### 6. 예외 처리 전략: Skip / Retry

- **Skip**: 특정 예외가 발생한 아이템은 처리를 포기하고 건너뛰어 나머지 chunk 처리를 계속하는 전략. 몇 건까지 skip을 허용할지(skip limit), 어떤 예외 타입만 skip할지를 설정한다. 잘못된 데이터 한두 건 때문에 전체 배치가 실패하는 것을 막는다.
- **Retry**: 일시적인 오류(네트워크 타임아웃 등)로 예외가 발생했을 때 같은 아이템 처리를 지정한 횟수만큼 재시도하는 전략. 몇 번까지 재시도할지, 어떤 예외에 대해 재시도할지를 설정한다.
- **Skip과 Retry의 조합**: 재시도를 다 했는데도 계속 실패하면 그때 skip으로 넘어가도록 함께 설정하는 것이 일반적인 패턴이다.

### 7. 실행 방식과 확장

- **스케줄링과의 관계**: Spring Batch 자체는 "언제 실행할지"를 결정하지 않는다. 실제 운영에서는 스케줄러(Spring `@Scheduled`, Quartz, 또는 외부 스케줄러/오케스트레이터)가 특정 시각에 `JobLauncher`를 호출해 `Job`을 실행시키는 방식으로 연동한다.
- **병렬/분산 처리**: 처리량을 늘리기 위한 확장 옵션으로 멀티스레드 Step(하나의 Step 내에서 여러 스레드가 chunk를 병렬 처리), 병렬 Step(서로 다른 Step을 동시 실행), Partitioning(데이터를 여러 파티션으로 나눠 여러 워커가 나눠 처리) 등이 있다. 실무 규모가 커질수록 이런 확장 전략이 필요해진다.
